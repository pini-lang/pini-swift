# Issue：HIR 引擎未应用 struct 值拷贝规则（`copyIfStruct` 在绑定点缺失）

- 状态：**已交付并闭环**（2026-09-18 复核）—— 缺口在四个落点全部关闭，最小见证一实测通过；见文末「2026-09-18 复核与闭环」。
- 发现渠道：G5（具名类型与字段）实现期。**归档版 `86fdafd` 的 docstring 已声称本项「Filed as a defect
  with its own ticket」，但实测 `docs/` 下无任何相关工单** ⇒ 本单是**把该声明真正兑现**，并订正该处表述。
  （归档只留声明、未留工单，属「归档自我声明必须复核」的第三个实证，见 G5 细目件实录。）
- 归属：**语言语义的实现面**（值类型 vs 引用类型的拷贝语义）。**非裁决项** —— 语义本身由解释器
  既有的 `Interpreter.copyIfStruct` 单方定义，本单只是「引擎尚未复刻」。
- 关联：
  - `docs/issue-interpreter-hir-plan-2026-09-12.md`（LR-4 逐格实录）；
  - `docs/issue-interpreter-hir-p2-plan-2026-09-13.md` §8.5（G5 实录，本单的来源格）；
  - P4（删除 AST 走查）—— **本单是它的前置**：现在 AST 通道承担着 struct 拷贝，
    P4 之后 HIR 独占，本洞即成为真实用户可见缺陷。

## 现象

`Interpreter.copyIfStruct` 是 `Interpreter` 的**实例方法**，HIR 执行引擎在下列**绑定点与写入点**
均未应用该规则：

| 落点 | 应有行为 | 现状 |
|---|---|---|
| `allocVar` | 把 struct 值绑进新槽时深拷贝 | ❌ 未应用 |
| `storeVar` | 赋值给 struct 槽时深拷贝 | ❌ 未应用 |
| `fieldStore` | 把 struct 存入字段时深拷贝 | ❌ 未应用 |
| `subscriptStore` | 把 struct 存入容器时深拷贝 | ❌ 未应用 |

⇒ HIR 通道下 `var b = a`（`a` 为 struct）会让 `b` 与 `a` **共享底层存储**，
而语言语义要求**拷贝**。修改 `b.x` 会连带改到 `a.x` —— 这是**静默的错误结果**，
不是显式分叉。

## 为什么 G5 才暴露、且现在仍不阻塞

- **G5 之前 struct 根本不可达**：引擎里没有任何节点能造出 struct 值（`construct` 未实现）
  ⇒ 该差异是**休眠**的，无可观测后果。
- **G5 让 struct 可达** ⇒ 差异从休眠变为**真实**。
- **但今日无可观测后果**：**没有任何夹具把 struct 值存进另一个槽**（实测全量语料 +
  73 个差分夹具均无该形状）⇒ 两通道的可观测输出**均不动**。
- ⇒ 本格**不实现**（实现即「无验证的改动」），**只立案**。

## 为什么不能靠单测 parity 挡住

本项**恰好是**「两通道共用代码」之外的**同型盲区**：`copyIfStruct` 是解释器的实例方法，
而 `HIRExecutorTests.assertParity` 只比 `hir` vs `ast` 两条通道。**若将来在两条通道里
都漏掉拷贝，两者会一致地错** ⇒ parity 恒绿而结果错。

⇒ 覆盖本项需要 **①绝对断言**（断言 `a` 未被 `b` 的写入影响）或 **②三通道探针**。
本格的手写用例 `testObjectAliasingThroughASecondBindingAndAPlainVariableBase` 正是
**按此形状**写的 —— 但它**刻意用 object（引用类型）**，因为引用类型下「别名成立」是**正确的**，
可以直接钉死；而 struct 半边若断言，就会**钉住一个已知错误答案**，比不测更糟
（归档 docstring 已记此理由，本格沿用）。

## 处置建议（不排期）

1. **优先级随 P4 抬升**：P4 删除 AST 走查后本洞变为用户可见 ⇒ **P4 前置**。
2. 实现时应**复用** `Interpreter.copyIfStruct` 而非另写一份（单源原则）；
   若因它是实例方法而不便复用，则**提到 static 单源**，与 G6 的
   `matchArmMatches` / `builtinGet` 同一处置。
3. 落地时必须**同时**补夹具（struct 存进另一槽的差分夹具），
   否则仍是「无验证的改动」——这正是本格不做的原因。

## 未做（本格边界）

- 未改任何实现（只立案）。
- 未补夹具（本格范围外；补夹具即要求先实现，两者须同批）。
- 未动 `Interpreter.copyIfStruct` 本体（不改既有单源）。


## 2026-09-16 复核：仍 **Open**，但「无法验证」这条不做实现的理由**已解除**

### 一、误归属订正（本单此前**经夹具清单关联**的 3 个夹具，与本单**无关**）

本单立案时由 P2a 收尾批的**剩余面归因表**关联到 `testDiffStructValue` / `examples/struct.pini` /
`examples/ffi.pini` 一类夹具。**2026-09-16 实测订正**：那些夹具**从来没有成为本单的见证者** ——
它们的首缺口是更靠前的 **`sqrt` 无主 callee**（另一张工单），**一次都没走到 struct 拷贝的路径**。
⇒ 那是**误归属**：归因表看的是夹具**主题 / 目录**，而表头问的是「**各自归谁**」，判据应当是**错误码**。

**P4-0 清掉该遮蔽后**，这两个夹具在 HIR 下**通过**（与 AST 逐字节相同）⇒
它们**既不是本单的证据，其转绿也不归因于本单**。本单**至今仍无夹具**。

### 二、⭐ 新增**最小见证**（本单此前缺的正是这个）

2026-09-16 实测，两个 6 行程序（**刻意未入语料**，理由见第四节）：

| 程序 | AST 通道 | HIR 通道 | 判定 |
|---|---|---|---|
| `var b = a`（`a` 为 struct）→ `b.x = 99` → `print(a.x)` | **`1`** | **`99`** | ⚠️ **分歧** |
| `h.内 = p` → `p.x = 99` → `print(h.内.x)` | **`1`** | **`99`** | ⚠️ **分歧** |

见证一（`allocVar` 带初值的绑定点）完整源码：
```
(点)
x: I64 = 0

main|func() -> ():
    var a = 点()
    a.x = 1
    var b = a
    b.x = 99
    print(a.x)
    return
```
见证二（`fieldStore` 写入点）同形，把 `var b = a` 换成 `h.内 = p`
（`(盒)` 有一个 `点` 型字段；`(点)` 的声明与其参数序见见证一）。

⇒ 两通道 `rc` **皆为 0**、**只在输出值上分歧** ⇒ 正是本单预告的**静默错误结果**，
不是显式分叉。

### 三、本次复核**推翻**的两处前提

1. **「今日无可观测后果」不再成立**：缺口**6 行即可复现**。
   限定条件（不变）：只在 `PINI_INTERP_ENGINE=hir` 下可见；**翻转后才对用户可见**
   ⇒ 本单「**P4 前置**」的定性**不变**。
2. **「无法验证 ⇒ 不实现」这条理由解除**：本单原写「实现即『无验证的改动』」、
   「补夹具即要求先实现，两者须同批」。**见证现已在册** ⇒ 夹具可以**先于**实现存在，
   实现批次不再需要「同时造夹具、并同时赌它写对了」。

### 四、**刻意不**把见证加进语料（范围声明）

两个见证**只登记在本单内**，**未**加进 `Tests/` 的差分语料。理由：加夹具会改探针分母（现 **319**），
而本单的处置是**实现**、不是登记；夹具应与实现同批落地（那批会一并重取冻结件）。
⇒ 本单保持「**只登记不修**」，**不因本次复核改变排期**。

### 五、未做（本次复核边界）

未改任何实现 · 未加语料夹具 · 未动 `Interpreter.copyIfStruct` · 未改探针判据 ·
**四个落点只实测了两个**（`allocVar` 带初值 · `fieldStore`）—— `storeVar` 与 `subscriptStore`
**未单独测**，其形态按同源推定而**非实测**。

## 2026-09-18 复核与闭环（`G-6c`）

**触发**：删除 AST 走查时核对「本单自称的 P4 前置」是否还成立，并顺手订正
`HIRExecutor` docstring 里那条指向已删符号的缺口条目。实测结论：**缺口已关闭，本单可闭环。**

### 实现面（现测）

`RuntimeOps.copyIfStruct` 是本条规则的唯一实现，且**在本单列出的四个落点全都已应用**：

| 落点 | 现测位置 | 形态 |
|---|---|---|
| 绑定（`allocVar`，带初值） | `HIRExecutor` 里 `var value = try initializer.map { RuntimeOps.copyIfStruct(…) }` | ✅ 已应用 |
| 绑定（`storeVar`） | `…currentEnv.assign(name:value: RuntimeOps.copyIfStruct(…))` | ✅ 已应用 |
| 下标写（`subscriptStore`） | `let newValue = RuntimeOps.copyIfStruct(…)` | ✅ 已应用 |
| 字段写（`fieldStore`） | `try storeField(…, value: RuntimeOps.copyIfStruct(…))` | ✅ 已应用 |

⇒ 本单标题所述「`copyIfStruct` 在绑定点缺失」**不再成立**。

### 见证面（现测，用本单自己记的那两个）

| 见证 | 本单登记（缺口开着时） | **2026-09-18 现测** | 判定 |
|---|---|---|---|
| 一（`allocVar` 带初值）：`var b = a` → `b.x = 99` → `print(a.x)` | HIR `99`（错误） | **`1`**（值拷贝语义） | ✅ **关闭** |
| 二（`fieldStore`）：`h.内 = p` → `p.x = 99` → `print(h.内.x)` | HIR `99`（错误） | ⚠️ **未能复现**：按本单 §二 的描述转写出的夹具在 `h.内 = p` 处报 `E4-001 type mismatch` | ⚠️ **无见证证据** |

另有测试面证据：`ValueSemanticsTests.testStructCopySemantics` **通过**（该用例正是本单「现象」一节的复现对象）。

### ⚠️ 如实登记的两条限制（不得据此把本单写成「证据完备」）

1. **见证二没有复现** —— 转写出的夹具被检查器拒（`h.内 = p`），说明本单 §二 记的那个形态**不足以直接重建**。
   该落点（`fieldStore`）因此**只有代码证据、没有见证证据**：调用点存在且形态正确，但没有人用输入证明过它。
   ⇒ 若后续要一个完整的账，补的是**见证二的可复现形态**，不是实现。
2. **本次未加语料夹具**（与本单 §四 的范围声明一致）⇒ 探针分母不变，本单的闭环**不依赖**新夹具。

### 闭环判定

判据「四个落点全部应用 `copyIfStruct`」**实测达成**（四个调用点逐处存在）+ 见证一现测通过 + 该语义的测试在册且绿。
⇒ **本单状态改「已交付并闭环」**。上面第 1 条作为**已知证据缺口**随本单保留（不另立工单：它是登记完备性问题，不是缺陷）。
