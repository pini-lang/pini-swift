# P4-1（包运行入口）· 规划

> 状态：**待裁决**（2026-09-16 落盘；**规划件，不含任何实现**）
> 对象：HIR 引擎的**目录/模块运行入口**，以及该批**验收判据本身的可达性**。
> 上游：`docs/issue-hir-p4-plan-2026-09-16.md` 的「分批计划」表（P4-1 行）·「判据」节 ·「止损点」节。
> **本件只做规划；开工仍须单独点名。**

## 0. 本件要解决的两处不自洽（均为规划阶段实测所得）

上游分批表给 P4-1 的验收判据是一句话：**`PINI_INTERP_ENGINE=hir` 下 `7 failures → 0`**。
开工前实测发现这句话**按现行批次划分不可达**，且**它依赖的验收通路本身是坏的**。

### 0.1 「7 → 0」不可达：7 个失败里有 3 个不由包运行入口引起

那 7 个失败全部落在 `Tests/PiniTests/ImportInjectionTests/ImportInjectionTests.swift`，
分属 **4 个用例方法**、**7 个断言**。按断言逐条定性（行号为实测）：

| 失败断言 | 用例 | 触发的路径 | 缺口归属 |
|---|---|---|---|
| L152 `r.code == 0` | `testInjectionEndToEndViaCLI` | `pini run <目录>` | **装配层** |
| L153 `r.out == "hi\nhi\n"` | 同上 | 同上 | **装配层** |
| L163 `r.err 含 E3-002` | `testNonUnderscoreBareCallRejectedViaCLI` | `pini run <目录>` | **装配层** |
| L189 `single.out == "[甲, 乙]\n"` | `testArgvPassthroughViaCLI` | `pini run <单文件> 甲 乙` | **降载层**（`argv`） |
| L195 `module.out == "[X]\n"` | 同上 | `pini run <目录> X` | **装配层 + 降载层**（叠加） |
| L198 `empty.out == "[]\n"` | 同上 | `pini run <单文件>` | **降载层**（`argv`） |
| L223 `r.out == "来自注入\n"` | `testCrossModuleInjectionPropagation` | `pini run <目录>` | **装配层** |

⇒ **纯装配层 4 条 · 纯降载层 2 条 · 两层叠加 1 条。**
只做装配层，读数只能从 **7 走到 3**；剩下 3 条要等 `argv` 在 HIR 层落地。

> ⚠️ 一处易漏：L162 的 `XCTAssertNotEqual(r.code, 0)` **现在是通过的**——不是因为行为正确，
> 而是因为「目录被拒绝」也让 `code != 0`。装配层接通后这条仍需成立（语义层报 `E3-002` ⇒ 非 0），
> 故它是**修复后的回归点**，不是已解决的问题。

### 0.2 `argv` / `moduleRoot` 的**实现**在当前批次划分里没有户口

上游分批表把「`argv` / `moduleRoot` 在 HIR 侧无节点」登记在 **P4-2**，而同一行的验收列明写
**「本批是勘测，不修」**。于是这两项**只有勘测、没有实现**，而 P4-1 的验收又要求它们转绿。

⇒ 二者必须二选一：**要么把实现并入 P4-1**，**要么把 P4-1 的验收判据改成装配层面的判据**
（并把残余 3 条如实登记）。本件建议后者 + 另立实现批，理由见 §3。

## 1. 事实基础（全部 2026-09-16 实测，`56fd716`，构建件 `/tmp/pini-build/debug/pini`）

### 1.1 那个缺口**不在包运行**

实测（单文件夹具，`main|func() -> (): print(argv())`）：

| 命令 | 结果 |
|---|---|
| `pini run s.pini 甲 乙`（默认 `ast`） | rc=0，stdout `[甲, 乙]` |
| `PINI_INTERP_ENGINE=hir pini run s.pini 甲 乙` | **rc=1**，`IRGen Error [E6-004]` — `unsupported feature 'call to unknown function 'argv' (intrinsics beyond print are later grids)'` |
| `pini emit s.pini`（LLVM 通道） | **同一个错**（逐字相同） |
| `pini emit <包内>/main.pini`（走整包降载） | **同一个错** |

⇒ **`argv` 不是「HIR 解释器 vs AST 解释器」的差异，而是整个 HIR 层（两个非 AST 后端）共有的降载面缺口。**
它出现在单文件路径，与包运行**无关**——这条事实决定了它不该被塞进包运行批。

`moduleRoot` 同型（实测：`ast` 下 rc=0 并打印模块根；`hir` 下同一个 `E6-004`）。

### 1.2 包运行这一侧，缺的是**装配层**，且比预期浅

| 命令 | 结果 |
|---|---|
| `pini run examples/multifile`（默认 `ast`） | rc=0，输出 `5 / 25 / 0` |
| `pini emit examples/multifile/main.pini` | **rc=0**（整包降载成功，含跨文件调用） |
| `pini run-llvm examples/multifile/main.pini` | rc=1，`E6-004` — 未支持的名字 `向量` |
| `PINI_INTERP_ENGINE=hir pini run <任意含 pini.toml 的目录>` | rc=1，`Error: PINI_INTERP_ENGINE=hir 暂不支持目录/模块运行，当前仅支持单文件。` |

**已具备的能力（比预期多，这是本批可行性的支点）**：

- **整包降载 `HIRLowerer.lower(package:)` 已存在且已被使用**。它把全包各文件的声明合并成一个
  虚拟模块再走单模块前置链，跨文件引用按同文件前向引用解析；排序按文件加载器的确定性序。
  **已在 LLVM 的包 emit 通道上使用，并已被 `HIRDifferentialTests` 的包级用例使用**，
  且本次实测经 `emit` 验证可用。
- HIR 单模块执行已成熟（P4-0 交付后探针阻塞面为 0）。
- CLI 已有 AST 侧的**参照实现**（同一条路径上：require↔import 漂移校验 → 语义 + 类型门禁 →
  取 `programBase` → 构造解释器 → 执行），HIR 侧可直接对齐。

**缺口（分层，共 6 项）**：

| # | 缺口 | 层 | 说明 |
|---|---|---|---|
| 1 | CLI 目录分支在 HIR 下直接拒绝 | 装配 | 单文件路径在其上方已分派完毕，目录路径被一句话挡掉 |
| 2 | 执行器缺 `ffiConfig` 装配输入 | 装配 | AST 侧传 `manifest.ffi`；HIR 侧执行器**无此参数** |
| 3 | 执行器缺 `processArguments` 装配输入 | 装配 | AST 侧 `interpreter.processArguments = argv`；HIR 侧无 |
| 4 | 执行器缺 `entryFiles`（入口一致性门禁） | 装配/门禁对等 | AST 侧有 `checkEntryConsistency()`；HIR 侧**无任何对应** |
| 5 | `argv()` 无节点 | 降载 | 见 §1.1；两个后端同缺 |
| 6 | `moduleRoot()` 无节点 | 降载 | 同上；无验收用例覆盖 |

> **#2 的辨析**：`ffiConfig` 亦不在 HIR 的**单文件**路径上——即它是 HIR 引擎的**既有**缺口
> （FFI 动态库加载面），不由包运行引入。本批**须实测**其在 HIR 侧的实际形态后再定归属，
> 不得默认「顺手带上」。

### 1.3 ⚠️ 验收通路本身有缺陷（**本批的头号风险**）

`ImportInjectionTests` 的所有 `...ViaCLI` 用例都经**子进程**执行 CLI，路径由 `#filePath` 上溯
四级推出，**硬编码为 `pini-swift/.build/debug/pini`**（不随 `--scratch-path` 走）。实测：

| 件 | mtime | md5 |
|---|---|---|
| `.build/debug/pini`（测试实际执行的那个） | **2026-09-14 22:47** | `03a048ac…` |
| `/tmp/pini-build/debug/pini`（本次构建） | 2026-09-16 09:13 | `cab60b7d…` |

⇒ **测试跑的是一个两天前的 CLI。** P4-1 要改的正是 `Sources/PiniCLI/main.swift`，
所以**按现行通路，本批修完后那 7 个断言仍会失败**（旧二进制依旧拒绝目录），
本批会陷入「怎么做都验收不过」的假红。

三条处置组合（须在开工第一步完成，见 §3）：

1. 开工时用**默认 scratch**（或同步刷新 `.build/debug/pini`）以对齐测试实际执行件；
2. 收口前**核对二进制的 mtime/md5 晚于本次源码改动**，把它写成判据的一部分；
3. 中期可选：让测试的二进制路径可被环境变量覆盖（消除硬编码），但那是测试基建改动，**不在本批**。

## 2. 分批建议

> 与上游分批表的排序原则一致（先清判据面、再清能力面、最后动接缝）；本件只把 P4-1 的
> **一个「中」批拆成两个更小的批**，原因是 §0/§1 实测显示它们**不属同一层**、验收判据也不同。

### P4-1a · 包运行入口（装配层）

- **内容**：解除 CLI 目录分支的拒绝，把 HIR 的包路径接到已有的整包降载上；对齐 AST 参照实现的
  既有门禁顺序（漂移校验 → 语义 → 类型 → `programBase`），并按 §1.2 的 #2/#3/#4 逐项实测后决定
  是补齐还是如实登记为缺口。
- **首个动作 = 「开门后重测」**，**不是**「补齐我认为缺的东西」：先让包能跑起来，再逐夹具记录
  真实的下一个缺口。理由见此项目反复出现的首缺口遮蔽（修掉第一道缺口后，夹具才撞上更下游的一道）。
- **验收**：① §0 表中 4 条纯装配断言转绿（7 → 3）；② 新增的包级夹具三通道（`interp-ast` /
  `interp-hir` / `llvm-hir`）逐字节一致；③ 三条常设判据（见 §3）全过。
- **规模**：小–中。**不动降载层、不动契约。**

### P4-1b · `argv` / `moduleRoot` 节点（降载层）

- **内容**：为两项宿主环境查询内建加降载规则 + 执行器/发射器两侧实现 + **契约登记**。
- **治理**：契约在 §2 把内建按**条目**登记（`printCall` / `printMulti` / `readLine` / `isAsciiDigit`
  同类），故两项落地即**两个新条目**（44 → 46，总 60 → 62），连带：契约计数基线、
  三方对照核验（契约条目 ↔ 节点集 ↔ 后端锚点）、下游引用面。契约自身写明「条目一经落地，
  变更须走 §1.3」⇒ **本批含治理动作，须先登记后实现**。
- **验收**：① §0 表中残余 3 条断言转绿（3 → 0）；② 契约三方对照核验双向零缺口；
  ③ `argv` 在**两个后端**上行为一致（`llvm-hir` 通道现与 HIR 解释器同缺，只做一个后端会让三通道不一致）。
- **规模**：中。**含契约与治理动作。**

> **为什么不让两批合成一个 P4-1**：装配层的验收是「包能跑且三通道一致」，降载层的验收是
> 「新节点与契约自洽」，两者判据不同、可回退点不同；混装会让 ① 本批混入治理动作（本项目已有
> 纪律：治理与实现不混批）②「7 → 3」这个中间读数消失，失去归因能力。

## 3. 判据

除上游分批表的**三条常设判据**（AST 全量回归 / HIR 全量回归 / 全量探针逐夹具对账）外，本批特有：

1. **执行件对齐**：收口时打印测试实际执行 CLI 的 mtime + md5，并断言其**晚于**本批最后一次源码改动
   （针对 §1.3）。
2. **分层读数**：报「纯装配 4 / 纯降载 2 / 叠加 1」的**逐条**状态，不合并成一个 `7 → N`。
3. **包级三通道一致**：新夹具须同时跑 `interp-ast`、`interp-hir`、`llvm-hir` 三臂并逐字节比对——
   探针只扫单文件，包级缺口在本批**无既有判据覆盖**（该结构性失明已由
   `docs/issue-hir-package-run-unsupported-2026-09-16.md` 立案）。

## 4. 止损点（在上游四条之外，本批新增）

1. **装配层若被证伪**：若接通 CLI 目录分支后发现缺口**不止装配层**（例如降载层无法承载包级
   入口、或跨模块符号解析需改 lowering）⇒ **停**，回报并重估上游「C（缩小 P4 范围）」的启用
   ——上游止损点已预先写了这一条，本次实测使其**更可能被触发**（`argv` 已确定在降载层）。
2. **执行件未对齐即停**：若 §1.3 的处置无法在做本批时完成（例如默认 scratch 构建受阻），
   **停**——此时所有 `...ViaCLI` 读数都不可信，继续下去只能产出假红或假绿。

## 5. 不做范围

- **本件不含任何实现**；`Sources/` 未动（本件为规划件）。
- **不修 `run-llvm` 丢弃 `lli` 退出码**（已立案，只登记不修）。
- **不修 B 组 5 项字符语义**（属「字符串字节语义格」）、**不动取址格**（均非 P4 前置）。
- **不做测试基建改造**（把二进制路径参数化）——只做 §3 判据 1 的**核对**。
- **不处置五条判据缺口**（已改挂「P4 前置 · 独立批次」）。
- 未 push。

## 6. 待裁（三项；每项含背景、选项与代价）

### 裁定 1 · 是否按「装配 / 降载」拆成两批（P4-1a + P4-1b）

- **这件事是什么**：上游分批表把「包运行入口」写成一个批，验收是 HIR 下 7 个失败清零。
  本件实测发现那 7 个里**只有 4 个**由包运行引起，另 2 个纯由 `argv` 缺失引起、1 个两者叠加；
  而 `argv` 的实现被上游划给了「只勘测不修」的另一批。
- **为什么现在要决定**：不拆的话，本批的验收判据必须改成装配层判据（否则不可达）；
  拆的话要多一次开分支与收口。
- **选项与代价**：
  - **A（推荐）**：拆成 P4-1a（装配，验收 7 → 3）+ P4-1b（降载含契约治理，验收 3 → 0）。
    代价：两个批次两次收口；上游分批表的 P4-1 行需改写。
  - **B**：合成一批，一次做到 7 → 0。代价：批内混装治理动作（契约新增两条例目 + 计数基线 +
    三方对照），且丢失「7 → 3」这个归因读数。
  - **C**：只做装配层，`argv` 留作翻转后语义债（**不推荐**）：`argv` 是 CLI 参数透传的
    **用户可见能力**，翻转后 AST 引擎退役，它若不落地即为能力回退。
- **我的建议**：**A**。两批的层不同、判据不同、可回退点不同；且 `argv` 的缺口是**跨后端**的，
  与包运行无关，塞进包运行批会把「一条用户路径」的问题伪装成「包运行没做完」。

### 裁定 2 · `argv` / `moduleRoot` 的实现归属

- **这件事是什么**：上游把这两项登记在「前置核对」批，而该批明确「不修」；于是它们没有实现户口。
- **为什么现在要决定**：它决定 P4-1 的验收能否写到 0，也决定 P4-2 的性质。
- **选项与代价**：
  - **A（推荐）**：实现移入 P4-1b；P4-2 保持纯勘测（`argv`/`moduleRoot` 行改指 P4-1b）。
    代价：上游两处载体需回填。
  - **B**：把实现并入 P4-2 并解除其「不修」限定。代价：P4-2 从「小（读）」变「中（含契约治理）」，
    且它原本的价值（一页影响面清单）会被实现细节淹没。
- **我的建议**：**A**。勘测与实现分开，正是本项目「小步、量准、再治」的既有做法。

### 裁定 3 · 验收通路缺陷的处置时机

- **这件事是什么**：所有 `...ViaCLI` 用例经子进程跑的是硬编码路径 `.build/debug/pini`，
  实测该件是 **09-14** 的构建（当前源码是 09-16），即**测试读的是两天前的 CLI**。
  P4-1 改的正是 CLI ⇒ 不处理则本批**永远验收不过**。
- **为什么现在要决定**：它可能需要在开工前先做一次与指标无关的构建/环境对齐动作。
- **选项与代价**：
  - **A（推荐）**：本批开工第一步 = 刷新 `.build/debug/pini`（或改用默认 scratch 构建），
    并把「执行件 md5/mtime 晚于源码改动」写成收口判据。代价：每批多一次全量构建（3–6 分钟）。
  - **B**：改测试，让二进制路径可被环境变量覆盖。代价：属测试基建改动，动了本批范围外的文件；
    收益（长期）更大，可另立小批。
- **我的建议**：**A 先做、B 另行立案**。A 是让本批判据可信的最小动作；B 是结构改善，
  不该夹在功能批里。
