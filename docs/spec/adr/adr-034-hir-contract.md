# ADR-034: HIR 契约——枢纽规范与多后端语义权威
（HIR Contract: Hub Specification and Multi-Backend Semantic Authority）

## Status

**Accepted（2026-09-12）** —— D1–D6 全部裁决；实施排期为 **P0b**
（见 `docs/issue-interpreter-hir-plan-2026-09-12.md`）。

本 ADR 是 **LR-4（解释器统一 HIR）** 的规范载体。LR-4 此前只有计划与审计载体
（`docs/issue-interpreter-hir-plan-2026-09-12.md`、
`docs/issue-interpreter-hir-gap-audit-2026-09-12.md`），**没有 ADR**——即「枢纽」的契约
本身没有规范落点（见 Context §2）。本 ADR 补上该落点，并把「语义权威归属」从
**事实现状**（以解释器为准）扳回**目标形态**（以 HIR 契约为准）。

## Context

### 1. 为什么是现在：HIR 已初步完成，缺的是契约而非实现

`ADR-031`（宿主级，LLVM 后端重写）的 M 系列已翻转完成：**HIR 成为唯一代码生成路径**
（M6b）。但彼时 HIR 的定位是**单一后端的中转**——它的节点语义为 LLVM 发射器服务，
其自述亦如此（`HIRNode.swift` 开头仍写 "for the LLVM backend"）。

用户裁决（2026-09-12）改变了这个定位：

> 「HIR 是要统合所有后端的，目前以 LLVM 端为最重要的一端，尽管在迁移过程里以解释器为基准，
> 然而 HIR 层已经初步完成，应当结合 spec，使得 HIR 完成统合。」

⇒ HIR 从「LLVM 的中转」升为**全部后端的共用枢纽**。枢纽必须有契约，否则每个后端
各自解释同一节点，分歧只能在执行时被发现。

### 2. 现状实测（E1，2026-09-12）

| 面 | 实测 | 位置 |
|---|---|---|
| **HIR 规范载体不存在** | ADR 列表 026–033 无 HIR 项；全仓仅 4 份文档提及 HIR | `docs/spec/adr/` |
| 节点语义唯一载体 | `HIRNode.swift` 的 `///` 注释（**非规范**，随实现漂移） | `Sources/PiniCore/HIR/HIRNode.swift` |
| **语义权威现状** | `interpreter` 提及 `HIRNode` 23 次 / `HIRLowerer` 36 次 / `IREmitter` 38 次；`parity\|mirror` 18/21/29 → **今天以解释器为准，HIR 照它塑形** | 全仓 |
| 节点面 | **44 expr + 16 stmt = 60**（本轮逐个复核，计数无误） | `HIRNode.swift` |
| 值层双份 | LLVM 侧 `PiniRuntime` 37 个 `@bk_*` 符号（C ABI）；解释器侧值层 1001 行 | `Sources/PiniRuntime/PiniRuntime.swift` |
| 规范锚点 | spec §2.8 载「**双通道一致性是硬约束**」——表述对象是「解释器通道 ↔ LLVM 通道」 | `docs/spec/pini-spec-v0.md` |

**「以解释器为准」是待纠正的现状，不是目标**。它是历史产物：解释器是第一个后端，
HIR 后出现，故照解释器塑形。HIR 统合后，两侧都是枢纽的消费者，**权威应上移到契约**。

### 3. 判准（用户裁决，2026-09-12）

> 「依然是那个判准：**优先兼容 LLVM 端**。」

判准的**意图**（用户同日澄清）是让 HIR 完成统合，不是让 LLVM 特权化：HIR 层已初步
完成（其行为即 LLVM 侧行为），LLVM 是当前最重要的一端，故在**有分歧且必须选一个**时
取其现行为——**省去改动已在枢纽中固化的那一侧**。

### 4. 判准与「规范独立表述」的张力（本 ADR 必须先化解的前提）

计划 §6 第 4 条要求「**规范独立表述语义**（WASM 约束）：不得以 `bk_*` 行为为语义定义处
——否则等于把某一后端的实现选择升格为全体后端的义务」。

这与判准表面冲突：判准说「按 LLVM 侧」，该条说「不得以某后端行为定义语义」。
**二者不矛盾，因为它们在不同层**：

| 层 | 问题 | 适用 |
|---|---|---|
| **选择层** | 两侧分歧时，统一到哪个行为？ | **判准**——优先 LLVM |
| **表述层** | 该行为在契约里怎么写？ | **规范独立表述**——写成语义，不写实现 |

例：`readLine` 统一到 LLVM 侧后，契约写「返回该行内容，**含行终止符**；超长按 **256 字节**截断」
—— 这是语义（各后端都要实现），而非「因为 LLVM 用 `fgets`」。**256 这个数字一旦入契约
即成为义务**；其合理性问题另案处置（见 D4 与后果节）。

## Decision

### D1: HIR 契约是语义权威，各后端与其一致（不以任一后端为定义处）

`docs/spec/hir-contract.md` 是 HIR 节点语义的**唯一权威载体**。判定次序：

1. 语言面语义（用户可见行为）以 `../pini-spec-v0.md` 为准（HIR 契约不得与之冲突）；
2. HIR 节点语义（后端间契约）以 **HIR 契约**为准；
3. 各后端实现（解释器 / LLVM / 未来 WASM）**与契约一致**，任一后端都不是定义处。

⇒ 由此，spec §2.8「双通道一致性」的表述对象须由「解释器通道 ↔ LLVM 通道」
改为「**各后端与 HIR 契约一致**」（落地见 D6）。

### D2: 分歧判准——优先兼容 LLVM 端（含适用边界）

**适用**：两侧**都已实现**且互为**偶然选择**（甲类）的真差异 → 统一到 **LLVM 侧**。

**不适用**（三类）：

| 类别 | 判据 | 处置 |
|---|---|---|
| **规范已裁** | 有更高权威（`ADR-019 D1` / 注册表 / 测试）已表态，某侧偏离 | 仍走**修实现对齐规范**（无裁量空间） |
| **一侧未实现** | 不是「选法不同」，而是某侧根本没做 | 属**缺口**，不属裁决；按既有工单处置 |
| **AOT 模型依赖** | 差异源于 LLVM 的编译期/AOT 模型，解释器无对应概念 | **不硬对齐**，走停损 7「允许差异 + 明文登记」 |

### D3: 甲类裁决结论（A 组 4 项，全部统一到 LLVM 侧）

| # | 项 | 统一后语义（= LLVM 侧） | 代价 |
|---|---|---|---|
| A1 | `readLine` | 不剥行终止符；超长行按 **256 字节**截断 | `testReadLine` 期望失效（须改 `world\n` → `world\n\n`）；语义与函数名直觉冲突 |
| A2 | `fileRead` | **64 KiB 上限** | 静默截断升为语义（已立案，见 D4） |
| A3 | `fileWrite` | 返回 `fclose` 的 **i32** | 裸 i32 泄入语言层 |
| A4 | `stringSplit` | **跳过空 token**（`"a,,b"` → 2 段） | 与 Swift/Python/JS 主流相反；`len` 同步为 2 |

**B 组（6 项）不受判准影响**：`stringSubstring` / `stringCase` / `len` / `contains` /
切片 / `arrayJoin` —— `ADR-019 D1` 已钉 grapheme 模型、`stringSubstring` 的注册表已定
`(start, end)`，属**规范已裁决、实现偏离**，走修实现对齐规范，**不占裁决额度**。

> **P1-4 订正记载（2026-09-12，非新规范内容）**：`arrayJoin` 的 B 组归属**系按邻近归类给出，
> 当时未经实测**（`docs/spec/hir-contract.md` §2.40 原文自述「本轮未实测行为」「差异缺探针」）。
> P1-4 补探针实测后，`interp-ast` 与 `llvm-hir` 在五类接收者形态与非 ASCII 输入上**逐字节一致**
> ⇒ 该节点的「实现偏离」**测量未予支持**。**正式移出 B 组属规范内容变更，本 ADR 不擅自改判**；
> 待裁后 B 组应为 **5 项**。证据落 `docs/spec/hir-contract.md` §2.40。

**C 组（4 项）**：`stringConcat` / `interpString` / `isAsciiDigit` / `printMulti` —— 差异在
「怎么实现」不在「结果是什么」，**规范改写即可，零行为变更**。

**D 组（3 项）**按 D2 边界三分：

| # | 项 | 处置 |
|---|---|---|
| D1 | `&` 取址（解释器快照 vs LLVM 真引用） | **统一到 LLVM（真引用）** —— 判准在此与正确性同向，快照是实现取巧 |
| D2 | 路径基准（LLVM 编译期烘焙 vs 解释器运行时 CWD） | **不硬对齐**。LLVM 侧依赖 AOT 模型，解释器无「编译期」概念 → 停损 7「允许差异 + 明文登记」。**spec G58 已记该差异为「v1 已知限制」，本裁决确认该口径** |
| D3 | 警告通道（LLVM 静默） | **判准不适用**（LLVM 未实现发射，非选择）→ 由 `docs/issue-diagnostic-channel-parity-2026-09-12.md` 处置 |

**E 组（乙类半语义 2 项）**：`optionalGet` 的 panic 面、`pointerLoad` 的符号扩展 —— 须在
契约里**表述为语义**（若写成约定，WASM 端可合法做出不同行为而无法判定谁对）。

### D4: 拆项（停损 6 处置）与缺陷立案

A 组 4 项均改用户可见行为，且按 D-B6「无兼容开关」先例**无迁移窗口** ⇒ 停损 6 触发
（4 > 3）⇒ 按计划 §9 拆项：

- **IO 语义格**：A1 + A2 + A3（同族，恰 3 项，不触发）；
- **`stringSplit` 格**：A4（1 项）。

**缺陷立案（按「完成计划 → 记下缺陷 → 提出工单」）**：判准要求对齐 LLVM，但 A1 的
256 字节上限与 A2 的 64 KiB 上限**是把发射器实现细节升为语言语义**，其中 A2 的截断为
**静默数据丢失**。二者不属于本次裁决的裁量范围（判准已定为「对齐」），故**另立工单**，
不改本次结论：见后果节。

### D5: 冻结纪律——照搬 `bk_*` 范本的「该取的那一面」

`ADR-031` 的 `bk_*` ABI 冻结是**做对了**的范本（37 符号在整场重写中零改动），**照搬**：
契约条目一经落地，变更须走治理，不得随实现漂移。

其**没做到**的一面（清单化）必须补齐，不可继承：① 口径不一致——`ADR-031` 两处写
「35 个」，代码 `@_cdecl` 实测 **37 个**；② 无单一权威清单。本 ADR 同步订正（见 D6）。

### D6: 同步变更（本批执行）

1. **新建** `docs/spec/hir-contract.md` —— 60 节点语义权威清单（含 `char` 节点与
   `.join` 挂起语义的**预留位**，见下）；
2. **修改** spec §2.8：`双通道一致性` 表述对象 → 「各后端与 HIR 契约一致」（走 §1.3）；
3. **订正** `ADR-031` 两处 `bk_*` 口径 35 → **37**；契约内附完整 37 符号清单。

**预留位说明**（两处，均为已裁未实施）：① **`char` 节点** —— `ADR-033` 已裁 Char 类型
引入（排期 P0d），契约先定其语义、标注「待 P0d 落地」；② **`.join` 挂起语义** —— CPS
路线已裁 `R2`（单列一格迁到 HIR），契约须预留挂起语义面，**不实现**。

## Consequences

**正面**：

- 「枢纽」首次有了可核验的契约落点；P1 的规范一致性核验脚本（清单 ↔ 代码节点集 ↔
  实现锚点 三方对照）有了对照基准；
- 语义权威从「事实以解释器为准」扳回「以契约准」，为 P4 删除 AST 走查提供依据；
- 60 节点计数经逐个复核，与计划一致（44 + 16 = 60），无隐藏缺口。

**代价与风险**（如实登记）：

1. **A 组统一到 LLVM 侧的迁移面**：解释器行为须变（A1–A4）。实施时 `testReadLine`
   的期望与注释须同步改；`examples/io.pini` 的 `readLine` 调用为注释态，不受影响。
2. **两处有害默认被固化**（须工单跟踪）：
   - A1 `readLine` **256 字节**上限 = `fgets` 栈缓冲尺寸升为语义；
   - A2 `fileRead` **64 KiB**上限 = `alloca` 尺寸升为语义，且**静默截断**（数据丢失）。
   两项已另立工单，改进须走 §1.3 反向修订契约。
3. **D2 路径基准的差异被正式承认**（非消除）：跨机不可移植性成为**已登记契约条款**，
   而非待修缺陷。这与 spec G58 的「v1 已知限制」口径一致。
4. **B 组仍为待修实现缺陷**：契约记录正确语义，但两侧实现尚未对齐（实施载体 =
   `docs/issue-hir-string-slice-byte-based-2026-09-11.md`）。
5. `HIRNode.swift` 头部「for the LLVM backend」的自述**已成错误陈述**，须订正
   （计划 §7 P5 已载）。
