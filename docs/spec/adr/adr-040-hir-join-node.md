# ADR-040: HIR 契约新增 `join` 节点（`await` / `wait` 的挂起点）

> **状态**：**active**（2026-09-17 用户裁决）｜**类别**：宿主级（HIR 契约；受 `ADR-034` 治理）
> **本件范围**：**§1.3 第 1–4 步同批交付**（提议 / 影响评估 / 登记 / 落地-规范面与节点面）。
> 第 5 步「证据登记」随本批一并完成（见「溯源」）。第 3 步的**实现面**（挂起语义本身）
> **不在本件**，留给格 `G3c` —— 理由见 §5.3。
> **触发**：`G-3` 规划期做「该簇 31 条红逐条归因」时，照出**两条已立判据指向相反动作**（见 §1）。

## 1. 提议（要解决什么）

`await` / `wait` 要在 HIR 里有落点，否则「解释器统一到 HIR」这条主线在并发面上是断的。
但**这个落点该怎么立**，仓库里当时有两条**互相矛盾**的已立判据：

| 出处 | 原话 | 指向的动作 |
|---|---|---|
| `docs/spec/hir-contract.md` §4.2 | 「`HIRLowerer` **须**为 `.join` 增加节点面（副产物约束，计划 §6）」；且 §4 标题自称「预留位（**已裁**未实施）」 | **可直接做**（已是登记的预留） |
| `P4-γ` 硬停条件 `D-P4-26` | 「若须动那 **60 个节点** ⇒ 停下先走 `spec §1.3`」 | **必须先停** |

⇒ 一个说「这是已裁的预留、实施它不算改动」，另一个说「动节点就得先走流程」。
**两者都是本仓的成文判据**，谁也没错——错的是它们对同一件事给了不同动作。
本件的第一个交付就是把这条歧义**判掉**：**走 `§1.3`**，即按后者的严格解读处理。

**理由**：`§1.3` 的要求是「**先走流程**」而不是「不许动」（见 `docs/spec/pini-spec-v0.md` §1.3 五步）。
走一遍的代价是五步文档动作，而绕过它的代价是**失去了「契约变更为何发生」的留痕**——
后者正是本仓反复吃过亏的地方（同一 ID 承载两个定义，见**元仓** `.workbuddy/prompt-architecture.md` §5 案例）。

## 2. 现状实测（提出方向前先量）

### 2.1 节点集与契约的实数（口径：`tools/hir-contract-check.py`）

| 面 | 改动前 | 改动后 |
|---|---|---|
| 契约条目 | 44 表达式 + 16 语句 = **60** | 45 + 16 = **61** |
| `HIRNode.swift` 节点集 | 44 + 16 = 60 | 45 + 16 = 61 |
| 锚点 `llvm` / `printer` / `interp-hir` | 各 60/60 | 各 **61/61** |

> ⚠️ **口径说明**：本表的表达式条目数**只认核验脚本的解析结果**。本批早期用一次性正则数 `HIRExpr`
> 时得出过「56 个 case」，**与脚本不符**——原因是该正则的扫描窗口跨过了 enum 边界、把邻近 enum 的
> case 也计入。⇒ **两个数不是「多」「少」之争，是口径不同**；本件此后一律以脚本口径为准。

### 2.2 三锚点是**双向**核验，这决定了本批的最小范围

核验脚本对同一份数据查两个方向：

```
contract-without-node    契约有条目、enum 无 case
node-without-contract    enum 有 case、契约无条目
node-without-anchor      某后端从不 dispatch 该节点
```

⇒ **「只改契约不改代码」在机械上不可行**：那样 `contract-without-node` 立刻报红。
实测（本批中途态）：

```
contract: 44 expr + 16 stmt = 60 entries
code:     45 expr + 16 stmt = 61 cases
anchor llvm / printer / interp-hir  各 covers 61/61
FAIL: node-without-contract: join
```

**这就是本批把「契约行 + enum case + 三锚点」当作一件事的实质理由** —— 不是风格选择，
是门禁强制的**最小自洽单元**。

### 2.3 代码面改动面（实测，编译器即探针）

在 `HIRNode.swift` 只加一个 case 后构建，编译器报出**恰好 4 处** `switch must be exhaustive`：

| 文件 | 行 | 函数 | 性质 |
|---|---|---|---|
| `Sources/PiniCore/Interpreter/HIRExecutor.swift` | 374 | `evaluate` | 执行 |
| `Sources/PiniCore/HIR/HIRPrinter.swift` | 115 | `exprText` | 打印 |
| `Sources/PiniCore/CodeGen/IREmitter.swift` | 1386 | `emitExpr` | 发射 |
| `Sources/PiniCore/CodeGen/IREmitter.swift` | 2838 | `hirType` | 类型推断 |

⭐ **`HIRLowerer` 不在其列** —— 该文件对表达式用的是一条 `default` 兜底
（构建时伴生告警 `default will never be executed`）。这意味着两件事：

1. **加节点不会替我们自动接上降载**：`HIRLowerer` 仍在原处兜底拒绝 `.join`
   （`Sources/PiniCore/HIR/HIRLowerer.swift` 的 `expression '\(expression.kindName)' is not yet lowered to HIR`）；
2. ⇒ **语言可观察行为零变化**（见 §5.1），这是本批最要紧的保真条件。

### 2.4 两侧既有形态（决定各锚点怎么写）

| 锚点 | 既有形态 | 本批怎么写 |
|---|---|---|
| `interp-hir` | 全 60 节点**已实现**；早期未实现者「fail loud，点名节点」（`HIRExecutor.swift` 头注），该机制已随 `P2b G9` 撤除 | **fail-loud**（`RuntimeError`），不返回静默 `.null` |
| `llvm` | 自称「no unsupported paths」，未实现位一律 `fatalError(… HIRLowerer guarantees …)` | **fail-loud**（`fatalError`）——语义 = 「不该到达」 |
| `printer` | 纯渲染，无语义 | **真实现**（`join(<future>)`） |
| `hirType(of:)` | 「每个 case 自带类型」的 typed-tree 契约 | **真实现**（返回节点自带的 `type`） |

## 3. 影响评估（触及契约 ⇒ 依硬停条件走 §1.3）

**本件触及契约三处**：§0.4 计数基线、§2 条目表（新增）、§4.2 预留位（兑现）。
`P4-γ` 硬停条件写明「若须动那 60 个节点 ⇒ 停下走 §1.3」⇒ 本件即该流程的入口。

### 3.1 语义面：`join` 的 `type` 是什么

`await` / `wait` 在同一站点**解构 `ok` / `err`**（`docs/spec/pini-spec-v0.md` §3.1.1），
故站点所得是 `Result<T>` ⇒ 节点签名取 `join(future:type:)`，`type` = `.result(ok: T)`。

⚠️ **`Future` 自身不是 `HIRType` 的 case**（`HIRType` 无 `future`）。这不是缺口：`Future` 是
**运行时值**（`Value.future`），不是 HIR 静态类型；`join` 的静态结果类型由契约条目钉住即可。

### 3.2 稳定性分级与递交条件

| 项 | 判定 |
|---|---|
| 该构造的稳定性级别 | **Provisional**（并发面 `G12` 为 Stable，但 HIR 侧承载面首次落地） |
| §1.3 第 4 步「递交语言参考」**三条条件** | ①✅ Provisional ②❌ **实现侧证据不足**（挂起语义未实施）③✅ 无未裁决张力 |
| ⇒ 结论 | **本批不递交**（②不成立）。语言参考侧条款维持现状，待 `G3c` 落地后随证据一并递交 |

### 3.3 爆炸半径

| 项 | 实数 |
|---|---|
| 契约条目 | +1（60 → 61） |
| `Sources/` 改动 | **4 处 switch、3 个文件**（§2.3 实测） |
| `HIRLowerer` 改动 | **0**（不接降载，见 §2.3） |
| 既有语料是否可观察到差异 | **否** —— `.join` 当前不可达（§5.1 实测） |
| 是否触及 `B 组缺陷`（规范已裁、实现偏离） | 否（本件不涉及字符串 / 切片面） |

## 4. 决定

**新增 `HIRExpr.join(future:type:)`；契约表达式条目 44 → 45、合计 60 → 61。**

同批落地四件事，顺序不可拆：

1. **契约**：§0.4 计数基线 → 61；§2 新增 `§2.45`（放新节 `§2.11 并发与挂起`）；
   §4.2 由「预留位」改为**兑现标记**（不删标题 —— 旧引用需可追，见 §6）；
2. **节点面**：`Sources/PiniCore/HIR/HIRNode.swift` 加 case；
3. **三锚点**：按 §2.4 的形态补齐（两处 fail-loud + 两处真实现）；
4. **本件 + 台账**：本 ADR 与 `docs/spec/pini-spec-v0.md` §3 台账 `G62`。

### D1 —— 节点面**本批落地**，挂起语义**留 `G3c`**（用户裁决：走 spec 流程加进去）

**理由**：契约查的是**存在**不是**行为**（核验脚本自述「existence, not behaviour」），
且 §2.4 的 fail-loud 形态保证「lowerer 若先接上、而引擎未跟上」会**报错而非算错**。
两者分开落地不会制造「规范描述了不存在的东西」—— 契约条目如实标注实现面未到（见 §5.3）。

### D2 —— 两处 fail-loud 而非静默 `.null`

**理由**：`HIRExecutor.swift` 头注已写明「A silent `.null` would have made this engine look
finished and let the differential probes compare against a fiction」。本批沿用该立场。

## 5. 后果与破坏性

### 5.1 破坏性判定：**非破坏**（语言可观察行为零变化）

| 面 | 本批前 | 本批后 | 判定 |
|---|---|---|---|
| `.join` 的降载 | 兜底拒绝（`not yet lowered`） | **不变**（`HIRLowerer` 未动） | 无变更 |
| 其余 60 节点行为 | — | 不变（三锚点只增一个不可达分支） | 无变更 |
| 契约计数 | 60 | 61 | 计数变更，非语义变更 |

**实测护栏**（本批执行，含一次**自查出的假绿及其订正** —— 记下来是因为它比结论本身更有用）：

| 步 | 做法 | 结果 |
|---|---|---|
| 1 | 备份改动 → `git checkout` 回 HEAD 版 → 构建 → 跑 10 个目录 **106 条夹具**（记 `rc` / 总字节 / 报文） | 基线 |
| 2 | 还原改动 → 构建 → 跑同一批 | 对比 |
| 3 | 对差异条**专项重现**：同一版本**连跑 6 次** | 归属判定 |

⚠️ **首轮判据是无效的（假绿），如实记账**：首轮的「备份 / 回退 / 恢复」三步**没有验证文件内容**，
而恢复所用的备份**本身就是 HEAD 版**（`cp` 退出码成功、内容却是回退后那份）⇒ 两侧跑的是
**同一个版本**，那轮得出的「105/106 一致」是**自己跟自己比**。事后以 `grep -c 'case join'` 复核才现形
（期望 1、实为 0）。⇒ **订正后的判据链，每一步都带内容验证**：

| 验证点 | 期望 | 实测 |
|---|---|---|
| 回退后 `grep -c 'case join'` | 0 | **0** ✅ |
| 恢复后 `grep -c 'case join'` | 1 | **1** ✅ |
| 两侧夹具对比（两版本确为不同源码） | — | 106 条中 **104 条逐字节一致**；**2 条**有差异 |

**2 条差异及其归属**（判据 = 同一版本连跑 6 次）：

| 夹具 | 差异形态 | 同版本 6 次跑 |
|---|---|---|
| `Tests/PiniTests/SuspendRuntimeTests/testWorkStealingOccurs.pini` | `rc` 与总字节（90060B）**不变**，仅「未使用变量」警告的**顺序 / 行号**不同（`c3`@8:5 ↔ `c5`@10:5） | **6 次 6 个不同输出** ⇒ 非确定 |
| `Tests/PiniTests/ConcurrencyTests/testConcurrentGenericTypeInstantiationIsRaceFree.pini` | 同上（154074B，`24:5` ↔ `20:5`） | **6 次 6 个不同输出** ⇒ 非确定 |

⇒ **结论**：本批不改变任何既有可运行程序的行为（104 条逐字节一致；2 条差异归因于夹具自身抖动）。
该「多警告并发夹具输出非确定」形态登记为**第三条读数上限**
（与既有 `SIGPIPE` 整跑崩、`SuspendRuntimeTests` 偶发信号 11 并列）。

⚠️ **两条可复用的判据纪律**（本批实测得来）：

1. **「备份 → 回退 → 恢复」必须逐步验证内容**（`grep` 关键字 / `diff`），**不能只看命令退出码**
   —— 本次踩坑的直接原因就是把 `cp` 的成功当成了内容的正确；不验证则两侧可能是同一版本，
   对比结果全绿而**毫无意义**。
2. **二进制哈希不能当版本判据** —— 实测同一份源码两次构建，`.build/debug/pini` 的 sha256 不同
   （Swift 产物**不可复现构建**）⇒ 版本判定的可靠依据只有**源码内容**。

### 5.2 一处**订正**（如实记账）

`D-P4-30` 的记号订正清单（「`R2` 在本仓指什么」）**漏了旧 §4.2** —— 那里的 `R2` 义项与
本仓现行用法相反。本批已在契约 §4.2 的兑现标记里点名该冲突，并指向规划件；
**记号订正本身**（`R2` 是否需按 `D-P4-30` 统一）**不在本件范围**。

### 5.3 契约条目的诚实标注（防「描述不存在的东西」）

`§2.45` 的注记列**必须**同时写明两件事：①节点面已落地；②**挂起语义的实现面尚未落地、
本节点当前不可达**。只写①会让读者以为并发面已通 —— 而 `G-3` 实测的 31 条红里
**没有一条的首缺口是 `join`**（26 条死在降载层），这个事实与「节点面已落地」并不矛盾，
但**极容易被读成矛盾** ⇒ 两者都要写，缺一即误导。

## 6. 不在范围

- **不实现挂起语义**（CPS 求值器迁移）—— 属格 `G3c`；本件只立节点面。
- **不给 `HIRLowerer` 加 `.join` 降载规则** —— 加了就会让节点从「不可达」变「可达而必失败」，
  行为**变差**（报错点从「未降载」变成「无引擎」），无收益。
- **不改 `SuspendEvaluator`**（890 行）与 `Interpreter` 的挂起状态。
- **不做 `R2` 记号的统一订正**（见 §5.2）。
- **不递交语言参考**（§3.2 条件②不成立）。
- **不删契约旧 §4.2 的标题** —— 它是旧引用的追溯锚（见 §6 上一条的替代说明：此处指保留标题）。
