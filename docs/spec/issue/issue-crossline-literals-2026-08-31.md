# 提案：跨行集合/元组字面量（A12 落点裁决，2026-08-31）

- 状态：**Proposed（待用户裁决）**——P0 批的 spec 先行项；裁决结果决定 F5 钉定批的范围
- 来源：冲突登记册 A12（草稿意图 vs 实现）；与 F5 块文法钉定（批 2）同源

---

## 1. 双方现状

| 侧 | 立场 |
|---|---|
| 草稿（行 11） | 「关于行敏感……遇到集合语法（如元组）允许多行」——集合/元组字面量**允许多行** |
| 实现现状 | 跨行集合/元组字面量被拒——单行必须写完（一行内括号配平）；冲突登记册 A12 实测「跨行集合/元组字面量被拒」 |

## 2. 两个方案

### 方案 A · 维持单行（不改）

- 理由：块文法（F5）只有「缩进块 + 顶格块」两种形态，括号内换行会引入第三种「表达式内跨行」规则，钉定面变大；现语料（897 夹具 + examples + 自举）零跨行字面量使用。
- 代价：长集合字面量可读性受限；与草稿意图偏离（草稿为意图参考，非权威）。

### 方案 B · 引入跨行（括号内容忍 NEWLINE）

- 语义：`( )` / `[ ]` / `{ }` / `< >`（类型实参）内部允许换行，换行等同空白；缩进不参与（括号深度即结构）。
- 代价：F5 钉定批须增加「括号内记号流」维度；lexer 的 newline 发射策略需按括号深度抑制（lexer 改动，波及 L0 门禁语料与自举 lexer——自举 lexer 的 newline 发射须同步）；错误恢复路径需重新验证。
- 收益：大集合/结构体字面量的可读性；与 Swift/Python 等参照系一致。

## 3. 影响面实测（2026-08-31）

- 语料：全仓 .pini 无跨行字面量使用（grep 括号未配平行零命中）——方案 A 零迁移；方案 B 亦零迁移但**实现+门禁成本实付**。
- F5 钉定批依赖本裁决：A 则 F5 只钉「缩进块 + 顶格块」；B 则加第三维度。

## 4. 建议

**方案 A（维持单行）先行，跨行登记为 F5 之后的可选增强**——理由：①零语料使用，无真实需求压力；②F5 钉定面最小化；③未来引入跨行是纯向上扩展（单行恒合法），不构成迁移负担。若用户有真实可读性诉求，批 2 后单独立项。
