## 一、A 级裁决

### A1 · capture 位置 → **体内部，散落分布，不要求集中**

- 实现在**签名前** → 偏离 → 收敛项 **H-1**。
- spec 落点：capture 子句位于匿名函数体内部，可多处出现，不要求集中。

### A2 · 谁可以捕获 → **仅匿名函数**

- 草稿该句用词不当致歧义；正确语义是仅匿名函数可捕获，self 由 `|self` 修饰符表达，不进 capture 列表。
- 实现拒 `capture self`（E2-001）**符合裁决**，无需改动。

### A3 / A4 / A5 · 内建清单 → **以 spec 为准，不参考草稿**

- 事实源 = 宿主 `BuiltinRegistry`（ADR-020 D3/D4）；草稿的内建函数部分不作为依据。
- 三条**消解**，不产生 spec 修订需求。

### A8 · 冒号开块 → **B 案：凡带执行块的函数一律带冒号**（已接受 → **已落地**，收敛项 H-4）

- **裁决**：讨论后接受 **B 案**——带执行块的函数（**含顶级声明**）一律以 `:` 开块。
- **实测（2026-08-31）**：

  | 形态 | 现状 |
  |---|---|
  | 函数字面量 `func (x: I32,) -> (I32,):` + 缩进块 | ✅ 通过 |
  | 顶级 `main\|func() -> ():` | ❌ E2-007 拒（冒号处） |

  → 实现只支持「引导子块的 `func` 带冒号」，**顶级不支持** → 收敛项 **H-4**。
- **迁移成本（实测计数）**：存量顶级声明 **195 处**（宿主 `examples/` 78、自举 `src/` 117）；
  函数字面量仅 5 处（本就带冒号，不受影响）。
- **收益**：与 `if` / `while` 的冒号开块规则统一——「有执行体即有冒号」。
- **待排期**：属破坏性变更（Provisional 窗口），需宿主解析器 + 存量迁移 + 自举同步同批。

### A9 · 约束分隔符 → **`:`**（因 `|` 右侧一般为关键字）

- 顶级声明中 `|` 右侧常为块形态关键字，故约束分隔符用 `:`（`(结构块)<泛型:约束,>`）。
- 实现当前拒冒号分隔 → 收敛项 **H-2**。
- 与 A8 不冲突：A8 是块引导冒号，A9 是类型约束分隔符冒号，位置不同。

### A13 · 「路径」→ **确认为「字符串按路径规则解析」，另立条目**

- 原 A13（「`path` 关键字」）**撤销**：草稿全篇无 `path`，`[路径|path]` 是审计者的试探写法。
- **用户确认**：草稿「路径」所指为**字符串以路径规则解析**（非枚举关键字）。
- → 另立条目 **P-path**（待定义）：语义未明（何种规则？是否引入路径类型？路径字面量与字符串
  的区分？），需补充定义后方可立项。暂不下结论。
- **【出账 2026-09-02】**「字符串按路径规则解析」已由批 5（G58 / ADR-030）定义：IO 内建
  （`readFile`/`writeFile`）的字符串路径按形态三段式解析（绝对原样 / `./` `../` 运行时 CWD /
  其余相对程序基准），不引入路径类型、路径与字符串无记法区分（路径即字符串参数）。
  P-path 就此关闭；规范落点见 §2.4.1 G14 行与 `docs/spec/adr/adr-030-io-path-base.md`。

### A14 · 测试入口 → **重整描述（现状已符合，写入 spec 即可）**

**裁决（用户重整）**：

1. 测试入口**不直接暴露给用户**，而是通过对 `|test` 的处理交到用户手上；
2. 测试函数的执行**不应有顺序差别**（测试间不得有顺序依赖）；
3. 收集方式灵活：**默认全局收集** / **可指定路径收集** / **可指定文件收集**；
4. **测试入口与 main 入口互斥**。

**2026-08-31 实测**（模块含 `main` 打印 `MAIN-RAN` + 两个 `|test`）：

| 命令 | 结果 | 对应要求 |
|---|---|---|
| `pini test <模块根>` | 仅 t1、t2 通过，**无 MAIN-RAN** | 与 main 互斥 ✓、默认全局收集 ✓ |
| `pini test <文件>` | 仅收集该文件（t2） | 可指定文件收集 ✓ |
| `pini run <模块根>` | 仅 MAIN-RAN，不跑测试 | 互斥（反向）✓ |

→ **四项要求现状均满足，无需实现改动**；缺口只在 spec 未明写。

### A15 · 下标访问语义 → **三通道（草稿「`a[i]` 取下标元素」不含安全语义，以 spec 为准）**

**草稿原句**（`docs/spec/Pini草稿.md` §`a[i] 下标访问`）：「以 `a[i]` 取下标元素（数组/字典/集合支持，`i` 为索引或键）」——**未规定越界 / 缺键行为**，故与本轮 spec 不构成文字冲突，而是**语义空缺由 spec 填补**。

**裁决（用户 2026-09-01，D-1~D-7）**：

| 通道 | 形态 | 越界 / 缺键 | 返回类型 |
|---|---|---|---|
| 安全断言 | `a[i]` | **panic**（`RuntimeError.indexOutOfRange`，E5-005） | `T` |
| 安全可选 | `a.get(i)` | `Optional.none` | `Optional<T>` |
| 不安全 | `unsafe a.getUnchecked(i)` | **UB**（解释器以「UB 陷阱」E5-006 近似） | `T` |

- Array / Dictionary / String 一致，**字典缺失键与越界同义**（D-5）。
- **定性证据**：LLVM 运行时 `bk_array_get` 一直 `bk_panic`，是解释器返回 `.none` 造成双后端分叉 → 本项**不是新增能力，而是向 LLVM 既有行为收敛**（出处 `docs/issue-host-optional-slice-2026-08-28`）。
- **破坏性**：越界由「得 nil」改「终止」，类型 `Optional<T>` → `T`；迁移见 `docs/spec/migration-2026-09.md` §A。
- 落点：spec §2.4.1 **G48**（修订）、§3 缺口 **G56**、ADR-028。

→ **草稿按 DEPRECATED 约定保持原样，不就地改写**；本条即其冲突/裁决记录。

### A16 · 括号内关联记号 → **用 `=`（草稿「`[字典键:字典值,]`」与现规范冲突）**

**草稿原句**（`docs/spec/Pini草稿.md` §`[字典键:字典值,]`）：「字典包含多个同构散列元素，每个元素内用 `:` 分隔」——与现规范 `[键 = 值]` **直接冲突**。

**裁决（用户 2026-09-02，D-1~D-8）**：记法原则 **`=` = 值的注入方向**（实参标签 / 字典条目 / 元组标签 / 默认参数），**`：= 标注与取出方向`**（类型标注 / 块开启 / match 具名绑定）。

| 位置 | 草稿 / 旧记法 | 现规范 |
|---|---|---|
| 字典条目 | `[键: 值]` | `[键 = 值]` |
| 实参标签 | `f(a: 1)` | `f(a = 1)` |
| 枚举具名构造 | `E(x: 1)` | `E(x = 1)`（**触及 G54 构造位**，计划修正案 AM-2） |
| 元组标签 | `(a: 1,)` | `(a = 1,)` |
| match 具名绑定 | — | **保持 `:`**（`case A(x: v):`，取出方向） |

- **同向支撑（非冲突）**：草稿「缺省参数是具值的元组元素」一节用 `IDENT '=' expression` 表达默认值——`=` 作值绑定在草稿中**早有先例**，本裁决是其推广而非新造。
- **草稿另一处已由实现追认**：草稿「遇到集合语法（如元组）允许多行」——此意图在批 1.5（A12 方案 B / 路 C）落地，实现跟随草稿。
- 落点：spec §2.2 记法原则、规则 3.15（修订）、§3 缺口 **G57**、ADR-029；迁移见 `docs/spec/migration-2026-09.md` §B。

→ **草稿按 DEPRECATED 约定保持原样**；本条为冲突记录，**规范与 ADR-029 为准**。
- **spec 落点**：①测试由工具对 `|test` 的处理执行，测试入口不暴露给用户；②执行顺序不保证，
  测试之间不得有顺序依赖；③收集粒度三种（默认全局 / 指定路径 / 指定文件）；④测试入口与
  main 入口互斥。
- 背景（为何不是「入口依次调用」）：`Interpreter.runTests` 本就遍历整个 module 的 declarations
  （G41 原意完好，历史偏离只在 CLI 单文件喂入）；生产入口须纯净；测试需独立退出码与输出；
  收集范围可变（可加回被 `[build] exclude` 排除的目录）。

## 二、R-c 复查与 H-3 裁决

**原缺陷（内建名劫持）确认不复现**，并查出一个静默矛盾，现已裁决。

| 场景 | 结果 |
|---|---|
| 与 String 成员方法同名的自由函数（`contains` / `upper` / `split` / `substring` / `slice`）+ 成员形式共存 | ✅ 7/7（自由调用命中用户函数、成员调用命中内建） |
| 源码依据 | `Interpreter` 已无 `if fv.name == "contains"` 按名分支；成员调用走「ADR-020 步骤 B：派发表驱动（`BuiltinRegistry.memberMethods`）」 |
| 与**自由内建**同名（如 `len`） | ❌ E3-004 `redeclared symbol 'len'`——内建名受保护，诊断清晰 |
| 用户给 `String` 写同名**扩展方法** `contains\|self(sub:)` | ⚠️ check 通过，但运行时内建**静默压过**用户方法（无诊断） |

**H-3 裁决（用户）**：内建的类型也是类型；若其派发是默认派发，就应当允许用户扩展覆盖——
**默许用户修改**，因此「内建静默压过用户扩展方法」属于**意料之外的行为**。

- → 收敛项 **H-3**：用户扩展方法**覆盖**同名的内建成员方法（用户优先），而非被静默压过。
- 原缺陷登记：关闭，记为「随 ADR-020 步骤 B 消解」；补一组同名共存回归测试防回退。
