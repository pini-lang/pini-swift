## 一、A 级裁决

### A1 · capture 位置 → **体内部，散落分布，不要求集中**

- **裁决**：capture 子句位于匿名函数**体内部**；可多处出现（散落），不要求集中在一处。
- **实现现状**：capture 在**签名前**（`func capture o () -> ():`），体内部被 E2-006 拒。
- **结论**：实现是偏离方 → 登记**宿主收敛项**（改 capture 的解析位置，允许多处）。
- **spec 落点**：capture 条文改写为「体内部、可散落、不要求集中」。

### A2 · 谁可以捕获 → **仅匿名函数**

- **裁决**：草稿该句用词不当导致歧义；正确语义是**仅匿名函数可捕获外部对象**。
  本身方法访问 self 由 `|self` 修饰符表达，**不是** capture 列表的成员。
- **实现现状**：`func capture self () -> ():` 被 E2-001 拒（capture 列表仅收 IDENT）——**符合裁决**。
- **结论**：实现无需改动；spec 明写「capture 仅用于匿名函数；`self` 不进 capture 列表」。

### A3 / A4 / A5 · 内建函数清单 → **以 spec 为准，不参考草稿**

- **裁决**：内建清单一律以 spec（事实源 = 宿主 `BuiltinRegistry`，ADR-020 D3/D4）为准，
  草稿的内建函数部分**不作为依据**（不订正、不引用）。
- **结论**：A3「草稿列 contains 等为自由函数」、A4「cancel/join 命名」、A5「清单双向出入」
  三条**消解**——不产生 spec 修订需求。
- **附带（非草稿相关）**：见第二节 R-c 的**新矛盾**（用户扩展方法与内建同名时的遮蔽）。

### A8 · 冒号开块 → **仅作为引导子块的 `func` 带冒号**（B 案待确认）

- **裁决**：仅「引导子块的关键字 `func`」带冒号；顶级函数声明不带冒号。
- **2026-08-31 实测**：

  | 形态 | 结果 |
  |---|---|
  | 函数字面量 `var f = func (x: I32,) -> (I32,):` + 缩进块 | ✅ 通过（`f(1)` = 2） |
  | 顶级 `main\|func() -> ():` | ❌ E2-007 拒（冒号处） |

  → **实现现状正是裁决形态，零改动**。
- **你提出的 B 案**（考虑「带执行块的都带冒号」，因函数内部缩进已成规定）：

  | 案 | 内容 | 成本 | 一致性收益 |
  |---|---|---|---|
  | **A（现状=裁决）** | 仅引导子块的 `func` 带冒号，顶级不带 | 0 | — |
  | **B** | 凡带执行块的函数一律带冒号（含顶级） | 解析器改动 + 存量 **195 处**顶级声明改写（宿主 examples 78、自举源码 117）；`func` 字面量仅 5 处不受影响 | 与 `if` / `while` 的冒号开块规则统一，「有执行体即有冒号」 |

  **待确认**：取 A（零成本）还是 B（一致性优先，需破坏性迁移）。

### A9 · 约束分隔符 → **`:`**（因 `|` 右侧一般为关键字）

- **裁决**：顶级声明中 `|` 的右侧通常为块形态关键字（`object` / `enum` / `struct` / `import` …），
  故**约束分隔符用 `:`** 更合理（`(结构块)<泛型:约束,>`）。
- **实现现状**：冒号分隔被 E2-001 拒（`|` 通过）。
- **结论**：实现是偏离方 → 登记**宿主收敛项**（支持 `:` 作约束分隔符）。
- **注意**：与 A8 的 B 案无冲突——A8 讨论「块引导冒号」，A9 讨论「类型约束分隔符冒号」，位置不同。

### A13 · `path` 关键字 → **撤销该条**

- **核实**：`docs/spec/Pini草稿.md` 全篇**无 "path"** 字样。草稿 §`[路径枚举|关键字]` 原文仅
  「包含采用路径语法的用例」，**未规定关键字名**；`[路径|path]` 是 draft-audit 作者的**试探写法**，
  不是草稿依据。
- **结论**：A13 **撤销**（无草稿依据，不构成意图证据）。「路径」的正确所指待你确认——
  可能指**字符串按路径规则解析**（你提出的读法），若是，则另立条目，不属本审计。

### A14 · 测试函数的调用 → 解释「为什么需要 `pini test` 子命令**

- **草稿**：「编译器收集所有测试函数并在**入口**依次调用」。
- **实践**：`pini run` 只执行 `main`；测试由 `pini test` 收集执行。
- **你的判断**：原意（收集 `|test` 集中调用）与实践（集中在 tests/）**不冲突**；疑问是
  为什么需要子命令。依据 `docs/spec/issue/issue-tdd-module-blockers-2026-08-28.md`：

  1. **G41 原意完好**：`Interpreter.runTests` 本就遍历**整个 module 的 declarations** 收集 `|test`；
     历史偏离只在 CLI 单文件喂入（D2 修复 = 削掉单文件退化）。即「收集执行」的语义一直在，
     只是入口形态是子命令而非 main。
  2. **生产入口须纯净**：`pini run` 是程序入口；若自动跑测试，每次生产执行都承担测试开销、
     副作用与输出污染。
  3. **退出码与输出语义**：测试需要「失败即非 0 退出」与独立输出格式；混入 main 输出无法区分。
  4. **收集范围需可变**（D2）：`pini test [path]` 无参 = 模块根全量收集；显式路径 = 限定范围，
     且可**加回**被 `[build] exclude` 排除的目录（如检视 examples/ 下的语料）——入口自动调用
     无法表达范围。
  5. **跨文件可见**：模块包完整加载后收集，tests/ 内手动 `main` 串联（单文件时代 workaround）
     因此退场。

  → 「入口」应理解为**测试入口（由工具提供）**，而非程序的 `main` 入口；`pini test` 就是那个入口。
- **待确认**：spec 是否按此明写（测试函数由 `pini test` 收集执行，不在 `pini run` 中调用）。

## 二、R-c 复查（应要求再查一次）

**原缺陷（内建名劫持）确认不复现**，并查出一个**新的静默矛盾**。

| 场景 | 结果 |
|---|---|
| 与 String 成员方法同名的自由函数（`contains` / `upper` / `split` / `substring` / `slice`）+ 成员形式共存 | ✅ 7/7 断言通过（自由调用命中用户函数、成员调用命中内建，互不干扰） |
| 源码依据 | `Interpreter` 已无 `if fv.name == "contains"` 按名分支；成员调用走「ADR-020 步骤 B：派发表驱动（`BuiltinRegistry.memberMethods`）」 |
| 与**自由内建**同名（如 `len`） | ❌ E3-004 `redeclared symbol 'len'`——内建名受保护，**诊断清晰**，非劫持 |
| **新**：用户给 `String` 写同名**扩展方法** `contains\|self(sub:)` | ⚠️ **check 通过，但运行时内建静默压过用户扩展方法**（断言"扩展方法覆盖内建"失败）——**无诊断** |

**新矛盾（待裁决）**：用户扩展方法与内建成员方法同名时，现状是「内建优先 + 静默」。三选一：

1. 内建优先 + **必须给出诊断**（警告或错误，明示用户方法未生效）；
2. 用户扩展方法优先（用户意图胜出）；
3. 禁止同名（check 期报错）。

倾向：①（保留内建不可被静默覆盖的语义安全，同时消除静默）。

**原缺陷登记处置**：按你的「可以」——关闭，记为「随 ADR-020 步骤 B 消解」；并补一组同名共存
回归测试防回退（成员名自由函数 + 成员形式共存）。
