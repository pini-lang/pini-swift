### 1.5 外部行为调研：Swift 的默认实例语义（2026-09-19 实测）

用户第 11 条要求「先调研 Swift 行为，不一致再问我」。四个独立编译单元的探针（`swiftc` 6.4 · macOS · arm64）：

| 问题 | 实测输出 | 与「读法一」的关系 |
|---|---|---|
| `static let` 是否惰性 | 首次访问**之前**初始化日志计数为 0；访问后才出现记录 | 支持「未访问不物化」 |
| 并发首次访问是否**恰一次** | 64 路并发取用 ⇒ 不同实例数 **1**、初始化次数 **1** | 支持「恰一次」 |
| 同模块**两个文件**是否各得一份 | 另一文件取到的 id 与本源取到的**相同** | **否证**读法二（「每个使用它的文件各自实例化一份」） |
| 跨模块 `import` 是否共享 | 访问前计数 0 → 首次访问后 **1**；引入侧**两个文件**取到的 id 相同，最终计数仍为 **1** | **支持读法一**：存放位与初始化都在**定义侧**，引入侧只引用 |
| 定义侧的文件级全局 `let` | 同样惰性、同样跨文件共享 | 文件级槽位与类型级槽位行为一致 |
| 泛型类型的 `static` **存储**属性 | ⛔ **编译错误**：`static stored properties not supported in generic types` | ⇒「每特化一份」的槽位**不能**是一处通用存储，必须由编译器**按特化合成**（§2.4） |
| 泛型类型的 `static` **计算**属性 | 可用；同特化稳定、跨特化不同 | 特化粒度与既有泛型机制自洽 |

⇒ **读法一成立**，与用户倾向一致，**无需回问**。附带一条对 P2 有用的推论：泛型给定块的槽位必须**逐特化合成**，与用户第 7 条「每特化一份且必须带默认构造」自洽。

### 1.6 `[[T]]` 的含义重叠怎么收（用户第 12 条）

两条现状实测：`[[T]]` 在解析期被钉为 `.enumExt`，而该 kind **在降载层没有任何消费者**（§1.2）；全仓 `.pini` 语料对该形态**零使用**。于是有两条落法：

| 落法 | 做什么 | 代价 |
|---|---|---|
| **① 语义按被扩展者分派**（**采用**） | `[[X]]` 保持「方括号 = 通用扩展」的原意：扩展语义由 **`X` 的类别**决定（枚举 / 给定块） | 归并处须按目标符号类别分派；「kind 由定界符决定」变为「kind 由解析结果决定」，须在规范写明 |
| ② 另立 `.givenExt` | 新增一个 kind，定界符仍取 `[[` | 定界符与 kind 不再一一对应，两种 kind 抢同一形状，更绕 |

用户第 12 条的「方括号本身应是通用的，其他扩展应是糖」= 落法 ①：`((` / `{{` / `<<` 是**按类型类别专门化的糖**，`[[` 是通用形。**另一条佐证**：声明位 `[名]` / `[名\|修饰符]`（单方括号）本来就是**声明总线**（枚举声明 + `[名称\|import]` / `[名称\|export]` 块）⇒ `[名\|given]` 落在同一分支，扩展位取 `[[` 与之一致。

⚠️ **须留痕的一处**：`.enumExt` 无消费者 ⇒「枚举扩展块」在当前 HIR 路径下**可能从未生效**（语料零使用 ⇒ 无观测，无法判「缺陷」还是「未实现」）。本件**不顺手改**（超范围），只登记为待点名项（§7）。

## 2. 默认实例的承载方案（已裁：方案 B）

### 2.1 为什么必须新建面（已不是待裁，是定案前提）

ADR §2.2 承诺四项行为：**惰性** · **恰一次** · **地址稳定** · **无启动风暴**。这四项都需要一个**存放位**（「这一份实例放在哪」）与一个**物化入口**（「谁来跑各字段初值」）。

实测表明现成的路都不通：

| 看似可用的设施 | 为什么不成立 |
|---|---|
| `LazyRef<T>` | ⛔ 用户第 4 条已裁定：它只在**字段内部**做细粒度缓冲，**不**承担默认实例的物化 |
| `HIRModule` 的四个面 | 都不是「模块级可变状态」的载体 |
| 顶层 `let` | ADR §1 背景表已列：无模块级绑定语义、无程序级唯一性、无惰性 |
| `IREmitter` 的 `global` | 仅 `@__stdinp`（外部声明），不是语言层定义的存放位 |

⇒ **「零新运行时机制」这句（ADR §4.1）在实测下不成立**，须订正为「零新**惰性**机制；默认实例的**存放位**与**物化入口**是最小的新面」。

### 2.2 候选对比（A 已排除 · C 未被选 · **B 定案**）

**方案 A（扩 `LazyRef` 元素 ABI）—— 已由用户第 4 条排除。**
补充实测证据（说明它本来就贵）：`IREmitter.lazyRefElemABI` 只认 5 种元素（`i32` / `f64` / `boolean` / `string` / `char`），其余落 `fatalError`；且 `bk_lazyref_value` 的语义是**每个 handle 一次**，而默认实例需要**每类型一份**——语义层级不同，不是加一条 case 能解决的。

**方案 B（新增最小运行时面 `bk_given_*`）—— ✅ 用户第 10 条定案**

- **读法**：用户第 11 条取**读法一**（声明所在文件发射槽位与初始化函数，其它文件 import 后引用**同一份**）⇒ 下面「跨文件/跨模块」那条落法**已定**。

- 形状：`bk_given_get(slot, init_fn, bytes) -> ptr`。内部：`*slot == null` 时加锁 → 分配 → 调 `init_fn` → 写 slot；否则直接返回 `*slot`。
- `slot` 是**发射层定义的静态全局**（`@__given_<T>`），地址天然稳定；`init_fn` 是发射层**合成的具名函数**（先例：`IREmitter.ensureLazyRefWrapper` 已在合成 wrapper）。
- once 骨架**照抄** `bk_lazyref_value`（`NSLock` + 缓存），成本约 20 行。
- 跨文件/跨模块：定义处发射 slot，使用处 `external global` 引用（**沿用 `@__stdinp` 的既有先例**），链接期可见性**随类型可见性**（用户第 6 条）。
- HIR 侧：新增**一个表达式节点**（如 `givenDefaultInstance(type:)`），语义写「取该类型的默认实例；惰性物化、恰一次、地址稳定」，三锚点齐备。

**方案 C（纯发射层：静态全局 + 一次性守卫，零新符号）—— ❌ 未被选（用户第 10 条选 B）**

- 优点：零新运行时符号。
- 代价（三条，逐条实测支撑）：
  1. **线程安全要自己写**——而一旦为此调用运行时原语，就退回方案 B。
  2. **两台引擎各写一套 once**——`HIRExecutor` 侧要独立的表 + 标志。这与 `LR-4` 的判据（「同一程序在每个后端意思相同」，手段是「单一 C-ABI 边界 + HIR 为唯一中枢」）**正面冲突**，且要额外用差分夹具去守两侧一致。
  3. **省不掉 HIR 新节点**——「此处须做一次且仅一次」这个信号在 HIR 里仍需表达，否则两台引擎只能靠约定各自猜。
- ⇒ **相对 B 只省 1–2 个符号，却多一份双实现风险。**

### 2.3 定案与理由（用户第 10 条：**选方案 B**）

**已裁 = 方案 B**。理由三条（上轮据以推荐，用户采纳）：

1. **与 `LR-4` 的方向一致**：once 逻辑只写一次（运行时），两台引擎调同一个语义。方案 C 要维护两份并额外立差分判据。
2. **用户第 6 条（文件级 + 可见性一致）在 B 里是自然结果**：slot 由**声明文件**定义、随类型可见性导出，使用文件 external 引用 —— 不需要额外的机制设计。
3. **成本已被实测锚定**：`bk_lazyref_value` 的骨架可直接照抄；`HIRTypeDecl.Field.defaultValue` 已存在；`HIRExpr.construct` 三锚点已在 —— 真正的增量只有「一个节点 + 一条契约 + 1–2 个符号」。

⚠️ **B 与 ADR §4.1 的表述冲突须一并订正**（工作内容，非待裁）：ADR 那句「复用既有设施……`LazyRef` 运行时」应改为「惰性四项复用既有**实现骨架**；`LazyRef` 本身不承担默认实例的物化」。

### 2.4 B 的完整新面清点（定案后的成本清点）

| 面 | 增量 | 治理动作 |
|---|---|---|
| 运行时 | `bk_given_get`（+ 可能的 `bk_given_destroy` 供 `bk_runtime_cleanup` 兜底） | `bk_*` 权威清单 **37 → 38/39**（同步 HIR 契约 §5.2 与语言规范 §3.2） |
| HIR | 一个表达式节点 + 一个契约条目 | **走语言规范 §1.3 五步**（先登记后落码） |
| 发射 | 合成 `init_fn` + 定义 slot + 跨文件 external | 复用 `ensureLazyRefWrapper` 与 `emitConstruct` 的既有形态 |
| 发射 | **泛型特化槽位**：槽位名带特化后缀、**逐特化合成** | ⚠️ Swift 实测：泛型类型上**不允许** `static` 存储属性（§1.5）⇒ 不能指望「一处通用槽位」；与用户第 7 条一致 |
| 降载 | **特化名 → 槽位** 在发射期是否可见（上轮列为 P2 前置核实项） | ✅ **已解除**：特化在 `HIRLowerer` 的降载预扫登记（`precollectGenericUses` → `structSpecializations` / `registerEnumSpecialization`），`IREmitter` 侧**无**运行时单态化队列 |
| 引擎 | `HIRExecutor` 侧一张「类型名 → 实例」表 + once | 与 LLVM 侧同语义 |

## 3. 分批

> 每批独立验收、独立提交、`--no-ff` 合并后删分支。每批第一条命令 = 建分支（契约 C1）。

### P0 · 治理前置（零源码改动）

1. 走 §1.3 五步：为「默认实例取用」新增 HIR 契约条目（**先登记后落码**——ADR 自身的规矩）。
2. 规范侧：`G71` 的稳定性、`using` 入关键字表（34 → 35）、ADR §4.1 那句订正、ADR §7 逐项标「已裁 / 后置」。
3. 补 `G71` 行中两个**已删**载体的「载体已删」标记（§1.4 载体失效标记 MUST，本身**零成本**）。

**判据**：契约条目可被 `hir-contract-check.py` 读到且不报缺口；规范内 `using` 关键字计数与 `Keyword` 枚举一致。

### P1 · 语法面（不接后端）

- 词法：`Keyword` 加 `using`（34 → **35**）；`given` **不入**关键字表——它只出现在 `|` 右侧的修饰符位，走既有白名单接出路径（先例：`|test` / `|foreign` 均非独立关键字）。
- 语法（**声明位**）：`[名|given]` 落在**单方括号声明总线** `Parser.parseBracketDecl` 的 `|` 修饰符分支（§1.2）——**不新增产生式**。
- 语法（**扩展位**）：`[[名]]` 沿用 `parseExtensionDecl`；按用户第 12 条，扩展的 kind **按被扩展者分派**（§1.6 落法①）。既有 `[[枚举]]` 形态语料零使用 ⇒ 改动**无回归面**。
- 语法（**参数位**）：`Parser.parseParameter` 接出 `using` 前缀；`Parser.extractTraits` **须实测确认**给定块走同一路径（若是，ADR §7 第 6 项可关闭）。
- AST：`Parameter` 加 `isUsing`；新增 `GivenDecl`（字段 + 方法 + 特征，与 `ObjectDecl` 同形）。
- 降载：`HIRParam` 加 `isUsing`；`givenDecl` 暂**落 fail-loud**（明确报「本批未接后端」），不静默。
- ⛔ **本批的中间态必须显式登记**：解析通过、降载响亮拒绝。

**判据**：新增 `GivenUsingTests`（内联 raw）覆盖——接受态（`[T|given]` 块 + 字段初值 + `using 名: 类型` 参数）、拒绝态（`using` 出现在非参数位；字段缺初值与「必须带默认构造」的冲突面）。全量回归**集合相等（新增红 0）**。

### P2 · 默认实例（核心；方案 B 与读法一**已定案**）

- 运行时：`bk_given_*`（骨架照抄 `bk_lazyref_value`）。
- **存放位归属（读法一）**：slot 由**声明所在文件**发射，随类型可见性导出（跨模块门槛 = 仅 `public`，语言参考 §10.5 已有规则）；使用侧只做 `external` 引用 ⇒ 同一类型的默认实例在**全程序一份**，与 ADR §2.2 / §2.5 相容。
- **泛型（每特化一份）**：槽位名带特化后缀、**逐特化合成**（Swift 实测排除「一处通用存储」，§1.5）；特化登记点校验「字段初值全齐」（用户第 7 条）。
- HIR：新增节点 + 三锚点（`IREmitter` / `HIRExecutor` / `HIRPrinter`）。
- 发射：合成 `init_fn`；定义 slot；跨文件 external。
- 降载：`using` 取用点解析为默认实例取用。

**判据（四条可观测行为，不是「能跑」）**：
1. **未访问不物化**——初值里放可见副作用（如 `print`），未取用即不出现在输出里；
2. **恰一次**——两处取用，初值副作用只出现一次；
3. **共享**——两处取用拿到同一实例（自构造的实例**不**共享，且**语言不报错**——ADR §2.5 的代价 1 须有落地证据）；
4. **跨文件同一份**——取用点分处**两个文件**（同包），两处拿到同一实例、初值副作用只出现一次（这是**读法一的直接判据**）。
   ⚠️ **跨模块**那一级本批**不判**：语言参考 §12.3 已知限制已登记「跨模块 · IR 后端不支持（后续批次）」⇒ 跨模块判据**随该批次**补，本批不得用它充数（假绿）。

### P3 · 强制规则

- 「依赖不得隐藏」检查：值位引用给定块类型 ⇒ 签名须声明 `using`；抽象签名（无体）豁免。
- 「字段不齐 ⇒ `using` 无从物化」的报错。

**判据**：负向夹具（内联）逐条断言**错误类型与判定码**，且断言「不该发生的确实没发生」。

### P4 · 收口

- 全量回归（**一次**，取新基线）、契约核验、元仓读数刷新（`project_head` / `branches` / `tests`）。
- 环检测**后置**（用户第 5 条）——本批只做 §3.5 的余量设计。
- ADR 与规范回填、`G71` 状态更新。

### 3.5 环检测的「余量」设计（用户第 5 条：后置但要留余量）

「留好检测余量」落到三条**当期就要做对、但不产出诊断**的事：

1. **依赖关系要留痕**：降载时记录「哪个函数 / 哪个字段初值引用了哪个给定块类型」，即使当期只用于警告或不报。有了这张表，后置的环检测是**加一条遍历**，不是重新解析。
2. **解析过程不得做成不可回溯的一次性趟**：`using` 的解析在**每个取用点独立完成**，不要聚成「必须一次扫完」的全局过程。
3. **诊断码预留**：为环检测预留码位并登记（append-only 约定下，预留须显式写）。

### 7.1 仍待裁：跨模块 `using` 的类型标注形态（用户第 14 条）

调研结论 = **既有规则不完备**：跨模块的**调用**走 `别名.符号`（`HIRLowerer` 把别名前缀加到签名表键上），但**类型位置没有限定名形态**——`TypeAnnotation` 只有五个 case，`parseTypeAnnotation` 的「简单类型」分支只吃单个标识符 ⇒ `using 应用: 服务.应用服务` 这种写法**今天解析不了**。三选一：

| 选项 | 做什么 | 代价 |
|---|---|---|
| **a · 用注入导入**（**推荐**） | 文件内写 `_服务 = "路径"`（语言参考 §10.5 注入导入）⇒ 该模块 `public` 符号进入**本文件裸名空间** ⇒ 写成 `using 应用: 应用服务` | **零新规则**；代价是该文件多一个注入别名，且注入符号与本文件裸名相撞会触发 **E3-013 歧义错误** |
| b · 新增类型位置的限定名 | 让 `TypeAnnotation` 支持点号链（或加一个 case） | 须走规范 §1.3 五步登记；波及类型解析、`isStructurallyEquivalent` / `describe`、契约 ⇒ **明显超本单元** |
| c · 本批不支持跨模块取用 | 只支持同文件/同包，跨模块登记为**不覆盖面** | 工作量最小；与用户第 6 条「import 来的 given 可能带默认实例」暂不兑现 |
