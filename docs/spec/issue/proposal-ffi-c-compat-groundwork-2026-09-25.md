## 1. 起点实测（当次实测，载体 = `.build/debug/pini`，零源码改动）

> 命令一律在 `/tmp` 下的**自建模块**里跑（不进仓）；探针源码见 §1.1。
> 自建 dylib 的理由：`strlen` / `memcpy` 等是 **shim 白名单成员**，走的是 shim 路径而**非裸 C 绑定路径**，
> 拿它测裸绑定边界会得到**无效读数**（我本轮踩过，见 §7 第 1 条）。

| # | 面 | 结论 | 读数 / 证据 |
|---|---|---|---|
| 1 | 标量 · `*标量` · shim 白名单 | ✅ **可运行** | `examples/ffi.pini` · `examples/ffi_module/` 既有样例 |
| 2 | ⛔ **实参 > 8** | **静默丢弃**（第 9 个起） | 见 §3.1 |
| 3 | ⛔ **多返回签名** `-> (I64, I64,)` | **静默坍缩为单返回** | 见 §3.2 |
| 4 | by-value 结构体作顶层类型 | ✅ 照拒 | `E4-001`（check 即拒） |
| 5 | 回调（函数类型参数） | ✅ 照拒 | `E4-001`（check 即拒） |
| 6 | **变参** `printf(fmt: *U8, ...)` | ✅ 拒 —— 但**文法里就不可表达** | `E2-002 expected token identifier`（比「out-of-scope」更强：不是没实现，是**写不出来**） |
| 7 | GPR 与浮点**混用**签名 | 检查放行 · **运行期**拒 | `E5-006 invalid operation: FFI 裸绑定暂不支持 GPR 与浮点混合签名`（`rc=1`，**响亮**） |
| 8 | ⛔ `*CChar` | **check 过、run 报** | `E6-004 unsupported feature 'parameter … lacks a resolvable type'` |
| 9 | ⛔ `*结构体` | **check 过、run 报** | 同族 `E6-004`（与第 8 条**同一处**触发点） |
| 10 | LLVM 腿的 FFI 面 | 整条 unsupported | `E6-004`「LLVM 后端暂不支持 `[名称\|foreign]` 块；请改用解释器 `pini run`」 |
| 11 | 既存 C ABI 边界 | `PiniRuntime.swift` 实测 **55** 个唯一 `bk_*` `@_cdecl` 导出 | ⚠️ 并发提案 §3 记「清单 **52**」—— **口径不同**（一个数**实现导出**、一个数**契约登记**）⇒ 二者**不可直接相减**；差 3 的成因**未追**，如实登记 |
| 12 | 本机 LLVM 工具链 | `clang` 在 · **`lli` / `llvm-as` / `llc` / `opt` 全缺** | `run-llvm` 报 `lli not found` ⇒ 第 10 条**在本机无法执行验证** |

⭐ **四类结局**（本表按此归类，比逐条读更有用）：
**可运行**（1）· **静默错**（2 · 3 · 13/14 见下）· **响亮拒**（4–7）· **声明过但跑不了**（8 · 9 · 10）。

### 1.1 探针源码（内联，可复跑）

```c
/* probe.c —— 自建依赖库；clang -shared -o libprobe.dylib probe.c */
long probe_sum8(long a,long b,long c,long d,long e,long f,long g,long h){
    return a*1+b*2+c*3+d*4+e*5+f*6+g*7+h*8;
}
long probe_sum9(long a,long b,long c,long d,long e,long f,long g,long h,long i){
    return a*1+b*2+c*3+d*4+e*5+f*6+g*7+h*8+i*9;
}
```

```toml
# pini.toml —— 探针模块清单
[package]
name = "arityprobe"

[ffi]
abi = "C"
search_paths = ["lib"]     # lib/libprobe.dylib
libs = ["libprobe"]
```

```pini
; arity.pini —— §3.1 / §3.2 的语料
[probe|foreign]
probe_sum8(a: I64, b: I64, c: I64, d: I64, e: I64, f: I64, g: I64, h: I64,) -> (I64,)
probe_sum9(a: I64, b: I64, c: I64, d: I64, e: I64, f: I64, g: I64, h: I64, i: I64,) -> (I64,)

main|func() -> ():
    var r8 = unsafe probe_sum8(1, 2, 3, 4, 5, 6, 7, 8)      ; 对照：期望 204
    print("sum8 =", r8)
    var r9 = unsafe probe_sum9(1, 2, 3, 4, 5, 6, 7, 8, 9)   ; 期望 285
    print("sum9 =", r9)
    var r9b = unsafe probe_sum9(0, 0, 0, 0, 0, 0, 0, 0, 5)  ; 期望 45
    print("only9th =", r9b)
    return
```

⚠️ **一处形态坑（供后人照抄时避免）**：`[<路径>|foreign]` **不能**写路径（块名须为标识符，写路径报 `E2-002`）；
外库须经 `pini.toml` 的 `[ffi] search_paths` + 块名解析为 `lib<块名>.{dylib,so}`（既有官方样例 `examples/ffi_module/` 同形）。

## 2. 方向形状（用户 2026-09-25 选定：ABI 契约单源 · 外呼新建 · 数据布局兼容）

> ⚠️ **三个方向当日稍后已逐项裁定**，各节开头均有**裁定行** ⇒ **存活下来的只有 §2.1**。
> 各节的**叙述与代价分析一律保留不动** —— 那记的是**裁定时点**的实况，⛔ 不据以读现况。
> §2.4 是同日后半段新增的**捷径面**（在上述三个方向之外）。

### 2.1 ABI 契约**单源**

**现状：类型映射没有单一事实源**，分散在三处且**已有漂移证据**：

| 处 | 内容 |
|---|---|
| 规范 §2.7（散文） | 顶层白名单 + `CChar` 的显式立名（`G65`） |
| `ForeignThunk.swift` 的 `enum Kind` 与 `kind(of:)` | **实现侧**的映射（`I8…U64 / F32 / F64 / Bool / ptr`） |
| `IREmitter.swift` 的 shim 名单与 `bk_cstr` 符号名特判 | 发射侧的**另一份**名单 |

⭐ **漂移证据（当次按代码读，未实测行为）**：`TypeChecker.swift` 的 `ffiTopLevelScalars` 实测**不含 `CChar`**，
而规范已把它立为 FFI 单字节字符的显式名字 ⇒ 该集合靠「**未知简单名一律放行**」兜住 ——
该处注释自己已承认「**它不是一张有效白名单，而是一张『已知标量』表**」。
⇒ 后果：白名单**判不出**违规，只能事后由运行期撞出来（第 8 条就是这么来的）。

**铺垫的形状**：把「**Pini 类型 ↔ C 类型 ↔ ABI 传递方式**」收成**一张表**，落在**规范 §2.7**（语言面权威），
实现侧只留**指针**；⛔ 与 `IR 契约` 的 `bk_*` 调用约定**分界**（那是**运行时面**）。
⭐ 这是三方向里**最便宜**的一个：零源码改动即可先落表，且**后面两个方向都要以它为基准**。

### 2.2 外呼（C → Pini）新建 —— ⛔ **已拒**

> **裁定（用户 2026-09-25）**：**拒绝**，原话「工作量太大，拒绝」。它要新语法 + 类型面 + 两端
> + **库产物**（见下表第 ① 件），量级最大。⇒ 本节**整体关闭**；形状与代价**如实保留**（裁定时点实况）。
> ⚠️ **连带效果**：**「外呼 × LLVM 降档」那个张力随之自动消解** —— 它唯一的实例不存在了。

⭐ **三件形状，缺一不可 —— 而最硬的那件不是 ABI**：

| # | 形状 | 现状 | 说明 |
|---|---|---|---|
| ① | **产物形态** | ⛔ **不存在** | 今天 `pini run` 跑解释器、`pini compile` 产**可执行文件**。C 要调 Pini ⇒ 需要一个**库产物**（`.dylib`/`.so`）⇒ 外呼的真前置是**构建面**，不是 ABI 面 |
| ② | **导出声明形态** | 无（三选，**随本方向关闭而作废**） | `|export` 修饰符 / `[X\|export]` 块 / `pini.toml` 的 `[ffi] exports`。⚠️ 与既有 `[X\|foreign]`（**入**）对称是加分项 |
| ③ | **跨出类型白名单** | 无 | 与 §2.7 内呼白名单**同集**（标量 / `*T` / `void`）。⛔ `object` / `Result` 不得跨出；⚠️ `String` 是**生态刚需**，只能经 `*U8` + **显式所有权约定**（谁分配谁释放，照 `cstr` 既有形态），⛔ **不得**把 Pini `String` 的宿主表示暴露给 C —— 依据 = 规范 §3.2「不得泄漏 Swift 类型」这条**已立**硬约束 |

⛔⛔ **本方向给目标出了个直接张力（必须报，不掩饰）**：外呼**只在编译后端上有意义**
（解释器腿没有可供 `dlsym` 的产物）⇒ 若外呼是 MVP 要的，而**唯一的编译后端又被降档**，
则「降低 LLVM 端重要性」与「外呼」**自相矛盾**。
（**已裁（2026-09-25）**：**外呼被拒** ⇒ 该张力**自动消解**，见 §2.2 裁定行与 §6-1。）

### 2.3 数据布局兼容（by-value 结构体） —— ⏸ **已搁置**

> **裁定（用户 2026-09-25）**：**搁置**，原话「如果自举不需要就可以搁置」——
> 与规范 §2.7 既有的「**自举编译器不需要**，仅在生态确实需要时立项」**同向**。
> ⇒ 既不立 Phase 2c、**也不**走「只定形状不定排期」：**整体搁置**，§2.7 该条**不变**。

⭐ **前置缺口（实测）**：`*结构体` **今天已不可用**（§1 第 9 条 `E6-004`）⇒
**by-pointer 都没通，by-value 谈不上**。这是本方向的第一件事实。

**形状（若做）**：

1. **字段序 = 声明序**，⛔ **不得重排**（重排会与 C 的 `offsetof` 直觉相悖）；
2. **对齐**按目标平台自然对齐 + 尾部补齐；须写明**判据**（不能只说「按 C 规则」）；
3. **传参分类**：**AAPCS64**（arm64）与 **SysV AMD64**（x86-64）**两套都须成文** —— 本机是 arm64，只写一套等于把另一套留给下一个人猜；
4. **「C 兼容结构体」须可判定**：只含标量 / 指针字段（与 `*T` 元素的既有规则**同源**，⛔ 不新立第二套）。

⚠️ **与规范相冲**：§2.7 明写 Phase 2c「**自举编译器不需要**，仅在生态确实需要时立项」
⇒ 选它必须二选一：**立项 Phase 2c**，或**只定形状不定排期**。（**已裁：两者皆不取，整体搁置 —— 见本节裁定行。**）

### 2.4 捷径面：内呼 × 自写 C（同日后半段提出）

⭐ **本节记两个同日裁定，它们合起来改变了「C 兼容铺垫」的落点**：

| 裁定 | 内容 | 连带效果 |
|---|---|---|
| **外呼拒 · 内呼留** | C → Pini 不做；**Pini → C 保留** | 内呼从「不在本件」升为**捷径的承载面** |
| **C 后端升格** | 由「逃生路径」升为「**自举路径的一环**」 | 它同时是「**降 LLVM**」与「**造第二个种子**」的答案；升格已落在语言参考侧 |

**用户对「捷径」的原话，与我的核对**：

- 原话甲：「FFI 可能是一个捷径」。
- 原话乙：「FFI 的捷径之处在于，**可以利用 C 的丰厚的库来免掉许多实现**，虽然这并不能称之为自举，
  而是一种半迁移到 C 的实现，考虑到语言特性中大量与 C 兼容，这可能并不那么出格」。
- ⚠️ **核对结果：这条成立，但它指向的不是「内呼能力」** —— 「用 C 库省下实现量」是**依赖选择**（用谁），
  与「能否调到 C」是两件。本语言确实**照 C 的形状长**（定宽整数 · 显式指针 · `unsafe` · `load`/`store`），
  故「半迁移」对它的语义伤害**小于**对 GC 语言 ⇒ 用户的判断成立。⇒ 本件拆成三层登记：

| 层 | 内容 | 判 |
|---|---|---|
| **(a) 依赖 libc** | 人人如此；规范已把「自举纯 libc」写作长期愿景 | **地板，不是捷径**（无争议） |
| **(b) 依赖第三方 C 生态** | 这才是「省实现量」的本体；代价付在**可复现性 / 环境面** | ⛔ **已被 (c) 取代** |
| **(c) 主动编写 C** | 用户当日第三步提出；同日裁定**三档作废、由它取代** | 施工序 **D → B → A**，**不做 C 种子** |

⭐ **(c) 为何优于 (b)**：走 (b) 须为每个第三方库写「为何 Pini 自己做不了」并冻版本；
**自己写 C 把这一层整个绕开**（可控、可复现、无环境负担），且让既有的硬约束
（**shim 边界必须是 C ABI，不是 Swift 泛型 ABI**）**由构造满足**，不靠纪律维持。

⚠️ **「写 C」是四件事，代价差一个数量级 —— 本件只登记层次，不替其排定**：

| 档 | 内容 | 仓内状态 |
|---|---|---|
| **D** 写 C 粘合 | 小工具函数（逃生舱） | 未登记 |
| **B** 写 C 运行时 | 替换 Swift 实现的那一层运行时 | 对应规范的长期愿景「阶段 3」 |
| **A** 发射 C | 后端输出 C，交系统 C 编译器 | **参考已登记**（◐ 设计完成，未落地，优先级「高」） |
| **C′** 写 C 种子 | 用 C 写第一个编译器 | 未登记；**已裁不做** |

⚠️ **一条须提前知道的后果链（不粉饰）**：D 档若需要 `*CChar` / `*结构体` **真正可用**，而它们
**今天不通**（§1 第 8·9 条）⇒ 这两格会由「未立案」升为「**阻塞**」；
而用户的 ⑥ 是「**形成阻塞就修**」⇒ **修复授权由后果自动成立**，但仍须**单独点名**方可开工。
⛔ 本件**不含**任何施工。

⚠️ **一条反方向的代价**：写 C 会让「**三份实现并存**」（Swift 宿主 · C 宿主 · Pini 自举）成为可能 ——
⇒ 若采纳，C 必须**冻结**（种子纪律）**并带删除计划**，否则它会变成永久的第三份。

## 3. 两处静默缺陷（立案依据）

> ⚠️ 两者的共同性质：都是「**静默**」类 —— **无诊断、`rc=0`、只读代码看不出**。
> 这正是本仓判据纪律里最贵的一类（宁 fail-loud 不静默）。

### 3.1 FFI 实参上限 8 —— 超出**静默丢弃**

**复现**（语料见 §1.1）：`probe_sum9` 按系数 1…9 加权求和。

| 调用 | 期望 | **实测** | 结论 |
|---|---|---|---|
| `probe_sum8(1,…,8)` | 204 | **204** | ✅ 对照正确 |
| `probe_sum9(1,…,9)` | **285** | **204** | ⛔ 恰等于**前 8 项**加权和 |
| `probe_sum9(0×8, 5)` | **45** | **0** | ⛔ 第 9 个实参**完全没到** |

**无诊断 · `rc=0`**。

**根因（符号级）**：`ForeignThunk.swift` 的 GPR 路径 ——
`while cargs.count < 8 { cargs.append(0) }` **只补零、不设上限**，随后
`fn(cargs[0], cargs[1], …, cargs[7])` 只取**前 8 个** ⇒ 第 9 个起被丢弃。

⚠️ **同族一处「注释与代码不符」**：该文件头注释写「超出 8 参数、混用浮点者走浮点路径 / **拒绝**」——
**实际既不拒绝**，也不走浮点路径（混用确实会拒，但走的是「GPR 与浮点混用」那条**另一条**判据）。

**影响**：自举的 C 调用若超 8 参 ⇒ **静默错值**；`rc=0` ⇒ **退出码看不见**。

**判据可建性**：**可建**（进程内单测 + 自建 dylib 夹具；夹具形态照 §1.1）。
⛔ **本批未建** —— 用户选定「只出提案件」。

### 3.2 多返回签名 —— **静默坍缩为单返回**

**复现**：把同一符号声明为 `-> (I64, I64,)`。

| 步 | 读数 |
|---|---|
| `pini parse` | **两个返回都还在**：`func probe_sum8(a: I64) -> (I64, I64) [unsafe]` ⇒ **丢弃不在解析层** |
| `pini check` | **通过**（无诊断） |
| `pini run` | 打印 **204** —— 即**单返回**语义（取第一个槽），**无诊断 · `rc=0`** |

**根因（符号级）**：`IRLowerer.swift` 降载 foreign 块时用
`funcDecl.returnTypes.first.map { … }` —— **只取首个**，其余**静默丢弃**。

⭐ **对照（这是本条的判据支点）**：普通函数走 `resolveReturnType`，`count > 1` 时**建 `.tuple`**
（该函数注释写明「Multiple return slots collapse into a tuple value (D7)」）；
而 **foreign 分支绕过了它** ⇒ **两条路不同**，正是这处分岔造成了静默。

**规范依据**：§2.7 的**永远禁止**清单明列「元组（**含多返回元组**）」⇒ **声明期就该拒**。
⇒ 实现与规范**方向相反**：**规范禁止、实现放行且静默**。修法方向因此是**拒**（补一条声明期诊断），
⛔ **不是**去支持元组。

**判据可建性**：**可建**（`check` 层拒绝 + 一条负向判据）。⛔ **本批未建**。

## 4. LLVM 降档 —— 裁定：**降档不是目标，是压力的产物**

> **裁定（用户 2026-09-25）**：原话「LLVM 降档是收到了实现难度的压迫，如果语言足够稳定就不需要降档」。
> ⇒ ① **降档非目标**：它是难度压力下的**被迫**选择、是**条件性**的 —— **语言足够稳定则不需要**。
> ② **不新立「后端成熟度」这根轴**（原问题 3 与原问题 1 属**同一件事**）。
> ③ 其余与降档有关的问题（档位 / 时机）—— **待讨论**，其尺子 = **语言稳定性**。
> ⭐ **由此有一个重要转向**：若降档的真因是**难度**，真正的解法便不是**改口径**（那只是**表**），
> 而是**减压** —— **C 后端升格（§2.4）正是减压件**：它把 LLVM 从关键路径上摘出去。
> ⇒ **降档是表，换后端是里。**

**当次实测的事实**（⛔ 不改，仍据以判）：

1. 本机 **`lli` / `llvm-as` / `llc` / `opt` 全缺**（`clang` 在）⇒ `run-llvm` 报 `lli not found`；
2. LLVM 腿的 **FFI 面整条 unsupported**（§1 第 10 条）；
3. ⛔ **降档前须先修「测量装置」**：`tools/capability-sweep.tsv` 的 `emit` 列与 `ir` 列**跑的是同一条命令**
   （脚本里两处都是 `"$BIN" emit "$f"`），却有 **11 / 59 行**结论**相反** ⇒ 该矩阵作为**现况读数不可信**；
   而同表的 `llvm` 列写着 40 个 `PASS`，**本机无 `lli` 根本无法复现**（读数是别的环境留下的）。

⭐ 依据本仓判据纪律（**断言失败先怀疑断言**）⇒ **先修矩阵、再据它做档位判断**。
今天拿一个自相矛盾的矩阵去论证「LLVM 端该降到多低」，等于用一个**已知失准的尺**去量。
