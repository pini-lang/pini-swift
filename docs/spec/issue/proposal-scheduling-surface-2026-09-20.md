## 0. 一句话

`=>` 的**急切派发今天已经成立**（§2.1 实测），但派发点的**调度后端在语言层没有表面**：
唯一契约是一个**宿主内部的 Swift 协议**，且它**只有一种实现**（§2.2）。
本件提议把调度面做成**语言可见的可替换点**（内置特征 + 默认扩展方法 + 给定块承载），
并把 `await` 的**让出**语义接回来 —— 后者**正是「协作式」的定义本身**，
所以两件事不是两件事，是**同一机制的两面**（§5.1）。
另：本件兼任「Result 窄化修复」支线的计划件（§8），该支线**先于决策记录拟定**执行（用户裁定）。

## 2. 事实基础（逐条实测，2026-09-20）

### 2.1 `=>` 急切派发：**今天成立，且可观测**

判据程序：两个 `=>` 函数各自打印两次、中间夹 `sleep(80)`，`main` 先取两个 Future 再等。

- 连跑 **3 次**，**每一次**都出现 `A1` `B1` **先行** —— 即乙在甲**尚未结束**时已开始执行。
- `A2` / `B2` 的**先后顺序逐次漂移**。

⇒ 这不是顺序执行，是**真并发**；且派发**不需要 `wait`/`await` 触发**。
⇒ 用户裁定 1 的**前提成立**，本提案可以直接建立在它上面。

### 2.2 调度面：唯一契约是**宿主内部协议**，语言层**零表面**

| 面 | 现状 |

### 2.4 锁：语言与规范**零载体**（本轮不提案）

- `Lock` / 锁 / 互斥 / Mutex / 原子（内存模型意义）在**语言规范与语言参考中零出现**。
- 唯一相关表述在运行时 shim 边界一节：把 `NSLock` / `NSCondition` / GCD 列为**待替换项**（非语言面）。
- ⚠️ **代价必须诚实登记**：不做语言级锁 ≠ 不需要同步。`HIRExecutor` 自己付过代价 ——
  四项执行状态因 `=>` 派发引入而撞**多线程竞态**（工作线程与主线程对同一计数做无条件增减，
  实测以 **SIGTRAP / SIGSEGV** 收场），最终靠 `ThreadLocal` 兜住。
  ⇒ 协作式调度器**自身的任务队列**仍需线程安全 —— 那是**实现内部**的事，不是语言特性；
  但**本件不得因此宣称「并发面已无共享状态问题」**。

### 2.6 并发样例的红：**根因是一处缺失的分派支**

**现状**：`examples/` 下 8 个 `concurrency*` 语料，**逐个实测全红**（`E6-004`）。
7 条报「printing a Result value…」，1 条报「type mismatch: result(ok: i32) is not i32」。

**根因定位**（源码 + 探针双证）：

`HIRLowerer` 的 `lowerMatch` 按 **scrutinee 类型**三岔分派 ——
`.optional` → 专支 · `.enumeration` → 专支 · **`.result` → 无分支**（落默认，按「裸值 / 字面量」处理）。

⇒ 后果：**`case ok(v)` 绑定的 `v`，其静态类型仍是 scrutinee 的 `Result` 类型，不是载荷类型。**

**四条探针**（`2>/dev/null` 取纯 stdout；`造|func() -> (^I32,)` 是**同步**函数 —— 与并发无关）：

| 探针 | 写法 | 结果 | 说明 |
|---|---|---|---|
| p1 | `case ok(v): let w: I32 = v` | ⛔ `type mismatch: result(ok: i32) is not i32` | 静态类型是 `Result` |
| p2 | `case ok(v): print(v + 1)` | ⛔ `operator '…' operand types differ` | 同因，**无门禁参与** |
| p3 | `case ok(v): let w = v` 后 `print(w)` | ⛔ `printing a Result value…` | 类型**传播**为 `Result` |
| p4 | `case ok(v): print(v, "")` | ✅ **rc=0，打印 `5`** | 多参 print **无该门禁**，故绕过；但**载荷值本身是对的** |

⇒ ⭐ **一条根因解释了被删工单登记的全部三类报文**（打印 / 类型不匹配 / 运算类型不符）。
这不是「Result 消费面未实现」那一量级，而是**一处缺失的分派支**。

**由此附带查出的一处新不一致**（⚠️ **只登记，不在本支线修**）：
`print` 的**单参**形式有 Result 门禁（报文即 p3 那条），而**多参**走另一条路径、**无该门禁**
（该段实现注释自陈「no Result / nominal gates there yet」）⇒ **同一个值，单参被拒、多参放行**。

**⚠️ 首缺口遮蔽预告（不承诺「8 条全绿」）**：本根因消除后**可能暴露第二层**缺口
（本仓反复出现的性质：某批接通上游后，一批用例的**首缺口**整体下移）。
⇒ 本支线只承诺「**本根因消除** + 实测出**新的首缺口**」，不承诺样例全绿。

### 2.7 ⛔ 硬发现：LLVM 腿在异步程序上**崩**（不是报错）

**实测**（同一程序：一个 `=>` 函数 + `main` 里 `wait` + 解包，**解释器腿 rc=0、打印正确**）：

```
$ pini run-llvm <该程序>
PiniCore/IREmitter.swift:1727: Fatal error: IREmitter: join has no emission
                                        — the lowerer has no rule for it
rc = 133        (128 + 5 = SIGTRAP)
```

**三点必须说清**：

1. 这是**进程崩溃**，不是诊断 —— `rc=133`。用户看到的不是「该特性暂不支持」，是**工具挂掉**。
2. **崩溃点的自述已经过时**：发射器说「the lowerer has no rule for it」，
   而**降载层今天已有 `join` 规则**（异步管道那批交付的）。⇒ 该节点**会**到达发射器，
   ⇒ 这行 `fatalError` 是**可达路径**，不是防御性断言。**理由失效了，断言还在。**
3. 与已知的「`run-llvm` 丢弃退出状态造成假绿」**不是同一问题** —— 本例 `rc=133` 是**响的**；
   假绿问题在另一形态上（本件不展开，各有其主）。

**⭐ 对照实验（证明崩只发生在并发面，且本机可验收）**：

| 程序 | LLVM 腿实测 |
|---|---|
| **非并发**（打印一行） | ✅ `rc=0`，输出正确 |
| **并发**（一个 `=>` + `wait` 解包） | ⛔ `rc=133`，即上面那行 `fatalError` |

⇒ 这条对照同时给出两件事：
① **LLVM 腿本身健康** —— 崩是**并发面专有**的，不是工具链坏了；
② **本机可验收** —— 工具链在（`lli` 装在包管理器目录下、**不在 `PATH` 上**，
需经 `PINI_LLVM_BIN` 指定；源码支持该变量并会给出「未找到」的提示）⇒
「本批可用」这条裁定**有验收手段**，不是空头承诺。

⇒ **对本提案的约束（裁定 15 已把下限抬高）**：原下限是「不再崩」，**现裁定为「本批可用」**
⇒ 「并发在 LLVM 腿」要从**零**建起来，量级见 §7.4 —— **它已超出 `D` 批原定范围**。

### 2.8 两处「文档与实现相反」

| # | 面 | 实测 |
|---|---|---|
| 1 | 语言参考的并发章（标着 `Stable`）通篇写 `async 名() => ()` 形态，而 **`async` 不在关键字表**（表内 34 个，无 `async`） | ⛔ 实测：该形态与**随机标识符** `zzz` **逐项同判**（`check` 均 rc=0；`run` 均报同一码同一位置）⇒ **`async` 不是语法，是一个被当成修饰符的名字**。⇒ 该章**不可作为事实源** |

## 5. 拟定决策（供决策记录采纳）

> ⚠️ 本节**部分已裁、部分仍待裁**（§10）。标「已裁」者来自 §1 的用户裁定，并注明轮次。

### 5.1 承重事实：`await` 点 **就是** 调度决策点（已裁，见裁定 3 + 6）

「协作式调度」在既有载体里的定义是：**任务在 `await` 点主动让出**。
而「挂起」的定义是：**在 `await` 点保存续体、释放当前 OS 线程**。

⇒ **两个定义指向同一个位置**。这不是巧合，是同一机制的两面：
**没有挂起，就没有「让出」这个动作可做**；没有可替换的调度后端，「让出后交给谁」无解。

⇒ **本件因此把二者绑为一件事**（裁定 3 与裁定 6 是同一决定的两半）：
调度面 = 「`await` 点上，让出 + 交回调度器决定谁接着跑」。

⇒ 这同时解释了为什么 `await` 与 `wait` **今天行为相同**（挂起退役后二者都退化为阻塞 join）；
恢复挂起后，那个被规范称为「语用位」的区别**自动补上**：`await` = 让出，`wait` = 占用。

### 5.2 `Scheduler` 作**内置特征** + **软关键字**（已裁：裁定 3 方向 + 裁定 14 形态）

语言今天**没有「内置特征」这一类**。既有内置面 = **33 个内建函数** + `LazyRef` + `Error` / `CancelError` / `Result`。
⇒ 「内置特征 + 默认扩展方法」是**新增类别**，须**显式登记**（缺口台账 + 语言参考），
不能当作「加几个内建函数」处理。

**形态（已裁）**：语言提供一个名为 `调度器` 的**特征**，其默认实现由语言侧提供 ——
即「默认扩展方法」= 语言侧内置的默认方法体（与内建函数表的性质平行，**不是**用户可见的普通扩展块）。

⭐ **`调度器` 取名但用「软关键字」处置：不入关键字表**（裁定 14）。

| 面 | 规格 |
|---|---|
| 关键字的**识别** | 只在**特定语法位**被识别（修饰符位 / 特征的实现位）⇒ 其余位置**仍是普通标识符** |
| 关键字**表** | ⛔ **不动** —— 表内保持 34 个，**不新增** |
| 与既有先例 | ✅ 与 **`given` 同族**（`given` 不入表，理由是「它只出现在 `|` 修饰符位，走既有白名单」）；⛔ 与 **`using` 相反**（后者入表，因为它出现在**书写面**的形参位） |
| 收益 | **零破坏性** —— 今天合法的标识符 `调度器` **不会**变成保留字（入表则是一次破坏性更名，其代价已在 `using` 那次付过） |
| 代价 | 实现侧要**按位置**判定，而非按表查；⇒ 须在语言参考里**写明它出没的位置**，否则读者会以为它是普通标识符 |

⚠️ **一条必须写进语言参考的区分（否则会重犯 §2.8 的错）**：
软关键字 ≠ 「写得像关键字的普通标识符」。后者的实例就是 `async` ——
它**不在表里、也不在任何语法位被识别**，于是那些程序**照原样被当成标识符**处理（§2.8 实测）。
⇒ 软关键字的**定义必须包含「位置」**：「在某位置被识别为关键字」是它的全部内容；
只声明一个名字而不声明位置，等于造出第二个 `async`。

### 5.3 派发点如何取得调度器（已裁：裁定 13 · 方案 `B`）

**约束来源**：`=>` 派发**发生在异步函数的调用点** ⇒ 调度器必须在**调用点**可见。
而 ADR-001 的取用参数有一条**已落地的收窄**：`using` 形参**只在有 Pini 调用方的位置合法** ——
被宿主直接调用的位置（`main` · `|test` · `|foreign`）在**解析期响亮拒绝**。

⇒ ⛔ **两个选项被直接排除**：
- 「让每个异步函数都声明 `using 调度: 调度器`」⇒ **`main` 无法声明** ⇒
  **在 `main` 里派发异步任务这条最常见的路径断掉**；
  且它与语言参考并发章的示例形态冲突（该章示例正是在 `main` 里直接派发）。
- 「隐式全局查找」⇒ 与 ADR-001「无运行时查找、无 vtable」的既定口径冲突。

**已裁方案（`B`，裁定 13）**：**派发点由编译器插入对 `调度器` 默认实例的取用。**

| 面 | 规格 |
|---|---|
| 解析 | **编译期按类型**解析 `调度器` 的默认实例 —— 与 `using` 同一机制（程序级存放位 + 取用点），**零新解析机制** |
| 书写 | **零书写** —— 派发点不写任何东西 |
| `main` | ✅ **正常工作**（不需要声明 `using`，故不受参数位收窄影响） |
| 定制 | ✅ **调用点显式传入**自己构造的调度器实例（走既有 `using` 实参位）⇒ **替换路径不需要新机制** |
| 默认实例承载 | 给定块 `[应用服务\|given]` 的 `调度器` 字段（§5.5 的「可变共享状态必须放进引用字段」规则**在此生效**：调度器状态须住**引用**字段，否则共享**静默失效**） |

⇒ **收益**：ADR-001 提供的全局量**确实可用**（用户裁定 5 成立），且**不需要新增解析机制**。
⇒ **代价**（诚实登记）：这是一处**隐式取用** —— 与 ADR-001「依赖不得隐藏」的**精神**相反。
理由：ADR-001 该条已因前提被否证而**降级为诊断**，故此处不构成冲突；但**须在决策记录里写明**，
不能装作不存在。

### 5.4 `Lock`：**不做**（已裁，裁定 8）

不引入语言级锁 / 互斥 / 原子表面。**代价见 §2.4**：并发面的共享状态问题**仍然存在**，
只是不在语言层暴露；协作式调度器**自身的队列**仍需实现内部同步。

### 5.5 `Stable` 全降 + 补两条禁则（已裁，裁定 7 / 9）

**动作**（纯文档面，按裁定 9 的「小规模修改」口径）：

| # | 动作 |
|---|---|
| 1 | **乙类**（构造标注，14 处）：`Stable` → `Provisional`，两侧同批改（规范 + 语言参考） |
| 2 | **丙类**（清单 schema 4 字段）：同上，**只改标记、不改字段语义** |
| 3 | **甲类不动**（5 处机制定义） |
| 4 | 新增**禁则**：「v0.x 期内**不得有构造处于 `Stable`**；`Stable` 是 **v1.0 的到达状态**，不是可提前授予的标记」 |
| 5 | 新增**授予判据**：`Stable` 授予须同时满足「核心构造名单内」+「测试覆盖达标」+「**在册缺口零**」 —— 否则 v0.x 永远迁不出去 |

⚠️ **为什么必须补 4 / 5**：只降不补，则下一个批次会**再犯同一个错**（把新构造标成 `Stable`）；
且没有授予判据，`Stable` 的定义虽有、却无从产生合法实例。

⚠️ **顺带处置**（本批或另立，待裁）：§2.8 第 2 条 —— 规范声称「工具链读取稳定性分级表」，
该声称**未实现**且与「不要兼容性闸门」的既定裁决矛盾 ⇒ 应**订正该声称**（而不是去实现它）。

### 5.6 不承诺（明确的非目标）

- ⛔ **不承诺 `Stable` 降级后语义会变** —— 降的是**承诺强度**，不是行为。
- ⛔ **不承诺并发样例全绿**（§2.6 首缺口遮蔽）。
- ⛔ **不承诺 LLVM 腿的挂起** —— §2.7 的处置**下限**是「不再崩」，上限须另裁。
- ⛔ **不提供语言级锁**（§5.4）。
- ⛔ **不承诺真·跨模块调度器** —— 真·跨模块在本编译器**无通路**（既定登记）。
- ⛔ **不承诺结构化并发契约扩展** —— 该契约维持不变，只做「恢复后仍满足」的复核。

### 7.2 ⚠️ 裁定 17（取乙）⇒ `D` / `E` 合并，且这是本提案最大的一批

裁定 17 把「可用」定为**含 `await` 让出**。而让出**就是**挂起本体（§5.1：`await` 点即调度决策点）
⇒ **`D` 的验收标准里含 `E` 的产物** ⇒ 两批**互为前提**，不能分开交付（分开则 `D` 永远验收不了）。

| 批 | 原定 | 现定 |
|---|---|---|
| `D` | LLVM 腿 `join` 处置 | **`D`+`E` 合并为一批**：LLVM 腿并发运行时（C ABI）+ 挂起本体（两腿让出）+ 调度接缝 |
| `E` | 挂起本体 | 并入上一行 |

⚠️ **合并后这一批的量级**：它是本提案**唯一**需要同时动「两腿 + 新运行时 + 语义变更」的批次
⇒ 建议**内部再切**为可独立验证的子段（例如：先「阻塞 join 在 LLVM 腿可用」，
再「让出（挂起）在两腿可用」），**但对外仍是一次裁定的范围**。
⇒ 子段如何切、切几段，**须点名**（§10 待裁 9）。

### 7.3 调度器接缝形态：维护成本分析（分析已出，**裁决待用户** —— 裁定 18）

> ⚠️ 本节是**分析**，不是裁定。裁决见 §10 待裁 8。

#### 7.3.1 先拆一处概念混淆：这里其实是**两个不同的接缝**

「两腿交集（C ABI）还是两腿各一份」这句话里混着两层，必须分开判，否则会答错问题：

| 层 | 内容 | 是否受本问题影响 |
|---|---|---|
| **语言层接缝** | **用户可替换的调度器** —— 用户自己写的调度器是**一个 Pini 值** | ⛔ **不受影响**：Pini 值经 HIR 执行，**两腿天然同源**（这是 `LR-4` 统一降载的直接收益）⇒ 用户侧**本来就是单源**，C ABI 问题在这里**不成立** |
| **内置默认实现的内部** | 语言提供的**默认调度器**，其机制（线程池 / 队列）住在哪 | ✅ **这才是本问题的真正范围** |

⇒ 问题 8 的**实际范围比字面小**：它只问「**内置默认实现**在两腿怎么落地」，不问用户面。
⇒ 这一缩小很重要：**用户可替换调度器**这个卖点**不需要**任何 C ABI 决定就能成立。

#### 7.3.2 实测：**「两腿各一份」是本仓既有的、无例外的模式**

| 实测 | 数字 |
|---|---|
| 解释器腿对运行时库的**真实调用** | ⭐ **0** （仅两处**注释**提及，且内容正是「与 LLVM 运行时行为一致」） |
| 运行时库的调用方 | **只有发射层一侧**（HIR 降载 / 节点 / 发射器）⇒ 该库**只服务 LLVM 腿** |
| 已有「每条腿一份」承载的**特征数** | **7 / 7** —— 数组 · 字典 · 集合 · COW 句柄 · `LazyRef` · FFI 指针 · 给定块槽位 |
| 对应关系 | Swift 侧**8 个**原生承载类/结构 ↔ 运行时库**38 个**符号（其中并发 **0 个**） |
| 运行时库今天的线程能力 | **无**（只有 3 把锁，无池、无分派） |

⇒ **「每腿一份」不是新方案，是本仓的既有模式**（`LazyRef` 就是活标本：一边 `LazyRefBox`、
一边 `bk_lazyref_*`）。
⇒ 若选「交集」，**并发会成为第一个走运行时库的解释器侧特性** —— 一处**孤例式的不对称**。

#### 7.3.3 成本对比（关键：**两条路都必须从零建 LLVM 腿的并发运行时**）

这是本分析最要紧的一句：**共同成本**是「在 C ABI 上建起 LLVM 腿的并发运行时」
（Future 表示 + 派发 + join + 任务树 + 取消树 + 失败上浮 + `detach`）。
**两条路都躲不掉它**，因为它由裁定 15/17 决定，与接缝形态无关。

| 项 | 甲（交集 / 共享 C ABI） | 乙（每腿一份） |
|---|---|---|
| 共同成本（LLVM 腿并发运行时） | ✅ 必做 | ✅ 必做 |
| 解释器腿 | ⚠️ **改写 ~600 行**（见下）到一个句柄表示上 | ✅ **不动** |
| Swift 原生内省（REPL / 调试器 / DAP） | ⚠️ 句柄表示会削弱它 | ✅ 保持 |
| 与既有 7/7 模式的一致性 | ⛔ **破例**（并发成孤例） | ✅ 一致 |
| 漂移风险 | ✅ 结构上**不可能漂移** | ⚠️ **存在**，且守卫今天**不在岗**（7.3.4） |
| ⇒ 结论 | **前期更贵**，只在「长期漂移」上赢 | **前期更省**，代价是漂移 |

解释器腿**必须改写**的行数（实测）：
`FutureValue` 类体 **327** · `RuntimeOps` 并发段 **161** · `Scheduler` **111** ≈ **600 行**
—— 且这 600 行里含**取消树 / 弱父引用 / 递归取消**这类**结构较富**的东西，
换成不透明句柄后，这几项的**表达力会下降**。

#### 7.3.4 ⭐ 真正的成本项：`乙` 的漂移守卫**今天不在岗**（实测）

「两腿各一份」的代价全部押在**「一致性由测试守住」**上。而实测：

| 守卫 | 现状 |
|---|---|
| 测试面 **69 条** | ⛔ **零条**跑 LLVM 腿（全域 `rg` 无 `run-llvm` / `lli` 命中） |
| 探针的默认根集 **6 个** | ⛔ **5 个已不存在**（仅 `examples` 幸存） |
| 差分测试类（含曾守两腿等价的那些） | ⛔ 已随测试面重建整体退役 |
| ⇒ 今天两腿的一致性靠什么？ | ⛔ **靠注释断言** —— 源码里**原话**即「The LLVM side reaches the same observable state by a different mechanism」 |

⇒ **这是本分析最重要的一条**：选 `乙` 而**不重建任何守卫** = 接受**无人看守的漂移**。

⚠️ **而它已经咬过两次（有据可查，非推断）**：
1. **挂起工作只做了一条腿** —— 被删的 1049 行是 **AST 腿**的，HIR 腿**从来没有对应物**。
   这正是「每腿一份」的代价**兑现**的样子：同一件事做了 N 遍，其中 N−1 遍还会被删掉。
2. **两腿的并发在正确性上分过岔** —— AST 腿撞上真实的共享可变状态缺陷（实测以 SIGTRAP/SIGSEGV 收场），
   HIR 腿靠 `ThreadLocal` 避开；且 HIR 腿自己的注释**记录了这次代价**。

#### 7.3.5 我的建议：`乙` + **一处极廉价的守卫**（守裁定 11 的克制）

**建议采纳 `乙`**，理由三条：
① 与既有 **7/7** 模式一致（`甲` 会让并发成为孤例）；
② **用户可替换的调度器本就单源**（经 HIR），所以 `乙` **不牺牲**那个卖点；
③ 前期**不必**改写解释器腿那 600 行。

⚠️ 但必须**同批**加一处守卫，否则就是 7.3.4 说的「无人看守」。守卫取**最廉价的形态**：

| 守卫 | 形态 | 新增面 |
|---|---|---|
| ⭐ **两腿同源对拍** | **同一批程序在两腿上跑，比对 stdout** | ⭐ **零新夹具** —— 语料用**既有的**那批并发样例；`examples/` 又是探针**唯一幸存**的根 |

⇒ 它的**额外好处**：它同时就是**合并后的 `D`+`E` 批的验收标准**
（那批做完后，既有并发样例**必须**在两腿上输出一致）。
⇒ 成本：≈ **0 个新文件**（复用既有语料 + 既有两腿入口 + 幸存的探针根）。

⚠️ **诚实标注这条守卫的弱点**（不夸大）：
**stdout 相等是弱判据** —— 它抓不到**时序**、也抓不到**取消树 / 失败上浮**这类**不外显**的不变量。
⇒ 它是「廉价但**部分**」的守卫；是否要为那部分不变量另加判据，**须点名**（§10 待裁 10）。

⚠️ **一处新的成本项（`乙` 独有，须登记）**：运行时库将获得**它的第一套线程机制**（线程池）。
今天该库**无线程能力**（只有 3 把锁）⇒ 这是**一类新东西**进了这个库，
且它必须守住 C ABI 纪律（运行时边界的 MUST）。
⇒ 与裁定 8（不做语言级 `Lock`）**不冲突** —— 库内的线程池是**实现内部**，不是语言特性。

#### 7.3.6 若选 `甲`，有一处必须先答的问题

`甲` 要解释器腿改走句柄表示 ⇒ **取消树 / 弱父引用 / 递归取消**要搬到 C ABI 面上。
而今天的 `FutureValue` 是 Swift `final class`，其 `parent` 是 **`weak`** ——
C ABI 面没有「弱引用」这个概念，须**自建**（引用计数或旁表）。
⇒ 这不是「搬代码」，是**在 C ABI 上重新设计一遍对象生命周期**。
⇒ 建议：**若倾向 `甲`，先把这处的设计做出来再裁**，否则量级会被低估。

### 7.4 裁定 15 的量级：`D` 批从来不是「修一个崩溃」

裁定 15 把 `D` 的下限从「不再崩」抬到「**可用**」。两者**不是一个量级**，须说清楚：

| 面 | 「不再崩」要做的事 | 「可用」要做的事 |
|---|---|---|
| 发射层 | 把 `join` 的 `fatalError` 换成**响亮诊断** | 为 `join` **写发射规则** |
| 运行时 | **零** | Future 的**表示** + **派发** + **阻塞 join** + 任务树 + 取消树 + 失败上浮 + `detach` —— 即**在 C ABI shim 上新建一整条并发运行时** |
| 归属 | 一行级 | ⭐ **超出本提案其余部分**（调度接缝 + 挂起本体 + 内置特征 + 文档订正之和） |

**为什么会这么大**：解释器腿的并发**全部住在 Swift 侧** ——
`Scheduler` 是 Swift 协议、任务树 / 取消树住在 Swift 的值表示里。
而 LLVM 腿**够不到**这些东西 ⇒ 它们必须在 `libPiniRuntime` 的 **C ABI 面上重做一份**。

⚠️ 且这是**硬性约束**（运行时 shim 边界的 MUST）：shim 与用户代码的边界**必须是 C ABI**，
不能是 Swift 泛型 ABI —— 「违反即锁死自举终态，使 Swift 成为永久依赖」。
⇒ 没有捷径可走：不是「把 Swift 的调度器暴露给 LLVM」，而是**按 C ABI 重新实现一遍并发语义**。

⭐ **由此暴露一处架构张力（须在设计阶段就面对，不能等到实现时才发现）**：
「**可替换的调度器**」这个卖点，在两条腿上的**接缝形状不同** ——
解释器腿的接缝是那个 Swift 协议，LLVM 腿的接缝只能是 C ABI 函数表。
⚠️ **但该张力已被 §7.3.1 部分化解**：该张力的**真实范围**只在「**内置默认实现**」那一层，
因为**用户写的调度器是 Pini 值、经 HIR 执行 ⇒ 两腿天然同源**。
⇒ 本条据此**收紧为**：须在 `F` 批定案前裁的，是**内置默认实现**落在哪一层（§10 待裁 8）。

### 8.2 根因与修法（已定位，见 §2.6）

**根因**：`HIRLowerer` 的 `lowerMatch` 缺 `.result` 分派支 ⇒ `case ok(v)` 的绑定
静态类型留在 scrutinee 的 `Result` 上，未取载荷类型。

**修法**：照 `lowerOptionalCases` 的既有形态，增一个 `Result` 版分支
—— 把 `ok` 绑定的类型设为**载荷类型**。**一处缺失分支 + 一个分支函数。**

⚠️ **`err` 侧的处置须单独判**：既有的 try-else 路径把错误绑定登记为**类型擦除**形态
（发射器对「打印错误绑定」有专门门禁，理由是「err 槽是类型擦除的」）。
⇒ 支线**不得顺手改**该形态；`err` 绑定维持现状，只做**正向验证**。
