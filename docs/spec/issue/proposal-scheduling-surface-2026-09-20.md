## 0. 一句话

`=>` 的**急切派发今天已经成立**（§2.1 实测），但派发点的**调度后端在语言层没有表面**：
唯一契约是一个**宿主内部的 Swift 协议**，且它**只有一种实现**（§2.2）。
本件提议把调度面做成**语言可见的可替换点**（内置特征 + 默认扩展方法 + 给定块承载），
并把 `await` 的**让出**语义接回来 —— 后者**正是「协作式」的定义本身**，
所以两件事不是两件事，是**同一机制的两面**（§5.1）。
另：本件兼任「Result 窄化修复」支线的计划件（§8），该支线**先于决策记录拟定**执行（用户裁定）。
⭐ 且「后端」**不是两条腿**：参考里是**两张口径不同的表**，去重后 **7 个名字**（今天活了 **3** 个引擎），
而并发面的**成本随「接缝形状类别数」增长、不随「后端数」增长**（§7.5.3）—— 这条决定 `F` 批的**写法约束**与守卫的**参照物**（§7.5.4）。
⚠️ 后端名册另见 **§7.7**（已立，⛔ **明确不具参考性**）。

## 2. 事实基础（逐条实测，2026-09-20）

> 所有行为读数取自 `pini` 二进制；该二进制已用**行为探针**验过与当前提交一致

### 2.1 `=>` 急切派发：**今天成立，且可观测**

判据程序：两个 `=>` 函数各自打印两次、中间夹 `sleep(80)`，`main` 先取两个 Future 再等。

- 连跑 **3 次**，**每一次**都出现 `A1` `B1` **先行** —— 即乙在甲**尚未结束**时已开始执行。
- `A2` / `B2` 的**先后顺序逐次漂移**。

⇒ 这不是顺序执行，是**真并发**；且派发**不需要 `wait`/`await` 触发**。
⇒ 用户裁定 1 的**前提成立**，本提案可以直接建立在它上面。

### 2.2 调度面：唯一契约是**宿主内部协议**，语言层**零表面**

| 面 | 现状 |
|---|---|
| 契约 | `Sources/PiniCore/Interpreter/Scheduler.swift` —— `protocol Scheduler { func spawn(_:work:) ; var activeTaskCount: Int }` |
| 唯一实现 | `GCDScheduler`（有界并发池 + 信号量背压 + 高水位告警） |
| 接入点 | `Sources/PiniCore/Interpreter/HIRExecutor.swift` —— `private let scheduler: Scheduler = GCDScheduler.shared` |
| 语言层 | ⛔ **零表面** —— 无关键字、无内建、无特征；Pini 程序**够不到**它 |

⇒ 缺口是**真实的**：今天既不能换后端，也不能观测调度，更不能在语言层表达「用哪个调度器」。

### 2.3 挂起：**不是「恢复」，是「在 HIR 上首次实现」**

### 2.4 锁：语言与规范**零载体**（本轮不提案）

- `Lock` / 锁 / 互斥 / Mutex / 原子（内存模型意义）在**语言规范与语言参考中零出现**。
- 唯一相关表述在运行时 shim 边界一节：把 `NSLock` / `NSCondition` / GCD 列为**待替换项**（非语言面）。
- ⚠️ **代价必须诚实登记**：不做语言级锁 ≠ 不需要同步。`HIRExecutor` 自己付过代价 ——
  四项执行状态因 `=>` 派发引入而撞**多线程竞态**（工作线程与主线程对同一计数做无条件增减，
  实测以 **SIGTRAP / SIGSEGV** 收场），最终靠 `ThreadLocal` 兜住。
  ⇒ 协作式调度器**自身的任务队列**仍需线程安全 —— 那是**实现内部**的事，不是语言特性；
  但**本件不得因此宣称「并发面已无共享状态问题」**。

⭐ **支撑裁定 7 的两条硬论据**（皆为登记在案的事实，非推断）：

1. **`Stable` 在 v0.x 内是个死锁，而本提案今天正好撞上它。**
   分级表定义：`Stable`「**不允许**破坏性变更（如需，须走 v1.0 路径）」；
   而 v1.0 触发条件 = 「**核心构造**（类型声明、函数、控制流、错误处理、访问控制）定为 `Stable`」。
   今天的 `Stable` 实例是**并发** —— 它**不在**那份「核心构造」名单里
   ⇒ 它**被锁死**（要改须走 v1.0 路径），**却又不影响 v1.0 触发**（不是核心构造）
   ⇒ **解锁的唯一闸门不认识它**。这正是本提案（要改并发语义）撞上的东西。
2. **「已锁定语义」这个承诺已被自身证伪。** 该异步语义模型于 v0.43.0 定 `Stable`，
   此后其权威小节**至少两次自我订正**（分层订正 + 阻塞语义表述订正），
   且**挂起模式从 `Stable` 降为 `Provisional` 并退役**。两个月内反复修订的构造标着「已锁定」。

⭐ **附带实测（好消息）**：裁定 7 与 9 **零代码影响，纯文档面**。
规范有一句声称「工具链读取 `spec` 后锁定对应稳定性分级表，据此决定哪些特性可用」——
`Sources/` 实测**零命中** ⇒ 该声称**未实现**；且它与本仓「不要兼容性闸门」的既定裁决**互相矛盾**。

### 2.6 并发样例的红：**根因是一处缺失的分派支**

**现状**：`examples/` 下 8 个 `concurrency*` 语料，**逐个实测全红**（`E6-004`）。
7 条报「printing a Result value…」，1 条报「type mismatch: result(ok: i32) is not i32」。

**根因定位**（源码 + 探针双证）：

`HIRLowerer` 的 `lowerMatch` 按 **scrutinee 类型**三岔分派 ——
`.optional` → 专支 · `.enumeration` → 专支 · **`.result` → 无分支**（落默认，按「裸值 / 字面量」处理）。

⇒ 后果：**`case ok(v)` 绑定的 `v`，其静态类型仍是 scrutinee 的 `Result` 类型，不是载荷类型。**

**四条探针**（`2>/dev/null` 取纯 stdout；`造|func() -> (^I32,)` 是**同步**函数 —— 与并发无关）：

| 探针 | 写法 | 结果 | 说明 |
|---|---|---|---|
| p1 | `case ok(v): let w: I32 = v` | ⛔ `type mismatch: result(ok: i32) is not i32` | 静态类型是 `Result` |
| p2 | `case ok(v): print(v + 1)` | ⛔ `operator '…' operand types differ` | 同因，**无门禁参与** |
| p3 | `case ok(v): let w = v` 后 `print(w)` | ⛔ `printing a Result value…` | 类型**传播**为 `Result` |
| p4 | `case ok(v): print(v, "")` | ✅ **rc=0，打印 `5`** | 多参 print **无该门禁**，故绕过；但**载荷值本身是对的** |

⇒ ⭐ **一条根因解释了被删工单登记的全部三类报文**（打印 / 类型不匹配 / 运算类型不符）。
这不是「Result 消费面未实现」那一量级，而是**一处缺失的分派支**。

**由此附带查出的一处新不一致**（⚠️ **只登记，不在本支线修**）：
`print` 的**单参**形式有 Result 门禁（报文即 p3 那条），而**多参**走另一条路径、**无该门禁**
（该段实现注释自陈「no Result / nominal gates there yet」）⇒ **同一个值，单参被拒、多参放行**。

**⚠️ 首缺口遮蔽预告（不承诺「8 条全绿」）**：本根因消除后**可能暴露第二层**缺口
（本仓反复出现的性质：某批接通上游后，一批用例的**首缺口**整体下移）。
⇒ 本支线只承诺「**本根因消除** + 实测出**新的首缺口**」，不承诺样例全绿。

### 2.7 ⛔ 硬发现：LLVM 腿在异步程序上**崩**（不是报错）

**实测**（同一程序：一个 `=>` 函数 + `main` 里 `wait` + 解包，**解释器腿 rc=0、打印正确**）：

```
$ pini run-llvm <该程序>
PiniCore/IREmitter.swift:1727: Fatal error: IREmitter: join has no emission
                                        — the lowerer has no rule for it
rc = 133        (128 + 5 = SIGTRAP)
```

**三点必须说清**：

1. 这是**进程崩溃**，不是诊断 —— `rc=133`。用户看到的不是「该特性暂不支持」，是**工具挂掉**。
2. **崩溃点的自述已经过时**：发射器说「the lowerer has no rule for it」，
   而**降载层今天已有 `join` 规则**（异步管道那批交付的）。⇒ 该节点**会**到达发射器，
   ⇒ 这行 `fatalError` 是**可达路径**，不是防御性断言。**理由失效了，断言还在。**
3. 与已知的「`run-llvm` 丢弃退出状态造成假绿」**不是同一问题** —— 本例 `rc=133` 是**响的**；
   假绿问题在另一形态上（本件不展开，各有其主）。

**⭐ 对照实验（证明崩只发生在并发面，且本机可验收）**：

| 程序 | LLVM 腿实测 |
|---|---|
| **非并发**（打印一行） | ✅ `rc=0`，输出正确 |
| **并发**（一个 `=>` + `wait` 解包） | ⛔ `rc=133`，即上面那行 `fatalError` |

⇒ 这条对照同时给出两件事：
① **LLVM 腿本身健康** —— 崩是**并发面专有**的，不是工具链坏了；
② **本机可验收** —— 工具链在（`lli` 装在包管理器目录下、**不在 `PATH` 上**，
需经 `PINI_LLVM_BIN` 指定；源码支持该变量并会给出「未找到」的提示）⇒
「本批可用」这条裁定**有验收手段**，不是空头承诺。

⇒ **对本提案的约束（裁定 15 已把下限抬高）**：原下限是「不再崩」，**现裁定为「本批可用」**
⇒ 「并发在 LLVM 腿」要从**零**建起来，量级见 §7.4 —— **它已超出 `D` 批原定范围**。

### 2.8 两处「文档与实现相反」

| # | 面 | 实测 |
|---|---|---|
| 1 | 语言参考的并发章（标着 `Stable`）通篇写 `async 名() => ()` 形态，而 **`async` 不在关键字表**（表内 34 个，无 `async`） | ⛔ 实测：该形态与**随机标识符** `zzz` **逐项同判**（`check` 均 rc=0；`run` 均报同一码同一位置）⇒ **`async` 不是语法，是一个被当成修饰符的名字**。⇒ 该章**不可作为事实源** |
| 2 | 规范声称「工具链读取稳定性分级表并据此决定特性可用性」 | ⛔ `Sources/` 零命中 ⇒ **未实现**（§2.5 附条） |

### 2.9 判据面：并发**零用例**

`Tests/PiniTests/` 下实测**仅 4 个套件**（两个 given 相关 + 语法验收 + 主套件），
**并发用例数为 0**；`examples/` 的 8 个并发语料**不在任何门禁的扫描面内**
（提交钩子的四道闸门与 CI 工作流**都不含** `examples/`）。
⇒ 今天「并发样例全红」这件事**没有任何机制会报出来**。

## 4. 破坏性判定

| 项 | 判定 | 依据 |
|---|---|---|
| 调度器可替换 | **新增能力** | 今天语言层无法表达 ⇒ 无既有写法被改变 |

## 5. 拟定决策（供决策记录采纳）

> ⚠️ 本节**部分已裁、部分仍待裁**（§10）。标「已裁」者来自 §1 的用户裁定，并注明轮次。

### 5.1 承重事实：`await` 点 **就是** 调度决策点（已裁，见裁定 3 + 6）

「协作式调度」在既有载体里的定义是：**任务在 `await` 点主动让出**。
而「挂起」的定义是：**在 `await` 点保存续体、释放当前 OS 线程**。

⇒ **两个定义指向同一个位置**。这不是巧合，是同一机制的两面：
**没有挂起，就没有「让出」这个动作可做**；没有可替换的调度后端，「让出后交给谁」无解。

⇒ **本件因此把二者绑为一件事**（裁定 3 与裁定 6 是同一决定的两半）：
调度面 = 「`await` 点上，让出 + 交回调度器决定谁接着跑」。

⇒ 这同时解释了为什么 `await` 与 `wait` **今天行为相同**（挂起退役后二者都退化为阻塞 join）；
恢复挂起后，那个被规范称为「语用位」的区别**自动补上**：`await` = 让出，`wait` = 占用。

### 5.2 `Scheduler` 作**内置特征** + **软关键字**（已裁：裁定 3 方向 + 裁定 14 形态）

语言今天**没有「内置特征」这一类**。既有内置面 = **33 个内建函数** + `LazyRef` + `Error` / `CancelError` / `Result`。
⇒ 「内置特征 + 默认扩展方法」是**新增类别**，须**显式登记**（缺口台账 + 语言参考），
不能当作「加几个内建函数」处理。

**形态（已裁）**：语言提供一个名为 `调度器` 的**特征**，其默认实现由语言侧提供 ——
即「默认扩展方法」= 语言侧内置的默认方法体（与内建函数表的性质平行，**不是**用户可见的普通扩展块）。

⭐ **已裁（裁定 28）：默认实现按「策略 / 原语」拆两半**（见 §7.5.7）⇒
本节「默认扩展方法体」的**落点收窄**：**策略层**改为**语言提供的 Pini 值**（与用户可替换调度器**同一机制**），
只有**原语层**仍是宿主侧的默认实现。⇒ ⭐ **顺带化解**本节开头那处「**新增语言类别**」的不确定：
若默认调度器就是一个 Pini 值，则**不必**为它新造「内置特征」这一类。
⚠️ 但**本节其余结论不变** —— 尤其 **`软关键字`（裁定 14）照旧**：它管的是
「**这个名字在哪些位置被识别**」，与该值住在策略层还是原语层**无关**。
⚠️ 「内置面 = 33 个内建函数 + `LazyRef` + 三个错误类型」的**计数**也照旧（策略层用 Pini 写，**不新增内建函数**）。

⭐ **`调度器` 取名但用「软关键字」处置：不入关键字表**（裁定 14）。

| 面 | 规格 |
|---|---|
| 关键字的**识别** | 只在**特定语法位**被识别（修饰符位 / 特征的实现位）⇒ 其余位置**仍是普通标识符** |
| 关键字**表** | ⛔ **不动** —— 表内保持 34 个，**不新增** |
| 与既有先例 | ✅ 与 **`given` 同族**（`given` 不入表，理由是「它只出现在 `|` 修饰符位，走既有白名单」）；⛔ 与 **`using` 相反**（后者入表，因为它出现在**书写面**的形参位） |
| 收益 | **零破坏性** —— 今天合法的标识符 `调度器` **不会**变成保留字（入表则是一次破坏性更名，其代价已在 `using` 那次付过） |
| 代价 | 实现侧要**按位置**判定，而非按表查；⇒ 须在语言参考里**写明它出没的位置**，否则读者会以为它是普通标识符 |

⚠️ **一条必须写进语言参考的区分（否则会重犯 §2.8 的错）**：
软关键字 ≠ 「写得像关键字的普通标识符」。后者的实例就是 `async` ——
它**不在表里、也不在任何语法位被识别**，于是那些程序**照原样被当成标识符**处理（§2.8 实测）。
⇒ 软关键字的**定义必须包含「位置」**：「在某位置被识别为关键字」是它的全部内容；
只声明一个名字而不声明位置，等于造出第二个 `async`。

### 5.3 派发点如何取得调度器（已裁：裁定 13 · 方案 `B`）

**约束来源**：`=>` 派发**发生在异步函数的调用点** ⇒ 调度器必须在**调用点**可见。
而 ADR-001 的取用参数有一条**已落地的收窄**：`using` 形参**只在有 Pini 调用方的位置合法** ——
被宿主直接调用的位置（`main` · `|test` · `|foreign`）在**解析期响亮拒绝**。

⇒ ⛔ **两个选项被直接排除**：
- 「让每个异步函数都声明 `using 调度: 调度器`」⇒ **`main` 无法声明** ⇒
  **在 `main` 里派发异步任务这条最常见的路径断掉**；
  且它与语言参考并发章的示例形态冲突（该章示例正是在 `main` 里直接派发）。
- 「隐式全局查找」⇒ 与 ADR-001「无运行时查找、无 vtable」的既定口径冲突。

**已裁方案（`B`，裁定 13）**：**派发点由编译器插入对 `调度器` 默认实例的取用。**

| 面 | 规格 |
|---|---|
| 解析 | **编译期按类型**解析 `调度器` 的默认实例 —— 与 `using` 同一机制（程序级存放位 + 取用点），**零新解析机制** |
| 书写 | **零书写** —— 派发点不写任何东西 |
| `main` | ✅ **正常工作**（不需要声明 `using`，故不受参数位收窄影响） |
| 定制 | ✅ **调用点显式传入**自己构造的调度器实例（走既有 `using` 实参位）⇒ **替换路径不需要新机制** |
| 默认实例承载 | 给定块 `[应用服务\|given]` 的 `调度器` 字段（§5.5 的「可变共享状态必须放进引用字段」规则**在此生效**：调度器状态须住**引用**字段，否则共享**静默失效**） |

⇒ **收益**：ADR-001 提供的全局量**确实可用**（用户裁定 5 成立），且**不需要新增解析机制**。
⇒ **代价**（诚实登记）：这是一处**隐式取用** —— 与 ADR-001「依赖不得隐藏」的**精神**相反。
理由：ADR-001 该条已因前提被否证而**降级为诊断**，故此处不构成冲突；但**须在决策记录里写明**，
不能装作不存在。

### 5.4 `Lock`：**不做**（已裁，裁定 8）

不引入语言级锁 / 互斥 / 原子表面。**代价见 §2.4**：并发面的共享状态问题**仍然存在**，
只是不在语言层暴露；协作式调度器**自身的队列**仍需实现内部同步。

### 5.5 `Stable` 全降 + 补两条禁则（已裁，裁定 7 / 9）

**动作**（纯文档面，按裁定 9 的「小规模修改」口径）：

| # | 动作 |
|---|---|
| 1 | **乙类**（构造标注，14 处）：`Stable` → `Provisional`，两侧同批改（规范 + 语言参考） |
| 2 | **丙类**（清单 schema 4 字段）：同上，**只改标记、不改字段语义** |
| 3 | **甲类不动**（5 处机制定义） |
| 4 | 新增**禁则**：「v0.x 期内**不得有构造处于 `Stable`**；`Stable` 是 **v1.0 的到达状态**，不是可提前授予的标记」 |
| 5 | 新增**授予判据**：`Stable` 授予须同时满足「核心构造名单内」+「测试覆盖达标」+「**在册缺口零**」 —— 否则 v0.x 永远迁不出去 |

⚠️ **为什么必须补 4 / 5**：只降不补，则下一个批次会**再犯同一个错**（把新构造标成 `Stable`）；
且没有授予判据，`Stable` 的定义虽有、却无从产生合法实例。

⚠️ **顺带处置已裁**（裁定 25，见 §10 待裁 6）：§2.8 第 2 条 —— 规范声称「工具链读取稳定性分级表」，
该声称**未实现**（`Sources/` 零命中）且与「**不要兼容性闸门**」的既定裁决矛盾
⇒ ⛔ **订正该声称**（**而不是去实现它**），并**并入本 `C` 批**（与「标记与实际不符」同源，裁定 25）。
⇒ 理由：本条与上面 5 条动作**同一病根** —— 「文档声称了一个系统没有的性质」；
分开做会让同一类订正分两次走流程。

### 5.6 不承诺（明确的非目标）

- ⛔ **不承诺 `Stable` 降级后语义会变** —— 降的是**承诺强度**，不是行为。
- ⛔ **不承诺并发样例全绿**（§2.6 首缺口遮蔽）。
- ⛔ **不承诺 LLVM 腿的挂起** —— §2.7 的处置**下限**是「不再崩」，上限须另裁。
- ⛔ **不提供语言级锁**（§5.4）。
- ⛔ **不承诺真·跨模块调度器** —— 真·跨模块在本编译器**无通路**（既定登记）。
- ⛔ **不承诺结构化并发契约扩展** —— 该契约维持不变，只做「恢复后仍满足」的复核。

| 1 | ⭐ **LLVM 腿的并发要从零建**（裁定 15 抬高了下限） | 解释器腿的并发**全住在 Swift 侧**（调度器协议 + 任务/取消树），LLVM 腿够不到 ⇒ 须在 C ABI shim 上**重建一份**。**这是本提案最大的未知量** —— 量级见 §7.4 |
| 2 | **挂起的上下文还原** | 既有实现（已删）记录：跨线程复用 OS 线程时，续体必须捕获并还原五项解释器上下文，否则**上下文串台**。恢复时这条约束**依然成立** |
| 3 | **协作式的公平性下限** | 协作式**不提供**公平性保证 —— 紧循环不让出则不可被抢占（既有规范已具名）。⇒ 不得把「协作式」宣传为「公平」 |
| 4 | **阻塞 join 的线程占用仍然存在** | 恢复挂起**才**消除它；在此之前「高扇出耗尽线程池」是固有边界 |
| 5 | **隐式取用的精神冲突**（§5.3 末） | 须在决策记录写明，不得隐去 |
| 6 | **无语言级锁下的共享状态** | §2.4：问题仍在，只是不外显 |
| 6b | ⭐ **两腿的调度接缝形状不同**（§7.4 末） | 解释器腿的接缝是 Swift 协议、LLVM 腿只能是 C ABI ⇒ 该张力的**真实范围**只在「**原语层**」（用户写的调度器、以及策略层，经 HIR **天然同源**）。⭐ **已据裁定 19 / 20 化解**（§7.5.3 + §7.5.7）：成本随**接缝形状类别数**（今天 **2**）增长，**不随后端数**（今天 3 个引擎活着、名册共 **7** 个名字）增长；并加一条**写法约束**（该份运行时不得依赖 LLVM 特有物）。⚠️ 残余风险转记 6c 与 6d。⚠️ 名册另见 §7.7（⛔ 不具参考性） |
| 6c | ⭐ **「后端 × 特性可用性」没有载体**（§7.5.5，实测零命中） | 于是「此后端不支持此特性」只能落在实现里 ⇒ 今天 2 处特性缺口被表达为**崩溃**。⚠️ 且它会让裁定 19 的守卫**误报红** —— 在没有矩阵时，守卫无法区分「回归」与「本来就不该一致」（例：嵌入式配置下并发不可用是**正确**的） |
| 6d | ⭐ **策略层 / 原语层的交界未定**（§7.5.7） | 若调度策略是 Pini 值（⇒ 天然同源），则**调度决策本身运行在 `await` 点上** ⇒ 「调度决策能否被让出（重入）」须在 `DE-1` 定清，否则这是**递归挂起**的入口 |
| 7 | **判据面为零**（§2.9） | 验收须**新建**判据；但按裁定 11 **克制**（§8.5） |
| 8 | **两处文档与实现相反**（§2.8） | 会使后续批次**抄错**；须在动并发前先订正，否则新决策会建立在错误事实上 |

## 7. 批序（通往该决策记录的路径）

> ⚠️ 本节是**拟定**，各批均**须逐一单独点名**。

### 7.1 两条贯穿全序的硬约束（为什么顺序不能随便调）

| 约束 | 内容 | 违反的后果 |
|---|---|---|
| **① `C` 必须先于 `D`+`E`** | 改并发语义就是改一个**标注为 `Stable`** 的构造；而 `Stable` 在 v0.x 内**不允许**破坏性变更 | ⛔ 流程**自己把自己挡住**（须走 v1.0 路径，而那是一个不存在的路径） |
| **② `A` 必须先于一切** | 它是裁定 10 明定的**先于决策记录拟定**的支线；且它修的是**并发样例的首缺口** | ⚠️ 后续各批的验收会**建立在一批红样例之上**（无从判断新缺口是不是自己造的） |

⚠️ 三条**不属于本件裁决**、但影响排期的既有约束，一并列出以免被当作可协商项：

- 各批**不得顺手互做**（本仓硬禁：改文件时发现相邻问题应**报告**而非**顺手修**）。
- 真·跨模块调度器**无通路**（既定登记，不在任何批内）。
- selfhost 是**嵌套独立仓** ⇒ 其自身的红**不随任何批转绿**（且宿主门禁已显式排除它）。

| 批 | 内容 | 前置 |
|---|---|---|
| **`A`** | **支线：Result 窄化修复**（§8）—— **先于决策记录拟定**（裁定 10） | 本件 + 用户点名 |
| **`B`** | **文档订正批**：§2.8 两处「文档与实现相反」 | `A` 可并行；须先于 `C` |

| **`E`** | **挂起本体**（HIR 侧首次实现）+ 调度器接缝 | 同上（**并入 `D` 批**） |

而 `Stable` 在 v0.x 内**不允许**破坏性变更 ⇒ `E` 会被流程自己挡住。

### 7.2 ⚠️ 裁定 17（取乙）⇒ `D` / `E` 合并，且这是本提案最大的一批

裁定 17 把「可用」定为**含 `await` 让出**。而让出**就是**挂起本体（§5.1：`await` 点即调度决策点）
⇒ **`D` 的验收标准里含 `E` 的产物** ⇒ 两批**互为前提**，不能分开交付（分开则 `D` 永远验收不了）。

| 批 | 原定 | 现定 |
|---|---|---|
| `D` | LLVM 腿 `join` 处置 | **`D`+`E` 合并为一批**：LLVM 腿并发运行时（C ABI）+ 挂起本体（两腿让出）+ 调度接缝 |
| `E` | 挂起本体 | 并入上一行 |

⚠️ **合并后这一批的量级**：它是本提案**唯一**需要同时动「两腿 + 新运行时 + 语义变更」的批次
⇒ 建议**内部再切**为可独立验证的子段（例如：先「阻塞 join 在 LLVM 腿可用」，
再「让出（挂起）在两腿可用」），**但对外仍是一次裁定的范围**。
⇒ 子段如何切、切几段，**须点名**（§10 待裁 9）。

⛔ **上面这个切法已被 §7.5.6 修正**（裁定 20 的多后端复审）：
它是按「**特性**」切的，**没按「可复用性」切** ⇒ 会漏掉一处**硬顺序约束**。
现行建议见 **§7.5.6** 的 `DE-1`…`DE-5` —— 其中 `DE-1`（**只定 C ABI 形状、不写实现**）
**必须先于 `DE-3`**，否则 LLVM 腿那份运行时会按「只有一条腿」的形状写死，第 4 个后端来时**重写**。

### 7.3 调度器接缝形态：维护成本分析（**已裁：裁定 19 取 `乙`**；多后端复审见 §7.5）

> ⚠️ 本节是**分析**，不是裁定。裁决见 §10 待裁 8。

#### 7.3.1 先拆一处概念混淆：这里其实是**两个不同的接缝**

「两腿交集（C ABI）还是两腿各一份」这句话里混着两层，必须分开判，否则会答错问题：

| 层 | 内容 | 是否受本问题影响 |
|---|---|---|
| **语言层接缝** | **用户可替换的调度器** —— 用户自己写的调度器是**一个 Pini 值** | ⛔ **不受影响**：Pini 值经 HIR 执行，**两腿天然同源**（这是 `LR-4` 统一降载的直接收益）⇒ 用户侧**本来就是单源**，C ABI 问题在这里**不成立** |
| **内置默认实现的内部** | 语言提供的**默认调度器**，其机制（线程池 / 队列）住在哪 | ✅ **这才是本问题的真正范围** |

⇒ 问题 8 的**实际范围比字面小**：它只问「**内置默认实现**在两腿怎么落地」，不问用户面。
⇒ 这一缩小很重要：**用户可替换调度器**这个卖点**不需要**任何 C ABI 决定就能成立。

#### 7.3.2 实测：**「两腿各一份」是本仓既有的、无例外的模式**

| 实测 | 数字 |
|---|---|
| 解释器腿对运行时库的**真实调用** | ⭐ **0** （仅两处**注释**提及，且内容正是「与 LLVM 运行时行为一致」） |
| 运行时库的调用方 | **只有发射层一侧**（HIR 降载 / 节点 / 发射器）⇒ 该库**只服务 LLVM 腿** |
| 已有「每条腿一份」承载的**特征数** | **7 / 7** —— 数组 · 字典 · 集合 · COW 句柄 · `LazyRef` · FFI 指针 · 给定块槽位 |
| 对应关系 | Swift 侧**8 个**原生承载类/结构 ↔ 运行时库**38 个**符号（其中并发 **0 个**） |
| 运行时库今天的线程能力 | **无**（只有 3 把锁，无池、无分派） |

⇒ **「每腿一份」不是新方案，是本仓的既有模式**（`LazyRef` 就是活标本：一边 `LazyRefBox`、
一边 `bk_lazyref_*`）。
⇒ 若选「交集」，**并发会成为第一个走运行时库的解释器侧特性** —— 一处**孤例式的不对称**。

#### 7.3.3 成本对比（关键：**两条路都必须从零建 LLVM 腿的并发运行时**）

这是本分析最要紧的一句：**共同成本**是「在 C ABI 上建起 LLVM 腿的并发运行时」
（Future 表示 + 派发 + join + 任务树 + 取消树 + 失败上浮 + `detach`）。
**两条路都躲不掉它**，因为它由裁定 15/17 决定，与接缝形态无关。

| 项 | 甲（交集 / 共享 C ABI） | 乙（每腿一份） |
|---|---|---|
| 共同成本（LLVM 腿并发运行时） | ✅ 必做 | ✅ 必做 |
| 解释器腿 | ⚠️ **改写 ~600 行**（见下）到一个句柄表示上 | ✅ **不动** |
| Swift 原生内省（REPL / 调试器 / DAP） | ⚠️ 句柄表示会削弱它 | ✅ 保持 |
| 与既有 7/7 模式的一致性 | ⛔ **破例**（并发成孤例） | ✅ 一致 |
| 漂移风险 | ✅ 结构上**不可能漂移** | ⚠️ **存在**，且守卫今天**不在岗**（7.3.4） |
| ⇒ 结论 | **前期更贵**，只在「长期漂移」上赢 | **前期更省**，代价是漂移 |

解释器腿**必须改写**的行数（实测）：
`FutureValue` 类体 **327** · `RuntimeOps` 并发段 **161** · `Scheduler` **111** ≈ **600 行**
—— 且这 600 行里含**取消树 / 弱父引用 / 递归取消**这类**结构较富**的东西，
换成不透明句柄后，这几项的**表达力会下降**。

#### 7.3.4 ⭐ 真正的成本项：`乙` 的漂移守卫**今天不在岗**（实测）

「两腿各一份」的代价全部押在**「一致性由测试守住」**上。而实测：

| 守卫 | 现状 |
|---|---|
| 测试面 **69 条** | ⛔ **零条**跑 LLVM 腿（全域 `rg` 无 `run-llvm` / `lli` 命中） |
| 探针的默认根集 **6 个** | ⛔ **5 个已不存在**（仅 `examples` 幸存） |
| 差分测试类（含曾守两腿等价的那些） | ⛔ 已随测试面重建整体退役 |
| ⇒ 今天两腿的一致性靠什么？ | ⛔ **靠注释断言** —— 源码里**原话**即「The LLVM side reaches the same observable state by a different mechanism」 |

⇒ **这是本分析最重要的一条**：选 `乙` 而**不重建任何守卫** = 接受**无人看守的漂移**。

⚠️ **而它已经咬过两次（有据可查，非推断）**：
1. **挂起工作只做了一条腿** —— 被删的 1049 行是 **AST 腿**的，HIR 腿**从来没有对应物**。
   这正是「每腿一份」的代价**兑现**的样子：同一件事做了 N 遍，其中 N−1 遍还会被删掉。
2. **两腿的并发在正确性上分过岔** —— AST 腿撞上真实的共享可变状态缺陷（实测以 SIGTRAP/SIGSEGV 收场），
   HIR 腿靠 `ThreadLocal` 避开；且 HIR 腿自己的注释**记录了这次代价**。

#### 7.3.5 我的建议：`乙` + **一处极廉价的守卫**（守裁定 11 的克制）

**建议采纳 `乙`**，理由三条：
① 与既有 **7/7** 模式一致（`甲` 会让并发成为孤例）；
② **用户可替换的调度器本就单源**（经 HIR），所以 `乙` **不牺牲**那个卖点；
③ 前期**不必**改写解释器腿那 600 行。

⚠️ 但必须**同批**加一处守卫，否则就是 7.3.4 说的「无人看守」。守卫取**最廉价的形态**：

| 守卫 | 形态 | 新增面 |
|---|---|---|
| ⭐ **两腿同源对拍** | **同一批程序在两腿上跑，比对 stdout** | ⭐ **零新夹具** —— 语料用**既有的**那批并发样例；`examples/` 又是探针**唯一幸存**的根 |

⇒ 它的**额外好处**：它同时就是**合并后的 `D`+`E` 批的验收标准**
（那批做完后，既有并发样例**必须**在两腿上输出一致）。
⇒ 成本：≈ **0 个新文件**（复用既有语料 + 既有两腿入口 + 幸存的探针根）。

> ⛔ **本表的表述形态已被 §7.5.4 修正**（裁定 20 的复审）：结论与成本**不变**，
> 但「**两腿对比**」这个参照物**在本仓已被订正过一次** —— 正确形态是
> 「**各后端 vs 同一份期望输出（契约参照）**」。理由与先例见 §7.5.4。本表保留原样以留历史链。

⚠️ **诚实标注这条守卫的弱点**（不夸大）：
**stdout 相等是弱判据** —— 它抓不到**时序**、也抓不到**取消树 / 失败上浮**这类**不外显**的不变量。
⇒ 它是「廉价但**部分**」的守卫；是否要为那部分不变量另加判据，**须点名**（§10 待裁 10）。

⚠️ **一处新的成本项（`乙` 独有，须登记）**：运行时库将获得**它的第一套线程机制**（线程池）。
今天该库**无线程能力**（只有 3 把锁）⇒ 这是**一类新东西**进了这个库，
且它必须守住 C ABI 纪律（运行时边界的 MUST）。
⇒ 与裁定 8（不做语言级 `Lock`）**不冲突** —— 库内的线程池是**实现内部**，不是语言特性。

#### 7.3.6 若选 `甲`，有一处必须先答的问题

`甲` 要解释器腿改走句柄表示 ⇒ **取消树 / 弱父引用 / 递归取消**要搬到 C ABI 面上。
而今天的 `FutureValue` 是 Swift `final class`，其 `parent` 是 **`weak`** ——
C ABI 面没有「弱引用」这个概念，须**自建**（引用计数或旁表）。
⇒ 这不是「搬代码」，是**在 C ABI 上重新设计一遍对象生命周期**。
⇒ 建议：**若倾向 `甲`，先把这处的设计做出来再裁**，否则量级会被低估。

### 7.4 裁定 15 的量级：`D` 批从来不是「修一个崩溃」

裁定 15 把 `D` 的下限从「不再崩」抬到「**可用**」。两者**不是一个量级**，须说清楚：

| 面 | 「不再崩」要做的事 | 「可用」要做的事 |
|---|---|---|
| 发射层 | 把 `join` 的 `fatalError` 换成**响亮诊断** | 为 `join` **写发射规则** |
| 运行时 | **零** | Future 的**表示** + **派发** + **阻塞 join** + 任务树 + 取消树 + 失败上浮 + `detach` —— 即**在 C ABI shim 上新建一整条并发运行时** |
| 归属 | 一行级 | ⭐ **超出本提案其余部分**（调度接缝 + 挂起本体 + 内置特征 + 文档订正之和） |

**为什么会这么大**：解释器腿的并发**全部住在 Swift 侧** ——
`Scheduler` 是 Swift 协议、任务树 / 取消树住在 Swift 的值表示里。
而 LLVM 腿**够不到**这些东西 ⇒ 它们必须在 `libPiniRuntime` 的 **C ABI 面上重做一份**。

⚠️ 且这是**硬性约束**（运行时 shim 边界的 MUST）：shim 与用户代码的边界**必须是 C ABI**，
不能是 Swift 泛型 ABI —— 「违反即锁死自举终态，使 Swift 成为永久依赖」。
⇒ 没有捷径可走：不是「把 Swift 的调度器暴露给 LLVM」，而是**按 C ABI 重新实现一遍并发语义**。

⭐ **由此暴露一处架构张力（须在设计阶段就面对，不能等到实现时才发现）**：
「**可替换的调度器**」这个卖点，在两条腿上的**接缝形状不同** ——
解释器腿的接缝是那个 Swift 协议，LLVM 腿的接缝只能是 C ABI 函数表。
⚠️ **但该张力已被 §7.3.1 部分化解**：该张力的**真实范围**只在「**内置默认实现**」那一层，
因为**用户写的调度器是 Pini 值、经 HIR 执行 ⇒ 两腿天然同源**。
⇒ 本条据此**收紧为**：须在 `F` 批定案前裁的，是**内置默认实现**落在哪一层。
⭐ **该问已于裁定 19 关闭（取 `乙`）**，并据裁定 20 的复审在 **§7.5.3** 精化（「接缝形状类别」）
与 **§7.5.7** 收窄（作用域限于原语层）。

⇒ ⭐ **本节的「架构张力」已在 §7.5 得到完整回答**：形状差异**不在语言层**，
而在**原语层**；且 §7.5.3 给出「成本随形状类别数 K 而非后端数 N 增长」的判据。

### 7.5 按「更多后端」前景的复审（裁定 20；结论：不动裁定 19，改一处表述 + 加一条约束）

> **授权**：裁定 20（「先考虑今后有概率要引入WASM等更多后端，额外考虑、分析」）。
> ⚠️ 本节是**复审与建议**，其中**两条为修正**（7.5.4 守卫表述 · 7.5.7 作用域精化），**一条为登记建议**（7.5.5 矩阵）。

#### 7.5.1 先纠正一处口径：名册不是「两条腿」，而是**两张口径不同的表**

裁定的措辞是「有概率要引入 WASM 等更多后端」。**这与本仓现状不符，方向反了** ——
WASM **已在册**，且是**第三个已登记的后端**，不是未来可能。

⚠️ **本节初稿写「名册共六个」—— 该计数口径已据 §7.7.1 的实测更正**（详见下注）。

| 项 | 实测/登记 | 出处 |
|---|---|---|
| 后端名册（表一） | 解释器（AST）✅ · 解释器（HIR）✅ · LLVM IR ✅ · **字节码 ◐** · **C 后端 ◐** · **WASM ◐** —— 三个「设计完成、未落地」 | 语言参考的「**当前实现状态**」表 |
| 后端优先级（表二） | **解释器**（AST/HIR **合并**）**核心** · LLVM **核心** · **字节码 高** · **C 高** · WASM 中 · ⭐ **JIT 低** | 同上「**后端优先级**」表 |
| ⭐ **两表的差异**（实测） | **行数都是 6，成员集合不同**：「解释器」一行 vs 两行；⭐ **`JIT` 只在表二出现** ⇒ 去重后共 **7 个名字** | 见 **§7.7.1** |
| HIR 契约的地位 | 「各后端实现（解释器 / LLVM / **未来 WASM**）与本契约一致；**任一后端都不是定义处**」 | `HIR 契约` §0.1 第 3 条 |
| 该纪律的**用意**（契约自陈） | 禁止以 `bk_*` 行为定义语义 —— 「否则等于把某一后端的实现选择**升格为全体后端的义务**（HIR 契约是语义权威、**WASM 约束**）」 | `HIR 契约` §0.2 |

⭐ **两条对本分析分量最重的推读**：

1. **按参考自己的优先级，字节码与 C 后端（均为「高」）会先于 WASM（「中」）落地。**
   ⇒ 若只按 WASM 一个后端做准备，会漏掉**排在它前面的两个**。
2. **多后端不是前景，是本仓已写进契约的现行纪律** —— 契约的表述纪律本身**就是为多后端立的**
   （§0.2 那句「升格为全体后端的义务」是**已发生过的教训**的记录，不是假想）。

#### 7.5.2 并发面在各已登记后端里的预登记（逐条列出，标注证据级别）

| 后端 | 并发面的登记 | 证据级别 | 出处 |
|---|---|---|---|
| 解释器（HIR） | ✅ 现行**唯一**可跑的腿 | **实测**（本件 §2.1） | — |
| LLVM IR | ⛔ 崩（发射器 `fatalError`，`rc=133`） | **实测**（本件 §2.7） | — |
| 字节码 | ◐ **指令集已有「任务」类 5 条**（示例 `AWAIT`、`DETACH`）；设计原则含「**任务边界显式** \| Pini 结构化并发」 | 文档登记 | 语言参考（字节码） |
| WASM | ◐ 映射表**已预登记一行**：「**任务 → 宿主函数**」 | 文档登记 | 语言参考（WASM 后端） |
| 嵌入式最小配置 | ⭐ 「**并发 可选**」 | 文档登记 | 语言参考（嵌入式优先） |
| C 后端 | **无**并发面登记 | 文档登记（缺失） | — |

⭐ **两条对本次判断最关键的**：

1. **WASM 那一行「任务 → 宿主函数」** ⇒ WASM 腿的并发**不是自己实现，而是要求宿主提供**
   （浏览器事件循环 / 嵌入方）。而 WASM **默认单线程**；threads 提案存在但需宿主配合
   （`SharedArrayBuffer` + COOP/COEP 响应头），**并非普适可用**。
   ⇒ 挂起语义在 WASM 上只能是**委托**，不是**实现**。
   ⛔ **本条第 3 句原写作「在无线程的宿主上，『让出 OS 线程』这件事语义为空（没有线程可让）」——
   该表述已被 §7.6.4 证伪并订正**：正解是**语义保持、只降级执行策略**（无线程 ⇒ 单处理器语义），
   **不是把语义抹掉**。原文保留以留历史链。
2. **「并发 可选」** ⇒ 本仓**已经承认**并发是**按后端裁剪**的特性面。
   ⇒ ⭐ **「全后端可用」从来不是本仓的承诺**，本提案也不应把它写成承诺。

#### 7.5.3 ⭐ 核心：成本随「**接缝形状类别数**」增长，不随「后端数」增长

把并发面切三层，逐层看多后端下的份数：

| 层 | 内容 | 多后端下的份数 | 有选择吗 |
|---|---|---|---|
| ① **语义定义** | HIR 契约 + 语言规范 | **1** | ⛔ 无 —— 契约明写「任一后端都不是定义处」 |
| ② **发射 / 降载** | LLVM 的 `join` 发射规则 · WASM 的 `block`/`loop` · 字节码的 `AWAIT` 指令 | **N**（每后端一份） | ⛔ 无 —— 各后端的指令形状**本就不同**，这不是重复劳动 |
| ③ **运行时对象** | 任务树 · 取消树 · Future 表示 · 队列 · 让出/恢复原语 | **有选择** | ⭐ **只有这一层** |

⇒ 「每腿一份 vs 交集」之争**只在第 ③ 层**。裁定 19 也是在这一层做的选择。

⭐ **而第 ③ 层的正确答案不是「每后端一份」，是「每类接缝形状一份」**：

| 接缝形状 | 能被哪些后端消费 |
|---|---|
| **Swift 原生** | 解释器腿**仅此一家** |
| **C ABI** | LLVM ✓ · C ✓ · WASM ✓（wasm 的 import/export 就是 C ABI 声明的函数）· 字节码 ◐（VM 链接 C ABI 库）· 无 OS 嵌入式 ✗（参考已登记「并发 可选」） |

⇒ **若第 ③ 层从第一天就锚在 C ABI 契约上，形状类别数 K 可长期保持 2**
（Swift 原生 + C ABI），而**后端数 N 会从 2 长到 7**（口径见 §7.7.1）。
⇒ **成本随 K 增长而非随 N 增长** —— 这是唯一能避免成本随后端数线性膨胀的做法。

⚠️ **但这不翻转裁定 19（取 `乙`）**，而是**精化它**：

| 裁定 19 的原表述 | 精化后的表述 |
|---|---|
| 「每腿一份」 | 「每**类接缝形状**一份」；且 ⭐ **新增一条面向多后端的约束** —— LLVM 腿那份并发运行时**从第一天起不得依赖 LLVM 特有物**（不引 LLVM 内部类型、不假设 LLVM 内存模型），因为它是字节码 / C / WASM 后端**唯一的复用对象** |

⇒ 该约束**不增加当下的工作量**（它是一条**写法约束**，不是新交付物），
但它决定**第 4、5 个后端来时是「复用」还是「重写」**。

#### 7.5.4 ⛔ 修正：守卫的表述应从「两腿对比」改为「**契约参照**」——仓内已有先例

§7.3.5 我把守卫写成「**两腿同源对拍**（同一批程序在两腿上跑，比对 stdout）」。
**这个表述在本仓已经被订正过一次** —— 先例就在规范正文里：

> **规范「F64 展示」条的一致性表述订正**（走 §1.3）：
> 本条原写「**双通道一致性**是硬约束」，且以「解释器通道 ↔ LLVM 通道」**互为基准**。
> HIR 升为**全部后端共用枢纽**后，**该表述对象已不准确**（`HIR 契约` D1）：
> 「**各后端与 HIR 契约一致**，任一后端都不是语义定义处」。
> 动机原文：「本修订**零行为变更**，仅改表述对象以**补全第三后端（WASM）的判据面**」。

⇒ ⭐ **本仓处理过一次「双后端 → 多后端」的判据迁移，处置方式正是把参照物从「另一条腿」改成「契约」。**
⇒ §7.3.5 的「两腿对比」若照抄，就是**退回那个已被订正掉的旧表述**。

**修正后的守卫形态**：**每个后端各自与同一份期望输出比对**（**不是**两两对比）。

| 形态 | N=2（今天两条腿） | N=7（名册全落地） | 增长 |
|---|---|---|---|
| 朴素「两两对比」 | 1 组 | 会二次膨胀（**N 越大越糟**） | **二次** |
| ⭐ **契约参照**（各后端 vs 同一份期望） | 1 组 | **7 组** | **线性** |

⇒ 期望输出**只有一份**（契约是权威）；仍**零新夹具**（沿用既有并发样例 + 一份期望输出）。
⇒ 成本不变，**但它在 N 增长下不退化** —— 这正是裁定 20 要的「额外考虑」。

⭐ **已裁（裁定 26）**：守卫**取「契约参照」**（各后端 vs **同一份**期望输出），
**废弃** §7.3.5 的「两两对比」表述；据裁定 19 采纳建议时**此处为唯一被修正的一处表述**。
⚠️ 外部同类先例见 **§7.6.5**：Rust 把「**是否在 CI 跑测试**」写进 target **等级定义**
⇒ 「支持」= **构建 + 测试**两项承诺，与本形态同向。

#### 7.5.5 一处必须登记的缺失：「后端 × 特性可用性」**没有载体**（实测零命中）

实测：全仓**零命中**「能力矩阵 / 特性矩阵 / 后端能力 / per-backend」这类载体。
⇒ 「**此后端不支持此特性**」这件事**没有登记处**，只能落在实现里。
⇒ 后果今天可见：发射器 37 处 `fatalError` 里，**35 处是内部不变式断言**（「`HIRLowerer` guarantees」型，**合法**），
真正属于「此后端做不到」的是 **2 处** —— `join` 与 `detach`。
⚠️ **而这 2 处的辩护理由互相矛盾、且都已过时**（**断言腐烂**，实测）：

| 节点 | 代码里的理由（原文） | 与实测的关系 |
|---|---|---|
| `detach` | 「the HIR async pipeline is **not connected**」（管道**未接通**） | 与下面那句互相矛盾 |
| `join` | 「the lowerer has **no rule** for it」（降载层**无规则**） | ⛔ **过时** —— 实测：`join` 节点**在契约里**、`HIRExecutor` **能执行**它 |

⇒ **两处断言的理由不一致，且至少一处已被实测否证，断言却还在** ⇒ 落在**可达路径**上 = 崩溃。

**建议（克制口径）**：这不是新建门禁，是**一份登记** ——
「后端 × 特性 → { 可用 / 不可用（须给诊断） / 委托宿主 / 不适用 }」。
它同时给三件事一个落点：LLVM 腿的 `join` · WASM 腿的宿主委托 · 嵌入式配置的「并发可选」。

⚠️ **且它与裁定 19 的守卫是同一个问题的两面**：
守卫问「各后端**行为是否一致**」，登记问「各后端**该不该一致**」。
⇒ **没有它，守卫会在「本来就不该一致」的格子上误报红**
（例：嵌入式配置下并发不可用是**正确**的，不是回归）—— 这是本次复审**新暴露**的一处设计缺口。

⭐ **已裁（裁定 27）：立，但形态按 §7.6.5 修正 —— 不是「矩阵」，是「分层 + 等级」。**

| 项 | 裁定 |
|---|---|
| **形态** | ⛔ **不是矩阵** —— 矩阵是**过强**形态（能表达**不可能存在的组合**）。改为 **C++ 概念式分层**：**一层套一层** |
| 本仓的层 | **有让出 ⇒ 必有调度**；**无线程 ⇒ 无让出，但调度仍在**（§7.6.4 订正后的读法） |
| **承诺** | 采 **Rust tier 式等级**，但 ⚠️ **本仓当前一律不给等级**（见 §7.7：语言远未成熟） |
| **运行时形态** | 采 **GCC fmv 式三条纪律**（§7.6.6）：**启动时解析一次** · **结果固化、进程内不变** · **无合格版本则降级不失败** |
| 落地时机 | 归 **`D`+`E` 批** 的 `DE-1`（形状定案时一并定）—— 不在本支线做 |
| 即时代价 | ≈ **2 行代码**（`join` / `detach`：**崩溃 → 诊断**），可随 `D`+`E` 一起 |

#### 7.5.6 裁定 20 对 `D`+`E` 内切的实际影响：新增一条**硬顺序约束**

§10 待裁 9（原建议）把 `D`+`E` 内切成两层：①阻塞 join 可用 ②让出可用。
**该切法按「特性」切，没按「可复用性」切** ⇒ 在多后端前景下**不够**。修正后的内切：

| 子段 | 内容 | 为什么在这个位置 |
|---|---|---|
| ⭐ **`DE-1`** | **形状定案**：并发运行时的 **C ABI 面**（**只定契约、不写实现**）+ 策略层 / 原语层的**分界**（见 §7.5.7） | ⛔ **必须在 `DE-3` 之前** —— 否则 LLVM 腿那份会按「只有一条腿」的形状写死，第 4 个后端来时**重写**。⭐ **这是多后端前景带来的唯一实质顺序约束** |
| **`DE-2`** | 解释器腿：挂起本体（HIR 侧首次实现）+ 让出语义 | 先做解释器腿：有 REPL / 调试可见性，迭代最快 |
| **`DE-3`** | LLVM 腿：`join` 发射规则 + **按 `DE-1` 的形状**建 C ABI 运行时 | 依赖 `DE-1` |
| **`DE-4`** | 守卫：**契约参照**的 stdout 对照（各后端 vs **同一份**期望输出，见 §7.5.4） | 零新夹具；同时是合并批的验收标准 |
| **`DE-5`** | 收口：§8.5 的处置 + 检查点语义订正 + 判据固化 | — |

⚠️ `DE-1` 的产物**本身就是下一个后端的复用凭据** —— 它是本复审建议新增的唯一交付物。

#### 7.5.7 ⭐ 作用域精化：内置默认实现应拆成「**Pini 策略**」+「**宿主原语**」两半

§7.3.1 已说「**用户可替换的调度器是 Pini 值、经 HIR 执行 ⇒ 两腿天然同源**」。**把这个判断推到底**：

| 半 | 内容 | 可以是 Pini 代码吗 | 多后端下 |
|---|---|---|---|
| **策略** | 队列 / 优先级 / 归约阈值 / 选择下一个任务 | ✅ **可以** —— 它是纯逻辑，无宿主依赖 | ⭐ **全后端同源**（LR-4 已让 HIR 成为唯一执行路径） |
| **原语** | 让出 / 恢复 · 续体保存 · 任务树 · 取消树 | ⛔ **不可以** —— 必须触碰宿主 | 每**接缝形状**一份（§7.5.3） |

⇒ **裁定 19 的作用域应精确到「原语层」**：**策略层根本不存在选择**，因为它是 Pini 代码 ⇒ 天然同源。
⇒ 这**大幅缩小**了「每腿一份」的实际作用面，且**不改变裁定 19 的结论**。

⭐ **附带好处**：内置默认调度器与用户可替换调度器**变成同一机制**（都是 Pini 值），
只是默认的那份由语言提供 —— 这比「内置特征 + 宿主侧默认方法体」**更简单**，
且**自动绕开**「内置特征是**新引入的语言类别**」这处本提案最大的不确定（§5.2）。

⚠️ **一处须在 `DE-1` 定清的交界**（本件**不替它定**）：策略层要「**选择任务**」，
原语层要「**保存 / 恢复续体**」—— 两者的交界处**就是挂起点**。
若策略是 Pini 值，则**调度决策是一次 Pini 函数调用，而它运行在 `await` 点上**
⇒ 「调度决策自身是否也能被让出（重入）」须明确定清，否则这是**递归挂起**的入口。

⭐ **已裁（裁定 28）：拆。** 内置默认实现**按上表分两半** —— **策略层写成 Pini 值**（与用户可替换调度器同一机制）、
**原语层**按接缝形状各一份。三条后果随之确定：

| 后果 | 说明 |
|---|---|
| ⭐ **作用域** | 裁定 19 的「每腿一份」**精确到原语层**；策略层**全后端同源**（无选择余地） |
| ⭐ **§5.2 的形态简化** | 「内置特征 + 宿主侧默认方法体」**不再必需** —— 默认调度器就是一个**语言提供的 Pini 值** ⇒ **绕开**「内置特征是**新引入的语言类别**」这处本提案最大的不确定。⚠️ §5.2 的**软关键字**结论（裁定 14）**不变**，因为它管的是「**名字在哪儿被识别**」，与该值住在哪一层无关 |
| ⚠️ **交界仍须在 `DE-1` 定** | 「调度决策能否被让出（重入 / 递归挂起）」**仍开着** —— 它随 `DE-1` 一起定（§7.5.6），本件不替它定 |

⚠️ **一处诚实标注：这一步无外部先例。** §7.6.8 已记 ——
外部四语言的策略层**都写在宿主语言里**（Rust 的 executor 是 crate、Swift 的是协议实现），
**不是「被编译语言里的值」**。⇒ 本裁定是本仓的**独立判断**，**不能**引外部先例为据。

#### 7.6.1 「原语在语言、策略在库」是跨语言共识 —— Go 是唯一反例

| 语言 | 挂起原语（语言 / 核心） | 调度策略（库 / 用户） |
|---|---|---|
| Rust | `Future::poll` + `Waker` + `Pin`（在 `core`） | executor 全在 crate：**tokio** · **embassy** · **wasm-bindgen-futures** |
| C++ | `co_await` 机制 + 协程帧 | `std::execution`（P2300）的 **`scheduler` 概念** |
| Swift | 并发运行时（任务 / actor 模型） | **`SerialExecutor` 协议**（只要求实现 `enqueue` 一个核心操作） |
| Kotlin | 挂起函数机制 | **`CoroutineDispatcher`**（`expect` / `actual` 逐平台） |
| ⛔ **Go** | **runtime 内置调度器** | ⛔ **无此层，不可替换** |

⭐ **Rust RFC 2394（async/await 稳定化）写下的三条「不内置运行时」理由**，逐条对应本仓处境：

| Rust 的理由 | 本仓对应项 |
|---|---|
| 嵌入式与 `no_std` 兼容 —— 内置运行时会「把线程池、**epoll** 等 OS 依赖**强加**给所有目标平台」 | 语言参考（嵌入式优先）已登记「**并发 可选**」（§7.5.2） |
| **调度策略不可统一** —— 服务器要 work-stealing、CLI 只需单线程、实时系统要优先级 | 本提案 §5.2 / 参考「混合式调度」的动机 |
| 避免生态锁定 | 「**用户可替换调度器**」的初衷 |

⇒ ⭐ **语言可见的可替换点不是本仓的独创需求，是四种主流语言的共同选择**；
而**把它做进 runtime 且不可替换**（Go 的路）**与本仓已登记的「并发 可选」自相矛盾**。

#### 7.6.2 ⭐ 同一抽象、多个驱动：Rust 是唯一三端都跑的样本

`async` / `.await` / `Future` **只有一份**；驱动**三份、且互不兼容**
（官方说明：同一二进制里混用会在**运行期 panic**，因为所需 reactor 没在跑）：

| 驱动 | 宿主机制 | 形态 |
|---|---|---|
| tokio | OS 线程池（work-stealing）+ epoll/kqueue/IOCP | 多线程 |
| **wasm-bindgen-futures** | **浏览器 event loop + microtask 队列** | ⭐ **没有运行时**（`spawn_local` 单线程） |
| **embassy** | 中断 + 定时器唤醒，**无堆 / 静态分配 / 单栈 / WFI 自动睡眠** | 协作式于 `await` 点 |

⭐ **embassy 的边界自陈**（与本仓 §6 风险 3 同向）：「协作式调度 —— 一个不让出的 CPU 密集任务会阻塞 executor」；
且「**硬抢占（CPU 密集任务的强制剥夺）仍需 RTOS**」。

#### 7.6.3 ⭐ 对参考「混合式调度」的一处补充：抢占有**第二条路**

本仓语言参考的「混合式」定义是「协作式 + **归约计数**，长时间运行任务可被抢占」——
那是**时间片式**抢占。**embassy 给出的是另一条路**：

> 「任务在同一 executor 上协作运行，**但你可以创建多个不同优先级的 executor**，
> 让高优先级任务抢占低优先级任务。」

⇒ **分层抢占（多 executor + 优先级）vs 时间片抢占（归约计数）** 是两种不同机制。
⚠️ **本仓参考只登记了后者**，而**前者在无线程环境（嵌入式 / 单线程 WASM）下是唯一可行的抢占手段**
（没有第二个线程，就谈不上时间片）。

⭐ **已裁（裁定 29）：登记，不实现。** 这是**本件带出的第二处参考订正**（第一处见 §7.6.4）。

| 项 | 裁定 |
|---|---|
| 动作 | 在语言参考「**混合式调度**」名下**补登「分层抢占」**，与既有「归约计数」并列 |
| 性质 | ⛔ **只登记、不实现**（照本仓「只登记不改码」的既有先例，如环检测的余量登记） |
| 稳定性标记 | ⚠️ **仍为 `Experimental`** —— 该节现状即 `Experimental`（§6 风险登记「混合式调度 \| Experimental」）⇒ **不新增级别** |
| 归属 | 属**参考面订正**，与 `C` 批的「标记与实际不符」同族（裁定 25）—— 可并批，但**须用户点名**（本件不代其排期） |

#### 7.6.4 ⛔ 订正：无线程后端上「让出」的**语义不是空，是降级**

§7.5.2 原写「在无线程的宿主上，『让出 OS 线程』这件事**语义为空**」。**该表述错误。**

**Go 官方对 WASM 目标的回答是更好的形态**：WASM 目标不支持线程
⇒ 程序行为**等价于 `GOMAXPROCS=1`**，且「**只要你在代码里用了正确的同步，
从正确性角度看什么都不变。channel 与 goroutine 的语义也不变**」。

⇒ ⭐ **正确表述**：无线程 ⇒ **退化为单处理器语义**（调度策略降级、**语义保持**），
**不是**「语义为空」。**GopherJS** 同证：单线程 ⇒ **协作式调度器**，`GOMAXPROCS()` 恒返回 **1**。

⚠️ 该订正**改变一条设计含义**：§7.5.7 的交界问题（策略运行在 `await` 点）在无线程后端上**同样成立**，
因为「让出」在那里**仍是一个语义事件**（让给同线程上的其他任务），只是**不让出线程**。
⇒ 若按原错误表述，会得出「WASM 腿不需要挂起点」的**错误结论**。

#### 7.6.5 后端能力差异的**载体**：四种成熟形态 —— **没有一种叫「矩阵」**

> ⭐ 这一条**直接修正待裁 11 的建议形态**：外部先例里没有「能力矩阵」这种东西。

| 形态 | 先例 | 机制 | 对应「不支持」的表示 |
|---|---|---|---|
| **编译期能力谓词** | Rust `cfg(target_has_atomic = "64")` · Clang `__has_builtin` / `__has_feature` / `__has_cpp_attribute` | 条件编译 | 代码路径**不存在** |
| **分层概念（refinement）** | C++ P2300：基础 `scheduler` → 扩展 `time_scheduler`（`schedule_after` / `schedule_at` / `now`）→ 文件 / 网络扩展 | ⭐ 概念**一层套一层** | ⭐ **不满足该概念** ⇒ 编译期检出，**无需维护任何表** |
| **逐平台实现** | Kotlin `expect` / `actual` | 每平台一份 `actual` | ⭐ **三种并存**：**编译期无成员**（`Dispatchers.IO` 在 JS 无）· **降级等价**（`Main` 在 JS ≡ `Default`）· **运行期抛错**（JVM 缺 Main 库） |
| **与测试承诺绑定的支持等级** | Rust target **tier 1 / 2 / 3** | 等级定义里**写明测试承诺** | tier 1 = 保证构建**且跑测试**；tier 2 = 保证构建、**不保证跑测试**；tier 3 = 不保证 |

⭐ **三条对本仓分量最重的推读**：

1. **能力差异是「分层」的，不是任意布尔组合** —— C++ 用 `time_scheduler` **扩展** `scheduler`：
   有时间的必有调度、有调度的未必有时间。**本仓同构**：**有让出 ⇒ 必有调度**；无线程 ⇒ 无让出，但**调度仍在**。
   ⇒ 「矩阵」这个形态是**过强**的（它允许表达不可能的格）。
2. ⭐ **Rust 把「是否在 CI 跑测试」写进了支持等级的定义里**——
   这**正是**待裁 13（守卫）与 §7.3.4（守卫不在岗）问的那件事的**先例**：
   「支持」= **构建 + 测试**两项承诺，**不是**「编译器认识这个名字」。
   且 Rust 有 **demotion 先例**（32-bit Apple 从 tier 1 降到 tier 3，走 RFC）⇒ **等级可降，且降级有流程**。
   ⚠️ **但本仓当前用不了这条** —— 见 **§7.7.2**：语言远未成熟 ⇒ **承诺列 7 行全空**（裁定 30）。
   ⇒ 该先例的**形态已采**（等级列已留）、**内容尚不可填**。
3. **「不适用」报在哪一级有成熟模板** —— Clang 的 HLSL availability diagnostics：
   API 在语言里暴露、但在目标 stage / model 上不可用 ⇒ **编译期诊断**，且分三档
   （**只查可达代码** / 降为警告 / 全量）。⭐ **与本件 §7.5.5 的发现正面对照**：
   本仓那 2 处**落在可达路径上的 `fatalError`**（崩溃），按此模板**应当是诊断**。

#### 7.6.6 ⚠️ 本仓的**特殊性**：外部先例几乎都是编译期静态后端

上表四种形态**全部是编译期**（Rust `cfg` · C++ 概念 · Kotlin `actual` · HLSL availability）。
⛔ **而本仓的后端是运行时可选** —— 同一个 `pini` 二进制能跑解释器腿与 LLVM 腿（§2.7 实测）。
⇒ **不能照搬编译期形态**；最贴切的外部先例是 **GCC / Clang 的 function multiversioning**：

| 机制 | 内容 |
|---|---|
| 形态 | 编译器生成**多个版本** + 一个 **resolver** |
| 探测 | **CPUID 硬件能力位**（glibc 硬件能力位） |
| 时机 | ⭐ **启动时解析一次**，结果存入**动态符号表** ⇒ 此后调用**走指针、零运行期开销** |
| ⭐ 不变式 | 「**一旦选定即固定，进程生命周期内不再改变**」 |
| ⭐ 降级 | 无更具体版本合格时，**降级到 `default` 版本**（**不是报错**） |

⇒ 两条可直接借用的设计纪律：**①解析一次、结果固化；②无合格版本时降级、不失败**。

## 8. 支线计划：Result 窄化修复（本件兼任计划件）

> **授权**：用户裁定 10（原话：「应该把并发示例的修复放到提案中，在进入ADR的拟定之前，开支线修复它」）

> ⚠️ **本支线会推翻一条已裁事项** —— 见 §8.4 `S0`。

### 8.1 目标

| 项 | 内容 |
|---|---|
| **要** | 消除 §2.6 的**单一根因**（`match` 对 `Result` 型 scrutinee 缺分派支） |
| **兼要** | 让 8 个 `concurrency*` 样例的**首缺口**前移（不承诺全绿） |
| **不要** | 见 §8.7 |

### 8.2 根因与修法（已定位，见 §2.6）

**根因**：`HIRLowerer` 的 `lowerMatch` 缺 `.result` 分派支 ⇒ `case ok(v)` 的绑定
静态类型留在 scrutinee 的 `Result` 上，未取载荷类型。

**修法**：照 `lowerOptionalCases` 的既有形态，增一个 `Result` 版分支
—— 把 `ok` 绑定的类型设为**载荷类型**。**一处缺失分支 + 一个分支函数。**

⚠️ **`err` 侧的处置须单独判**：既有的 try-else 路径把错误绑定登记为**类型擦除**形态
（发射器对「打印错误绑定」有专门门禁，理由是「err 槽是类型擦除的」）。
⇒ 支线**不得顺手改**该形态；`err` 绑定维持现状，只做**正向验证**。

### 8.3 改动面（已实测处数，非估计）

**起因**：用户给出裁定 19（采纳提案方建议）· 20（按「今后有概率引入 WASM 等更多后端」额外复审）· 21（守卫弱点先不补）。

**② 裁定 20 的复审（新增 §7.5，六个小节）** —— 本轮主要工作，是**一处口径纠正 + 两条修正 + 一条新增建议**：

| 项 | 内容 |
|---|---|
| ⭐ **口径纠正** | 裁定措辞是「今后**有概率**引入 WASM 等更多后端」，而 **WASM 已在册**：后端名册共**六个**（解释器 AST / 解释器 HIR / LLVM 三个已落地；**字节码 / C / WASM** 三个「设计完成、未落地」），且按参考自己的优先级表，**字节码与 C 都是「高」、WASM 是「中」** ⇒ 那两个**会先来**。更关键：`HIR 契约` §0.1 第 3 条**已把 WASM 写进纪律**（「任一后端都不是定义处」），§0.2 的表述纪律**本身就是为多后端立的**（原话：否则等于把某一后端的实现选择「**升格为全体后端的义务**」）⇒ **多后端不是前景，是现行契约纪律** |
| ⭐ **核心洞察** | 并发面切三层：① 语义定义（**1 份** —— 契约明写「任一后端都不是定义处」）② 发射 / 降载（**N 份** —— 各后端指令形状本就不同，**不是**重复劳动）③ 运行时对象（**有选择**）。⇒「每腿一份 vs 交集」之争**只在第 ③ 层**。而第 ③ 层的正确答案**不是「每后端一份」，是「每类接缝形状一份」**：Swift 原生仅解释器腿可消费；**C ABI** 则 LLVM ✓ / C ✓ / WASM ✓（wasm 的 import/export 就是 C ABI 声明的函数）/ 字节码 ◐ ⇒ **形状类别数 K 可长期保持 2，而后端数 N 会从 2 长到 6** ⇒ **成本随 K 增长，不随 N 增长** |
| ⛔ **修正 1（守卫表述）** | §7.3.5 原写「**两腿同源对拍**」。**该表述在本仓已被订正过一次**：规范「F64 展示」条的一致性表述订正原文——「本条原写『双通道一致性是硬约束』，且以『解释器通道 ↔ LLVM 通道』**互为基准**」，HIR 升为全后端枢纽后**表述对象已不准确**，改为「**各后端与 HIR 契约一致**」；动机原文即「仅改表述对象以**补全第三后端（WASM）的判据面**」。⇒ 照抄「两腿对比」= **退回那个已被订正掉的旧表述**。修正后形态：**各后端 vs 同一份期望输出**（N=6 时 **6 组、线性**；而两两对比是 **15 组、二次**） |
| ⛔ **修正 2（`D`+`E` 内切）** | 原两层切法（按**特性**切）在多后端前景下**不够** ⇒ 改为 §7.5.6 的 `DE-1`…`DE-5`。**新增 `DE-1`（只定 C ABI 形状、不写实现）并置于 `DE-3` 之前** —— 这是多后端前景带来的**唯一实质顺序约束**；跳过它，LLVM 腿那份会按「只有一条腿」的形状写死，第 4 个后端来时**重写** |
| ⭐ **新增建议（矩阵）** | 实测全仓**零命中**「后端能力 / 特性矩阵 / per-backend」这类载体 ⇒ 「**此后端不支持此特性**」**没有登记处**，只能落在实现里。后果今天可见：发射器 **37 处 `fatalError`** 中 **35 处是内部不变式断言**（「`HIRLowerer` guarantees」型，**合法**），**2 处**才是真正的后端能力缺口（`join` / `detach`）—— 且这 2 处的**辩护理由互相矛盾、至少一处已被实测否证**（`detach` 说「管道**未接通**」、`join` 说「降载层**无规则**」，而实测：`join` 节点**在契约里**、`HIRExecutor` **能执行**它）⇒ **断言腐烂**，落在**可达路径**上 = 崩溃。⚠️ 且**矩阵是守卫的判读依据** —— 没有它，守卫会在「**本来就不该一致**」的格子上**误报红** |
| ⭐ **作用域收窄** | 原「每腿一份」的作用域应缩到**原语层**：**策略层**（队列 / 优先级 / 归约阈值 / 选下一个任务）**可以**是 Pini 值 ⇒ 经 HIR ⇒ **全后端同源**，且与用户可替换调度器**变成同一机制**；只有**原语层**（让出 / 恢复、续体、任务树、取消树）必须宿主实现。⇒ 顺带**绕开**「内置特征是新增语言类别」这处本提案最大的不确定 |
