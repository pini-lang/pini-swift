## 0. 结论先行

1. **其他语言里没有一个**让「指向被调方栈帧的指针」当值流传。只有两条路：
   **① 目的位置由调用方给**（C / Rust / Swift / Go / Zig 的聚合返回都是这条）；
   **② 值住在堆上 + 有所有权**（Java/JS/Python 的引用语义、Swift class/ARC）。
2. ⚠️ **本仓的洞不是一个，是两个**（本轮实测）：你点的「返回外逃」是一条，**另一条是「缺值语义拷贝」**
   —— 后者**不在册**（契约无条款、evidence-table 无条目、缺陷台账无编号）。两者同一病根：
   **`%struct.X` 的身份是「指向某块存储的指针」，而这块存储的归属与寿命没人负责**。
3. **建议走 ①**，分两片（返回路径 / 四个拷贝点），第三片（写时免拷贝优化）延后。理由与代价见 §5。
4. ⚠️ **另有一处语义要你裁**：**形参绑定两个后端都「共享」**（实测：被调方改形参，调用方看得见），
   与契约「值类型」的字面读法不一致，而**规范未明文**。这条属**语言语义**，我不擅动（见 §6.2）。

### 0.1 ⚠️ 同日补测订正（**上面第 3 条的建议已被本轮实测推翻**）

把「外逃」在**四类名义值 + 闭包捕获**上各测一遍，并**逐条配同帧对照**（命令见 §9）：

| 探针 | 形态 | 解释器（权威） | LLVM 原生 |
|---|---|---|---|
| A | 结构体返回，跨调用读字段 | `A 7 1110` | ⛔ `A -255950760 1110` |
| B | **结构体字段**（嵌套结构体）随外层返回 | `B 8 1110` | ⛔ `B -229641480 1110` |
| C | **对象**（引用语义）返回 | `C 9 1110` | ⛔ `C 1 1110` |
| D | **带载荷枚举**返回后 `match` | `D 2.0 1110` | ⛔ `Pini runtime error: match value matched no case` |
| E | **闭包捕获的变量**随闭包外逃 | `E2 101 666` | ⛔ `E2 -255950759 666` |
| A–E **同帧对照** | 构造与使用在同一帧内 | 与左列同值 | ✅ **全部通过**（`A-ctl 7` / `B-ctl 8` / `C-ctl 9` / `D-ctl 2.0` / `E-ctl 101`） |

⇒ **洞的准确表述**：**名义值（结构体 / 对象 / 枚举）的箱、以及闭包捕获的变量槽，都分配在创建帧里；
任何跨帧引用即失效。** 「值语义拷贝」只是**结构体那一格**的症状，不是病根。
⇒ 第 3 条建议（目的位置 + 自有箱 + 四个拷贝点）**不足以修好**：**对象与枚举在解释器里是引用语义**
（`RuntimeOps.copyIfStruct` 对它们**原样返回**）⇒ 它们的箱**必须比创建帧活得久** ⇒ 区域/目的位置模型
对它们**不适用**；闭包捕获同理（捕获的是**变量槽**，须装箱）。
⇒ **订正后的建议见 §9.3**（堆箱 + 引用计数，**且四个值语义点做即时深拷贝、不做写时复制**）。

⚠️ 另有一处**旁支发现**（与本专项同批量到，属另一族）：**闭包捕获的检查（`E3-008`）只在解释路径生效** ——
同一份源在 `run` 上被拒、在 `compile` 上被接受并跑出结果（§10）。

## 1. 问题重述（全部为实测读数）

### 1.1 四个位置的现状

夹具：`examples/selfhost/tools/.fixtures/structret-escaping.pini`（上一批留存）+ 本轮两条新探针。
命令见 §7。左列是**解释器**（权威），右列是 **LLVM 原生**：

| # | 位置 | 代码形态 | 解释器 | 原生 |
|---|---|---|---|---|
| ① | `allocVar` | `var b = a` 后 `b.x = 2` | `1 2`（拷贝） | **`2 2`（别名）** |
| ② | `storeVar` | `d = c` 后 `d.x = 4` | `3 4`（拷贝） | **`4 4`（别名）** |
| ③ | `fieldStore` | `h.p = 造点(5,)` 后读 `h.p.x` | `9` | **`-255950760`（垃圾值）** |
| ④ | 形参绑定 | 被调方 `p.x = 50` | `50`（**共享**） | `50`（共享）**两路一致** |
| ⑤ | 返回值 | `let f = 造()` | `7 9` | `7 9` 单次调用正确；**跨调用/回写即崩**（见下） |

**⑤ 的外逃形态**（上一批实证，夹具 `structret-escaping.pini`）：解释器 `BEFORE 7 9` / 原生 `BEFORE 1842884192 1`
—— `makeLocation` 生成 `%t1 = alloca %struct.SourceLocation` 后 `ret` 该地址，调用方拿**悬垂指针**。

### 1.2 为什么「返回值」一个词盖不住这件事

看自举整包 IR 里的 nominal 布局（实测摘录）：

```llvm
%struct.Block   = type { %enum.StatementList*, %struct.SourceLocation* }
%struct.FuncDecl = type { i8*, %enum.StringList*, ..., i1, %enum.OptionalBlock*, %struct.SourceLocation* }
```

**聚合字段一律是指针** ⇒ 一个结构体值 = 一棵**箱图**。于是「拷贝」**不是一次 memcpy**，
而是**递归拷贝**（注释/对象照旧共享）——这正是解释器侧 `RuntimeOps.copyIfStruct` 的规则。
⇒ 谁要修这个洞，就必须回答「**箱的归属与寿命**」，而不只是「返回时谁来分配」。

### 1.3 规则现住在哪一边（这是缺口的结构性原因）

- 解释器侧：`RuntimeOps.copyIfStruct`，**在四个位置**被调用（`allocVar` / `storeVar` / `fieldStore` /
  `subscriptStore`），注释明写「Both engines owe this rule at every binding and store site」。
- 契约侧：`docs/spec/ir-contract.md` **没有「值类型拷贝」条款**（§1 只说 `isObject=false` 是值语义）；
  `docs/spec/evidence-table.toml` 无条目。
- LLVM 侧：**四个位置都没有**（① ②实测为别名，③被 ⑤ 掩盖，⑤ 未开通）。
⇒ 「**两个引擎都欠的规则，只在一个引擎上落了地**」——这是本类缺陷的成因，也是它没被登记的原因。

## 2. 其他语言怎么做（带出处）

### 2.1 返回路径：**目的位置由调用方给**（destination-passing）

| 语言 / 平台 | 规则（>16 字节或放不进寄存器的聚合） | 出处 |
|---|---|---|
| C · SysV AMD64 | 类为 `MEMORY` ⇒ **调用方提供空间**，地址当**隐藏首参**经 `%rdi` 传入；`%rax` 回同一个地址 | System V AMD64 psABI §3.2.3 Returning of Values |
| C · AAPCS64 | 寄存器 `r8` 的角色原文即 **"Indirect result location register"**；调用方分配、地址经 `x8`，callee 写入 | AAPCS64 Table 2 + Result Return |
| **Swift** | **优先寄存器直返**（立意「约 3 个指针大小」）；否则**间接返回**：IR 结果类型置 `void`，**追加一个指针参数**指向「原始直接结果组合的 tuple」；本质 address-only（含 weak / 泛型布局未知）**必须**间接 | Swift ABI `CallingConvention.rst` |
| **Go** | 结果**要么全寄存器、要么全栈**（不可拆）；栈分配的结果区**由 caller 在自己帧里预留**，callee 返回前写入；**参数才有 spill space，结果没有** | Go internal ABI `abi-internal.md` |
| **Rust** | MIR 的 `_0` 即 **return place**；codegen 走 out 指针。caller 提供的返回位与 callee 的 `_0` 是否同一块内存，在 rustc 内部仍是有争议的语义细节 | rustc MIR `RETURN_PLACE`；rust-lang/rust#71117；unsafe-code-guidelines#417 |
| **Zig** | **RLS（结果位置语义）**：结果位置**由上下文提供**，`fn nice() Point { return Point{...} }` 直接写进最终结果位置 —— **语义保证零中间拷贝** | Zig 0.5.0 release notes（RLS 引入）；语言参考 RLS 节 |

⭐ **Zig 的 RLS 最值得本仓看**：它把「返回/构造/绑定」连成一条**写进最终位置**的直线，
既拿到零拷贝，又**从根上不存在「临时箱交给调用方」**这件事。本仓已有同形约定（见 §3.1）。

### 2.2 值语义的拷贝位置

| 语言 | 赋值/绑定 | 返回 | 优化如何免拷贝 |
|---|---|---|---|
| C / C++ | 拷贝 | 拷贝 | **RVO/NRVO**（C++），拷贝省略 |
| Swift | 拷贝（值类型） | 拷贝（owned） | 寄存器直返；`inout` **总传地址**（不可寻址则物化后写回） |
| Go | 拷贝 | 拷贝 | 逃逸分析决定栈/堆 |
| Rust | **move**（默认不拷贝） | move | 返回位直接写 |
| Zig | 拷贝 | 拷贝 | **RLS**：目的位置已知时**不产生中间值** |

### 2.3 另一条路：**住在堆上 + 有所有权**

- Java / JS / Python：对象是引用语义、住堆、由 GC 回收 ⇒ **「栈地址外逃」这个类根本不存在**。
- Swift `class` / ObjC：堆 + 引用计数（ARC）。
- ⭐ **本语言自家已有这条成熟通道**：`array` / `dict` / `set` / `object` / `lazyRef` **都带 refcount 头**
  （`docs/spec/ir-contract.md` §1「refcount 头是实现」），容器还是 **COW 值语义**。

### 2.4 归纳成两条定律

- **定律一**：聚合值的存储只有两个合法归属 —— **调用方（或其指定的目的位置）**，或**堆（且有所有权）**。
  第三者「被调方栈帧」**不允许**把地址当值交出去。
- **定律二**：**优化只能删「规范观察不到的拷贝」**（RVO / RLS 属此类），**不能删规范要求的拷贝**。
  ⇒ 「值语义的拷贝点」与「免拷贝优化」是两件事，不能互相顶替。

## 3. 落到本仓：三条既有的表示法并存

### 3.1 `%out`（目的位置）家族**已经存在**，而且是本仓自己的惯例

| 处 | 形态 |
|---|---|
| 默认实例初始化器 | `define ptr @__given_init_<T>(ptr %out)`（ADR-001 `P2b`） |
| 惰性引用包装 | `define ptr @__lazyref_wrapper_<T>(ptr %code, ptr %env, ptr %out)` |
| 任务体 | `define i32 @<task>(ptr %code, ptr %env, ptr %out)`；运行时 `bk_task_await(hand, %out)` |
| 给定块取值 | `bk_given_get(槽位, 初始化器, 字节数)` → 盒指针 → **`memcpy` 一份到本地** |

⚠️ 一处口径提醒：这些**不是** LLVM 的 `sret` **属性**（LangRef：「A function that accepts an sret argument
**must return void**」），是**自家约定**。改不改用属性，是实施期的细节，不影响方案选择。

### 3.2 **SSA 内联聚合也已经存在**

元组 / 可选 / `Result` 走 `insertvalue` / `extractvalue`（不落栈、无指针身份）。
⇒ 仓里其实是**三条表示法并存**：SSA 聚合（元组族）· 栈上箱 + 指针（nominal 结构体）· refcount 句柄（容器/对象）。
**洞在第二条上。**

## 5. 建议

**走甲′，分三片；片一、片二同批，片三延后。**

- **片一（返回路径）**＝你点的待裁项 1：让返回的箱**归调用方给的槽**，消灭「指向被调方栈帧的指针」这一类。
  ⚠️ **片一单独不足以修好 ① ②** —— 那两处不是返回值，是**绑定/赋值**。
- **片二（四个拷贝点）**＝本轮新发现的那个洞：与解释器 `copyIfStruct` 逐点对齐（含递归与「enum/object 字段照旧共享」）。
- **片三（可延后）**＝RLS/RVO 式免拷贝：把「构造 → 临时箱 → 拷进绑定」的双写压成单写（Zig 那条），**属优化，不属语义**。

**不选乙′**：代价面（布局 + ABI + 全量 retain/release + 等价性论证）远大于收益，且它与语言**刻意**分开的
`%struct`（无计数）与 `%object`（有计数）两格相冲突 —— 那条分界看起来是有意的。
**不选丙′**：递归类型使它**做不到**（§4 反面证据）。

⚠️ **甲′ 的如实代价**：绑定/赋值处是**递归深拷贝**，与解释器同阶 ⇒ 片一+片二先买**正确性**，
速度靠片三。这与「门禁提速」的初衷不冲突：当前门禁根本跑不通原生臂（读数不一致就不许接，见 `auth-73` scope ⑦）。

## 6. 要你裁的

> ⚠️ **2026-10-01 同日订正**：第 1 条已按 §0.1 的补测**改写**（原问「走甲′吗」⇒ 现问「走**堆箱 + 引用计数**吗」）。
> 第 2 · 3 条**不变**。

1. **走「堆箱 + 引用计数 + 四个点即时深拷贝」吗？**（§9.3；若走，先立授权条目）
   ⚠️ 与 **0.1 之前的「甲′」不同**：甲′ 只覆盖结构体、且把箱放在调用方给的槽里 —— 对**对象 / 枚举 / 闭包捕获**
   不成立（它们是引用语义 / 变量槽）。
   ⚠️ 也与我 **§4 表里的「乙′」不同**：乙′ 是**写时复制（COW）**，而**参数共享**这一实测事实
   （`C-AFTER-PARAM 50`：被调方改形参，调用方看得见）**排除了 COW** —— COW 会在形参写路径上分裂，
   把调用方**看不见**那次改动，与解释器分道扬镳。⇒ 必须是**绑定点即时深拷贝**。
2. ⚠️ **形参绑定要不要一并裁**？（**语言语义**变更，须你定）
   - 现状：**两后端都共享**（被调方写形参，调用方看得见）—— 两路**一致**，但与契约「值类型」的字面读法不符，**规范无明文**。
   - 选项：**保持并在规范明文写清**（把它定义成「形参是入口引用」）／**改成拷贝**（向 Swift/C/Go 看齐，代价：自举大结构体传参会多拷贝）。
   - 我的建议：**保持现状 + 明文登记**（且它**与 1 不冲突**：1 的承包住它当前的可观察行为）。
3. **可延后的那片（写时免拷贝 / 结果位置直写）进不进同批**？我的建议：**不进**（先正确性，后速度）。

### 8.1 `probe-aggregate-copies.pini`（① ② ③ + 返回）

```pini
; 探针：值类型拷贝规则（G-2R）的四个位置，在原生路径上各是什么状态
; 解释器为权威；每行注释写解释器期望值
(点)
x: I32 = 0

(盒)
p: 点 = 点()
n: I32 = 0

造点|func(v: I32,) -> (点,):
    var q = 点()
    q.x = v
    return q

main|func() -> ():
    ; ① allocVar：期望 1 2
    var a = 点()
    a.x = 1
    var b = a
    b.x = 2
    print("ALLOC \(a.x,) \(b.x,)")

    ; ② storeVar：期望 3 4
    var c = 点()
    c.x = 3
    var d = 点()
    d = c
    d.x = 4
    print("STORE \(c.x,) \(d.x,)")

    ; ③ fieldStore：期望 5
    var h = 盒()
    h.p = 造点(5,)
    h.p.x = 9
    let got = h.p
    print("FIELD \(got.x,)")

    ; ④ 形参绑定：期望共享（现状两路一致）
    print("RETURN \(造点(7,).x,)")
```

**实测**：解释器 `ALLOC 1 2` / `STORE 3 4` / `FIELD 9` / `RETURN 7`；
原生 `ALLOC 2 2` / `STORE 4 4` / `FIELD -255950760` / `RETURN 7`。

### 8.2 `probe-aggregate-shares.pini`（共享边界：赋值 / 形参 / 传入再返回 / 两次调用）

```pini
; 探针二：结构体在各位置上的「共享 / 拷贝」边界（解释器为权威）
(盒)
v: I32 = 0

取盒|func(b: 盒,) -> (盒,):
    return b

过手|func(b: 盒,) -> (I32,):
    b.v = 50
    return b.v

main|func() -> ():
    ; ① 赋值：期望值语义（1）
    var a = 盒()
    a.v = 1
    var b = a
    b.v = 2
    print("A-ASSIGN \(a.v,) \(b.v,)")

    ; ② 形参内改写：期望值语义则 3；共享则 50
    var c = 盒()
    c.v = 3
    var viaParam = 过手(c,)
    print("C-AFTER-PARAM \(c.v,) VIA \(viaParam,)")

    ; ③ 参数传入再返回：期望值语义则 7；共享则 9
    var d = 盒()
    d.v = 7
    var back = 取盒(d,)
    back.v = 9
    print("D-AFTER-RETURN \(d.v,)")

    ; ④ 返回值自身别名：期望值语义则 11
    var one = 取盒(d,)
    var two = 取盒(d,)
    two.v = 11
    print("ONE \(one.v,)")
```

**实测**：解释器 `A-ASSIGN 1 2` / `C-AFTER-PARAM 50 VIA 50` / `D-AFTER-RETURN 7` / `ONE 7`；
原生 `A-ASSIGN 2 2` / `C-AFTER-PARAM 50 VIA 50` / `D-AFTER-RETURN 9` / `ONE 11`。

⚠️ 两处表层语法注意（写这类探针时先看）：`let` 绑定**不可写字段**（`E4-010`，须用 `var`）；
结构体声明是**带括号的名字** +「字段行」（`(点)` / `x: I32 = 0`）。

## 9. 补测：外逃的边界（2026-10-01 同日）

### 9.1 五条外逃探针

统一骨架：被调方**在自帧内构造并返回**，调用方**先垫一次别的调用**再用它
（`垫栈|func()` 里放四个局部变量 —— 用它覆盖上一帧留下的内存）。`1110` = `垫栈` 的返回值，
它同时充当「后续活动真的发生过」的在场证明。

| 探针 | 形态 | 解释器（权威） | LLVM 原生 | 失败形态 |
|---|---|---|---|---|
| A | 结构体返回 | `A 7 1110` | `A -255950760 1110` | 垃圾值 |
| B | 结构体里**套结构体**（结构体字段） | `B 8 1110` | `B -229641480 1110` | 垃圾值 |
| C | **对象**返回 | `C 9 1110` | `C 1 1110` | 读到 `1`（疑似 refcount 头那格） |
| D | **带载荷枚举**返回后 `match` | `D 2.0 1110` | `match value matched no case` | 标签被覆盖 |
| E | **闭包捕获的变量**随闭包外逃 | `E2 101 666` | `E2 -255950759 666` | 垃圾值 |

### 9.2 同帧对照（把「外逃」与「通道本身有缺陷」分开）

同样的四类值，**构造与使用都在同一帧内**：

| 对照 | 读数 |
|---|---|
| A-ctl 结构体 | `A-ctl 7` —— 两路一致 ✅ |
| B-ctl 结构体套结构体 | `B-ctl 8` —— 两路一致 ✅ |
| C-ctl 对象 | `C-ctl 9` —— 两路一致 ✅ |
| D-ctl 枚举 `match` | `D-ctl 2.0` —— 两路一致 ✅ |
| E-ctl 闭包捕获（同帧调用） | `E-ctl 101` —— 两路一致 ✅ |

⇒ ⭐ **通道全部是好的；五条失败**全是**跨帧**造成**。这一条对照是本轮归因成立的关键：
没有它，D 的 `match no case` 会被读成「match 代码生成缺陷」（6.3 那处旧归因就是这么来的）。

### 9.3 订正后的模型与切片建议

**模型（一句话）**：**所有名义箱上堆 + 引用计数；四个值语义点（`allocVar` / `storeVar` /
`fieldStore` / `subscriptStore`）与返回路径做即时深拷贝；闭包捕获的变量装箱。**

| 片 | 内容 | 依赖 |
|---|---|---|
| **A · 表示与分配** | 结构体 / 枚举的箱加引用计数头（对象已有），分配改走运行时段 | — |
| **B · 寿命** | `retain` / `release` 插入：**复用容器那套既有位置**（别名点 retain · 作用域退出 release · 字段/变量写前 release 旧值）+ 每类型一份「释放胶水」（递归释放名义字段、归还容器字段） | A |
| **C · 值语义** | 四个点 + 返回按 `RuntimeOps.copyIfStruct` 的规则即时深拷贝（⛔ 不是 COW，理由见 §6.1） | A · B |
| **D · 捕获装箱** | 被捕获的变量槽上堆（闭包与帧共享同一盒） | A |
| **E · 判据** | §9.1 五条 + §9.2 五条对照进常跑集；每片一条只打自己的变异；自举全层两路对照 | 随各片 |

⚠️ **如实登记的代价与风险**：

- **释放错误比悬垂更难查**（`use-after-free` / 双释放可能表现为长跑后才崩）。⇒ 建议 A 片先落、
  跑一次**未定义符号差集**（比全量回归便宜三个数量级，见手则 §4.zd），再动 B 片的插入点。
- **布局变了**（结构体 / 枚举的字段索引整体后移一格）⇒ 所有字段 GEP、`match`、打印、给定块初始化、
  枚举载荷都要一起改，属**系统性**改动。
- **性能**：堆分配 + 计数开销；但这是**与解释器同阶**的代价（解释器本来就是 ARC + 装箱），
  而原生路径仍省掉整层树遍历解释。
- ⛔ **不要与「门禁提速」混读**：门禁接原生臂的前置仍是「自举各层两路读数一致」（`auth-73` scope ⑦），
  而本模型是那条前置的**实质内容**。

## 10. 旁支发现：`E3-008`（闭包捕获须声明）**只在解释路径生效**

写 E 探针时第一版没写 `capture` 行，两路的反应**不同**：

| 路径 | 反应 |
|---|---|
| `pini run`（解释） | ⛔ `Semantic Error [E3-008]`：外层变量 `k` 须经 `capture` 声明后使用 |
| `pini compile`（LLVM） | ✅ **照跑**（同帧变体印出 `E-ctl 101` 这个「正确」值） |

⚠️ **归因边界**：本批**未**追这条的成因（是检查器覆盖面差、还是 LLVM 入口少跑了一步检查，未测）；
但**读数确凿**：同一份源，一条路径拒、另一条路径接受。
⚠️ 这不是「后端各有分工」（语法/语义检查应在两路之前共用），属**检查覆盖面分叉**，
与语言规范台账里已登记的同类问题（`G77`「一个后端替另一个后端把缺陷兜住了」）**同族**。
