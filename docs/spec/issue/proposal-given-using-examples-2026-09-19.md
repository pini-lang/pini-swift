## 3. 示例

### 例 1 · 声明与取用（正典）— `given.pini`

```
; 演示：给定块（程序级单例）的声明、扩展与 using 取用
; 侧证：状态跨调用累积 —— 两次调用得到 1 和 2，证明是同一个实例
; 运行：pini run examples/given.pini
; 预期：1 / 2

[队列|object]
元素: [I32] = []

{{队列}}
推入|self(数据: I32,) -> ():
    self.元素 = self.元素.append(数据)
    return

[应用服务|given]
队列: 队列 = 队列()

[[应用服务]]
提交|self(数据: I32,) -> (I32,):
    self.队列.推入(数据)
    return len(self.队列.元素)

处理|func(using 应用: 应用服务, 数据: I32,) -> (I32,):
    return 应用.提交(数据)

main|func() -> ():
    print(处理(1,))
    print(处理(2,))
    return
```

**这一例演示三件事**：块头 `[名|given]`、扩展块 `[[名]]`、参数修饰符 `using 名: 类型名`。

**新语法只有三处**：`|given`、`|given` 块的字段、`using` 参数。`队列` 是普通 `object`，其余每一行都是现行写法。

**关键点**：`元素` 的可变发生在 `队列`（一个 `object`）里，**不在**给定块字段上 —— 这正是 D1 的形状。

**等价体实测**（`given` → `object`、`using` → 显式传参）：

```
[队列|object] 元素: [I32] = []
[应用服务|object] 队列: 队列 = 队列()
处理|func(应用: 应用服务, 数据: I32,) -> (I32,):
    return 应用.提交(数据)
main|func() -> ():
    let 服务 = 应用服务()
    print(处理(服务, 1,))
    print(处理(服务, 2,))
```

```
check OK
run → 1
      2
```

; 演示：给定块在首次访问时才构造；从未访问者从不构造（无启动风暴）
; 侧证：「审计：已打开」不出现 —— 该块从未被访问

               1

### 例 4 · 对照：参数传染 vs 取用（对照用，**不进** `examples/`）

这一例是 ADR「为什么要有 `using`」的论证材料，不是可运行示例 —— 它演示的是**两段代码的差**，不是某个运行时行为。

```
; 不用 given —— 资源实例逐层传递：每一层签名多一个参数，每个调用点多一个实参

记账|func(服务: 应用服务, 数额: I32,) -> ():
    服务.日志.写(数额)
    return

汇总|func(服务: 应用服务,) -> ():
    记账(服务, 1,)
    记账(服务, 2,)
    return

main|func() -> ():
    汇总(应用服务())
    return
```

```
; 用 given —— 签名只声明来源，调用点不传

记账|func(using 服务: 应用服务, 数额: I32,) -> ():
    服务.日志.写(数额)
    return

汇总|func(using 服务: 应用服务,) -> ():
    记账(1,)
    记账(2,)
    return

main|func() -> ():
    汇总()
    return
```

**差别恰好是**：`服务` 从**每一层签名**里消失，且每个**调用点**不再传它。`main` 里的 `应用服务()` 也消失 —— 这是 D2
（入口不带参数）与单例取用共同的结果。

**左栏等价体实测**（右栏是左栏去掉 `服务` 参数，等价体即左栏本身）：

```
check OK
run → [app]
      [app]
```

## 4. 哪些行依赖尚不存在的机制

把示例拆开，逐行标出「今天成不成立」，免得把三样东西混成一样：

| 写法 | 出现在 | 今天的实测结果 | 性质 |
|---|---|---|---|
| `using 名: 类型名` 参数 | 例 1/3/4 | `E2-005`（与不认识的修饰符同码） | **新语法** |
| `[名\|given]` 块头 | 例 1/2/3 | `E2-005`（同上） | **新语法** |
| `[[名]]` 扩展块 | 例 1/3 | 现行合法，按类型名挂载 | 照抄 ✓ |
| `名.字段`（类型名当值） | 例 3 | `E6-004 不支持的特性` | **新机制** |
| `main\|func() -> ()` | 全部 | 现行合法 | 照抄 ✓ |
| `[名\|object]` + 字段 + `{{名}}` | 例 1/4 | 现行合法 | 照抄 ✓ |

> 补充实测：给定块的扩展块**不需要新语法**。现行扩展块按类型名挂载、**不校验目标种类** ——
> `[[句柄]]` 挂在 `[句柄|object]` 上实跑通过，且同一目标可并挂 `[[X]]` 与 `{{X}}`。
> 这同时钉住一件事：给定块的扩展块**用哪个括号**都行，选择属风格问题，不是语法问题。

## 5. 订正与待裁点

> ⚠️ **本节 2026-09-19 第二轮已按用户裁决重写**。原 §5.1「类型名当值」的定性**有误**，已改正；
> 原 §5.2 的两选项已被裁掉一个（取「块种类隐含」）。凡与第二轮结论冲突的旧表述，以本节为准。

### 5.1 ✅ 已裁 · 给定块**默认绑定常量**（不是「类型名当值」）

**用户裁决**：不是「类型名当值」这种通用机制，而是**给定块声明默认绑定一个常量**。

⇒ 本件的定性据此改正。`[存储服务|given]` 一次声明产出**两个**名字：

| 命名空间 | 名字 | 含义 |
|---|---|---|
| 类型 | `存储服务` | 可用作类型标注（`using 应用: 存储服务`） |
| 值 | `存储服务` | 绑定到那个单例的**常量** |

这与 Scala 的 `object` 同构（类型 + 单例值同名）。

**这个改正让例 3 需要的机制变少了**：原先记的 `E6-004（类型名当值，不支持）` 应拆成两半 ——
**新机制只有「名称解析」那一半**（表达式位的裸名 `存储服务` 要能解析到常量）；
**取成员那一半走既有路径**，零新机制。佐证（实测）：

| 形态 | 今天 | 说明 |
|---|---|---|
| `let 配置 = 配置(); print(配置.名)` | → `x` ✓ | 名字是**局部变量** ⇒ 取成员走既有路径 |
| `print(配置.名)`（`配置` 是类型名） | → `E6-004` | 名字是**类型** ⇒ 解析不到值，取成员无从谈起 |

⇒ 差别**只在名字怎么解析**，不在成员访问本身。

**但带出一条硬约束（本轮新实测）**：顶层符号表是**单一命名空间**，类型名与值名会撞车。

```
[服务|object]
值: I32 = 1

服务|func() -> (I32,):      ; ← 同名顶层函数
    return 2
→ E3-004  redeclared symbol '服务'
```

而**局部**变量同名是允许的（`let 计数 = 计数()` → `7` ✓）。⇒ 常量绑定若与类型名同名，
现有顶层重声明检查会拒。**须为「类型 / 值」两个命名空间开一道口子**，或让给定块绑定走豁免。
这是本裁决的唯一落地成本，量级 = 顶层符号表加一层命名空间区分。

**另需裁**：常量可否被遮蔽 / 重绑？按「常量」定性，`存储服务 = 别的` 应当报 `E4-010`（与 `let` 同）。

### 5.2 ✅ 已裁 · 给定块字段不可变是**块种类隐含的**，不新增语法

**用户裁决**：天然不可变 —— 这就是上下文该有的设计。

⇒ 取原 §5.2 的 **A 方案**。`field-decl` 产生式 `IDENT ':' 类型 ['=' 表达式]` **不改**：
同一产生式在 `|given` 块内语义为「不可变字段」，在 object / struct 块内语义为「可变字段」（D1）。
语法面零变宽。

**兑付判据（必须写，否则 D1 不可验）**：给给定块字段赋值须报错。两个位置各一条负向用例：

```
[审计|given]
句柄: I32 = 1

main|func() -> ():
    审计.句柄 = 2            ; ① 经常量写字段 → 应报错
    return
```

```
[[审计]]
置|self(v: I32,) -> ():
    self.句柄 = v            ; ② 经 self 写字段 → 应报错（此路更易漏）
    return
```

② 是更尖锐的一例：今天 `self.字段 = ...` 是 object / struct 的**标准写法**，
给定块若只挡 ① 不挡 ②，不变性从扩展块就绕过去了。

### 5.3 ✅ 已查明 · 参数可变：不是「写错了」，是**这条规则从未写过**

**用户问**：「参数不应该可变，即便可变也是因为引用，而不是指引用的句柄可变，是写错了吗？」

分三层回答。

**① 规范层：零处规定。** `docs/` 全域检索「参数 + 不可变 / 只读」**零命中**；
规范、语言参考、`Pini草稿.md` 三处均无任何关于形参可变性的条款。
⇒ 所以不构成「违反某条规则」——**是这条规则不存在**。

**② 实现层：落在函数签名的默认值上，不是有意为之。**

```
TypeEnvironment.defineVariable(name:type:isMutable: Bool = true)      ← 默认 true
TypeChecker.checkFuncBody:
    for param in funcDecl.params:
        typeEnv.defineVariable(name: param.name, type: paramType)     ← 省略该参数 ⇒ 取默认 true
HIRExecutor（调用环境）:
    callEnv.define(name: name, value: args[index], isMutable: true)   ← 运行时同样按可变
```

对照：`var` / `let` 局部**显式**传 `isMutable`（`TypeChecker` 两处），
`self` 与字段也省略（那两处另当别论）。⇒ 参数是**顺着默认值漏进去的**。

**③ 用户描述的区分，实现里已经有了。** `TypeChecker` 对 `let` 绑定有按类型的豁免：

> 引用类型（object）的 `let` 仅约束引用本身、对象内容仍可变，须豁免；仅值类型（struct）整体不可变才拦截。

实测两条与用户表述一一对应：

| 用户表述 | 探针 | 今天 | D1 生效后应为 |
|---|---|---|---|
| 「指涉物可变」 | `改|func(c: 计数,)` 内 `c.加()` | ✅ 合法（外部可见 → `1 1`） | **不变**（走既有豁免） |
| 「句柄不可变」 | `换掉|func(c: 计数,)` 内 `c = 计数()` | ❌ 今日合法（→ `0`） | 应报 `E4-010` |

⇒ **把参数登记为不可变即可拿到用户描述的语义，零新机制**：
句柄不可重绑、指涉物照旧可改。

**④ 影响面已量化（本轮扫描）**：

| 范围 | 文件 | 带参函数 | 形参 | 参数重绑处数 |
|---|---|---|---|---|
| `examples/` + `Tests/` | 88 | 54 | 69 | **1** |
| `examples/selfhost/`（嵌套独立仓） | 19 | 107 | 197 | **0** |

唯一那处在 `examples/ffi_module/cstring.pini`，是一个**钳位惯用法**：

```
分配并写|func(值: I32,) -> (*U8,):
    if 值 < 0:
        值 = 0              ; ← 全仓唯一的参数重绑
```

⇒ 收紧的代价 = 该处改为函数首行 `var 值 = 值` 本地影子（或把钳位提到调用侧），**1 行**。

**⑤ 附带**：`self` 已经是不可重绑的（`self = 计数()` → **E2-007** 解析错），
所以参数是**唯一**漏网的绑定类别。

### 5.4 ⏳ 待裁 · 给定块该不该有 `self`（用户提出，需讨论）

用户：「按照语义，given 块可能不应该有 self，不太确定。」

先把它拆成**两个可独立回答**的问题，因为混在一起会得出错误结论。

#### (b) 先拆：体内写不写 `self.`？—— 与修饰符无关

实测 `|own` 方法体内**今天就能用 `self.字段`**（读 → `5`，写 → `9` 均通过）。
⇒ **选 `|own` 并不能去掉 `self`**。若真要「无 self」，要的是**隐式成员作用域**，代价两条：
① 给定块扩展将成为全语言**唯一**有隐式成员作用域的地方（其余一律显式 `self.`）；
② 需改文法 —— 规则 3.14 现在明令「扩展块内无修饰符的函数声明 → 报错」。

⇒ 建议 (b) 保持 `self.` 显式。

#### (a) 修饰符用 `|self` 还是 `|own`？—— 关键事实：**两者在实例上不可区分**

| 探针 | `|self` | `|own` |
|---|---|---|
| 读字段 `self.值` | ✅ | ✅（→ `5`） |
| 写字段 `self.值 = v` | ✅ | ✅（→ `9`） |
| 被实例调用 | ✅ | ✅ |
| 被类型名调用 | ❌ `E6-004` | ❌ `E6-004`（同因） |
| 同块内并存 | ✅ 可并存（→ `3` / `1`） | ✅ |

⇒ 修饰符在实现里是**纯声明位标记**，无强制能力差异。
而给定块**只有一个实例**、且该实例被绑成一个常量 ⇒「类型级」与「实例级」指向同一对象。

#### ✅ 已裁（D9，2026-09-19）：**两者同时保留** —— 常量就是 `self` 的指代

**用户裁决**：`|self` 与 `|own` **同时保留**，关键点在于 **given 会创建常量，这个常量就是它的 `self` 指代**。

⇒ 这条定性把两个修饰符**分开落到两个不同的东西上**：

| 修饰符 | 体内 `self` 是什么 | 需要实例吗 |
|---|---|---|
| `\|self` | **那个常量**（= 单例实例） | 需要 |
| `\|own` | 类型本身（与 enum 的 `\|own` 一致） | **不需要** |

**由此得到的可观察差异（这才是两者并存有意义的地方）**：

> `|self` 方法操作单例 ⇒ **触发惰性初始化**；
> `|own` 方法是类型级的、**不碰实例** ⇒ **不触发初始化**。

⚠️ 这条差异**与 ADR 的招牌卖点直接咬合**：ADR 论证的核心之一正是「未访问的给定块从不初始化」。
若 `|own` 也要实例，两个修饰符就**退化为同义词**（这正是我上一轮建议「留一废一」的依据）；
按 D9 保留两者，就必须让 `|own` **不碰实例**，否则保留无意义。

**⇒ 由此推出一项待裁**（记入 §5.5 第 ① 项）：`|own` 方法体内**是否可以使用 `self.字段`**？
实测今天是**可以**的（读 → `5` / 写 → `9`），但按 D9 的定性应为**不可** ——
否则 `|own` 拿到实例、触发初始化，两个修饰符的差异归零。

> 上一轮「留 `|self`、令 `|own` 报错」的建议**已被 D9 取代**，保留于此仅作决策痕迹。
> 其中三条理由仍需在 ADR 里回答（尤其「体内必须读字段」这条 —— 它现在变成
> **`|own` 方法能读什么**的问题，而不是「该不该有 `|own`」的问题）。

**反方（我推的最强版本，供否决）**：给定块可以**一个方法都没有** —— 上下文是纯数据，
操作一律写成带 `using` 的自由函数。概念上最干净，代价是给定块成为**唯一没有逻辑的复合类型**，
与「数据与逻辑分离」（每类复合类型都有扩展块）不对称。

#### (c) 同源的连带问题：给定块的扩展块该挂哪个括号？

实测现行扩展块**按名挂载、不校验目标种类**（`[[句柄]]` 挂 `[句柄|object]` 通过；
同目标可并挂 `[[X]]` 与 `{{X}}`）。⇒ 语法上 `((应用服务))` / `{{应用服务}}` / `[[应用服务]]` **全都合法**。
不给规则则风格失控。ADR 草案用的是 `[[…]]`（枚举括号）—— 与「类 enum 复合类型」的定性一致，
但需明文写进文法，否则它只是「恰好能用」。

## 5.5 剩余待讨论（第三轮提出，按「是否挡事」排序）

前两项由 D9 **直接推出**（不是新增议题，是那条裁决的必然后果）。

### ① ⭐ `|own` 方法能不能碰实例？（D9 的必然后果，最该先定）

见 §5.4 末。判据很清楚：**能碰 ⇒ 两个修饰符同义 ⇒ D9 的保留失去意义**。
若裁「不能碰」，则 `self.字段` 在 `|own` 体内应报错 —— 这需要一条新诊断（现有 `E4-009 无此成员`
语义不对，那是「成员不存在」，这里是「此上下文不可触实例」）。

### ② ⭐ 同名类型与常量 ⇒ 「经类型名取成员」必须消歧（D9 + D5 的合成后果）

D5 让类型与常量**同名**，于是 `应用服务.提交(数据)` 这一句**语法上同时是两种取用**：

| 若按**常量**解析 | 取到实例成员 ⇒ `\|self` 方法 / 字段 |
|---|---|
| 若按**类型**解析 | 取到类型级成员 ⇒ `\|own` 方法 |

⇒ **同名之下，成员种类决定走哪条路**，这必须写进消歧规则（不能靠「谁先找到」）。
今天两条路**都不通**（`色彩.名字()` 与 `计数.新建()` 均 `E6-004`），所以这是全新规则，
不是既有行为的选择。

> 这一项同时是「常量绑定」与「扩展块」两处设计的交汇点，**建议与 ① 同批裁**。

### ③ ⚠️ 间接成环：ADR 的 SCC 看不见（实测，本仓已有同类崩溃）

ADR 写「编译期检测给定块引用图的强连通分量。成环报错」。**但 SCC 只看得见字段引用。**
环若**经由函数体**绕回来，引用图上没有边，SCC 判不出：

```
建乙|func() -> (I32,):         ; ← 这个环靠函数体绕回来
    乙类型()
    return 1

[甲类型|object]
标记: I32 = 建乙()             ; 字段 → 函数

[乙类型|object]
标记: I32 = 甲类型().标记       ; 字段 → 另一个类型
```

**实测（用现有 `object` 同构复现）**：`check` 通过，`run` → **`rc=139`（SIGSEGV，栈溢出）**，
无任何诊断。而同结构的**直接**互引（`甲⇄乙`）在**构造它**时同样 `rc=139`。

⚠️ 对给定块而言，这个形态可能**更坏**：ADR 规定「首次访问仅一个执行流执行初始化，其他等待」
⇒ 初始化中途再次访问**同一个**给定块 = **等自己的初始化锁** ⇒ **死锁**（挂死而非崩）。
（此条是**按 ADR 设计推演**，非实测 —— 给定块尚无实现，如实标注。）

**另一件必须一起知道的事**：本仓**已经有**一份成环检测的规范，但**零实现**。
语言参考「循环检测」节声明 L1–L5 五层机制（L1 = 直接双向字段赋值 → 类型图强连通分量检测）与复杂度表，
**但 `Sources/` 全域无 SCC / tarjan，`E7` 段只有 2 个码（未使用变量 / 别名不一致），无环告警码**。
⇒ ADR 提议的这道 SCC 不会「接到既有设施上」，它将是本语言的**第一个**真正运行的环检测。
范围与验收须据此重估。

### ④ ⚠️ 与测试纪律直接对撞（用仓库自己的规矩）

`../pini-spec-v0.md` 的测试入口四项之二：**「测试执行顺序不保证，测试之间不得有顺序依赖」**；
测试规范「隔离与复用」：**「每测试独立自建 fixture、不依赖共享状态、自清理」**。

而给定块 = **程序级单例 + 惰性初始化 + 活到程序结束**，且（D5/D6 之后）**可变状态必然藏在它引用的
`object` 里** ⇒ **跨测试共享**。ADR 的未决问题 7「测试框架如何覆盖单例」正好落在这条冲突上，
但 ADR 没把它连到本仓既有纪律。

⚠️ **本件例 1 就是这个形状**（`[应用服务|given]` 内含可累积的 `[队列|object]`）：
作为 `examples/` 是可读的，但**若原样写进 `|test` 块，它就违反上面两条**（第一次跑与第二次跑结果不同）。

⇒ 须裁其一：**① 给定块提供测试期重置/重建通道** ② 测试内**禁止**触碰带可变状态的给定块
③ 明确豁免该纪律（须说明为何单例是例外）。

### ⑤ 给定块没有 teardown

惰性**初始化**有完整定义（时机 / 次数 / 原子性 / 递归检测），但**销毁零定义**：
持有文件句柄、连接、线程的给定块**什么时候关**？`defer` 是块作用域，套不上；
程序退出也没有钩子。须裁：**① 明确定义为「活到进程结束、不销毁」**（须同时说明资源如何释放）
② 引入退出期 teardown（则须定序：与初始化相反？失败如何处理？）。
⚠️ 本条对 ADR 的招牌用例（调度器 / 连接池 / 缓存）**不是边角** —— 它们是「必须释放」的资源。

### ⑥ `using` 可以降级为糖（可能是本批最大的一处范围收缩）

D5 之后，**任何函数都能直接写 `应用服务.提交(数据)`，不需要任何参数**。
于是 `using 应用: 应用服务` 实际只买两样东西：**① 签名自述**（依赖写在签名里）
**② 局部别名**（`应用` 比 `应用服务` 短）。它**不买能力** —— 按 ADR，解析是编译期按类型名做的、
无运行时查找 ⇒ **不是依赖注入**，不可替换、不可 mock。

⇒ 结论：**「无传染」是常量给的，不是 `using` 给的。** 故 `given` 与 `using` **可以分开落地**：
先落 `given`（承载全部价值），`using` 作为可选的书写糖随后。
这对 ADR 的代价表有直接影响 —— 关键字表加 2 个、参数产生式加修饰位，都可以推迟到第二步再付。

### ⑦ 文档面本身的待办（不挡设计，但要有主）

- **诊断码**：`using` 解析失败 / 环 / 写不可变字段，各归哪个段？现有 `E4-009`（无此成员）、
  `E4-010`（对 let 重赋值）覆盖不到「此上下文不可触实例」这类
- **稳定性分级**：`given` / `using` 落 Provisional 还是 Experimental？（决定能否随之递交语言参考）
- **顶层命名空间开口**（§5.1 的成本）会触及 `E3-004` 重声明检查的既有判据 —— 须一并评估回归面
