## 3. 示例

### 例 1 · 声明与取用（正典）— `given.pini`

```
; 演示：给定块（程序级单例）的声明、扩展与 using 取用
; 侧证：状态跨调用累积 —— 两次调用得到 1 和 2，证明是同一个实例
; 运行：pini run examples/given.pini
; 预期：1 / 2

[队列|object]
元素: [I32] = []

{{队列}}
推入|self(数据: I32,) -> ():
    self.元素 = self.元素.append(数据)
    return

[应用服务|given]
队列: 队列 = 队列()

[[应用服务]]
提交|self(数据: I32,) -> (I32,):
    self.队列.推入(数据)
    return len(self.队列.元素)

处理|func(using 应用: 应用服务, 数据: I32,) -> (I32,):
    return 应用.提交(数据)

main|func() -> ():
    print(处理(1,))
    print(处理(2,))
    return
```

**这一例演示三件事**：块头 `[名|given]`、扩展块 `[[名]]`、参数修饰符 `using 名: 类型名`。

**新语法只有三处**：`|given`、`|given` 块的字段、`using` 参数。`队列` 是普通 `object`，其余每一行都是现行写法。

**关键点**：`元素` 的可变发生在 `队列`（一个 `object`）里，**不在**给定块字段上 —— 这正是 D1 的形状。

**等价体实测**（`given` → `object`、`using` → 显式传参）：

```
[队列|object] 元素: [I32] = []
[应用服务|object] 队列: 队列 = 队列()
处理|func(应用: 应用服务, 数据: I32,) -> (I32,):
    return 应用.提交(数据)
main|func() -> ():
    let 服务 = 应用服务()
    print(处理(服务, 1,))
    print(处理(服务, 2,))
```

```
check OK
run → 1
      2
```

```
; 演示：给定块在首次访问时才构造；从未访问者从不构造（无启动风暴）
; 侧证：「审计：已打开」不出现 —— 该块从未被访问
```

### 例 4 · 对照：参数传染 vs 取用（对照用，**不进** `examples/`）

这一例是 ADR「为什么要有 `using`」的论证材料，不是可运行示例 —— 它演示的是**两段代码的差**，不是某个运行时行为。

```
; 不用 given —— 资源实例逐层传递：每一层签名多一个参数，每个调用点多一个实参

记账|func(服务: 应用服务, 数额: I32,) -> ():
    服务.日志.写(数额)
    return

汇总|func(服务: 应用服务,) -> ():
    记账(服务, 1,)
    记账(服务, 2,)
    return

main|func() -> ():
    汇总(应用服务())
    return
```

```
; 用 given —— 签名只声明来源，调用点不传

记账|func(using 服务: 应用服务, 数额: I32,) -> ():
    服务.日志.写(数额)
    return

汇总|func(using 服务: 应用服务,) -> ():
    记账(1,)
    记账(2,)
    return

main|func() -> ():
    汇总()
    return
```

**差别恰好是**：`服务` 从**每一层签名**里消失，且每个**调用点**不再传它。`main` 里的 `应用服务()` 也消失 —— 这是 D2
（入口不带参数）与单例取用共同的结果。

**左栏等价体实测**（右栏是左栏去掉 `服务` 参数，等价体即左栏本身）：

```
check OK
run → [app]
      [app]
```

## 4. 哪些行依赖尚不存在的机制

把示例拆开，逐行标出「今天成不成立」，免得把三样东西混成一样：

| 写法 | 出现在 | 今天的实测结果 | 性质 |
|---|---|---|---|
| `using 名: 类型名` 参数 | 例 1/3/4 | `E2-005`（与不认识的修饰符同码） | **新语法** |
| `[名\|given]` 块头 | 例 1/2/3 | `E2-005`（同上） | **新语法** |
| `[[名]]` 扩展块 | 例 1/3 | 现行合法，按类型名挂载 | 照抄 ✓ |
| `名.字段`（类型名当值） | 例 3 | `E6-004 不支持的特性` | **新机制** |
| `main\|func() -> ()` | 全部 | 现行合法 | 照抄 ✓ |
| `[名\|object]` + 字段 + `{{名}}` | 例 1/4 | 现行合法 | 照抄 ✓ |

> 补充实测：给定块的扩展块**不需要新语法**。现行扩展块按类型名挂载、**不校验目标种类** ——
> `[[句柄]]` 挂在 `[句柄|object]` 上实跑通过，且同一目标可并挂 `[[X]]` 与 `{{X}}`。
> 这同时钉住一件事：给定块的扩展块**用哪个括号**都行，选择属风格问题，不是语法问题。

## 5. 订正与待裁点

> ⚠️ **本节 2026-09-19 第二轮已按用户裁决重写**。原 §5.1「类型名当值」的定性**有误**，已改正；
> 原 §5.2 的两选项已被裁掉一个（取「块种类隐含」）。凡与第二轮结论冲突的旧表述，以本节为准。

### 5.1 ✅ 已裁 · 给定块**默认绑定常量**（不是「类型名当值」）

**用户裁决**：不是「类型名当值」这种通用机制，而是**给定块声明默认绑定一个常量**。

⇒ 本件的定性据此改正。`[存储服务|given]` 一次声明产出**两个**名字：

| 命名空间 | 名字 | 含义 |
|---|---|---|
| 类型 | `存储服务` | 可用作类型标注（`using 应用: 存储服务`） |
| 值 | `存储服务` | 绑定到那个单例的**常量** |

这与 Scala 的 `object` 同构（类型 + 单例值同名）。

**这个改正让例 3 需要的机制变少了**：原先记的 `E6-004（类型名当值，不支持）` 应拆成两半 ——
**新机制只有「名称解析」那一半**（表达式位的裸名 `存储服务` 要能解析到常量）；
**取成员那一半走既有路径**，零新机制。佐证（实测）：

| 形态 | 今天 | 说明 |
|---|---|---|
| `let 配置 = 配置(); print(配置.名)` | → `x` ✓ | 名字是**局部变量** ⇒ 取成员走既有路径 |
| `print(配置.名)`（`配置` 是类型名） | → `E6-004` | 名字是**类型** ⇒ 解析不到值，取成员无从谈起 |

⇒ 差别**只在名字怎么解析**，不在成员访问本身。

**但带出一条硬约束（本轮新实测）**：顶层符号表是**单一命名空间**，类型名与值名会撞车。

```
[服务|object]
值: I32 = 1

服务|func() -> (I32,):      ; ← 同名顶层函数
    return 2
→ E3-004  redeclared symbol '服务'
```

而**局部**变量同名是允许的（`let 计数 = 计数()` → `7` ✓）。⇒ 常量绑定若与类型名同名，
现有顶层重声明检查会拒。**须为「类型 / 值」两个命名空间开一道口子**，或让给定块绑定走豁免。
这是本裁决的唯一落地成本，量级 = 顶层符号表加一层命名空间区分。

**另需裁**：常量可否被遮蔽 / 重绑？按「常量」定性，`存储服务 = 别的` 应当报 `E4-010`（与 `let` 同）。

### 5.2 ✅ 已裁 · 给定块字段不可变是**块种类隐含的**，不新增语法

**用户裁决**：天然不可变 —— 这就是上下文该有的设计。

⇒ 取原 §5.2 的 **A 方案**。`field-decl` 产生式 `IDENT ':' 类型 ['=' 表达式]` **不改**：
同一产生式在 `|given` 块内语义为「不可变字段」，在 object / struct 块内语义为「可变字段」（D1）。
语法面零变宽。

**兑付判据（必须写，否则 D1 不可验）**：给给定块字段赋值须报错。两个位置各一条负向用例：

```
[审计|given]
句柄: I32 = 1

main|func() -> ():
    审计.句柄 = 2            ; ① 经常量写字段 → 应报错
    return
```

```
[[审计]]
置|self(v: I32,) -> ():
    self.句柄 = v            ; ② 经 self 写字段 → 应报错（此路更易漏）
    return
```

② 是更尖锐的一例：今天 `self.字段 = ...` 是 object / struct 的**标准写法**，
给定块若只挡 ① 不挡 ②，不变性从扩展块就绕过去了。

### 5.3 ✅ 已查明 · 参数可变：不是「写错了」，是**这条规则从未写过**

**用户问**：「参数不应该可变，即便可变也是因为引用，而不是指引用的句柄可变，是写错了吗？」

分三层回答。

**① 规范层：零处规定。** `docs/` 全域检索「参数 + 不可变 / 只读」**零命中**；
规范、语言参考、`Pini草稿.md` 三处均无任何关于形参可变性的条款。
⇒ 所以不构成「违反某条规则」——**是这条规则不存在**。

**② 实现层：落在函数签名的默认值上，不是有意为之。**

```
TypeEnvironment.defineVariable(name:type:isMutable: Bool = true)      ← 默认 true
TypeChecker.checkFuncBody:
    for param in funcDecl.params:
        typeEnv.defineVariable(name: param.name, type: paramType)     ← 省略该参数 ⇒ 取默认 true
HIRExecutor（调用环境）:
    callEnv.define(name: name, value: args[index], isMutable: true)   ← 运行时同样按可变
```

对照：`var` / `let` 局部**显式**传 `isMutable`（`TypeChecker` 两处），
`self` 与字段也省略（那两处另当别论）。⇒ 参数是**顺着默认值漏进去的**。

**③ 用户描述的区分，实现里已经有了。** `TypeChecker` 对 `let` 绑定有按类型的豁免：

> 引用类型（object）的 `let` 仅约束引用本身、对象内容仍可变，须豁免；仅值类型（struct）整体不可变才拦截。

实测两条与用户表述一一对应：

| 用户表述 | 探针 | 今天 | D1 生效后应为 |
|---|---|---|---|
| 「指涉物可变」 | `改|func(c: 计数,)` 内 `c.加()` | ✅ 合法（外部可见 → `1 1`） | **不变**（走既有豁免） |
| 「句柄不可变」 | `换掉|func(c: 计数,)` 内 `c = 计数()` | ❌ 今日合法（→ `0`） | 应报 `E4-010` |

⇒ **把参数登记为不可变即可拿到用户描述的语义，零新机制**：
句柄不可重绑、指涉物照旧可改。

**④ 影响面已量化（本轮扫描）**：

| 范围 | 文件 | 带参函数 | 形参 | 参数重绑处数 |
|---|---|---|---|---|
| `examples/` + `Tests/` | 88 | 54 | 69 | **1** |
| `examples/selfhost/`（嵌套独立仓） | 19 | 107 | 197 | **0** |

唯一那处在 `examples/ffi_module/cstring.pini`，是一个**钳位惯用法**：

```
分配并写|func(值: I32,) -> (*U8,):
    if 值 < 0:
        值 = 0              ; ← 全仓唯一的参数重绑
```

⇒ 收紧的代价 = 该处改为函数首行 `var 值 = 值` 本地影子（或把钳位提到调用侧），**1 行**。

**⑤ 附带**：`self` 已经是不可重绑的（`self = 计数()` → **E2-007** 解析错），
所以参数是**唯一**漏网的绑定类别。

### 5.4 ⏳ 待裁 · 给定块该不该有 `self`（用户提出，需讨论）

用户：「按照语义，given 块可能不应该有 self，不太确定。」

先把它拆成**两个可独立回答**的问题，因为混在一起会得出错误结论。

#### (b) 先拆：体内写不写 `self.`？—— 与修饰符无关

实测 `|own` 方法体内**今天就能用 `self.字段`**（读 → `5`，写 → `9` 均通过）。
⇒ **选 `|own` 并不能去掉 `self`**。若真要「无 self」，要的是**隐式成员作用域**，代价两条：
① 给定块扩展将成为全语言**唯一**有隐式成员作用域的地方（其余一律显式 `self.`）；
② 需改文法 —— 规则 3.14 现在明令「扩展块内无修饰符的函数声明 → 报错」。

⇒ 建议 (b) 保持 `self.` 显式。

#### (a) 修饰符用 `|self` 还是 `|own`？—— 关键事实：**两者在实例上不可区分**

| 探针 | `|self` | `|own` |
|---|---|---|
| 读字段 `self.值` | ✅ | ✅（→ `5`） |
| 写字段 `self.值 = v` | ✅ | ✅（→ `9`） |
| 被实例调用 | ✅ | ✅ |
| 被类型名调用 | ❌ `E6-004` | ❌ `E6-004`（同因） |
| 同块内并存 | ✅ 可并存（→ `3` / `1`） | ✅ |

⇒ 修饰符在实现里是**纯声明位标记**，无强制能力差异。
而给定块**只有一个实例**、且该实例被绑成一个常量 ⇒「类型级」与「实例级」指向同一对象。

#### ✅ 已裁（D9，2026-09-19）：**两者同时保留** —— 常量就是 `self` 的指代

**用户裁决**：`|self` 与 `|own` **同时保留**，关键点在于 **given 会创建常量，这个常量就是它的 `self` 指代**。

⇒ 这条定性把两个修饰符**分开落到两个不同的东西上**：

| 修饰符 | 体内 `self` 是什么 | 需要实例吗 |
|---|---|---|
| `\|self` | **那个常量**（= 单例实例） | 需要 |
| `\|own` | 类型本身（与 enum 的 `\|own` 一致） | **不需要** |

**由此得到的可观察差异（这才是两者并存有意义的地方）**：

> `|self` 方法操作单例 ⇒ **触发惰性初始化**；
> `|own` 方法是类型级的、**不碰实例** ⇒ **不触发初始化**。

⚠️ 这条差异**与 ADR 的招牌卖点直接咬合**：ADR 论证的核心之一正是「未访问的给定块从不初始化」。
若 `|own` 也要实例，两个修饰符就**退化为同义词**（这正是我上一轮建议「留一废一」的依据）；
按 D9 保留两者，就必须让 `|own` **不碰实例**，否则保留无意义。

**⇒ 由此推出一项待裁**（记入 §5.5 第 ① 项）：`|own` 方法体内**是否可以使用 `self.字段`**？
实测今天是**可以**的（读 → `5` / 写 → `9`），但按 D9 的定性应为**不可** ——
否则 `|own` 拿到实例、触发初始化，两个修饰符的差异归零。

> 上一轮「留 `|self`、令 `|own` 报错」的建议**已被 D9 取代**，保留于此仅作决策痕迹。
> 其中三条理由仍需在 ADR 里回答（尤其「体内必须读字段」这条 —— 它现在变成
> **`|own` 方法能读什么**的问题，而不是「该不该有 `|own`」的问题）。

**反方（我推的最强版本，供否决）**：给定块可以**一个方法都没有** —— 上下文是纯数据，
操作一律写成带 `using` 的自由函数。概念上最干净，代价是给定块成为**唯一没有逻辑的复合类型**，
与「数据与逻辑分离」（每类复合类型都有扩展块）不对称。

#### (c) 同源的连带问题：给定块的扩展块该挂哪个括号？

实测现行扩展块**按名挂载、不校验目标种类**（`[[句柄]]` 挂 `[句柄|object]` 通过；
同目标可并挂 `[[X]]` 与 `{{X}}`）。⇒ 语法上 `((应用服务))` / `{{应用服务}}` / `[[应用服务]]` **全都合法**。
不给规则则风格失控。ADR 草案用的是 `[[…]]`（枚举括号）—— 与「类 enum 复合类型」的定性一致，
但需明文写进文法，否则它只是「恰好能用」。

## 5.5 剩余待讨论（第三轮提出，按「是否挡事」排序）

前两项由 D9 **直接推出**（不是新增议题，是那条裁决的必然后果）。

### ① ✅ 已裁（2026-09-19）：`|own` 内**不得**使用 `self` 指代 —— 现行为是**错误行为**

**用户裁决**：`|own` 内期望不可使用 `self` 指代，**这是错误的行为**。

⇒ 与 D9 的定性一致（`|own` 是类型级、不该碰到实例），裁决明确为「**拒绝**」。

**⚠️ 但实测显示这不是给定块特有的问题，而是既有语言缺陷。** `|own` 在**三种复合类型**上都能用 `self`：

| 类型 | 探针 | check | run |
|---|---|---|---|
| `object` | `读|own() -> (I32,): return self.值` | OK | → `5` |
| `struct` | `读|own() -> (I32,): return self.x` | OK | → `7` |
| `enum` | `读|own() -> (I32,): return self.红` | OK | 调用点 `E6-004`（与 `self` 无关） |

写字段同样可以（`|own` 体内 `self.值 = v` → `9` 通过，见 §5.4 表）。
⇒ **`|own` 的规范语义（「本型方法 / 类型级方法」）在实现里没有落实**：
它今天是 `|self` 的同义标记，只不过恰好能经实例调用。

**因此本条的意义超出 given**：给定块只是**第一个**会因此出错的地方
（因为只有它的单例要求 `|own` 真做到「不碰实例、不触发初始化」）。
⇒ 处置建议：**按既有缺陷单独立案**（覆盖 object / struct / enum 三类），
不要塞进 given 的批次里 —— 否则 given 落地时会牵动三种既有类型的回归面。

**诊断码**：需要新码。现有 `E4-009 无此成员`（「成员不存在」）与
`E4-010`（「对 let 重赋值」）都**语义不符** —— 这里是「此上下文不可触实例」。

### ② ⭐ 同名类型与常量 ⇒ 「经类型名取成员」必须消歧（D9 + D5 的合成后果）

D5 让类型与常量**同名**，于是 `应用服务.提交(数据)` 这一句**语法上同时是两种取用**：

| 若按**常量**解析 | 取到实例成员 ⇒ `\|self` 方法 / 字段 |
|---|---|
| 若按**类型**解析 | 取到类型级成员 ⇒ `\|own` 方法 |

⇒ **同名之下，成员种类决定走哪条路**，这必须写进消歧规则（不能靠「谁先找到」）。
今天两条路**都不通**（`色彩.名字()` 与 `计数.新建()` 均 `E6-004`），所以这是全新规则，
不是既有行为的选择。

> 这一项同时是「常量绑定」与「扩展块」两处设计的交汇点，**建议与 ① 同批裁**。

### ③ ⚠️ 间接成环：ADR 的 SCC 看不见（实测）

ADR 写「编译期检测给定块引用图的强连通分量。成环报错」。**但 SCC 只看得见字段引用。**
环若**经由函数体**绕回来，引用图上没有边，SCC 判不出：

```
建乙|func() -> (I32,):         ; ← 这个环靠函数体绕回来
    乙类型()
    return 1

[甲类型|object]
标记: I32 = 建乙()             ; 字段 → 函数

[乙类型|object]
标记: I32 = 甲类型().标记       ; 字段 → 另一个类型
```

**实测（用现有 `object` 同构复现）**：`check` 通过，`run` → **`rc=139`（SIGSEGV，栈溢出）**，
无任何诊断。而同结构的**直接**互引（`甲⇄乙`）在**构造它**时同样 `rc=139`。

⚠️ 对给定块而言，这个形态可能**更坏**：ADR 规定「首次访问仅一个执行流执行初始化，其他等待」
⇒ 初始化中途再次访问**同一个**给定块 = **等自己的初始化锁** ⇒ **死锁**（挂死而非崩）。
（此条是**按 ADR 设计推演**，非实测 —— 给定块尚无实现，如实标注。）

> ⚠️ **不要引用语言参考的「循环检测」节当依托**（2026-09-19 用户指令）。
> 环检测**尚未落实** —— 拿它做论据会把「纸面条款」读成「已有设施」。
> `Sources/` 全域无 SCC / tarjan、`E7` 段无环告警码，这两条是**本轮实测**，
> 只用于说明「现在没有」，**不用于推论「将来该长什么样」**。
> ⇒ ADR 若提 SCC，须当作**从零新建**来评估范围与验收，不得按「接既有设施」估工。

### ④ ⚠️ 与测试纪律直接对撞（用仓库自己的规矩）

`../pini-spec-v0.md` 的测试入口四项之二：**「测试执行顺序不保证，测试之间不得有顺序依赖」**；
测试规范「隔离与复用」：**「每测试独立自建 fixture、不依赖共享状态、自清理」**。

而给定块 = **程序级单例 + 惰性初始化 + 活到程序结束**，且（D5/D6 之后）**可变状态必然藏在它引用的
`object` 里** ⇒ **跨测试共享**。ADR 的未决问题 7「测试框架如何覆盖单例」正好落在这条冲突上，
但 ADR 没把它连到本仓既有纪律。

⚠️ **本件例 1 就是这个形状**（`[应用服务|given]` 内含可累积的 `[队列|object]`）：
作为 `examples/` 是可读的，但**若原样写进 `|test` 块，它就违反上面两条**（第一次跑与第二次跑结果不同）。

**⚠️ 而且这条冲突不是「有可能」，是结构上的必然**（2026-09-19 实测实现）：

```
ProgramRunner.runCollectedTests:
    let executor = HIRExecutor(...)        ; ← 只创建一次
    try executor.prepare(module: module)
    for function in module.functions where function.isTest {
        results.append(runOneTest(function, on: executor))   ; ← 循环里复用同一个 executor
    }

runOneTest(_:on:) 体内：只做 args 注入 + callFunction —— 不重置任何状态
```

⇒ **所有 `|test` 共用同一个 `executor` 实例、且单条测试之间不重置状态。**
给定块的惰性初始化标记若挂在执行器（或其持有的运行时状态）上，
则**同一进程内所有测试共用一个单例** —— 测试互相污染是**结构决定**的，不是用例写法问题。

⇒ 须裁其一：**① 给定块提供测试期重置/重建通道** ② 测试内**禁止**触碰带可变状态的给定块
③ 明确豁免该纪律（须说明为何单例是例外）。

> 附：今天的 Pini **没有任何**程序级可变状态手段（顶层 `定` 不能被函数体引用，实测 `E3-001`）
> ⇒ 无法用现有语言构造复现这条冲突 —— 给定块引入的是一个**全新的**共享状态面，
> 所以这条冲突是随它一起进来的，不是既有的。

### ⑤ ✅ 已裁（D15，2026-09-19）：给定块的**终结不可判定**（见 §5.6 专论）

惰性**初始化**有完整定义（时机 / 次数 / 原子性 / 递归检测），**终结零定义**。
D15 的裁决是：**不去定义它** —— 因为定义它需要「调用侧不再调用」这个不可得的判据。
→ 展开见下节 §5.6（已按此重写，我上轮的推荐已撤回）。

### ⑥ ✅ 已修正（2026-09-19）：`using` 买的是**参数表的来源区分**，不是签名自述

**我上一轮的定性偏了。** 我写「using 只买签名自述 + 局部别名，不买能力」，据此建议降级为糖。
用户的解释纠正了这一点，而且理由比我给的更本质：

> 「因为 given 成块，只需要 using 一个块就可以了，至于需要为多个参数标记 using，那是**必要的噪音**，
> **函数本身的参数非常一致地从调用点传入，只不过编译器帮忙插入了 using 部分**。」

**正确的定性**：语言的设计要求是**「函数的全部输入都写在同一个参数表里」**——这一点对
**两类来源都成立**：普通参数从调用点传入，`using` 参数由编译器插入。
`using` 的作用是**把「编译器插入的那部分」标出来**，从而在**保持参数表完整**的前提下区分来源。

⇒ 因此它**不是糖**：
- **不是**「省略了实参的普通参数」——省略会破坏「全部输入都在签名里」这条不变式；
- **不是**子句（如 `[using]` 块）—— 块形式会与 `given` 的块形式重复，而取用本就没有「声明」性质；
  且会引入第二处需要维护的清单（块里写的名字 vs 参数表里的名字，两份必然漂移）。
- **必要噪音**是正确的代价判断：一个参数一个标记，换来的是**每个参数的来源各自可见**。

**对我原判断的影响**（如实记账）：
- 「**「无传染」是常量给的，不是 `using` 给的**」—— 这句**仍然成立**（常量在，直连取用就通）；
- 「**using 可以降级为糖**」—— 这句**撤回**。它与 ADR 的前提修正直接相关：
  常量让依赖**全局可达**，而 `using` 让依赖**在签名里明文可读** ——
  这正是把「隐式全局状态」拉回「可推理」的那一步。故它不是可省的美化，是**可推理性的载体**。
- 「**两者可分步落地**」—— **仍然成立**，但理由要改：不是因为 `using` 可省，
  而是因为它是**纯增量**（先落 given 时，参数表没有混合来源，不存在「来源不清」的问题；
  `using` 落地后再表达来源区分）。⇒ 仍是降风险的分步，只是不能拿「可省」当理由。

#### ✅ 已裁（D14，2026-09-19）：`using` 是**强制**的

**用户裁决与理由**：「using 是强制的，此语言的函数的纯度相当高——尽管大多是弱纯。」

⇒ **强制**的含义：**函数体内值位引用了某给定块常量 ⇒ 签名必须声明对应的 `using` 参数，否则报错。**

**判据须区分两个位**（与初始化触发判据同源，见 §5.6 零）：

| 位置 | 例 | 算依赖？ |
|---|---|---|
| **值位** | `应用服务.提交(数据)` | ✅ 须声明 `using`（且**触发初始化**） |
| **类型位** | 类型标注里的 `服务: 应用服务` | ❌ 不算依赖（不触发初始化，也不构成运行时输入） |

**三项配套必须一并定义**（缺一条则规则不完备）：

1. **入口豁免**：`main` 无调用点（D2 裁入口不带参数）⇒ **参数插入者不存在** ⇒ 规则对 `main` 不适用。
   建议明文写为「`main` 视为已隐式声明全部给定块」，而不是留作未写明的例外。
2. **扩展块方法的来源**：`|self` 方法体内的 `self` 是**已声明的实例来源**（不算隐式依赖）；
   但方法体若访问**别的**给定块常量，同样受本规则约束 ⇒ 须裁：扩展块方法的参数表**是否允许 `using`**
   （建议允许，与自由函数同规；否则方法将无法合法访问第二个给定块）。
3. **传递规则**：`f(using A)` 体内调用 `g(using A)` ⇒ 编译器可插入，合法；
   而 `f` **未**声明 A 却调用 `g(using A)` ⇒ 编译器无处插入 ⇒ **报错**（f 的签名缺 A）。

**⚠️ 由此必须修正 ADR 的「无传染」卖点。** ADR 后果表写着「无传染」，在强制之下这不准确：

| 说法 | 准确性 |
|---|---|
| 「无传染」 | ❌ 过度承诺 —— 每层都得写 `using 服务: 应用服务`，签名面确实被占用 |
| 「**无实参传染**」 | ✅ 准确 —— 调用点不必逐层传参，但**签名须逐层声明** |

⇒ 这正是 D10「**必要的噪音**」的准确含义：**传染没有消除，只是从实参位移到了签名位。**
ADR 的代价表须据此改词。

**关于「纯度」**：实测全仓检索 —— 「纯度 / 弱纯 / 纯函数」在规范、参考、术语表中**零登记**
（`纯` 只出现在「纯值类型结构体」与挂起模式的「已执行副作用不重跑」两处，均与本意无关）。
**但本条不需要它当判据**：按 §5.5 ④ 附注的实测，今天的 Pini **没有任何**程序级可变状态手段
（顶层 `定` 不能被函数体引用 → `E3-001`）⇒ **给定块常量是函数唯一的隐式运行时依赖通道**。
把这条通道锁进签名，函数的**依赖面即封闭**，无需独立的「纯度」概念。
「弱纯」那句仍然准确，但它说的是**效应面**（`print` / I/O / 时间 / 随机）——
那不属「输入来源」，`using` 不该也不必覆盖。**两个面分开，规则才完备。**

### ⑦ 文档面本身的待办（不挡设计，但要有主）

- **诊断码**：`using` 解析失败 / 环 / 写不可变字段，各归哪个段？现有 `E4-009`（无此成员）、
  `E4-010`（对 let 重赋值）覆盖不到「此上下文不可触实例」这类

- **顶层命名空间开口**（§5.1 的成本）会触及 `E3-004` 重声明检查的既有判据 —— 须一并评估回归面

## 5.6 专论：给定块的寿命（用户提问，2026-09-19；**已按 D15 重写**）

> **问题（用户原话）**：「给定块必须与程序生命周期一样长是正确的吗？请你讨论。」

### 零、✅ 已裁（D15，2026-09-19 四轮）：生命周期**不可判定**

**用户裁决（原话）**：
> 「无法确定 given 常量的生命周期，因为这需要运行时确定调用侧不再调用 given 常量，
> 那就引发了自相矛盾的检查，又要它活得久，又要清理它。
> 好消息是惰性构造和调用时触发是确定的。」

**这条论证比我上轮列的三条代价更根本，它直接否掉了我推荐的那条路。** 展开：

- **终结的安全性前提 = 「此后不再有任何调用」**。这个前提**既不可静态判定**
  （常量是编译期绑定，名字恒可见），**也不可运行时判定**（引用计数恒 ≥ 1，见下「二·3」；
  此外还有多线程、已注册回调、经 FFI 传出的指针等调用路径）。
- ⇒ 任何**自动**终结都必须先证明这个前提。而「证明它」正是
  **「又要它活得久（全程可调用），又要清理它（此后不可调用）」** —— 用户指出的自相矛盾。
- ⇒ 结论：**「同寿命」不是三个选项里的最优解，而是唯一不需要判据的解**；
  同时，语言**不提供自动终结**。

> ⚠️ **我上轮推荐「A · 结束期有序终结」由此撤回。** 撤回理由不是「时点难定」（那是我上轮写的表象），
> 而是更根本的一条：**A 仍是自动方案，仍需要那个不可得的判据**。
> 时点不确定（代价 2）只是它的症状，不是它的病根。

### 一、先把「已有的隐含承诺」说清楚

ADR 已经写了「地址稳定性降级为『**首次访问后不变**』」。
**不销毁是这句话的前提** —— 一旦能销毁，地址就会变（或更坏：常量指向已销毁的对象）。
⇒ 所以「同寿命」不是本次新加的决定，而是 ADR 里一个**从未写出来的承诺**。
提问切中要害：一条影响资源语义的承诺，不该只以「地址稳定」的形式间接存在。

### 二、为什么「同寿命」是默认（三条；第 3 条现为**不可判定**的机制证据）

1. **程序级资源本该全程序共享** —— 调度器、连接池、缓存的用途就是这个。
2. **惰性契约已经蕴含它**：首次访问后才构造、构造恰一次、地址此后不变 ⇒ 语义上已经「不销毁」了。
3. ⭐ **销毁机制在单例上根本无法触发** —— 这是最硬的一条：
   给定块的引用者**恒非空**（那个同名常量一直持有它），
   于是本仓主流的「引用计数归零 ⇒ 释放」「作用域退出 ⇒ 销毁」**对它一律失效**。
   ⇒ 就算语言宣布「给定块可销毁」，也**没有**任何既有机制能把它销毁。
   要真能销毁，必须引入**显式销毁原语**（`destroy` 之类），那是全新语法面。

**⭐ 一个正面推论（缩小了 §5.5 ③ 的严重性）**：
不可销毁 ⇒ **运行期的对象引用环泄漏不再算问题**（它们本来就会活到进程结束）。
⇒ 成环检测只需覆盖**初始化期**的递归（我实测的 `rc=139` 正是初始化期），
**不需要**做运行期环分析。ADR 若要做 SCC，范围可以据此收窄。

### 三、裁决为「不自动终结」之后，三条代价**依然存在**（只是换了承担者）

**⚠️ 代价 1（最重）：进程退出**不会**做外部资源的终结。**
OS 回收的只是**内存与文件描述符**。它**不会**：flush 文件缓冲、删临时文件、
向外部服务注销、优雅关闭连接（TCP FIN / DB 的 `QUIT`）。
⇒ 而 ADR 举的三个招牌用例里，**连接池属于「必须释放」**（最尖锐的一例：
**连接池不关闭 ⇒ 服务端连接挂到 TCP 超时**，DB 侧连接数泄漏，**外部可观测且 OS 兜不住**）。
⇒ D15 不消解这条代价，只是把它**从「语言的责任」变成「使用者的显式责任」**（见五·D 路）。

**⚠️ 代价 2：「进程」≠「一次程序执行」。** 三种场合里「程序生命周期」所指不明：

| 场合 | 问题 |
|---|---|
| 测试 | 同进程跑 N 个 `\|test`，且**实测共用同一个 executor、单测间不重置状态**（见 §5.5 ④） |
| 嵌入宿主 | Pini 作为库被宿主多次调用 ⇒ 给定块跨「一次执行」存活 |
| REPL / 调试器 | 同上（本仓有 `Debugger` 与 `ReplEvaluator` 目录） |

⇒ 即便「不定义终结」，**「程序」的所指仍须定义** —— 否则这些场合里
「活到程序结束」这句话本身无意义（不是终结问题，是**寿命基准**问题）。

**⚠️ 代价 3（⚠️ 本条已修正，与上轮写法相反）：本仓有两条范式，给定块走的是其中一条。**

上轮我写「与本仓既有取向相反」，**不准确**。实测本仓对资源释放有**两条**并行范式：

| 范式 | 适用对象 | 本仓立场 | 出处 |
|---|---|---|---|
| **作用域精确销毁** | 运行时**内部句柄**（数组 / 字典 / 集合） | 目标形态；`atexit` 是**待退化**的兜底 | `PiniRuntime.swift`：`/// 进程退出时释放所有活动句柄…（D0 阶段护栏；D4.2.3 收紧为作用域精确销毁后本函数退化为兜底）` |
| **用户手动释放 + `defer`** | 语言层面的 **`*T` 原始指针** | **明文契约**：`初始化与释放由用户手动保证（建议 defer 释放）` | `../pini-spec-v0.md` §2.7 `*T` 条目 |

⇒ **给定块若走「不自动终结 + 使用者显式清理」，与第二条范式一致**（不是与本仓取向相反）；
上轮那条判断只看到了第一条。**这是一处需要更正的记账。**

### 四、新的切分：**初始化侧可确定 / 终结侧不可判定**（按用户给的框架）

用户那句「**好消息是惰性构造和调用时触发是确定的**」给出了正确的一刀切：

| 侧 | 可判定性 | 规范应写什么 |
|---|---|---|
| **初始化** | ✅ **确定** | 完整规则：触发点 / 不触发点 / 恰一次 / 原子 / 地址稳定 / 未访问不构造 |
| **终结** | ❌ **不可判定**（见零） | **不写规则**；只写**责任归属**（谁负责释放） |

**初始化侧的「触发 / 不触发」须与 D14 的判据同源**（这是本轮顺带定的具体化）：

| 位置 | 例 | 触发首次访问？ |
|---|---|---|
| **值位** | `应用服务.提交(数据)`、取地址、作为实参传出 | ✅ 触发 |
| **类型位** | 类型标注里的 `服务: 应用服务` | ❌ 不触发（仅类型信息） |
| **`\|own` 方法体** | `读\|own() -> …` | ❌ **不触发** —— 按 D12，`\|own` 不得触实例 |

⇒ 上表若不写明，「未访问就不构造」这句就**不可验**（什么算「访问」没有定义）。

### 五、选项与推荐（已按 D15 重排）

| 选项 | 内容 | 裁决 |
|---|---|---|
| A · 同寿命 + 语言级**自动**结束期有序终结 | 我上轮的推荐 | ❌ **已撤回** —— 仍需要那个不可得的判据（见零） |
| B · 同寿命、**什么都不做** | 最简 | ❌ 不可接受 —— 代价 1 里「连接池」这类必然泄漏，且**不可检测** |
| **D · 同寿命 + 不自动终结 + 清理责任显式外置**（**推荐**） | 使用者显式书写清理；语言不介入 | ✅ 见下实测：**今天已有一个可用载体** |
| C · 给定块可销毁（引入显式销毁原语） | 常量持有 ⇒ 销毁后常量指向什么？ | ❌ 与「地址稳定」冲突，仍不推荐 |

#### D 路的实测证据：`main` 体内的 `defer` 就是程序级清理载体

**实测**（`.build/out/Products/Debug/pini`，三例均 `check OK`）：

```
b1  main|func() -> ():
        defer 关闭连接池()
        print("main 主体")
    → 输出：main 主体 / 关闭连接池          ← defer 在 main 返回时执行

b2  两个相邻 defer 项（书写序：甲、乙）
    → 输出：主体 / 乙 / 甲                  ← 跨项 LIFO

b3  defer: 块形式（块内 甲、乙）
    → 输出：主体 / 甲 / 乙                  ← 块内按书写序
```

三条与 `../pini-spec-v0.md` §A.2.4 记载**一致**（defer-stmt 双形态；LIFO 运行语义按 `G39` 待转正，
但**行为已实现**）。⇒ **D 路不需要任何新语法或新机制**：清理写成 `main` 函数体内的 `defer` 即可。

⇒ **清理的编排点因此落在 `main`**（`defer` 是块作用域，只有入口函数能覆盖「程序结束」这一刻）。
两个连带效果：**① 库模块无法自行收尾**，只能把自己的清理函数暴露给 `main` 调用；
**② 对 §5.5 ④ 的测试冲突是一条缓解线索** —— 每个 `|test` 是独立函数体，可在其内用 `defer` 重置状态
（但注意：那只重置它**引用的 object**，单例本身仍在）。

**⚠️ D 路唯一的硬问题：「已关闭」状态。** 清理后常量**仍可达**（这正是不可判定的另一面）⇒
后续访问的行为必须定义。建议：**不销毁对象**（保地址稳定），把「已关闭」作为**对象自身的状态**，
后续访问触发**已定义的运行时错误**（而非 UB）。这与本仓「不静默」的取向一致。

**⚠️ D 路的最重代价须如实登记**：**忘记写 = 泄漏，且不可检测。**
而 ADR 恰以「**显式初始化易漏、易错**」为由否决了显式初始化 ⇒ 两侧标准不同，须说明白理由：

| 侧 | 忘记的后果 | 危险度 |
|---|---|---|
| 初始化（ADR 取隐形/惰性） | **「未构造」** —— 最多是晚构造或不用 | 安全 |
| 终结（D 路取显式） | **「泄漏」** —— 外部可观测，OS 兜不住 | **不安全** |

⇒ 这个不对称是**真实的**，不是双标。但也正因如此，ADR **必须明写**「终结责任在使用者」——
留空会让作者以为语言会帮忙（B 路的失败方式）。

### 六、这处不对称的新结论：不是「缺一项」，而是「**被判定为不可定义**」

上轮我把「初始化写 5+ 项、终结零字」当缺陷。按 D15 它**是裁决结果**，但**规格上仍不能留空**：

⇒ ADR 须明写一句「**本语言不定义给定块的终结**」并把责任归属写出来，
仍建议把「**寿命与清理**」立为与「惰性构造」**并列的一节**
——「不提供 X」本身是一条规格，写在正文里才可评审，留在未决问题 7 里不可评审。
