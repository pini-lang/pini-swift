```
处理|func(应用: 应用服务, 数据: I32,) -> (I32,):
    return 应用.提交(数据)
main|func() -> ():

    print(处理(服务, 2,))
```

## 5. 订正与待裁点

> ⚠️ **本节 2026-09-19 第二轮已按用户裁决重写**。原 §5.1「类型名当值」的定性**有误**，已改正；
> 原 §5.2 的两选项已被裁掉一个（取「块种类隐含」）。凡与第二轮结论冲突的旧表述，以本节为准。

### 5.1 ⛔ **已作废（D31 + D35，2026-09-19 十二/十三轮）** · 没有常量，没有同名

> **本节（原「给定块默认绑定常量」）已被 D31 重述与 D35 撤销。**
> **没有用户可见的常量** ⇒ 类型 / 值单名空间的问题**不存在**；ADR / 示例里凡引用 `存储服务` 处
> 一律改为**显式构造** `存储服务()`（D35：与普通复合类型同规）。
> ⚠️ 连带：构成本节核心的「顶层撞名约束」**也随之消解**（它本来就是 `object` 的既有情形）。
> 保留下文仅为记录推演过程。

**原内容（已作废）**：

**用户裁决**：不是「类型名当值」这种通用机制，而是**给定块声明默认绑定一个常量**。

⇒ 本件的定性据此改正。`[存储服务|given]` 一次声明产出**两个**名字：

| 命名空间 | 名字 | 含义 |
|---|---|---|
| 类型 | `存储服务` | 可用作类型标注（`using 应用: 存储服务`） |
| 值 | `存储服务` | 绑定到那个单例的**常量** |

这与 Scala 的 `object` 同构（类型 + 单例值同名）。

**这个改正让例 3 需要的机制变少了**：原先记的 `E6-004（类型名当值，不支持）` 应拆成两半 ——
**新机制只有「名称解析」那一半**（表达式位的裸名 `存储服务` 要能解析到常量）；
**取成员那一半走既有路径**，零新机制。佐证（实测）：

| 形态 | 今天 | 说明 |
|---|---|---|
| `let 配置 = 配置(); print(配置.名)` | → `x` ✓ | 名字是**局部变量** ⇒ 取成员走既有路径 |
| `print(配置.名)`（`配置` 是类型名） | → `E6-004` | 名字是**类型** ⇒ 解析不到值，取成员无从谈起 |

⇒ 差别**只在名字怎么解析**，不在成员访问本身。

**但带出一条硬约束（本轮新实测）**：顶层符号表是**单一命名空间**，类型名与值名会撞车。

```
[服务|object]
值: I32 = 1

服务|func() -> (I32,):      ; ← 同名顶层函数
    return 2
→ E3-004  redeclared symbol '服务'
```

而**局部**变量同名是允许的（`let 计数 = 计数()` → `7` ✓）。⇒ 常量绑定若与类型名同名，
现有顶层重声明检查会拒。**须为「类型 / 值」两个命名空间开一道口子**，或让给定块绑定走豁免。
这是本裁决的唯一落地成本，量级 = 顶层符号表加一层命名空间区分。

**另需裁**：常量可否被遮蔽 / 重绑？按「常量」定性，`存储服务 = 别的` 应当报 `E4-010`（与 `let` 同）。

### 5.2 ⛔ **已作废（D32，2026-09-19 十三轮）** · 给定块字段**可写**

> **本节（原「字段不可变是块种类隐含的」）已被 D32 整体撤销。**
> D32：「`self` 指代不分值 / 引用语义，**写字段的各种问题归 COW 等优化管**，只管 enum 用例不能被修改。」
> ⇒ 给定块字段**可以赋值**，`self.元素 = …` **合法**；下面两条负向用例**不再成立**（它们会变成合法代码）。
> ⇒ 随之作废的还有：D1、D6、§5.8 三·「不变性」行、以及本件原文里一切「字段不可变」的表述。
> **唯一保留的不可变约束 = enum 用例不可修改**（该约束原本就有：`enum-case` 产生式无 `=` 位）。
> 保留下文仅为记录推演过程。

**原内容（已作废）**：

⇒ 取原 §5.2 的 **A 方案**。`field-decl` 产生式 `IDENT ':' 类型 ['=' 表达式]` **不改**：
同一产生式在 `|given` 块内语义为「不可变字段」，在 object / struct 块内语义为「可变字段」（D1）。
语法面零变宽。

**兑付判据（必须写，否则 D1 不可验）**：给给定块字段赋值须报错。两个位置各一条负向用例：

```
[审计|given]
句柄: I32 = 1

main|func() -> ():
    审计.句柄 = 2            ; ① 经常量写字段 → 应报错
    return
```

```
[[审计]]
置|self(v: I32,) -> ():
    self.句柄 = v            ; ② 经 self 写字段 → 应报错（此路更易漏）
    return
```

② 是更尖锐的一例：今天 `self.字段 = ...` 是 object / struct 的**标准写法**，
给定块若只挡 ① 不挡 ②，不变性从扩展块就绕过去了。

### 5.3 ✅ 已查明 · 参数可变：不是「写错了」，是**这条规则从未写过**

**用户问**：「参数不应该可变，即便可变也是因为引用，而不是指引用的句柄可变，是写错了吗？」

分三层回答。

**① 规范层：零处规定。** `docs/` 全域检索「参数 + 不可变 / 只读」**零命中**；
规范、语言参考、`Pini草稿.md` 三处均无任何关于形参可变性的条款。
⇒ 所以不构成「违反某条规则」——**是这条规则不存在**。

**② 实现层：落在函数签名的默认值上，不是有意为之。**

```
TypeEnvironment.defineVariable(name:type:isMutable: Bool = true)      ← 默认 true
TypeChecker.checkFuncBody:
    for param in funcDecl.params:
        typeEnv.defineVariable(name: param.name, type: paramType)     ← 省略该参数 ⇒ 取默认 true
HIRExecutor（调用环境）:
    callEnv.define(name: name, value: args[index], isMutable: true)   ← 运行时同样按可变
```

对照：`var` / `let` 局部**显式**传 `isMutable`（`TypeChecker` 两处），
`self` 与字段也省略（那两处另当别论）。⇒ 参数是**顺着默认值漏进去的**。

**③ 用户描述的区分，实现里已经有了。** `TypeChecker` 对 `let` 绑定有按类型的豁免：

> 引用类型（object）的 `let` 仅约束引用本身、对象内容仍可变，须豁免；仅值类型（struct）整体不可变才拦截。

实测两条与用户表述一一对应：

| 用户表述 | 探针 | 今天 | D1 生效后应为 |
|---|---|---|---|
| 「指涉物可变」 | `改|func(c: 计数,)` 内 `c.加()` | ✅ 合法（外部可见 → `1 1`） | **不变**（走既有豁免） |
| 「句柄不可变」 | `换掉|func(c: 计数,)` 内 `c = 计数()` | ❌ 今日合法（→ `0`） | 应报 `E4-010` |

⇒ **把参数登记为不可变即可拿到用户描述的语义，零新机制**：
句柄不可重绑、指涉物照旧可改。

**④ 影响面已量化（本轮扫描）**：

| 范围 | 文件 | 带参函数 | 形参 | 参数重绑处数 |
|---|---|---|---|---|
| `examples/` + `Tests/` | 88 | 54 | 69 | **1** |
| `examples/selfhost/`（嵌套独立仓） | 19 | 107 | 197 | **0** |

唯一那处在 `examples/ffi_module/cstring.pini`，是一个**钳位惯用法**：

```
分配并写|func(值: I32,) -> (*U8,):
    if 值 < 0:
        值 = 0              ; ← 全仓唯一的参数重绑
```

⇒ 收紧的代价 = 该处改为函数首行 `var 值 = 值` 本地影子（或把钳位提到调用侧），**1 行**。

**⑤ 附带**：`self` 已经是不可重绑的（`self = 计数()` → **E2-007** 解析错），
所以参数是**唯一**漏网的绑定类别。

### 5.4 ⏳ 待裁 · 给定块该不该有 `self`（用户提出，需讨论）

用户：「按照语义，given 块可能不应该有 self，不太确定。」

先把它拆成**两个可独立回答**的问题，因为混在一起会得出错误结论。

#### (b) 先拆：体内写不写 `self.`？—— 与修饰符无关

实测 `|own` 方法体内**今天就能用 `self.字段`**（读 → `5`，写 → `9` 均通过）。
⇒ **选 `|own` 并不能去掉 `self`**。若真要「无 self」，要的是**隐式成员作用域**，代价两条：
① 给定块扩展将成为全语言**唯一**有隐式成员作用域的地方（其余一律显式 `self.`）；
② 需改文法 —— 规则 3.14 现在明令「扩展块内无修饰符的函数声明 → 报错」。

⇒ 建议 (b) 保持 `self.` 显式。

#### (a) 修饰符用 `|self` 还是 `|own`？—— 关键事实：**两者在实例上不可区分**

| 探针 | `|self` | `|own` |
|---|---|---|
| 读字段 `self.值` | ✅ | ✅（→ `5`） |
| 写字段 `self.值 = v` | ✅ | ✅（→ `9`） |
| 被实例调用 | ✅ | ✅ |
| 被类型名调用 | ❌ `E6-004` | ❌ `E6-004`（同因） |
| 同块内并存 | ✅ 可并存（→ `3` / `1`） | ✅ |

⇒ 修饰符在实现里是**纯声明位标记**，无强制能力差异。
而给定块**只有一个实例**、且该实例被绑成一个常量 ⇒「类型级」与「实例级」指向同一对象。

#### ✅ 已裁（D9，2026-09-19）：**两者同时保留** —— 常量就是 `self` 的指代

**用户裁决**：`|self` 与 `|own` **同时保留**，关键点在于 **given 会创建常量，这个常量就是它的 `self` 指代**。

⇒ 这条定性把两个修饰符**分开落到两个不同的东西上**：

| 修饰符 | 体内 `self` 是什么 | 需要实例吗 |
|---|---|---|
| `\|self` | **那个常量**（= 单例实例） | 需要 |
| `\|own` | 类型本身（与 enum 的 `\|own` 一致） | **不需要** |

**由此得到的可观察差异（这才是两者并存有意义的地方）**：

> `|self` 方法操作单例 ⇒ **触发惰性初始化**；
> `|own` 方法是类型级的、**不碰实例** ⇒ **不触发初始化**。

⚠️ 这条差异**与 ADR 的招牌卖点直接咬合**：ADR 论证的核心之一正是「未访问的给定块从不初始化」。
若 `|own` 也要实例，两个修饰符就**退化为同义词**（这正是我上一轮建议「留一废一」的依据）；
按 D9 保留两者，就必须让 `|own` **不碰实例**，否则保留无意义。

**⇒ 由此推出一项待裁**（记入 §5.5 第 ① 项）：`|own` 方法体内**是否可以使用 `self.字段`**？
实测今天是**可以**的（读 → `5` / 写 → `9`），但按 D9 的定性应为**不可** ——
否则 `|own` 拿到实例、触发初始化，两个修饰符的差异归零。

> 上一轮「留 `|self`、令 `|own` 报错」的建议**已被 D9 取代**，保留于此仅作决策痕迹。
> 其中三条理由仍需在 ADR 里回答（尤其「体内必须读字段」这条 —— 它现在变成
> **`|own` 方法能读什么**的问题，而不是「该不该有 `|own`」的问题）。

**反方（我推的最强版本，供否决）**：给定块可以**一个方法都没有** —— 上下文是纯数据，
操作一律写成带 `using` 的自由函数。概念上最干净，代价是给定块成为**唯一没有逻辑的复合类型**，
与「数据与逻辑分离」（每类复合类型都有扩展块）不对称。

#### (c) 同源的连带问题：给定块的扩展块该挂哪个括号？

实测现行扩展块**按名挂载、不校验目标种类**（`[[句柄]]` 挂 `[句柄|object]` 通过；
同目标可并挂 `[[X]]` 与 `{{X}}`）。⇒ 语法上 `((应用服务))` / `{{应用服务}}` / `[[应用服务]]` **全都合法**。
不给规则则风格失控。ADR 草案用的是 `[[…]]`（枚举括号）—— 与「类 enum 复合类型」的定性一致，
但需明文写进文法，否则它只是「恰好能用」。

## 5.5 剩余待讨论（第三轮提出，按「是否挡事」排序）

### ① ✅ 已裁（2026-09-19）：`|own` 内**不得**使用 `self` 指代 —— 现行为是**错误行为**

**用户裁决**：`|own` 内期望不可使用 `self` 指代，**这是错误的行为**。

⇒ 与 D9 的定性一致（`|own` 是类型级、不该碰到实例），裁决明确为「**拒绝**」。

**⚠️ 但实测显示这不是给定块特有的问题，而是既有语言缺陷。** `|own` 在**三种复合类型**上都能用 `self`：

| 类型 | 探针 | check | run |
|---|---|---|---|
| `object` | `读|own() -> (I32,): return self.值` | OK | → `5` |
| `struct` | `读|own() -> (I32,): return self.x` | OK | → `7` |
| `enum` | `读|own() -> (I32,): return self.红` | OK | 调用点 `E6-004`（与 `self` 无关） |

写字段同样可以（`|own` 体内 `self.值 = v` → `9` 通过，见 §5.4 表）。
⇒ **`|own` 的规范语义（「本型方法 / 类型级方法」）在实现里没有落实**：
它今天是 `|self` 的同义标记，只不过恰好能经实例调用。

**因此本条的意义超出 given**：给定块只是**第一个**会因此出错的地方
（因为只有它的单例要求 `|own` 真做到「不碰实例、不触发初始化」）。
⇒ 处置建议：**按既有缺陷单独立案**（覆盖 object / struct / enum 三类），
不要塞进 given 的批次里 —— 否则 given 落地时会牵动三种既有类型的回归面。

**诊断码**：需要新码。现有 `E4-009 无此成员`（「成员不存在」）与
`E4-010`（「对 let 重赋值」）都**语义不符** —— 这里是「此上下文不可触实例」。

### ② ⭐ 同名类型与常量 ⇒ 「经类型名取成员」必须消歧（D9 + D5 的合成后果）

D5 让类型与常量**同名**，于是 `应用服务.提交(数据)` 这一句**语法上同时是两种取用**：

| 若按**常量**解析 | 取到实例成员 ⇒ `\|self` 方法 / 字段 |
|---|---|
| 若按**类型**解析 | 取到类型级成员 ⇒ `\|own` 方法 |

⇒ **同名之下，成员种类决定走哪条路**，这必须写进消歧规则（不能靠「谁先找到」）。
今天两条路**都不通**（`色彩.名字()` 与 `计数.新建()` 均 `E6-004`），所以这是全新规则，
不是既有行为的选择。

> 这一项同时是「常量绑定」与「扩展块」两处设计的交汇点，**建议与 ① 同批裁**。

### ③ ⚠️ 间接成环：ADR 的 SCC 看不见（实测）

ADR 写「编译期检测给定块引用图的强连通分量。成环报错」。**但 SCC 只看得见字段引用。**
环若**经由函数体**绕回来，引用图上没有边，SCC 判不出：

```
建乙|func() -> (I32,):         ; ← 这个环靠函数体绕回来
    乙类型()
    return 1

[甲类型|object]
标记: I32 = 建乙()             ; 字段 → 函数

[乙类型|object]
标记: I32 = 甲类型().标记       ; 字段 → 另一个类型
```

**实测（用现有 `object` 同构复现）**：`check` 通过，`run` → **`rc=139`（SIGSEGV，栈溢出）**，
无任何诊断。而同结构的**直接**互引（`甲⇄乙`）在**构造它**时同样 `rc=139`。

⚠️ 对给定块而言，这个形态可能**更坏**：ADR 规定「首次访问仅一个执行流执行初始化，其他等待」
⇒ 初始化中途再次访问**同一个**给定块 = **等自己的初始化锁** ⇒ **死锁**（挂死而非崩）。
（此条是**按 ADR 设计推演**，非实测 —— 给定块尚无实现，如实标注。）

> ⚠️ **不要引用语言参考的「循环检测」节当依托**（2026-09-19 用户指令）。
> 环检测**尚未落实** —— 拿它做论据会把「纸面条款」读成「已有设施」。
> `Sources/` 全域无 SCC / tarjan、`E7` 段无环告警码，这两条是**本轮实测**，
> 只用于说明「现在没有」，**不用于推论「将来该长什么样」**。
> ⇒ ADR 若提 SCC，须当作**从零新建**来评估范围与验收，不得按「接既有设施」估工。

### ④ ⚠️ 与测试纪律直接对撞（用仓库自己的规矩）· ⚠️ **已按 D34 大幅降级**

> **2026-09-19 第十三轮更新**：本条原建立在「给定块 = **程序级单例**」之上。
> **D34（允许多次实例化）+ D35（允许构造）撤销了单例** ⇒ 「跨测试共享」不再是**结构决定**的，
> 而是「测试用了同一个默认实例」的结果。测试自建实例（`应用服务()`）即可隔离。
> ⇒ 本条**从「必然冲突」降为「常规注意项」**，不再需要机制层面的解法。见 §7 B7。
> 保留下文仅为记录当时的事实（那段 `runCollectedTests` 的实测仍准确）。

`../pini-spec-v0.md` 的测试入口四项之二：**「测试执行顺序不保证，测试之间不得有顺序依赖」**；
测试规范「隔离与复用」：**「每测试独立自建 fixture、不依赖共享状态、自清理」**。

而给定块 = **程序级单例 + 惰性初始化 + 活到程序结束**，且（D5/D6 之后）**可变状态必然藏在它引用的
`object` 里** ⇒ **跨测试共享**。ADR 的未决问题 7「测试框架如何覆盖单例」正好落在这条冲突上，
但 ADR 没把它连到本仓既有纪律。

⚠️ **本件例 1 就是这个形状**（`[应用服务|given]` 内含可累积的 `[队列|object]`）：
作为 `examples/` 是可读的，但**若原样写进 `|test` 块，它就违反上面两条**（第一次跑与第二次跑结果不同）。

**⚠️ 而且这条冲突不是「有可能」，是结构上的必然**（2026-09-19 实测实现）：

```
ProgramRunner.runCollectedTests:
    let executor = HIRExecutor(...)        ; ← 只创建一次
    try executor.prepare(module: module)
    for function in module.functions where function.isTest {
        results.append(runOneTest(function, on: executor))   ; ← 循环里复用同一个 executor
    }

runOneTest(_:on:) 体内：只做 args 注入 + callFunction —— 不重置任何状态
```

⇒ **所有 `|test` 共用同一个 `executor` 实例、且单条测试之间不重置状态。**
给定块的惰性初始化标记若挂在执行器（或其持有的运行时状态）上，
则**同一进程内所有测试共用一个单例** —— 测试互相污染是**结构决定**的，不是用例写法问题。

⇒ 须裁其一：**① 给定块提供测试期重置/重建通道** ② 测试内**禁止**触碰带可变状态的给定块
③ 明确豁免该纪律（须说明为何单例是例外）。

> 附：今天的 Pini **没有任何**程序级可变状态手段（顶层 `定` 不能被函数体引用，实测 `E3-001`）
> ⇒ 无法用现有语言构造复现这条冲突 —— 给定块引入的是一个**全新的**共享状态面，
> 所以这条冲突是随它一起进来的，不是既有的。

惰性**初始化**有完整定义（时机 / 次数 / 原子性 / 递归检测），**终结零定义**。
D15 裁决：**不去定义它** —— 定义它需要「调用侧不再调用」这个不可得的判据。
D17 补充：清理权交开发者，提前清理只能走 unsafe 的 `free`；
而 §5.6 五的实测把「给定块可销毁」**在类型层排除**（`*T` 禁 `object`）。
→ 展开见下节 §5.6（已按此重写，我上轮的推荐已撤回）。

### ⑥ ✅ 已修正（2026-09-19）：`using` 买的是**参数表的来源区分**，不是签名自述

**我上一轮的定性偏了。** 我写「using 只买签名自述 + 局部别名，不买能力」，据此建议降级为糖。
用户的解释纠正了这一点，而且理由比我给的更本质：

> 「因为 given 成块，只需要 using 一个块就可以了，至于需要为多个参数标记 using，那是**必要的噪音**，
> **函数本身的参数非常一致地从调用点传入，只不过编译器帮忙插入了 using 部分**。」

**正确的定性**：语言的设计要求是**「函数的全部输入都写在同一个参数表里」**——这一点对
**两类来源都成立**：普通参数从调用点传入，`using` 参数由编译器插入。
`using` 的作用是**把「编译器插入的那部分」标出来**，从而在**保持参数表完整**的前提下区分来源。

⇒ 因此它**不是糖**：
- **不是**「省略了实参的普通参数」——省略会破坏「全部输入都在签名里」这条不变式；
- **不是**子句（如 `[using]` 块）—— 块形式会与 `given` 的块形式重复，而取用本就没有「声明」性质；
  且会引入第二处需要维护的清单（块里写的名字 vs 参数表里的名字，两份必然漂移）。
- **必要噪音**是正确的代价判断：一个参数一个标记，换来的是**每个参数的来源各自可见**。

**对我原判断的影响**（如实记账）：
- 「**「无传染」是常量给的，不是 `using` 给的**」—— 这句**仍然成立**（常量在，直连取用就通）；
- 「**using 可以降级为糖**」—— 这句**撤回**。它与 ADR 的前提修正直接相关：
  常量让依赖**全局可达**，而 `using` 让依赖**在签名里明文可读** ——
  这正是把「隐式全局状态」拉回「可推理」的那一步。故它不是可省的美化，是**可推理性的载体**。
- 「**两者可分步落地**」—— **仍然成立**，但理由要改：不是因为 `using` 可省，
  而是因为它是**纯增量**（先落 given 时，参数表没有混合来源，不存在「来源不清」的问题；
  `using` 落地后再表达来源区分）。⇒ 仍是降风险的分步，只是不能拿「可省」当理由。

#### ✅ 已裁（D14，2026-09-19）：`using` 是**强制**的

**用户裁决与理由**：「using 是强制的，此语言的函数的纯度相当高——尽管大多是弱纯。」

⇒ **强制**的含义：**函数体内值位引用了某给定块常量 ⇒ 签名必须声明对应的 `using` 参数，否则报错。**

**判据须区分两个位**（与初始化触发判据同源，见 §5.6 零）：

| 位置 | 例 | 算依赖？ |
|---|---|---|
| **值位** | `应用服务.提交(数据)` | ✅ 须声明 `using`（且**触发初始化**） |
| **类型位** | 类型标注里的 `服务: 应用服务` | ❌ 不算依赖（不触发初始化，也不构成运行时输入） |

**三项配套必须一并定义**（缺一条则规则不完备）：

1. **入口豁免**：`main` 无调用点（D2 裁入口不带参数）⇒ **参数插入者不存在** ⇒ 规则对 `main` 不适用。
   建议明文写为「`main` 视为已隐式声明全部给定块」，而不是留作未写明的例外。
2. **扩展块方法的来源**：`|self` 方法体内的 `self` 是**已声明的实例来源**（不算隐式依赖）；
   但方法体若访问**别的**给定块常量，同样受本规则约束 ⇒ 须裁：扩展块方法的参数表**是否允许 `using`**
   （建议允许，与自由函数同规；否则方法将无法合法访问第二个给定块）。
3. **传递规则**：`f(using A)` 体内调用 `g(using A)` ⇒ 编译器可插入，合法；
   而 `f` **未**声明 A 却调用 `g(using A)` ⇒ 编译器无处插入 ⇒ **报错**（f 的签名缺 A）。

#### ✅ 已裁（D16，2026-09-19）：**特征块下的签名未必要写 `using`**

**用户裁决与理由**：
> 「在特征块下的签名未必要写 using，因为**在函数的声明处才真正确定 using 这一编译器行为糖**。」

⇒ **强制规则的作用域须收窄为「有体的函数声明」**：
`using` 的确定点在**函数声明**，不在**特征签名**。特征抽象签名**没有体**，
而强制规则的判据（体内值位引用）在无体处**空成立** ⇒ 抽象签名天然豁免。

**本仓已有两条实测先例支持「修饰符按位置区别对待」：**

| 先例 | 实测 | 与 `using` 的关系 |
|---|---|---|
| ⭐ **`\|unsafe` 只在自由函数确定** | `<危>` 里写 `取\|unsafe() -> (I32,)` → **`E2-007` 解析错**（规范已登记「扩展块方法 / trait 签名标它报错」） | 证明「只在某处确定的修饰符，在 trait 签名里**被拒**」是本仓既有做法 |
| ⭐⭐ **接收者的两种写法可互换** | trait 里 `描述(self) -> (String,)`（`self` **是参数**）与 `描述\|self() -> (String,)`（`self` **是修饰符**）**双双 check OK**，且被认作**同一方法**（实现覆盖生效） | **调用约定级声明在 conformance 匹配时被擦除** —— 这正是 `using` 需要的机制 |

第二条先例最强：`self` 的书写位置（参数位 vs 修饰符位）**两种形态等价**，
说明本仓的一致性检查**比较的是类型形状，不是调用约定**。
`using` 同理 —— 它**不改变函数的类型**（`(数据: I32, 服务: 应用服务) -> I32` 两种写法同型），
故 trait 签名无须承载它，实现处的声明才是确定点。

#### ✅ 已裁（D18，2026-09-19）：`using` 参数**允许显式提供**

**用户裁决与理由**：
> 「这带来一个问题，那就是**编译期糖是否影响数据**，我看还是允许比较好。」

⇒ **允许。** 这条裁定的落点正是用户点出的那个问题：**`using` 是编译期糖，它不改变数据。**

| 侧 | `using` 做了什么 |
|---|---|
| **数据**（函数的参数表 / 类型） | ❌ **不动** —— 参数一直在参数表里，它是**真参数** |
| **糖**（由谁提供实参） | ✅ **只标这一项**：标了 ⇒ 编译器插入；不标 ⇒ 调用点传入 |

⇒ 既然参数**一直在参数表里**（不是被凭空造出来的），「调用点显式提供」在语义上**毫无障碍** ——
它只是**绕过插入、用调用点给的实参**。**这一步不需要任何新机制。**

**与 D16 同源**：D16 说「糖不改**类型** ⇒ trait 签名不必承载」；
本条说「糖不改**数据** ⇒ 调用点可以自己提供」。**两者是同一性质的推论**，
故应当同批成立 —— 若只取 D16 不取本条，D16 反而失去依据（见下）。

**为什么本条是 D16 成立的前提**：trait 抽象签名不含 `using` 后，**经特征类型视图调用**时
（调用点静态类型是特征），编译器看到的是特征签名 —— 它无从判断该不该插入。
- **允许显式提供** ⇒ 调用点两种写法都合法，特征视图下**无歧义**；
- 不允许 ⇒ 只能**要求特征签名也写 `using`**，那就把 D16 直接推翻。

⇒ 本仓 `描述(self)` 能覆盖 `描述|self()` 这条实测，说明「同一方法允许两种书写形态」
在本仓**已是被验证的设计**，不是新引入的宽容（与 Scala `using` / `given` 同型）。

#### ✅ 已裁（D19，2026-09-19）：开发者**可以不用** `using`；此时调用点必须显式传入

**用户裁决与理由**：
> 「这取决于开发者愿不愿意用 using，**在不用的情况下，在调用点必须手动传入实参，因此不是必须**。」

⇒ 对「特征默认实现（有体）是否须声明」这一问：**不必须**。理由把它交给开发者选择，
代价与后果写得很清楚 —— **不用，就要在调用点手动传入**。

**⚠️ 但这条理由本身是普遍的，故它同时精确化了 D14。** 按此理由，D14 的实质**不是**
「必须写 `using` 这个词」，而是 **「依赖不得隐藏」** —— 两条合法通道：

| 通道 | 写法 | 实参从哪来 |
|---|---|---|
| **① 声明 `using`** | `处理\|func(using 服务: 应用服务,)` | 编译器插入 |
| **② 声明普通参数**（不用 `using`） | `处理\|func(服务: 应用服务,)` | **调用点必须传入** |

⇒ **两条都满足 D14 的理由**（「函数的全部输入都落在参数表里」）——
因为**普通参数也在参数表里**。所以「不用 `using`」并不破坏纯度不变式，
只是把实参来源从编译器交还给调用点。
**⇒ D14 依然成立，但它的牙齿是「依赖不得隐藏」，不是「必须写这个词」。**

> ⚠️ **上面这一段是我的推论，标注待你确认**：按该理由，它**不限于特征默认实现**，
> 而适用于**所有有体函数**（即任何函数都可选择不用 `using`、改由调用点传参）。
> 若你的本意**只是**特征默认实现这一处，请裁 —— 那 D14 对普通函数仍是「必须写 `using`」，
> 规则会因此出现一处按块种类区分的例外，须明文登记。

#### ✅ 已裁（D20，2026-09-19）：扩展块方法**理应允许**声明 `using`

**用户裁决**：「理应允许声明。」

⇒ 与自由函数**同规**（D14 三项配套里的第 2 项由此关闭）。
代价照记：扩展块的参数表**也参与依赖检查**；换来的是方法**能合法访问第二个给定块常量**。
反向取法（禁止）会使「方法」比「自由函数」更弱，看不出理由，故不取。

**⚠️ 由此必须修正 ADR 的「无传染」卖点。** ADR 后果表写着「无传染」，在强制之下这不准确
（**并按 D16 收窄**：只有**有体的函数声明**才须逐层写）：

| 说法 | 准确性 |
|---|---|
| 「无传染」 | ❌ 过度承诺 —— **有体的**函数声明每层都得写 `using 服务: 应用服务`，签名面确实被占用 |
| 「**无实参传染**」 | ✅ 准确 —— 调用点不必逐层传参，但**函数声明须逐层声明**（特征抽象签名豁免，见 D16） |

⇒ 这正是 D10「**必要的噪音**」的准确含义：**传染没有消除，只是从实参位移到了签名位。**
ADR 的代价表须据此改词。

⚠️ 但 D16 让这处噪音**比上一版估计的小**：特征（接口）面**不被占用** ——
即「先声明接口、后处处实现」的路径上，噪音只出现在实现处，不出现在接口处。
对以特征为主要抽象手段的程序，这是**实质性的减负**，应计入 ADR 的代价表（而非只改词）。

**关于「纯度」**：实测全仓检索 —— 「纯度 / 弱纯 / 纯函数」在规范、参考、术语表中**零登记**
（`纯` 只出现在「纯值类型结构体」与挂起模式的「已执行副作用不重跑」两处，均与本意无关）。
**但本条不需要它当判据**：按 §5.5 ④ 附注的实测，今天的 Pini **没有任何**程序级可变状态手段
（顶层 `定` 不能被函数体引用 → `E3-001`）⇒ **给定块常量是函数唯一的隐式运行时依赖通道**。
把这条通道锁进签名，函数的**依赖面即封闭**，无需独立的「纯度」概念。
「弱纯」那句仍然准确，但它说的是**效应面**（`print` / I/O / 时间 / 随机）——
那不属「输入来源」，`using` 不该也不必覆盖。**两个面分开，规则才完备。**

### ⑦ 文档面本身的待办（不挡设计，但要有主）

- **诊断码**：`using` 解析失败 / 环 / 写不可变字段，各归哪个段？现有 `E4-009`（无此成员）、
  `E4-010`（对 let 重赋值）覆盖不到「此上下文不可触实例」这类
- **稳定性分级**：`given` / `using` 落 Provisional 还是 Experimental？（决定能否随之递交语言参考）
- **顶层命名空间开口**（§5.1 的成本）会触及 `E3-004` 重声明检查的既有判据 —— 须一并评估回归面

## 5.6 专论：给定块的寿命（用户提问，2026-09-19；**已按 D15 + D17 重写**）

> **问题（用户原话）**：「给定块必须与程序生命周期一样长是正确的吗？请你讨论。」

### 零、✅ 已裁（D15，2026-09-19 四轮）：生命周期**不可判定**

**用户裁决（原话）**：
> 「无法确定 given 常量的生命周期，因为这需要运行时确定调用侧不再调用 given 常量，
> 那就引发了自相矛盾的检查，又要它活得久，又要清理它。
> 好消息是惰性构造和调用时触发是确定的。」

**这条论证比我上轮列的三条代价更根本，它直接否掉了我推荐的那条路。** 展开：

- **终结的安全性前提 = 「此后不再有任何调用」**。这个前提**既不可静态判定**
  （常量是编译期绑定，名字恒可见），**也不可运行时判定**（引用计数恒 ≥ 1，见下「二·3」；
  此外还有多线程、已注册回调、经 FFI 传出的指针等调用路径）。
- ⇒ 任何**自动**终结都必须先证明这个前提。而「证明它」正是
  **「又要它活得久（全程可调用），又要清理它（此后不可调用）」** —— 用户指出的自相矛盾。
- ⇒ 结论：**「同寿命」不是三个选项里的最优解，而是唯一不需要判据的解**；
  同时，语言**不提供自动终结**。

> ⚠️ **我上轮推荐「A · 结束期有序终结」由此撤回。** 撤回理由不是「时点难定」（那是我上轮写的表象），
> 而是更根本的一条：**A 仍是自动方案，仍需要那个不可得的判据**。
> 时点不确定（代价 2）只是它的症状，不是它的病根。

### 一、先把「已有的隐含承诺」说清楚

ADR 已经写了「地址稳定性降级为『**首次访问后不变**』」。
**不销毁是这句话的前提** —— 一旦能销毁，地址就会变（或更坏：常量指向已销毁的对象）。
⇒ 所以「同寿命」不是本次新加的决定，而是 ADR 里一个**从未写出来的承诺**。
提问切中要害：一条影响资源语义的承诺，不该只以「地址稳定」的形式间接存在。

### 二、为什么「同寿命」是默认（三条；第 3 条现为**不可判定**的机制证据）

1. **程序级资源本该全程序共享** —— 调度器、连接池、缓存的用途就是这个。
2. **惰性契约已经蕴含它**：首次访问后才构造、构造恰一次、地址此后不变 ⇒ 语义上已经「不销毁」了。
3. ⭐ **销毁机制在单例上根本无法触发** —— 这是最硬的一条：
   给定块的引用者**恒非空**（那个同名常量一直持有它），
   于是本仓主流的「引用计数归零 ⇒ 释放」「作用域退出 ⇒ 销毁」**对它一律失效**。
   ⇒ 就算语言宣布「给定块可销毁」，也**没有**任何既有机制能把它销毁。
   要真能销毁，必须引入**显式销毁原语**（`destroy` 之类），那是全新语法面。

**⭐ 一个正面推论（缩小了 §5.5 ③ 的严重性）**：
不可销毁 ⇒ **运行期的对象引用环泄漏不再算问题**（它们本来就会活到进程结束）。
⇒ 成环检测只需覆盖**初始化期**的递归（我实测的 `rc=139` 正是初始化期），
**不需要**做运行期环分析。ADR 若要做 SCC，范围可以据此收窄。

### 三、裁决为「不自动终结」之后，三条代价**依然存在**（只是换了承担者）

**⚠️ 代价 1（最重）：进程退出**不会**做外部资源的终结。**
OS 回收的只是**内存与文件描述符**。它**不会**：flush 文件缓冲、删临时文件、
向外部服务注销、优雅关闭连接（TCP FIN / DB 的 `QUIT`）。
⇒ 而 ADR 举的三个招牌用例里，**连接池属于「必须释放」**（最尖锐的一例：
**连接池不关闭 ⇒ 服务端连接挂到 TCP 超时**，DB 侧连接数泄漏，**外部可观测且 OS 兜不住**）。
⇒ D15 不消解这条代价，只是把它**从「语言的责任」变成「使用者的显式责任」**（见五·D 路）。

**⚠️ 代价 2：「进程」≠「一次程序执行」。** 三种场合里「程序生命周期」所指不明：

| 场合 | 问题 |
|---|---|
| 测试 | 同进程跑 N 个 `\|test`，且**实测共用同一个 executor、单测间不重置状态**（见 §5.5 ④） |
| 嵌入宿主 | Pini 作为库被宿主多次调用 ⇒ 给定块跨「一次执行」存活 |
| REPL / 调试器 | 同上（本仓有 `Debugger` 与 `ReplEvaluator` 目录） |

⇒ 即便「不定义终结」，**「程序」的所指仍须定义** —— 否则这些场合里
「活到程序结束」这句话本身无意义（不是终结问题，是**寿命基准**问题）。

**⚠️ 代价 3（⚠️ 本条已修正，与上轮写法相反）：本仓有两条范式，给定块走的是其中一条。**

上轮我写「与本仓既有取向相反」，**不准确**。实测本仓对资源释放有**两条**并行范式：

| 范式 | 适用对象 | 本仓立场 | 出处 |
|---|---|---|---|
| **作用域精确销毁** | 运行时**内部句柄**（数组 / 字典 / 集合） | 目标形态；`atexit` 是**待退化**的兜底 | `PiniRuntime.swift`：`/// 进程退出时释放所有活动句柄…（D0 阶段护栏；D4.2.3 收紧为作用域精确销毁后本函数退化为兜底）` |
| **用户手动释放 + `defer`** | 语言层面的 **`*T` 原始指针** | **明文契约**：`初始化与释放由用户手动保证（建议 defer 释放）` | `../pini-spec-v0.md` §2.7 `*T` 条目 |

⇒ **给定块若走「不自动终结 + 使用者显式清理」，与第二条范式一致**（不是与本仓取向相反）；
上轮那条判断只看到了第一条。**这是一处需要更正的记账。**

### 四、新的切分：**初始化侧可确定 / 终结侧不可判定**（按用户给的框架）

用户那句「**好消息是惰性构造和调用时触发是确定的**」给出了正确的一刀切：

| 侧 | 可判定性 | 规范应写什么 |
|---|---|---|
| **初始化** | ✅ **确定** | 完整规则：触发点 / 不触发点 / 恰一次 / 原子 / 地址稳定 / 未访问不构造 |
| **终结** | ❌ **不可判定**（见零） | **不写规则**；只写**责任归属**（谁负责释放） |

**初始化侧的「触发 / 不触发」须与 D14 的判据同源**（这是本轮顺带定的具体化）：

| 位置 | 例 | 触发首次访问？ |
|---|---|---|
| **值位** | `应用服务.提交(数据)`、取地址、作为实参传出 | ✅ 触发 |
| **类型位** | 类型标注里的 `服务: 应用服务` | ❌ 不触发（仅类型信息） |
| **`\|own` 方法体** | `读\|own() -> …` | ❌ **不触发** —— 按 D12，`\|own` 不得触实例 |

⇒ 上表若不写明，「未访问就不构造」这句就**不可验**（什么算「访问」没有定义）。

### 五、选项与裁决（已按 D15 + D17 定案）

**用户裁决（D17，原话）**：
> 「提前清理恐怕只能靠 unsafe 领域的 free，**部分信任开发者**，
> **默认采用与程序等长寿命**，**清理权交给开发者**。」

| 选项 | 内容 | 裁决 |
|---|---|---|
| A · 同寿命 + 语言级**自动**结束期有序终结 | 我上轮的推荐 | ❌ **已撤回** —— 仍需要那个不可得的判据（见零） |
| B · 同寿命、**什么都不做** | 最简 | ❌ 不可接受 —— 代价 1 里「连接池」这类必然泄漏，且**不可检测** |
| C · 给定块**可销毁**（引入显式销毁原语） | 常量持有 ⇒ 销毁后常量指向什么？ | ❌ **实测否证** —— 不是「不推荐」，而是**今天连手段都不存在**（见下） |
| **D · 同寿命 + 不自动终结 + 清理权交开发者** | 使用者显式清理；语言不介入 | ✅ **已裁（D17）** |

#### ⭐ 实测把 C 路彻底排除：`free` **碰不到 object**

**（1）`free` 的签名只收 `*U8`** —— 现行语料 `examples/ffi.pini`：

```
[libc|foreign]
free(p: *U8,) -> ()
```

**（2）`*T` 明文禁止 `object`** —— `../pini-spec-v0.md` §2.7：
「`T` 须为 C 兼容类型（标量、纯值类型结构体、或其他指针类型），**禁止 `object` 或含 `object` 字段的复合类型**」。

**（3）实测**：

```
t5  [狗|object] 名字: String = "旺财"
    main: var d = 狗(); unsafe free(&d)      → E4-001 类型错

t6  var p = unsafe malloc(8); unsafe free(p) → check OK，run: 已释放   ← 阳性对照，器械有效
```

⇒ **给定块（一个 `object`）在类型上就不可能被 `free`。** C 路不是「不推荐」，是**不可达**。

**⭐ 一个比 D15 的论证更硬的推论**：「与程序同寿命」在本语言里
**不是一条策略选择，而是没有任何机制可以违反它** ——

| 路径 | 状态 |
|---|---|
| 引用计数归零 ⇒ 释放 | 失效（§5.6 二·3：单例的引用者恒非空） |
| 作用域退出 ⇒ 销毁 | 失效（给定块没有作用域） |
| 显式 `free` ⇒ 释放 | **类型上禁止**（本条 t5） |

⇒ **三条路全断**。故 ADR 的「地址稳定 / 首次访问后不变」是**被机制保证的**，不是靠约定。

> ⚠️ **但 ADR 那句「地址稳定，**可传 FFI**」仍不成立** —— 这正是 t5 的同一测量照出来的：
> `*T` 禁 `object`（§2.7）⇒ **给定块（object）无法作为 `*T` 传给 FFI**。
> ⇒ 地址稳定是**真的**（寿命被保证），但「可传 FFI」**买不到** ——
> 能传 FFI 的是它**持有的 `*T` 字段**（那本来就允许），不是它自己。
> **后果表须删掉「可传 FFI」这一条卖点**，或改述为「其持有的原始资源可传 FFI」。

#### 三层责任划分（D17 的落地形态）

| 层 | 谁负责 | 机制 | unsafe？ | 依据 |
|---|---|---|---|---|
| **语义清理**（关连接池、flush、注销） | 开发者 | 普通方法调用 + `main` 内 `defer` | ❌ 安全 | b1 / b2 / b3（下） |
| **原始资源释放**（块持有的 `*T` 缓冲） | 开发者 | `free` / foreign 调用 | ✅ **是** | t6 |
| **对象本身的生命期** | **无人**（语言也不管） | **无机制** —— 活到程序结束 | —— | t5 |

⇒ **D17 的「部分信任开发者」与本仓既有姿态一致，不是新引入的宽松**：
`*T` 条目的明文契约就是「**初始化与释放由用户手动保证（建议 `defer` 释放）**」。
给定块走的是**同一姿态** —— 语言不代管释放，把**权力与责任一并交出**。
（这同时坐实了§三·代价 3 的修正：给定块走的是本仓**第二条**范式，不是逆着取向走。）

#### D 路的实测证据：`main` 体内的 `defer` 就是**语义清理**载体

**实测**（`.build/out/Products/Debug/pini`，三例均 `check OK`）：

```
b1  main|func() -> ():
        defer 关闭连接池()
        print("main 主体")
    → 输出：main 主体 / 关闭连接池          ← defer 在 main 返回时执行

b2  两个相邻 defer 项（书写序：甲、乙）
    → 输出：主体 / 乙 / 甲                  ← 跨项 LIFO

b3  defer: 块形式（块内 甲、乙）
    → 输出：主体 / 甲 / 乙                  ← 块内按书写序
```

三条与 `../pini-spec-v0.md` §A.2.4 记载**一致**（defer-stmt 双形态；LIFO 运行语义按 `G39` 待转正，
但**行为已实现**）。⇒ **D 路不需要任何新语法或新机制**：清理写成 `main` 函数体内的 `defer` 即可。

⇒ **清理的编排点因此落在 `main`**（`defer` 是块作用域，只有入口函数能覆盖「程序结束」这一刻）。
两个连带效果：**① 库模块无法自行收尾**，只能把自己的清理函数暴露给 `main` 调用；
**② 对 §5.5 ④ 的测试冲突是一条缓解线索** —— 每个 `|test` 是独立函数体，可在其内用 `defer` 重置状态
（但注意：那只重置它**引用的 object**，单例本身仍在）。

**✅ 我上轮提的「已关闭状态」硬问题，已由 D17 + t5 解掉。** 上轮我问「清理后常量仍可达，后续访问怎么办」，
并建议「不销毁对象」—— 现在可以给更强的理由：**对象在类型上就不可能被销毁**（t5）
⇒「销毁后常量指向什么」这个难题**在本语言里根本不会出现**。随之：

- 「已关闭」只能是**对象自身的普通状态** ⇒ 由对象自己定义（与任何 object 的「已终止」标志同规），
  **不需要语言级新机制**；
- 后续访问报的错也是**普通运行时错误** ⇒ **不需要新的诊断码段**；
- 语言**不必**为它定义任何东西 —— 它落在「给定块持有一个 object、该 object 自己管状态」这条既有路径上。

**⚠️ D 路的最重代价须如实登记**：**忘记写 = 泄漏，且不可检测。**
而 ADR 恰以「**显式初始化易漏、易错**」为由否决了显式初始化 ⇒ 两侧标准不同，须说明白理由：

| 侧 | 忘记的后果 | 危险度 |
|---|---|---|
| 初始化（ADR 取隐形/惰性） | **「未构造」** —— 最多是晚构造或不用 | 安全 |
| 终结（D 路取显式） | **「泄漏」** —— 外部可观测，OS 兜不住 | **不安全** |

⇒ 这个不对称是**真实的**，不是双标。但也正因如此，ADR **必须明写**「终结责任在使用者」——
留空会让作者以为语言会帮忙（B 路的失败方式）。

### 六、这处不对称的新结论：不是「缺一项」，而是「**被判定为不可定义**」

上轮我把「初始化写 5+ 项、终结零字」当缺陷。按 D15 它**是裁决结果**，但**规格上仍不能留空**：

⇒ ADR 须明写一句「**本语言不定义给定块的终结**」并把责任归属写出来，
仍建议把「**寿命与清理**」立为与「惰性构造」**并列的一节**
——「不提供 X」本身是一条规格，写在正文里才可评审，留在未决问题 7 里不可评审。

## 5.7 专论：同名常量的消歧（用户提问，2026-09-19 七轮）

> **问题（用户原话）**：「我更关心 given 块自带的**同名常量**该如何消歧义。」

**先给结论**：这不是一个问题，是**四个半**。分层之后，**三层有干净判据**，
**一层靠 D24 顺手解掉**，**一层与 D25 相撞须先裁**。逐层如下。

### 一、先精确对象：「同名」在泛型下不成立

> ⛔ **本节结论已由 §5.8 三（D31 重述）取代** —— 重述后**没有用户可见的常量**，
> 「同名」这个对象**不复存在**。保留本节仅为记录推演过程（说明当时的定性会走到哪一步）。
> **不再据此裁任何事。**

D5 的图景是「类型名 + 同名常量」。这句话**只对非泛型成立**：

| 情形 | 声明 | 值位上的东西 |
|---|---|---|
| **非泛型** | `[应用服务\|given]` | **一个常量** `应用服务` |
| **泛型**（D22） | `[缓存<T>\|given]` | **一族单例** —— `缓存<I32>`、`缓存<String>` 各自独立 |

⇒ 精确表述应为：**非泛型 = 同名常量；泛型 = 同名常量族**。
这不只是措辞 —— 它决定**惰性初始化的粒度**：泛型给定块的初始化标记是**每实例化一份**，
而不是每块一份。ADR 的「未访问不构造 / 恰一次」须按此粒度重述。

### 二、声明层：类型与常量在当前实现里**会撞车**（实测）

```
x1  [服务|object]  值: I32 = 1
    服务|func() -> (I32,): return 2        → E3-004 语义错误（重声明）

x2  main|func() -> ():
        let 服务 = 服务()                  → check 通过，run 7 ✓（局部豁免）
        print(服务.值)
```

⇒ **顶层符号表是单一命名空间**（类型名与值名共用），而**局部天然是两个命名空间**。
⇒ 给定块要在顶层产出「类型 + 同名常量」，**必须给顶层开一道「类型 / 值」的口子**。
**这是本裁定唯一的落地成本**（已在 §5.1、§6.1 登记），且它触及 `E3-004` 的既有判据 ⇒ 须评估回归面。

### 三、引用层：**语法位置**决定命名空间（判据最干净）

| 位置 | 例 | 解为 |
|---|---|---|
| **类型标注位** | `数据: [I32]`、`服务: 应用服务` | **类型** |
| **表达式位** | `应用服务.提交(数据)` | **常量**（见四、成员层） |

⇒ 判据是**语法事实**（位置），不需要查表、不需要回退。
Scala 的 `object` 是同构先例：同一个名字，术语/类型两个命名空间各占一个。

### 四、成员层：**成员种类**决定走哪条路 —— 且**不会有平局**

`应用服务.提交(数据)` 有两种读法，对应 D9 保留的两个修饰符：

| 读法 | 取到 | 触发初始化？ |
|---|---|---|
| 按**常量** | `\|self` 方法 / 字段 | ✅ 触发 |
| 按**类型** | `\|own` 方法 | ❌ **不触发**（D12：`\|own` 不得触实例） |

⭐ **关键实测：同名 `|self` 与 `|own` 不能并存** ——

```
x5  {{服务}}
        取|self() -> (I32,): return self.值
        取|own()  -> (I32,): return 9        → E3-004 语义错误（重声明）
```

⇒ **一个成员名唯一对应一种种类** ⇒ **「按成员种类路由」是全函数，不存在平局情形**，
不需要 tiebreak 规则。这一点让方案可用 —— 否则就得再设计一条歧义裁决。

⭐ **副产物：这条路由给了 D9 一个可直接观察的差异。**
按 §5.5 ①（`|own` 不得触实例），`|own` 成为**「用给定块的命名空间但**不**触发其初始化」**的通道。
ADR 的招牌卖点「未访问的给定块从不初始化」由此有了一个**逐处可控**的表达手段，
不再是全有全无 —— 这是 D9「两者同时保留」的正当理由从「形态对称」升级为「语义分工」。

### 五、泛型层：与既有「构造表达式」撞形 —— **靠 D24 解掉**

⚠️ 实测：`名<实参>` 在**表达式位今天就是构造表达式**，且**确实构造**：

```
w3  (点<T>)  x: T = 建点()            ; 建点 里 print("侧效：构造发生了")
    ((点<T>)) 取|own() -> (I32,): return 9
    main: let v = 点<I32>.取()
    → 输出：侧效：构造发生了 9          ← 构造真的发生了
```

（隔离过混淆变量：**唯一能跑通的是「泛型 + struct」**这一格；
`盒<I32>.取()` 配 object、以及非泛型的 `点.取()`**都是 `E6-004`** —— 见八。）

⇒ 若泛型给定块的 `缓存<I32>` 在值位也用同一拼写，**两种含义冲突**：
「构造一个新实例」vs「取该实例化的单例」。

⭐ **D24（不支持显式构造）恰好把它解掉**：给定块**不可能被构造** ⇒
`缓存<I32>` 在给定块的语境里**只能**解为单例，**没有第二种可能**。
⇒ 消歧判据 = **按块种类**（一般类型 ⇒ 构造；给定块 ⇒ 单例）。

⚠️ 代价照记：**同一语法按块种类语义不同**。但它**不是新引入的做法** ——
D6 已裁「字段不可变由**块种类隐含**」（同一 `field-decl` 在 `|given` 内不可变、在 object 内可变）。
⇒ **有先例，且是同一类处理**（块种类隐含语义）。

⚠️ 另一条实测约束：**裸名在值位不可用**。

```
w4  (盒<T>)  内容: T
    主用|func(b: 盒<I32>,) -> (I32,): return 1
    main: print(主用(盒))                → E6-004（IRGen）
```

⇒ 泛型给定块**必须写类型实参**；`缓存` 裸名不能当作值。

### 六、跨模块层：本仓既有规则给出一条**必须明写的约束**

实测 §2.5（访问控制）：`_` 前缀 = **private**，可见范围「**当前类型内部**」；
且**跨模块引入门槛仅 `public`**（private / internal / package **一律不可跨模块引入**）。

⇒ ADR 写「类型名 `_` 前缀私有」有两个毛病：

1. **语义空洞**：private 的定义是「当前类型内部」，而给定块是**顶层**类型 ⇒ 该定义对它不成立；
2. **缺一条必须写的约束**：ADR 的核心动机之一是「**跨模块**共享同一实例」，
   而按现行规则 `_` 前缀的给定块**跨模块完全不可见** ⇒
   **要跨模块共享就必须 `public`**。ADR 没写这句，读者会以为 `_` 能同时满足封装与共享。

（字段级那条 ADR **是对的**：实测 `enforceFieldVisibility` 判「访问者类型 ≠ 声明类型 ⇒ `inaccessibleField`」，
正是封装所需 —— 只是 ADR 没说这是理由。）

### 七、⚠️ 与 D25 正面相撞：trait 实现怎么声明？

**`实现` 不是关键字**（实测：`KEYWORD` 表 34 个，无 `实现`），
trait 实现今天的写法是**一个无初值的字段声明**：

```
field-decl ::= IDENT ':' type-annotation ['=' expression];

examples/trait.pini:
    实现: 可描述                     ← 结构上就是「无初值的 field-decl」
```

⇒ **D23（支持 trait）+ D25（要求必须完整提供字段构造）在给定块上直接冲突**：

- D25 的兑付判据是「**缺初值的字段报错**」；
- 而 `实现: 可描述` **恰恰没有初值**（按 G57，`实现: T` 是**标注**、不是值注入，本不该有 `=`）。

⇒ 三条出路，**须一并裁**：

| 取法 | 内容 | 代价 |
|---|---|---|
| **甲** | `实现: T` 视为**独立的声明种类**（不是字段），D25 只管**状态字段** | 须在文法/语义层区分两者（今天同形）；判据从「字段」收窄为「状态字段」 |
| **乙** | 给定块的 trait 实现在**扩展块**声明（`<<给定块名>>`） | 与 object 的既有写法**不一致**；但语义更顺（实现是行为，不是状态） |
| **丙** | D25 放宽为更弱的形态（如只管引用类型字段） | 判据变复杂，且**丢掉 D25 的主要收益**（完整性保证） |

**我倾向甲**：`实现: T` 与本义上的字段是**两种东西**（一个是类型级标注、一个是值），
今天的同形是**实现层面借用**，不该让它决定语言层的判据。
取甲则 D25 的兑付判据精确化为「**状态字段缺初值 ⇒ 报错**」，
且 `实现: T` 在给定块内**照样合法**。

### 八、⭐ 第八轮提出：**「同名常量」与「支持泛型」互斥**（待裁，非裁决）

> ⛔ **本节结论已由 §5.8 三（D31 重述）整节消解** —— 重述后**无常量可绑**，
> 泛型给定块的每个实例化各有自己的默认值，**互斥不成立**。
> ⚠️ 连带：本节·b 记的「与 D22 / D23 的正面冲突」**也随之消失** —— **D22 不再与任何东西互斥**。
> 保留本节仅为记录推演过程（并作为「定性错一层、推论会连锁」的实例）。**不再据此裁任何事。**

> **用户原话（2026-09-19 八轮）**：
> 「假如 given 自带同名常量，你的问题**等价于** given 块**多次实例化到常量如何处理**。
> 这真的很难裁定，**可能把 given 排除到复合类型之外，它作为常量集是一个好的选择**，
> 我想不出什么场景下会需要 given 块多次实例化。」

#### (a) 用户给的等价关系成立，且可以再加一刀把它变成**互斥**

「同名常量」与「支持泛型」**不能同时成立**，理由是**值必须确定**：

| 步 | 内容 |
|---|---|
| 1 | 常量是一个**值**；一个名字在一个时刻只能绑定**一个**值 |
| 2 | `缓存<I32>` 与 `缓存<String>` 是**两个不同的值**（各自独立的单例） |
| 3 | ⇒ 名字 `缓存` 无法同时绑定两者 |

**唯一的逃生舱是「默认类型参数」**（`缓存<T = I32>` ⇒ 裸名取默认实例化）。
⭐ **实测：Pini 没有这个机制** —— `generic-params` 产生式在 §A **甚至未单列**
（只在 struct/object/enum/extension 四个 decl 里被引用），更无默认值语法。

⇒ **结论：`given` 有同名常量 ⇒ `given` 不能有泛型。二者必居其一。**
用户的直觉准确：这不是「消歧技巧」问题，是**两个设计不可共存**。

#### (b) ⚠️ 与上一轮刚裁的两条正面冲突（须你确认是修正还是我理解有误）

| 轮次 | 裁决 | 与本节的冲突 |
|---|---|---|
| 七轮 **D22** | **给定块应当支持泛型** | 与「同名常量」**互斥**（见 (a)） |
| 七轮 **D23** | **给定块应当支持 trait** | 「常量集」**不是类型** ⇒ 无 trait 可实现（trait 是类型层机制） |

**本件不替这两条选**，只把冲突摊开。用户八轮的话（「想不出场景」）读起来像是在**修正 D22**，
但 D23 与「常量集」的关系更根本 —— 若 given 不是类型，trait 实现**整个前提消失**。

#### (c) 实测：**泛型今天根本不能作参数类型** ⇒ 泛型 given 与 `using` 不可兼得

孤立变量后（同一份 struct 定义，只改泛型出现的位置）：

| 探针 | 泛型出现位置 | check | run |
|---|---|---|---|
| `u1` | **函数参数类型** `主用\|func(b: 盒<I32>,)` + 实际调用 | 通过 `rc=0` | **`E6-004`** `rc=1` |
| `u2` | **局部变量** `var h = 盒<I32>()` | 通过 `rc=0` | **`7`** ✅ |
| `u3` | 局部变量在**另一个函数内** | 通过 `rc=0` | **`7`** ✅ |

对照：`examples/generic.pini` 本身**能跑**（实测输出 `7` / `泛型值`）—— 它用的正是局部变量形态。

⇒ **泛型的可用范围止于函数内部**；**不能跨函数边界**（参数 / 返回）。
⚠️ 这与 D14 的 `using` 机制**直接相撞**：`using app: 应用服务` 要求类型出现在**参数表**里。
⇒ **泛型给定块 + `using` 在今天的实现上不可同时成立**（不是设计问题，是 `E6-004`）。

#### (d) 诚实评估：「多次实例化」的真实场景

用户说想不出。我推了四类，**逐一说明为何都不成立**：

| 候选场景 | 为何不成立 |
|---|---|
| **测试替身**（替换实现） | 按 §5.5 ⑥ 的分析，`using` **不是依赖注入**（编译期解析、无运行时查找）⇒ **本来就不可替换、不可 mock** ⇒ 泛型也给不了这个能力 |
| **多租户** | 那是**运行期**多实例，泛型是**编译期**实例化，帮不上忙 |
| **多环境 / 多后端**（主库 + 分析库） | 那是**两个不同的给定块**（两个名字），不是同一块的两次实例化 |
| **类型特化缓存**（`缓存<I32>` / `缓存<String>`） | ⭐ **唯一真正用到泛型的场景** —— 但可由「非泛型给定块 + 内部持泛型容器」替代（今天的泛型足以表达容器） |

⇒ **我同意用户：真实的「泛型程序级单例」需求很弱。**
而「泛型给定块」要付的代价（消歧难题 + 参数表不可用）**是确定的**。**收益弱、代价确定。**

#### (e) ⚠️ 「排除到复合类型之外」这个提法**缺少可操作判据**

实测：**本仓规范没有「复合类型」的定义条目** —— 该词只散见于 `*T` 的语境
（「禁 `object` 或含 `object` 字段的**复合类型**」）。
⇒ 因此「把 given 排除到复合类型之外」**目前无判据可依**，须先明确它指哪一族。

**两种读法，代价差别很大**：

| 读法 | given 的身份 | 连带后果 |
|---|---|---|
| **(i) 温和** —— given 仍是**类型**（可作标注），只是**不参与泛型、不实现 trait**（即不入 object/struct/enum 那一族） | 类型 + 同名常量 | 与 D22/D23 冲突，但**保住 ADR 的 `using` 锚点**（`using app: 应用服务` 仍有类型可写）、保住 D3、保住 D9 |
| **(ii) 激进** —— given **根本不是类型**，只是「命名常量集」（类模块 / 命名空间） | 只有常量 | ⚠️ 拆掉四处：**①** `using` 的**类型锚点消失**（`using app: 应用服务` 没有类型可写，须改锚）**②** `\|own`（类型级方法）**失去意义** ⇒ 与 D9「两者同时保留」冲突 **③** D3「给定块是常量复合类型」作废 **④** trait 更不可能 |

**我倾向 (i)**：

1. 用户的直觉（「常量集」）抓住了**本质** —— given 的价值是「**程序级唯一的名字**」，
   不是「类型参数化」。这个判断我认同；
2. 但 (ii) 会**拆掉 ADR 自己的 `using` 设计**（`using app: 类型名` 的「类型名」必须存在），
   代价远超它解决的问题；
3. (i) 用「**是类型、但不入复合类型族**」同时保住锚点与消歧 ——
   与 D6 的「块种类隐含语义」**同一手法，已有先例**。

⇒ **建议：取 (i)，并把 D22/D23 收窄为「给定块不参与泛型参数化、不实现 trait」**，
同时明写给出理由（泛型无真实场景 + 参数面不可用 + 消歧难题）。

### 九、验收提醒（实测）

**所有 `类型名.成员` 的失败用例，`pini check` 一律报「检查通过」**（`rc=0`）：

| 探针 | check | run |
|---|---|---|
| `服务.取()`（非泛型 object） | 检查通过 `rc=0` | **E6-004** `rc=1` |
| `点.取()`（非泛型 struct） | 检查通过 `rc=0` | **E6-004** `rc=1` |
| `盒<I32>.取()`（泛型 object） | 检查通过 `rc=0` | **E6-004** `rc=1` |

⇒ `E6-004` 属 **IRGen 层**，不在 `check` 的覆盖面内。
**`check` 的退出码本身是对的**（`rc=0` 表示「它自己那套判据通过」），
但它**对这条规则是盲的**。⇒ **消歧规则的验收不能靠 `check`**，
须用 `run` 或专项夹具。这与本仓已登记的「`clean` 不覆盖行为面」同族。

> 顺带一条方法论记账：本轮我先用 `pini check f | head -3; echo rc=$?` 取退出码，
> 得 `rc=0` 而**误以为「报错却返回 0」** —— 实际那是 **`head` 的码**。
> 改为重定向到文件后，`rc=1` 正确。**取退出码一律不接管道**（同类教训第二次发生）。

### 十、⭐ 第八轮续：「把字段过渡到用例」的评估（用户设想，**讨论**）

> **用户设想的原话**：「又或者，像 enum 那样，把**字段过渡到用例**，**每个字段都带构造器**，
> 但是**不允许被 match**。这个设想的问题是，它**无法自描述**，似乎**无法落实到自举**，请你考虑。我们在讨论。」

**我的结论：用户的诊断成立，但成因比「无法自描述」更具体，而且可以精确到一个类型论错位。**
（⚠️ 本轮是讨论，**不记为 D 号**。）

#### (a) 核心问题：**这是把积类型写成和类型**

| | 枚举 | 给定块 |
|---|---|---|
| 类型论位置 | **和类型（sum）**：N 选 1 | **积类型（product）**：N 个全在场 |
| 判据（实测规范） | 「枚举 match 缺变体且无 `case _:` → `nonExhaustiveMatch`」，**穷尽性检查总是开启** | **D25**：必须完整提供字段构造 ⇒ **每个字段都有初值** |
| 「哪个？」这个问题 | ✅ 有意义（match 就在回答它） | ❌ **不存在** —— 没有「哪个」可问 |

⇒ **两种收场，都不是好结果**：

- **若「用例」真是和**：给定块一次只能持有**一个**成员 ⇒ 与它的用途（调度器 **和** 队列 **和** 连接池同时在场）**直接矛盾**；
- **若「用例」不是和**：那它只是「字段」的**改名** ⇒ **零语义增量**。

⇒ ⭐ **「不允许 match」不是附加限制，而是这个错位的必然症状**：
match 是**和类型**才需要的操作；积类型**没有可分的情形**。
**被禁掉 match 的地方，正是「用例」这个词本该有内容的唯一地方。**
⇒ 换句话说：**这个设计把 case 的语义内容全部剔除了，只留下 case 的外观。**

（同源的一条：「每个字段都带构造器」在和类型里才成立 —— 因为**由使用点选择哪个用例**，
所以每个用例各有构造器。积类型**只有一个**构造，一次把全部字段收齐。
「N 个字段各带一个构造器」会得到「用一个字段构造出整个值」的怪论。）

#### (b) 自描述为什么必然失败 —— **自举编译器里已有实证**

⭐ 本仓的自举编译器**已经**把「字段声明」表示成**一个枚举用例**（`examples/selfhost/src/ast/ast.pini`）：

```
[field_decl]
; host FieldDecl: no initializer -> initializer = [expr].none
field_decl(name: String, annot: type_annot, initializer: expr, loc: src_loc,)

[decl]
struct_decl(name, generic_params, fields, methods, composed, traits, loc,)
func_decl(name, modifiers, generic_params, params, return_types, ...)
extension_decl(kind, target, target_annot, methods, loc,)
import_decl(alias, path, loc,)
export_decl(alias, symbol, loc,)
top_stmt(item: stmt, loc,)
```

**三个要点**：

1. **「字段是枚举用例」这句话在自举编译器里已经成立** —— 但那是**描述层**：
   编译器用枚举用例**描述**一个字段，其载荷是**未求值的** `expr`（注释明写「no initializer -> `[expr].none`」）；
2. `[decl]` 列出**全部**声明种类，**全部是用例**，且 `ast/` 模块内用了 **30 处 `match`** ——
   **自描述在本仓的实际形态 = 用枚举描述语言构造 + 用 match 处理它们**；
3. **提案说的是「字段本身应该成为枚举用例」（本体层）** ⇒ **与描述层形式相同、层次不同**。

⇒ ⭐ **这就是「无法自描述」的精确形态**：语言的**描述手段**与被描述对象**共用一个语法外观**，
而唯一能区分它们的操作（`match`）被禁止。
⇒ 自举编译器无法回答「我这一段是在**描述**一个用例，还是在**持有**用例」——
**而它整份代码都在做前者**（30 处 match 就在做这件事）。

#### (c) 自举判据是规范**明文**的，这个形态在判据上是**负分**

`../pini-spec-v0.md`「自举前置检查」：

> 2. **语言自宿主能力**：Pini 需能表达「重写 `@bk_*`」所需的程序结构……
>    ——当前 `ok`/`err`、**`match`**、泛型、**`LazyRef`**、`|test` 已提供**核心构件**。

> **执行指引 2**：语言新特性评估**自举可用性**：以 Pini 写的 Pini 编译器**能否用它表达宿主实现需求**为判据之一。

⇒ 按这条判据打分：

| 判据 | 本形态 |
|---|---|
| 贡献自举所需能力？ | ❌ **零** —— 自举要的是 `match`（被它禁）与 `LazyRef`（已有） |
| 减少已有负担？ | ❌ 零 —— 它**不替代**任何东西 |
| 引入特判成本？ | ⚠️ **有** —— 自举的 parser / ast 必须为「**看着像枚举但不是**」增设一条分支 |

⇒ **不减不增、只增一处特判** ⇒ 在规范这条判据上是**负分**。
（自举仓实测结构：`ast` / `lexer` / `parser` / `type` / `codegen` / `interpreter` / `semantic`，
`ast` 214 行 + `format` 353 行 + `lexer` 1375 + `parser` 1593，**其中 `ast` 是描述层的核心**。）

#### (d) 有用的内核：**几乎没有**，但有一处可回收

| 设想的成分 | 是否可回收 |
|---|---|
| 「成员各自带来源（构造器）」 | ❌ 已由 `field-decl` 的 `= expression` 表达 |
| 「成员的形状可独立于值命名」 | ❌ 已由**类型标注**表达 |
| 「成员在类型名下具名」 | ❌ 已由「字段名」+ 类型名表达 |
| 「**一个具名积类型**」 | ⭐ **这一条是真需求，但本仓已有手段** —— **单用例枚举**（自举自己就用：`[field_decl]` 是单用例枚举） |

⇒ **结论：设想里没有能在不改语义的前提下保留下来的成分。**
唯一的真需求（「一个有名字的积类型」）本仓已能表达。

#### (e) 我建议的替代：**保持「是类型」，并给出自举成本**

承接 §5.7 八·e 的 (i) 读法（**给定块仍是类型，只是不入复合类型族**）：

1. **消歧不需要新语法** —— 三层判据已经够了（§5.7 二/三/四）：位置（类型位 vs 值位）、
   块种类（**D24 禁构造 ⇒ `缓存<I32>` 只能是单例**）、成员种类（`|self`/`|own` 无平局）；
2. ⭐ **自举成本可当场量出**：自举只需在 `[decl]` 加**一个用例**，
   形如 `given_decl(name: String, fields: Any, loc: src_loc,)` ——
   **与既有的 `struct_decl(… fields: Any …)` 同构**（字段载荷**复用** `[field_decl]`，无需新表示）；
3. ⇒ 即**一个枚举用例 + parser/semantic 分支**，而**不**引入第四种「用例形态」。
   这正是规范「执行指引 2」要求的**自举可用性证据**：**成本可数、复用既有表示。**

⇒ **对比**：用户设想的形态会让自举必须新增一种「看着像用例、不能 match、且字段带已求值来源」的
声明表示 —— 与 `[field_decl]`（载荷是**未求值** `expr`）**不能共用** ⇒ 自举要多一套表示，
而它**一点新能力都不带来**。


## 5.8 重述：given = **带编译器默认实例的复合类型**（D27–D31；**已按 D32 / D38 订正**）

> 本节是**本件的主叙述**。它取代 §5.1（常量绑定）、§5.7 一（声明层撞名）、§5.7 八（与泛型互斥）三条结论。
> 装置与全文一致（`pini 0.54.0`）；本节所有实测均为**现行语义直测**，**不需要等价改写**
> —— 它们测的是**值类型怎么表现**，与给定块是否已实现无关。

### 一、方案 B 为何不可行（D27）

B = 把 given 的**字段类型与字段名**放进参数位：

```
处理|func(队列: 队列类型, 调度器: 调度器类型,) -> (I32,)
```

两个独立的死因：

1. **解析键丢失。** `using` 的解析键是**给定块的类型名**；B 的参数上只有**字段类型**。
   而 `队列类型` 可以出现在多个给定块里 ⇒ 到调用点「按类型找块」**没有唯一候选**。
2. **退化为普通参数。** 调用点若能自造 `队列()`，这个参数与普通参数**没有任何区别**
   —— `using` 的全部意义蒸发。**B 不是另一种设计，是把现状改个名。**

（这解释了为什么 B **不需要被批准**：它今天就是合法代码 —— 正因为它是普通参数。）

### 二、局部覆盖（D28 / D29）· ⛔ **本节已由 D33 整体撤销**

> **D33：「局部不覆盖，取消 `given`」** ⇒ D28（允许局部覆盖）与 D29（局部可取消 `given` 关键字）**撤销**，
> 本节全部设计**不再成立**。随之消失的还有：`using` 作为「可被覆盖的真绑定」的论证（D28 的由来）、
> 以及它的**偶然捕获风险**（任何同类型局部绑定都会成为插入源）。
>
> ⚠️ **但本节有一处结论在当前模型下必须保留** —— 那句「`using` 参数必须成为体内该类型名的绑定，
> 否则同一函数内两条路会拿到不同实例」的推理**前提是「覆盖存在」**；D33 撤掉前提后，
> **该推理不再需要**。当前模型下 `using 名` 只是把默认实例绑给局部名，逐层声明仍由 D14 / D19 规定。
>
> 另：本节记录的**三条已就位机制**（值/类型命名空间可分离 · 「期望类型优先 + 唯一回退 + 歧义拒绝」已实现 ·
> 嵌套成员访问可用）**仍然有效**，只是**当前模型用不到它们**（不再需要遮蔽 / 类型定向解析）。
>
> 保留下文仅为记录推演过程。**不再据此裁任何事。**

**原内容（已作废）**：

**可行形态**：作用域内声明一个**同类型的绑定**，即成为该作用域内该类型的插入源。

```
main|func() -> ():
    given 应用: 应用服务 = 应用服务()      ; 局部覆盖：本作用域内的插入源
    处理(1,)                                ; 处理 声明了 using 应用: 应用服务
    return
```

⚠️ **写法待裁**（§7 A 组第 4 项）：`given` 关键字是否保留（D29 说**可取消**）。

**三条机制已就位**（实测，均为现行语义）：

| 需要什么 | 实测 |
|---|---|
| **值 / 类型命名空间可分离** | `let 服务: 服务 = 服务()` ⇒ `服务.值` 走**局部值**（`5`），而类型标注 `let 乙: 服务 = …` 与构造 `服务()` **仍解析为类型** —— 全通过 |
| **解析算法** | 「**期望类型优先 + 唯一回退 + 歧义拒绝**」**已实现**（见 `pini-swift/examples/enum-dot-case.pini`，其注释即算法说明，与 Swift `UnresolvedMemberExpr` 同构）。四态实测：单枚举裸名无期望类型 ✅ 唯一回退；两枚举同名无期望类型 ❌ 歧义拒绝；有期望类型 ✅ 静态决议 |
| **嵌套成员访问** | `a.字段.方法(…)` 通（object 与 struct 皆可） |

**⇒ 局部覆盖不需要新命名空间机制，也不需要新解析算法。**

**它买到什么**：覆盖**穿透传递闭包**，而**不必重新穿参**。这是它与「D19 显式传参」的唯一实质差别——
显式传参要把普通参数**逐层穿过中间函数**，**正是 given 要治的病**。

**它同时把 `using` 变成真绑定**（D28）：`using 应用: 应用服务` 的含义由
「程序级那个单例」改为「**作用域里那个 A**」。⇒ 我此前「`using` 只承载文档」的判词**作废**。

⭐ **并由此把 D14 的「强制」从风格选择升级为逻辑必需**：若 `using` 在**调用点**解析以让覆盖穿透，
则函数体内对 `A` 的引用必须取到**同一个**绑定 ⇒ **`using` 参数必须成为体内该类型名的绑定**。
否则同一函数内 `app.提交()`（参数，局部实例）与 `应用服务.提交()`（裸名，程序级默认值）
会拿到**两个不同实例** —— 一个静默的错配。

**两条通道由此各有一句干净的意思**（D19 的定位也随之精确）：

| 写法 | 含义 |
|---|---|
| `using 应用: 应用服务` | 「A 来自环境」—— **可被覆盖** |
| `应用: 应用服务`（普通参数） | 「A 是我的」—— 调用点必须明说，**不可被覆盖**（= 退出环境解析） |

**诚实的限度**：**词法**而非动态 —— 无运行时替换、无按调用点替换、**不是依赖注入、不可 mock**；
作用域即覆盖可达范围。且**拒绝 `using` 而用普通参数的函数落在覆盖之外**。

⚠️ **一处风险**：若局部覆盖**纯按类型**，则**任何**同类型的局部变量都会**静默**改变该作用域下
所有嵌套 `using` 参数的取值（**偶然捕获**）。缓解见 §7 A 组第 5 项。

### 三、重述后的模型（D31）

> 用户原话：「它**表现得像一个具有编译器默认行为的值类型**，**常量是编译器带来的**，
> 考虑到**在函数参数位置上的不变性**，given 作为值类型，**字段究竟可不可变是无关紧要的**，
> **自动插入同一个量是编译器行为，甚至很难称得上是常量**。」

**模型**（**已按 D32–D37 收敛为终版**；取代 §5.1 的「类型名 + 同名常量」）：

| 面 | 内容 |
|---|---|
| 身份 | **复合类型**（D35：**真正视为复合类型**），可作类型标注 |
| 实例数 | ⭐ **任意多个**（D34）—— 与普通复合类型同规 |
| 构造 | ✅ **像一般复合类型那样构造**（D35，==撤销 D24==）⇒ `应用服务()` 合法 |
| 默认值 | 各**字段初值**合起来**就是**编译器提供的那**一个实例**；**惰性物化、恰一次**（每类型实例化一份）。⭐ 物化出来的**就是** `using` 绑定的那个实例本身（D38：非模板、非副本） |
| `using` 取用 | `using 名: 类型` ⇒ **绑定该类型的默认实例本身**（D38：**不是副本**，就是同一个实例）；解析**按类型**（D36） |
| 字段可变性 | ⭐ **可写**（D32）—— `self.元素 = …` 是合法写法；写语义问题归 **COW 等优化** |
| `self` | = **接收者实例**，**不做值 / 引用语义区分**（D32） |
| 声明期完整性 | 字段无初值 ⇒ **无完整默认值** ⇒ `using` 无从物化（D25 升为机制定义） |

> ⚠️ **D32–D37 撤销了本表两个早期约束**：D1/D6 的「字段不可变」（§5.2 已作废）与 D24 的「禁止构造」。
> 二者原本都是为「单例」服务的；单例一撤（D34），它们失去理由。

**⇒ 程序级共享从哪来？—— 来自引用字段。** 这是本次重述的**地基**，已实测：

```
[队列|object]
元素: [I32] = []

{{队列}}
入队|self(v: I32,) -> (I32,):
    self.元素 = self.元素.append(v)
    return len(self.元素)

(绑)
队列: 队列 = 队列()          ; 字段是 object（引用）

main|func() -> ():
    let a = 绑()
    let b = a                    ; 值复制
    print(a.队列.入队(1,))       ; → 1
    print(b.队列.入队(2,))       ; → 2   ← 同一个对象 ⇒ 共享成立
    return
```

作参数传入同样共享（返回 `1` / `2`，其后 `a.队列.入队(3,)` → `3`）。
**对照**：**两次独立构造**各得自己的对象（`1` / `1`）；**值字段每份一份**（写 `a.n` 不影响 `b.n`）。

⇒ **共享有两个来源，且两者现在都硬**：其一是**默认实例本身** —— D38 裁定 `using` **绑定同一个实例、不复制**
（复制是「不必要的细节」，还会**限制编译器优化**）；其二是**引用字段** —— 上面的实测证明，复制值类型后引用字段仍指向同一对象。
所以 D31 成立：given 可以是复合类型，程序级资源照样交付。

⚠️ **但「程序级」仍是「用法的性质」而非「类型的保证」**（D34 / D35 引入）—— 只是**破口只有一条路**：

| 写法 | 拿到的是 |
|---|---|
| `处理(1,)`（`处理` 声明 `using 应用: 应用服务`） | ⭐ **同一个默认实例本身**（D38：非副本）⇒ 与所有其他 `using` 取用共享**同一对象** |
| `处理(应用服务(), 1,)`（自己构造后显式传入） | **你自己的新实例** ⇒ **不共享** |

⇒ 只要**所有**取用都走 `using`，程序级共享就是**确定的** —— 绑定的是**同一个实例**，不是「内容相同的两份」。
⇒ **「程序级单例」不再是语言保证**，而是「大家都用 `using` 取用」的结果。
ADR 的招牌卖点须据此改述：**不再承诺唯一性，只承诺「同一个默认实例」**。
（诚实地说：若某处自行构造，资源就不再共享，而**语言不会报错**。）

⚠️ **另一条须明写的规则**：**可变共享状态必须放进引用字段**。
值字段随副本各一份 ⇒ 若把可变状态放进值字段，共享会**静默失效**。
（D32 说「写字段归 COW 管」成立于**写语义**；而**字段该放值还是放引用**仍有语义后果。）

**特征默认实现如何拿到实例**（十一轮的答案）：**走 `self`，零新机制。** 给定块自己实现该特征，
则默认体的 `self` **就是接收者实例**，`self.队列` 直接可达（实测：默认体 `return self.值` 对 object 有效）。
⇒ **特征默认实现不需要 `using`**；只有要访问**另一个**给定块时才需要声明。

| D25 | ⬆️ **从「兑付判据」升为「机制定义」** —— 字段初值合起来**就是**那个默认值；缺一项 ⇒ 无完整默认值 ⇒ **无法插入**。它与 `实现: T` 的冲突按「甲」（§5.7 七）更加站得住 |

**再加第十三轮（D32–D37）撤销的四条**：

| 已录内容 | 撤销后 |
|---|---|

### 五、⛔ **本节已由 D34–D38 整体关闭**

> 原文列出两项待裁（值位给副本还是本身 / 局部覆盖是否要求绑定名 = 类型名）。
> **两项均已关闭**：
> - 「值位引用给**本身**还是**副本**」—— ⭐ **D38 直接裁定给「本身」**：`using` **绑定同一个默认实例，不复制**。
>   （D34 允许任意多实例、D36 规定解析**按类型**，本来已无歧义；D38 把「不复制」也定死。）
> - 「局部覆盖是否要求绑定名 = 类型名」——**局部覆盖已撤销**（D33）。
>
> **净效果：§5.8 原有的两项待裁全部关闭，且未新增待裁。** 见 §7 的 A 组重编（**已降为 0 项**）。

### 六、代价（须进 ADR 代价表）—— **已按 D32–D38 更新**

| # | 代价 | 说明 |
|---|---|---|
| 1 | **字段初值可能多次求值** | 允许构造（D35）后，**每次构造都跑一遍字段初值**（默认实例仍是「恰一次」）。`连接数据库()` 读起来像只跑一次，须明写 |
| 2 | ⭐ **「程序级」从类型保证降为用法约定** | 自行构造的实例**不共享**，而语言**不报错**。ADR 不能承诺**唯一性**，可承诺「**同一类型的所有 `using` 取用共享同一个默认实例**」 |
| 3 | **可变共享状态必须放进引用字段** | 放值字段则共享**静默失效** |

> ⛔ **原第 1 条「`using` 每次插入一次默认实例的副本」已撤销**（D38，第十四轮）：`using` **绑定同一个默认实例，不复制**。
> 理由是这一条**不必要的细节**，且**会限制编译器优化**。⇒ 它从代价表**删除**，不是改述。
> 顺带的正面效果：「程序级共享」由「**内容相同的两份**」升级为「**同一个对象**」，**共享有了对象身份**（与上表「地址稳定」互相印证）。

### 6.7 第八轮续（「字段→用例」设想）的评估结论

> ⚠️ 本轮是**讨论**，产物是**评估**，不是裁决。下表是评估给出的可执行结论。

| 项 | 结论 | 依据 |
|---|---|---|
| **「字段过渡到用例」是否采纳** | ❌ **建议不采纳** —— 它是**把积类型写成和类型**：要么给定块变成「N 选 1」（与用途矛盾），要么「用例」只是「字段」改名（零增量） | §5.7 十·a |
| **「必须完整提供字段构造」（D25）与之的关系** | ⭐ **D25 正是「给定块是积类型」的正式声明** ⇒ **D25 与该设想互斥**（D25 要求全在场；用例形态意味着 N 选 1） | §5.7 十·a |
| **「不允许被 match」的性质** | ❌ **不是可选的限制，而是错位的症状** —— match 是和类型才需要的操作；**禁掉它的地方正是「用例」本该有内容的唯一地方** | §5.7 十·a |
| **自描述失败的机制** | 语言的**描述手段**（自举用枚举描述构造）与被描述对象**共用语法外观**，而区分它们的操作正是被禁的 `match` | §5.7 十·b（`ast/ast.pini` 实证） |
| ⭐ **自举成本（规范「执行指引 2」要求的证据）** | 采纳替代方案 ⇒ 自举只需在 `[decl]` 加**一个用例**：`given_decl(name: String, fields: Any, loc: src_loc,)`，**与既有 `struct_decl(… fields: Any …)` 同构**，字段载荷**复用** `[field_decl]` | §5.7 十·e |
| **`[decl]` 需新增的用例**（若采纳替代方案） | `given_decl` —— ⚠️ 自举仓是**嵌套独立仓**，改动须走**自举仓自己的分支 + `--no-ff` 合并**（跨仓 ⇒ 另一条授权线） | 同 `G70` 的跨仓纪律 |
