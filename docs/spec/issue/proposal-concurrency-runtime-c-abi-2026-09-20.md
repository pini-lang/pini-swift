## 2. 形状必须照的三条**既有**硬约束

| # | 约束 | 出处 |
|---|---|---|
| 1 | ⛔ **C ABI 是 MUST**：句柄 = `void*`（IR 中 `ptr`），对外函数一律 `@_cdecl`。理由原文：「否则阶段3 纯 libc 重写时**被锁死**」 | `PiniRuntime.swift` 自述 |
| 2 | **wrapper ABI 已统一**：codegen 生成的闭包装箱函数形如 `ptr (ptr code, ptr env, ptr out) -> ptr` —— `LazyRef` 与给定块两处**已在用** | `PiniRuntime.swift`（`bk_lazyref_create` / `bk_given_get`） |
| 3 | ~~**`Future` 没有 `HIRType` case**（契约立场：它是**运行时值**）~~ —— ⛔ **该条已作废，2026-09-20 订正**：用户裁定**取甲**（真建 L0）⇒ `DE-3a` 给类型层加了 `future(ok:)`，`=>` 的对外签名从此是句柄 | 原依据 = `HIR 契约` 的 `join` / `detach` 两条。⚠️ 订正后的依据见本件 §7 的 `DE-3` 行 |

⇒ 三条合起来的含义：**并发面照抄既有 ABI 形态，不新造第二套**；
且**不得**把 Swift 侧的 `FutureValue` / `Scheduler` 协议暴露到边界上（那正是「按 C ABI 重新实现一遍」的理由）。

## 3. 原语层 ABI 面（**拟定，供裁**）

命名照 `bk_*` 既有族；句柄 `void*`；长度 / 状态用 `i32`；返回值走 **out 缓冲**
（照 `bk_lazyref_value` 的「运行时分配、wrapper 写入」模式，规避返回栈地址的逃逸 UB）。

### 3.1 任务与 join

| 函数 | 签名 | 语义 |
|---|---|---|
| `bk_task_spawn` | `(wrapper, code, env, elemBytes, elemTag) -> handle` | 派发任务体。**照 §2 第 2 条的 wrapper ABI**，不新造 |
| `bk_task_join` | `(handle, out) -> status` | **阻塞** join（现行唯一形态）。`out` 写 `Result` 聚合 |
| `bk_task_join_within` | `(handle, ms, out) -> status` | 带超时阻塞 join；超时归约 `err(CancelError)`（与解释器腿 `joinWithin` 同构） |
| `bk_task_join_all` | `(handles, count, out) -> status` | 聚合，**fail-fast**：任一 `err` 即返回并取消其余 |

⭐ **`out` 的形态照 `Result` 的既有 ABI**（三槽）：**槽 0 = tag**（`ok=0` / `err=1`）·
槽 1 = ok 载荷 · 槽 2 = err 载荷（**擦除为 i64 宽度**）。
⇒ `await` / `wait` 站点解构时，**发射层已有三槽读写代码**（本仓 `match` 的 Result 分派同族），
故 `DE-3` 在这处**不需要新 ABI 概念**。

### 3.2 ⭐ 让出（本批新增的唯一原语）

| 函数 | 签名 | 语义 |
|---|---|---|
| `bk_task_yield` | `() -> i32` | **让出当前任务**：若后端能释放当前 OS 线程则释放并让调度器选下一个任务；**否则立即返回** |

⭐ **返回码 `1 = 真让出 / 0 = 降级为立即返回`** —— 这一个位就是「本次让出是否真的发生了」的**可观测差异**，
也正是 `D`+`E` 验收所需的那条（提案 §7.5 判据 3：`await` 让出 / `wait` 占用的可观测差异）。
⛔ **不许把它写成「无线程后端语义为空」** —— 已由提案 §7.6.4 订正为「**语义保持、只降级执行策略**」
（Go 的 WASM 目标等价 `GOMAXPROCS=1`）。`0` 是**合规降级**，不是错误。

### 3.3 取消与结构

| 函数 | 签名 | 语义 |
|---|---|---|
| `bk_task_cancel` | `(handle)` | **协作式**取消：不强杀，于下一检查点生效 |
| `bk_task_is_cancelled` | `() -> i32` | 检查点（对应解释器腿的循环头 / 函数入口 / 睡眠分片） |
| `bk_task_detach` | `(handle)` | 从父 scope **剪枝**、主动退出所有权（fire-and-forget 的唯一合法出口） |
| `bk_scope_close` | `(scope, out) -> status` | 关闭范围：收集 **leaked 失败**并上浮（`ok(v)` 翻 `err(aggregate)` —— 契约里的**唯一有界 override**） |

### 3.4 能力自述

| 函数 | 签名 | 语义 |
|---|---|---|
| `bk_capabilities` | `() -> u32` | 位图，**启动时解析一次、此后固化**（见 §5） |

⭐ **位值定案（2026-09-20，`DE-2b-3` 补遗）**：本表原先只定了**形态**（位图），而**位值本身是 ABI 的一部分**
—— `DE-3` 建 C ABI 运行时时必须照它发；两腿各定一套的话，`DE-4` 的契约参照就没有共同基准。
故在此定案：

| 位 | 层 | 值 |
|---|---|---|
| 0 | **L0 调度** | `1` |
| 1 | **L1 让出** | `2` |
| 2 | **L2 抢占** | `4` |

⚠️ **L2 不参与解析**：裁定 29 说登记不实现 ⇒ **任何后端都不许宣称它**（解析函数里刻意没有对应分支，
免得有人以为「多给一个参数就能开抢占」）。解释器腿的对应实现见
`Sources/PiniCore/Interpreter/ConcurrencyCapabilities.swift`；它在**可执行路径**上被读
（`await` 未决时先问后端能否让出），不是一份只给人看的自述。

## 4. 策略层 / 原语层的**分界**（裁定 19 精化 + §7.5.7）

| 半 | 内容 | 语言 | 多后端下的份数 |
|---|---|---|---|
| **策略** | 队列 · 优先级 · 归约阈值 · **选择下一个任务** | ✅ **Pini 值**（纯逻辑、无宿主依赖） | ⭐ **1** —— 经 HIR，**全后端同源** |
| **原语** | 让出 / 恢复 · 续体保存 · 任务树 · 取消树 | ⛔ 宿主 | 每**接缝形状**一份（今天 **2**：Swift 原生 · C ABI） |

⇒ **分界点就是 `await` 点**：策略要「选择任务」，原语要「保存 / 恢复续体」。
⇒ 由此**必须裁**的一条规则，见 §5。

## 5. ⛔ 重入规则（**待裁**，本件不替用户定）

若策略是 Pini 值，则**调度决策是一次 Pini 函数调用，而它恰好运行在 `await` 点上** ⇒
「调度决策自身是否也能被让出」**必须显式定清**，否则这是**递归挂起**的入口。

| 解读 | 含义 | 代价 |
|---|---|---|
| **甲（我的建议）** | **调度决策不得挂起**：决策期间 `bk_task_yield` 恒返 `0`（no-op），并**响亮诊断**（若策略真去让出） | 需要一层「决策中」标志；表达力受限（策略不能自己做异步等待） |
| **乙** | **允许**调度决策挂起（重入挂起） | 需要「调度器的调度器」；**递归深度无自然上界** ⇒ 须先定义终止条件 |

**建议 `甲`**，理由两条：① 外部先例里策略层都是**同步的**（Rust `Waker` / C++ `scheduler` 的选择动作皆非异步）；
② 本批的克制口径（裁定 11）不允许为一个尚未出现的需求预置无限递归面。**但这条我不擅自定。**

## 6. 能力**分层 + 等级**（裁定 27 形态，运行时解析）

### 6.1 分层（一层套一层，**不是矩阵**）

| 层 | 能力 | 依赖 | 本仓现状 |
|---|---|---|---|
| **L0 调度** | `spawn` / 阻塞 `join` | 无 | ✅ 解释器腿有；LLVM 腿 ⛔ 缺（`DE-3`） |
| **L1 让出** | `bk_task_yield` 能真让出 | **L0** + 有线程 | ✅ **解释器腿已落地**（`DE-2b` 让出本体 · `DE-2b-3` 与本节形状对齐）；⛔ LLVM 腿缺（`DE-3`） |
| **L2 抢占** | 分层抢占 / 时间片 | **L1** + 多线程 | ⛔ 无（登记不实现，裁定 29） |

⛔ **嵌套关系是有方向的，这正是「矩阵」不成立的理由**：有让出 ⇒ 必有调度；
**反过来不成立**（无线程 ⇒ 无让出，**但调度仍在**）。

### 6.2 运行时解析三纪律（照 GCC fmv，提案 §7.6.6）

1. **启动时解析一次**（不逐调用点判）
2. **结果固化、进程生命周期内不变**
3. ⛔ **无合格版本则降级，不失败**（例如无线程 ⇒ L1 降为 no-op 返回 `0`，**不是报错**）

### 6.3 等级列

⛔ **一律不授予**（照裁定 30：语言远未成熟，任何等级都承诺不出来）。**留列、留空**。

## 7. 对 `DE-2` / `DE-3` 的输入

| 子段 | 本件对它的约束 |
|---|---|
| **`DE-2`**（解释器腿：挂起本体 + 让出） | ⭐ 须**先补 `await` / `wait` 的载体**（§1 第 2 条）—— 它跨 Parser / AST / HIR **三层**，且**改 `HIR 契约` 节点面** ⇒ 须走契约 `§1.3` 并登记。⚠️ 起点是「阻塞 join 已跑通」（§1 第 1 条），**不是**从零 |
| **`DE-3`**（LLVM 腿：`join` 发射 + 按本件建 C ABI 运行时） | ⛔ **必须按本件 §3 的函数表建，不得按「只有一条腿」的形状写死** —— 否则第 4 个后端（字节码 / C，优先级均「高」）来时**重写**。<br>⭐ **2026-09-20 用户裁定取甲**（真建 L0，不做「承认同步执行」的降级）⇒ 本段切成三段：**`DE-3a`**（HIR 承载 `future`，✅ 已交付）· **`DE-3b`**（C ABI 运行时）· **`DE-3c`**（发射层接线 + LLVM 腿判据）。⚠️ 起点实测推翻了原估的两处，见 `proposal-scheduling-surface-2026-09-20.md` §11 的 `DE-3` 规划落档 |
| **两台腿共同的写法约束** | ⛔ 该份运行时**不得依赖 LLVM 特有物**（不引 LLVM 内部类型、不假设 LLVM 内存模型）—— 它是**后续后端唯一的复用对象**（提案 §7.5.3） |
| **`DE-4`**（守卫） | 判据取**契约参照**（各后端 vs **同一份**期望输出）；且 §3.2 的返回码 `1/0` 就是「让出是否发生」的可观测信号 |

### 7.1 即时代价（登记）

`join` / `detach` 在 `IREmitter.swift` 里是 **`fatalError`**（实测：LLVM 腿跑并发程序 `rc=133`）。
⚠️ **而发射器零 `throw` 路径** ⇒ 「改成诊断」在发射层**不可行**，只能改为**运行时可读的响亮终止**
⇒ 这一处与 `DE-3` **同批**做，**不单独提前**（提案 §7.5.5 记的「≈2 行代码」按此口径**偏乐观**，此处更正）。
