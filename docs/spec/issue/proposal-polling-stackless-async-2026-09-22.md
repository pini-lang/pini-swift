## 0. 一句话 · 以及它值不值得做

**值得做的前提只有一个：需要「可调度」。** 若只要「`await` 能真让出」，
现有 completion-driven（结果决出 ⇒ 直接重入体）**已经够了**，不必付轮询的复杂度。
⇒ **先回答「要不要可调度」，再读本文。** 这个问题不解决，`P-0`…`P-4` 全部不存在。

假定要：那么做法是把驱动器从「结果决出 ⇒ 直接重入体」改成「结果决出 ⇒ 入就绪队列 ⇒ 执行器 `poll`」，
**C ABI 面只增五个符号，既有 14 个 `bk_*` 一个不动**。

### 0.1 TL;DR（赶时间读这一段）

| 项 | 内容 |
|---|---|
| **要解决的问题** | 调度器「没有可挑的对象」——引擎里没有就绪队列，所以「选择下一个任务」无对象可选 |
| **做法** | 驱动器改道：结果决出 ⇒ **入就绪队列** ⇒ 执行器 `poll`（今天是结果决出 ⇒ 直接重入体） |
| **成熟度** | 11 条设计决策里 **9 条是业界成熟做法**，1 条无先例（已裁），1 条待裁 —— 见 §2.5 |
| **C ABI** | 新增 5 个符号（`poll` / `state` / `bind_sched` / `poll_wait` / `abi_version`）；**既有符号零改动** |
| **队列不进 ABI** | 队列属策略层；等待关系是**任务自己的字段**，不是运行时全局 —— 见 §3.3 |
| **最大风险** | ① 重入 / 递归挂起（待裁 2）② 跨 suspend 的值必须 spill（判据 6 守）③ 多队列下取消树须跨队列成立（§6.1） |
| **不做** | 不做 per-future 组合式 poll、不做抢占、不动策略层 / 原语层的既有分界 |

## 2. 起点：今天在哪个位置

严格说，现状是「**可恢复帧 + 重入 wrapper**」——属**续体式**，**还不是状态机**：

| 面 | 现状 | 与轮询式的关系 |
|---|---|---|
| 让出的表达 | **体 `return`「已让出」**，不是切栈的调用 | ✅ 无栈形态成立 |
| 续跑怎么做 | 运行时用同一 `(wrapper, code, env)` **再调一次** | ✅ 与 `poll` 的「再次调用」同构 |
| 续跑点存在哪 | 帧头那 8 字节，入口先读再清零 | ✅ 那就是状态机的 `state` 槽位 |
| 局部量 | `bk_task_slot` 帧内取槽，**可重放**（游标每次进入归零） | ✅ 那是跨 suspend 存活区 |
| `bk_task_await` 返回码 | `0` 决出 ok · `1` 决出 err/取消 · **`2` = 本次会让出** | ✅ **`2` 就是 `Pending`** |
| 驱动器 | 结果决出时 **`whenResolved` 直接重入体** | ⛔ 唯一不同的一处 |

⇒ **结论**（⛔ 不能说现状「已经是无栈状态机」，那是跳跃的）：
现状已是**可恢复**形态；`switch(state)` 分发是**本文才引入**的新东西。
所以本文的增量 = **状态机降级（§5）+ 驱动器改道（§3）**，不是「只差驱动器」。

### 2.5 ⭐ 成熟做法对照：哪些是前人之路，哪些是本仓独创

> **用户纠正（2026-09-22）**：不做百分百创新；**可靠地踩在前人踏出的经验之路上**，
> 只针对本语言的特点做**必要**偏离。⇒ 逐条对照：

| # | 设计决策 | 业界先例 | 判定 |
|---|---|---|---|
| 1 | 无栈 + **编译器可恢复帧**（让出 = `return`） | C# · Rust · Kotlin · Swift · C++20 **五家一致** | ✅ 前人之路（且**已裁：走乙**） |
| 2 | `poll -> Ready / Pending` 协议 | Rust RFC 2394 `Future::poll` | ✅ 前人之路 |
| 3 | **原语在语言 / 核心，策略在库 / 用户** | Rust executor crate · Swift `SerialExecutor` · Kotlin `CoroutineDispatcher` · C++ P2300 `scheduler` 概念 | ✅ **跨语言共识**（⛔ Go 是唯一反例 —— runtime 内置、不可替换，**与本仓已登记的「并发可选」自相矛盾**） |
| 4 | 调度器接口**只有一个方法** | ⭐ **Swift `SerialExecutor` 只要求实现 `enqueue` 一个核心操作** | ✅ **有强先例** ⇒ `F-2a` 定的「一个方法 `选择下一个任务`」正当性增强 |
| 5 | 多队列（按调度器句柄分组） | Go GMP 的 **per-P runqueue** · tokio 的 **per-worker queue**（work-stealing） | ✅ 前人之路（**不是本设计发明**） |
| 6 | 取消是**树上的、协作式** | Swift 结构化并发 + 取消 · Kotlin `Job` 树 · Go `context` | ✅ 前人之路 |
| 7 | 越界位置**硬拒绝**让出 | Lua **`nny` 计数器**（`yield across C-call boundary`） | ✅ 前人之路（已支持裁定 33 取 `α`） |
| 8 | C ABI 的 **opaque 句柄 + 函数指针表** | Rust `RawWaker` / `RawWakerVTable`（data ptr + vtable） | ✅ 前人之路 ⇒ waker 的**预留形态**照此 |
| 9 | ⛔ **不用 `llvm.coro.*`** | ⭐ coro.* 是**乙的现成通道**（`coro.begin/save/suspend/end`，自动拆 ramp / resume / destroy） | ⛔ **偏离，且是上一版的越权判断** —— 见 §2.5.1 |
| 10 | 无 waker（level-triggered） | ⭐ **WASI Preview 2 `pollable` + `poll_oneoff`** 正是 level-triggered、**无 waker** | ✅ 有先例，且契合 WASM 腿 —— 见 §2.5.2 |
| 11 | ⚠ **策略层是 Pini 值** | ⛔ **无外部先例** —— 外部策略层**都写在宿主语言里** | ⚠ **唯一的真创新**（已裁 28，见 §2.5.3） |

#### 2.5.1 ⛔ 自我纠正：上一版「不用 `llvm.coro.*` 是有意的」越权了

| 项 | 说明 |
|---|---|
| 仓内已有调研 | 调度面提案 §7.6.10 把 `llvm.coro.*` 列为**乙的现成通道**；代价写的是「跨 LLVM 版本**不保证**」与 `HIR 契约` 冻结纪律的**张力（须先面对）** —— ⛔ **不是否决** |
| 我的错误 | 上一版写成「**有意**不用」—— 那是**我的判断**，**不是任何裁定** |
| ⭐ 一处概念混淆 | `coro.*` 是 **IR 层 intrinsic**，⛔ **不影响** `bk_*` 的**运行时 C ABI 稳定性**。它的真实代价是「LLVM 升级时**发射层**要跟着维护」，不是「ABI 不稳」—— 上一版把两者混为一谈 |
| ⇒ 结论 | **默认应走 `coro.*`**（前人之路）。绕开的**唯一**正当理由 = 「不接受跨 LLVM 版本的发射层维护成本」，⛔ **须用户裁**，不由本文定 |
| 收益（走 coro.*） | ⭐ **优化器保证**跨 suspend 的 spill 正确性 ⇒ 判据 6 从「唯一抓手」降级为**双保险之一** |

#### 2.5.2 waker：当前选 level-triggered（WASI 式），waker 形态照 Rust `RawWaker` 预留

- **当前选择**：**level-triggered**（任务只被查询状态，不注册回调）—— ⭐ 这正是 **WASI Preview 2 的 `pollable`**
  模型：`poll_oneoff(&[pollable])` 阻塞等任一就绪。**本仓有 WASM 腿 ⇒ 这条路与它天然契合。**
- **队列空时在等什么**（上一版被批为逻辑漏洞）：⇒ 答：**在一组 `pollable` 上阻塞等待**（照 `poll_oneoff` 的语义），
  而不是自造一个「条件变量」。今天可用的 `pollable` 只有两类：**任务决出** 与 **`bk_sleep` 的定时器分片**。
- **预留**：将来若需 edge-triggered（真 IO / 信号），追加 `bk_wake_*` 面，
  形态照 **Rust `RawWaker`**：`data` 指针 + 函数指针表（`clone` / `wake` / `wake_by_ref` / `drop`）⇒ **opaque、零类型泄漏**。

#### 2.5.3 唯一的真创新：策略层是 Pini 值

⛔ 无外部先例 —— 外部四语言的策略层**都写在宿主语言里**（Rust 的 executor 是 crate、Swift 的是协议实现）。
⇒ 它是**已裁 28**，本文不推翻；但按「不做百分百创新」的原则，**它是唯一应被持续审视的那一条**，
其余各条都已对齐业界成熟做法。

## 3. 模型

```
┌─ 策略层（Pini 值 · 可替换 · 全后端同源）────────────┐
│  选择下一个任务 · 队列 · 优先级                       │
│  ⛔ 不进 C ABI（它是调度器的内部状态）                │
└──────────────────────────────────────────────┘
              ▲ 谁下一个跑（按调度器句柄分派）
┌─ 驱动层（执行器）───────────────────────────────┐
│  每个调度器实例一个就绪队列                        │
│  loop { pick() -> poll(h, out) -> 按返回码处置 }    │
└──────────────────────────────────────────────┘
              ▲ poll 协议（C ABI）
┌─ 原语层（每接缝形状一份 · 形状稳定）────────────────┐
│  任务盒子：(wrapper, code, frame, schedHandle, waitsOn) │
└──────────────────────────────────────────────┘
              ▲ 降级后的体
┌─ 状态机（编译产物）──────────────────────────────┐
│  switch (frame->state) { s0: ...; s1: ... }        │
└──────────────────────────────────────────────┘
```

### 3.1 poll 协议（**钉死** —— 这三处口径必须一致，否则语义未定义）

| 项 | 定义 |
|---|---|
| 单位 | **整个异步体** |
| 一次 poll 推进到哪 | **推进到下一个「未决」的 await 点，或跑完**。⛔ 不做「只推进一个 await 点」——已决的 await 点继续跑过去，不返回 |
| 返回 `0` / `1` | **已决**（ok / err·取消）。出队；帧由运行时释放 |
| 返回 `2` | **Pending**。任务留在等待态，**不入就绪队列** |
| 空转 | ⛔ 不存在。队列空 ⇒ 执行器在**一组 `pollable` 上阻塞**（`bk_poll_wait`，照 WASI `poll_oneoff`），由「入队」动作唤醒 |
| 重入 | ⛔ `poll` 被反复调用是**常态**，不是异常路径 |
| **次数上界** | ⭐ **承诺**：await 点数 + 1（每次 poll 至少消化一个未决点）。⛔ 不承诺**精确**次数 |

### 3.2 调度器怎么进模型（given / using 的接法）

⛔ **Future 不持有调度器**（裁定 ①）。调度器句柄挂在**任务盒子**（原语层），
由**派发点**在派发时写入 —— 这正是调度面提案 §5.3 方案 B 的形状，不另造机制。

| 面 | 接法 |
|---|---|
| 默认 | `[调度器\|given]` 语言预置（`F-2b` 已交付）⇒ 派发点取用得到默认实例 |
| 覆盖 | 调用点 `using s: 调度器` ⇒ 取到的是**用户那份**（`F-2b` 判据已验「用户可以顶掉默认」） |
| 测试 | 同上走 `using` 实参位注入 ⇒ **可按测试覆盖** |
| 绑定 | 派发点把该 **Pini 值**写进任务盒子（`bk_task_bind_sched`，新增符号） |
| 分派 | ⭐ **执行器按调度器句柄分组队列** ⇒ 同一程序内 io 任务与 cpu 任务可用不同策略 |
| 继承 | ⛔ **不继承** —— 子任务在**它自己的派发点**取用，与其父无关。⇒ 「换调度器」的单位是**派发点**，不是 Future 树 |

⇒ **#14 的 io/cpu 例子有解**，且**不需要** Future 持有：分派单位是派发点，粒度比「每个 Future 一个」更粗，
但比「一个执行器一个策略」细得多。⛔ 代价：同一棵任务树里的任务**可能落在不同队列** ⇒
**取消树与失败上浮必须跨队列成立**（见 §6）。

### 3.3 等待关系（⛔ 不是运行时的隐藏全局，是任务局部）

一种想当然的做法是「依赖图由运行时内部维护」——那是**程序级、跨任务共享、可变、语言层不可见**的隐式全局，**已否**。

改法：等待关系是**任务盒子自己的字段**（`waitsOn`），不是运行时全局表。

| 面 | 定法 |
|---|---|
| 谁记录 | **任务自己**：`bk_task_await` 返回 `2` 时，把「我等 `handle`」写进**当前任务**的 `waitsOn` |
| 谁入队 | 被等者决出时，运行时遍历**它的等待者链表**，逐个入**各自的**队列 ⇒ 机械传播，非隐藏状态 |
| 生命周期 | 随任务释放；任务取消 ⇒ 从被等者的链表摘除 |
| 队列空时在等什么 | ⭐ 在**一组 `pollable` 上阻塞**（`bk_poll_wait`，照 WASI `poll_oneoff`）。今天可用的 `pollable` 只有两类：**任务决出** 与 **`bk_sleep` 的定时器分片** |
| ⛔ 边界（登记） | **真 IO 事件源无法唤醒**（无 waker 面）。将来有真 IO 须追加 `bk_task_poll2(handle, cx, out)`，**不改 P1** |

## 4. C ABI 面

### 4.1 沿用三条既有纪律（不改）

1. 句柄 opaque `void*`；状态 / 长度 `i32`；返回值走 **out 缓冲**（规避返回栈地址逃逸 UB）。
2. `Result` 三槽：槽 0 = tag（`ok=0`/`err=1`）· 槽 1 = ok 载荷 · 槽 2 = err 载荷。
3. ⛔ **不泄漏宿主类型** —— 既有 §3.2 纪律。

### 4.2 形状：**只增，不改**

**新增 5 个**：

| 符号 | 签名 | 语义 |
|---|---|---|
| `bk_task_poll` | `(handle, out) -> i32` | 轮询一次：`0` ok · `1` err/取消 · `2` Pending。**与 `bk_task_await` 签名同构** |
| `bk_task_state` | `(handle) -> i32` | 观察态：`0` 未起 · `1` 可跑 · `2` 等待中 · `3` 已决 |
| `bk_task_bind_sched` | `(handle, sched) -> i32` | 派发点把调度器**值**写进任务盒子（§3.2） |
| ⭐ `bk_poll_wait` | `(handles, count) -> i32` | **level-triggered 阻塞**：等任一 `pollable` 就绪 ⇒ 返回其下标。照 **WASI `poll_oneoff`**（§2.5.2） |
| `bk_abi_version` | `() -> u32` | ABI 版本，启动期固化；不一致 ⇒ **响亮失败** |

> ⭐ **`bk_poll_wait` 为什么必须进 ABI**：「阻塞等待」要触碰宿主（线程挂起 / 事件循环），属**原语层**；
> 两腿各写一份就会在「什么时候醒」上分岔 —— 与 `bk_sleep` 进这张表**同一个理由**。

**一个都不动**：`bk_task_spawn` · `_join` · `_join_within` · `_join_all` · `_await` · `_yield` ·
`_frame` · `_slot` · `_cancel` · `_is_cancelled` · `_detach` · `_scope_close` · `_capabilities` · `_sleep`。

⇒ `bk_task_await` 保留，语义收窄为「`poll` 内部的 await 站点」⇒ **既有发射代码零改动**。

### 4.3 稳定性纪律

- **Addition over modification**：只加符号，不改既有签名与返回码取值。
- **版本化**：`bk_abi_version` 让后端与宿主启动期对账。
- **Hyrum's Law**：每个可观测行为都是承诺 ⇒ **不作承诺清单**（§8.3）必须显式写。
- **Opaque**：句柄是 `void*`，调用方不得解引用、不得假设布局。

## 5. 异步体怎么降级（状态机）

> ⛔ 本语言**没有 `async` 关键字**（不要写成「async fn」）：异步由**返回类型**标记
> —— `=> (T,)` 归一为 `Future<T, Error>`，体内 return 期望 `Result<T, Error>`。

### 5.1 ⛔ 先自评：上一版示例**不是**最佳实践

先前那段 IR 有四处问题，其中一处是**正确性错误**：

| # | 问题 | 性质 |
|---|---|---|
| a | 把 `0`（ok）与 `1`（err/取消）用同一个 `switch` 边路由到同一块 | ⛔ **正确性错误** —— err 应走既有 `Result` 解构路径，不该在 await 返回处合并 |
| b | 只 `store` 了续跑点，**没展示跨 suspend 活跃值的 spill** | ⛔ **漏掉了状态机降级最难的部分** |
| c | 每个 await 点一个完整 `switch i32 %r` | ⚠ 过度。主流实践只判「是否 Pending」，`icmp` + `br` 即可 |
| d | 没画 `bk_task_slot` 取槽排在入口块 | ⚠ 漏掉 `DE-6b` 已定的续跑正确性前提 |

### 5.2 修正后的形态

```llvm
; ── 入口块：取槽全部排在此处（顺序 = 声明顺序）⇒ 可重放 ──
entry:
  %sx = call ptr @bk_task_slot(i64 8)     ; 跨 suspend 的活跃值槽 #1
  %sy = call ptr @bk_task_slot(i64 8)     ; #2
  %st = load i32, ptr %frame              ; 帧头 = 续跑点
  store i32 0, ptr %frame                 ; ⛔ 读完即清零（既有约定）
  switch i32 %st, label %s0 [ i32 1, label %s1   i32 2, label %s2 ]

s0:
  %v0 = ...                               ; await 之前的计算
  store ptr %v0, ptr %sx                  ; ⛔ 跨 suspend 的值必须 spill
  store i32 1, ptr %frame                 ; ⛔ 续跑点必须在 call **之前**写
  %r0 = call i32 @bk_task_await(%h0, %out0)
  %p0 = icmp eq i32 %r0, 2                ; ⭐ 只判 Pending
  br i1 %p0, label %pending, label %s1    ; 0 / 1 ⇒ 交给既有 Result 三槽解构

s1:
  %v1 = load ptr, ptr %sx                 ; ⛔ 续跑时**从槽恢复**，不能靠寄存器
  ...
  store i32 2, ptr %frame
  %r1 = call i32 @bk_task_await(%h1, %out1)
  %p1 = icmp eq i32 %r1, 2
  br i1 %p1, label %pending, label %s2

s2:
  ; 写 out 三槽（tag / ok / err）；帧由运行时释放
  ret i32 0

pending:
  ret i32 2                               ; ⛔ 帧不释放；out 一字不写
```

### 5.3 六条纪律（缺一条就是静默错误，不是报错）

1. ⭐ **跨 suspend 的活跃值必须 spill 到槽**。这是无栈降级最难的一处：
   suspend 后栈帧消失，留在寄存器 / `alloca` 里的值全废。⭐ **`out` 每次进入都是新的一块**
   ⇒ 续跑路径若依赖上次写进 `out` 的值，会静默读到空块。
2. **取槽代码全部排在入口块、顺序 = 声明顺序** —— 可重放的前提（`DE-6b` 已定）。
3. **读 state 后立刻清零** —— 既有约定（让出信号走帧不走返回值）。
4. **`store` 续跑点必须在 `call` 之前**。
5. **只判 Pending；`0` / `1` 交既有 `Result` 解构** —— err 与取消在那里处理，不新造分支。
6. **Pending 时不写 `out`、不释放帧**。

### 5.4 ⛔ 更正：默认应走 `llvm.coro.*`（上一版的判断已撤回）

> ⛔ **一条已撤回的判断**：本设计早期曾写「不用 `coro.*` 是**有意的**」—— 那是**个人判断，不是任何裁定**。
> 调度面提案 §7.6.10 把 `llvm.coro.*` 列为**乙的现成通道**；其代价是「跨 LLVM 版本不保证」的**维护成本**，
> 且 ⛔ **它不影响 `bk_*` 的运行时 C ABI 稳定性**（它是 IR 层 intrinsic，不是运行时符号）。

| 路 | 做法 | 收益 | 代价 |
|---|---|---|---|
| **甲（默认 · 前人之路）** | 用 `coro.begin / save / suspend / end`，**仅作标记**：suspend 点由 intrinsic 标注，**帧仍由 `bk_task_frame` 提供** | ⭐ **优化器看见 suspend 点** ⇒ 跨 suspend 的 spill 由**编译器保证** | 须解决「coro frame ↔ `bk_task_frame` 堆帧」的对齐；LLVM 升级时发射层要跟着维护 |
| 乙（若裁为不接受甲） | 不用 intrinsic，帧布局全是发射层私事 | 无 LLVM 版本耦合 | ⛔ spill 正确性**靠人工** ⇒ 判据 6 成为**唯一**防线 |

⇒ **未裁前，§5.3 六条纪律与判据 6 两条路都要**：甲下它们是**双保险**，乙下它们是**唯一防线**。
⇒ ⛔ 本文**不替用户选** —— 见 §10 待裁 5。

## 6. 与既有语义的交互（⛔ 常被漏掉的一节）

### 6.1 取消传播

| 场景 | 处置 |
|---|---|
| 任务在**等待态**（Pending）被取消 | 从被等者的等待者链表**摘除**；⛔ 不再入队 |
| 任务在**就绪队列**里被取消 | 出队丢弃（省一次 poll）；或保留入队、poll 时发现已取消后返回 `1` |
| 取消树 | ⭐ **跨队列成立** —— 取消树挂在**任务盒子**（原语层），与调度器分组**正交** |
| 语义不变 | ⛔ 取消是结构化并发的固定语义，**不得由调度器决定** |

### 6.2 失败上浮

- 未 join 的子任务失败 ⇒ 在**父返回边界**上浮，与 poll 次数无关（走既有 `bk_scope_close` 的 leaked 收集）。
- ⛔ 失败上浮**不经过队列**：它是任务树的行为，不是调度的行为 ⇒ **调度器分组不影响它**。

### 6.3 帧的所有权（Pending 变常态后的逐路径钉法）

| 路径 | 谁收帧 |
|---|---|
| 正常跑完（返回 `0`/`1`） | **运行时**（既有一条：所有权在运行时） |
| Pending 中被取消 | **运行时**（体不再被进入，只有运行时能安全收） |
| `detach` 后 | 运行时；任务脱离父 scope 但帧仍归运行时 |
| 泄漏（父已返回、子未决） | ⛔ **须登记**：与既有 leaked 语义同源；建议随父 scope 关闭时由运行时收 |

⇒ ⛔ 一条铁律：**体永远不释放帧**。Pending 成常态后这条更要守，否则 double free。

## 8. 代价与风险

### 8.1 ⛔ 重入规则那条待裁必须重开

轮询下 `poll` 反复调用是常态，且「调度决策（策略层是 Pini 值）运行在 await 点上」
⇒ **递归挂起的入口**（调度面提案 §6 的风险表 6d 行）从理论变日常。**不重开这条裁定就动工会踩坑。**

### 8.2 多队列的真实代价

按调度器句柄分组 ⇒ 一棵任务树的任务可能落在不同队列 ⇒
**取消树、失败上浮、结构化 scope 关闭**都必须跨队列成立（§6）。
⇒ 这是「可 per-派发点定制策略」换来的代价，不是免费的。

### 8.3 明确**不作承诺**（Hyrum's Law 反面清单）

- ⛔ 不承诺 `Pending` 后在同一线程续跑。
- ⛔ 不承诺公平性（协作式不提供；队列顺序是策略层私事）。
- ⛔ 不承诺 `poll` 的**精确**次数（**只承诺上界 = await 点数 + 1**）。
- ⛔ 不承诺「一次 poll 只推进一个 await 点」（已决的点会跑过去）。
- ⛔ 不承诺抢占（L2 已裁「登记、不实现」）。
- ⛔ 不承诺真 IO 事件源可唤醒（无 waker 面，见 §3.3）。

### 8.4 性能

每次 poll 多一次入队/出队 + 一次 `switch` 分发，单次纳秒级，远小于一次分配。
⇒ 真正的代价是**复杂度**（队列 ↔ 等待关系 ↔ 执行器三层状态），不是性能。

## 9. 验收判据（克制，六条）

| # | 判据 | 读法 |
|---|---|---|
| 1 | **推进性**：含 N 个 await 点的体，poll 次数 **≤ N+1** 且最终跑完 | 断言运行结果，非「没报错」 |
| 2 | **Pending 可观测**：`bk_task_state` 在 await 未决时为 `2` | 阴性对照：无 await 的体**恒不为 `2`** |
| 3 | ⭐ **轮询特征**：**同一任务被 poll ≥2 次，且每次从 `frame.state` 分发** | 变异：去掉 state 分发（改成顺序重跑）⇒ 本条**必须红** |
| 4 | **合规降级不变**：L1 位未置时 `poll` 不返回 `2`，语义保持、只降执行策略 | 兑现「`0` 是合规降级不是错误」 |
| 5 | **按调度器分派**：两个不同调度器实例的任务进**不同**队列 | 兑现 #14；缺它则 io/cpu 分派不存在 |
| 6 | ⭐ **跨 suspend 的值存活**：await 之前的局部变量，在续跑后仍读到**同一个值** | 变异：去掉 spill（让值留在寄存器）⇒ 本条**必须红**。⛔ 这是不用 `llvm.coro.*` 后**唯一**能抓住纪律 1 的地方 |

⛔ **判据 3 是命门**：它直接验「每次从 state 分发」，而不是间接验「选了下一个」。
另一条更直观的候选（验「选择下一个任务被调用 ≥1 次」）区分力不足 —— 回调式下它也可能绿。
