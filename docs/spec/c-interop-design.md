# C 互操作：导入面与导出面

本文把 C 互操作拆成两个面。导入面把既有 `[库|foreign]` 块从「只能声明函数签名」改成「一张外部符号表」；导出面把 Pini 自由函数与给定块存储发布成 C 符号。两块均已落地，状态见文末分片表。不含 C++ / Rust 互操作、结构体按值、异步跨边界。

**「不覆盖」的读法**：名同（标识符即外部符号名）、只声明（导入不产生定义）、不遮蔽（同名冲突一律报错）。三条各自可独立成立——若你只指其中一条，对应小节可单独裁掉。

## 改前现状

| 事实 | 位置 |
|---|---|
| 块内只有函数签名，形态是裸签名 `malloc(大小: I64,) -> (*I8,)`；`\|unsafe` 不是合法标志 | `ForeignSymbol.knownFlags` |
| 块名即库键：`libc` 走进程映像，其余按 `search_paths` 找 `lib<名>.{dylib,so}` | `FFILoader.swift:22` |
| 符号名等于 Pini 名，无别名机制：解释器 `dlsym`、LLVM 发 `@mangle(名)` | `IRExecutor.swift:395`、`IREmitter.swift:367` |
| 作用域文件级（跨文件 E5-017），但 IR 与解释器按模块合并，同名后者覆盖前者 | `IRExecutor.swift:264` |
| 多返回：IR 只取第一个返回类型，解释器注册期整条拒绝 | `IRLowerer.swift:807`、`ForeignThunk.swift:27` |
| 类型面：解释器认 I16/U16/U32/F32，IR 只认 I8/U8/I32/I64/U64/F64/Bool | `IRLowerer.swift:5608` |
| `[ffi].libs` 解析进配置，无消费方 | `FileLoader.swift:269` |
| 解析靠前瞻区分「签名」与「带体函数」 | `Parser.swift:589` |
| 无导出面：`[文件名\|export]` 是模块可见性重命名，与 C 无关 | `ImportExportDecl.swift` |

这张表里有两件事直接决定新形状的可行性。前瞻启发式会消失：`标识符: 类型` 不可能是顶层声明开头（`top-level-decl` 里没有以标识符加冒号起头的形态），块尾判据退化成两 token 前瞻；导出面则要从零建，IR 里连导出块的位置都没有。

## 三条不变量

| 不变量 | 内容 | 执行面 |
|---|---|---|
| 名即符号 | 块内标识符就是外部符号名，不提供别名映射 | 标识符须为 C 标识符（ASCII 字母、数字、下划线，不以数字起头） |
| 只声明 | 导入不产生定义、不插桩、不拦截 | LLVM 侧只发 `declare`；不为导入符号合成任何包装 |
| 不遮蔽 | 同名冲突一律报错，不合并、不后者胜 | 模块级一张符号表，冲突在语义期裁决 |

名即符号是这三条里最贵的。它换掉的是「Pini 侧随便起中文名、另行指向 C 符号」的自由——边界上的标识符只能是外部世界已有的那几个 ASCII 名。补偿手段是本仓既有的写法：边界保持原名，中文命名留给安全封装层（`examples/ffi_module/cstring.pini` 的 `c串长度` 就是这层）。

## 两条路线

| | 声明视图 | 桥接层 |
|---|---|---|
| 标识符 | 外部符号名 | Pini 别名，外部名另置于块内 |
| 生成代码 | 无 | 每个符号一个 shim（函数转发、变量取址转发） |
| 平台差异 | 写 C shim 库（一行一个符号） | 块内按平台切分支 |
| 与「不覆盖」 | 天然满足 | 别名即盖面，须靠约定自律 |
| 代价 | 名字受外部世界约束；平台差异要在 C 侧解决 | 两套名字长期并存，改名要同步两处 |

按「不覆盖」这条约束，只有声明视图成立——桥接层的别名本身就是外部符号的盖面。桥接层唯一的正当理由是平台差异无法用 shim 吸收；本仓 `examples/ffi_module/lib/ffilib.c` 已经证明 shim 吸收得动，所以不另立路线。

## 导入面

### 语法

```
[libc|foreign]
malloc: (U64,) -> (*U8,)
free: (*U8,) -> ()
stdout: *U8
optind: I32

[ffilib|foreign]
ffi_version|readonly: I32
```

两块并存不是笔误：一个文件可以绑多个库，每块一个，块名仍是库键（`FFILoader.swift:22` 的既有语义不变）。

文法增量：

```
foreign-decl     ::= '[' IDENT '|' 'foreign' ']' foreign-body;
foreign-body     ::= { foreign-symbol };
foreign-symbol   ::= IDENT { '|' foreign-flag } ':' type-annotation;
foreign-flag     ::= 'readonly';
```

与现状的唯一差异是条目形状。函数签名从 `malloc(大小: U64,) -> (*U8,)` 变成 `malloc: (U64,) -> (*U8,)`——函数类型语法语言里早就有（`examples/lambda-typed.pini` 的 `(I32,) -> (I32,)`），这里只是把它放到冒号右边。

代价是参数名消失：函数类型不带标签，`大小` 这类名字写不进去，只能用行尾注释补。不建议为 foreign 单独给函数类型加标签——同一套类型语法在别处不带标签，只在块内带，读者要多记一条规则。

标志位放在标识符与冒号之间，与语言其余修饰符同位（`名|unsafe`、`名|test`、`[名|foreign]`）。冒号由此只做一次切分：左边是符号与它的标志，右边是类型——扫一眼左列就知道有哪些符号，不用读到行尾。`readonly` 不入关键字表，走 `|given` / `|import` / `|export` 那条标识符白名单路径（`Parser.swift:490`），词法不动。

标志是封闭白名单，v1 只有 `readonly`；未知标志报错。这条必须显式做：修饰符位现在收任意标识符（`Parser.swift:1424` 的 `parseIdentifier`），不做白名单校验，`|readonyl` 会静默通过，而这个错只在读回数据时才显形。多条标志可并列、顺序无关；同一条写两次即报错。

| 标志 | 适用 | 语义 | 状态 |
|---|---|---|---|
| `readonly` | 数据符号 | 禁写：`store(&符号, ...)` 在语义期拒绝 | v1 |
| `macro` | 任意类型条目 | 不解析符号，构建期由 C 预处理器求值并烘成常量；蕴含 `readonly`，不可取址 | v1 |
| `threadlocal` | 数据符号 | 每次访问重新取地址（TLS 描述符不是普通符号地址） | 缓；v1 报错并提示写 shim 函数 |
| `weak` | 函数 | `dlsym` 未命中不 fail-fast，返回空句柄 | 缓；先确认空句柄在 Pini 侧怎么表达 |

### 判型

条目是函数还是数据，由类型决定，不另设关键字。

| 类型 | 含义 | 调用面 | 可带标志 |
|---|---|---|---|
| 函数类型 | 外部函数 | 只能调用，不能取作函数值 | 无（v1） |
| 其余类型 | 外部数据符号（变量 / 外部常量） | 读、取址 | `readonly` |
| 其余类型 + `\|macro` | 编译期常量 | 只读，不取址 | `macro` |

函数类型进块前须满足三条：捕获集为空、取用位为空、返回至多一项。多返回在语义期报错，不再留给 IR 静默截断。

导入的函数不能作值：Pini 的函数值统一是 `{ code, env }` 胖指针（`IRNode.swift:65`），而 C 函数没有环境槽。回调是这条规则的唯一例外，且方向相反 —— 写到外部函数形参位上的顶层自由函数名，交出的是这个函数自己的符号地址，不是胖指针；详见「回调」一节。

导入符号属模块内部，不进包级可见性（`Visibility.swift:187` 的既有裁决不变）。解析仍是注册期 fail-fast：声明了却解析不到的符号在加载时报错，哪怕从未调用——「只声明」不等于「可以悬空」。

### 类型面

块内每一项的类型都过一张闭合表。不在这张表里的标注在语义期报错：放行会产生「能过 `check`、换个通道就换行为」的声明，而这类不一致不在调用点显形。

| 写法 | C 形态 | IR | 位置 |
|---|---|---|---|
| `I8` / `U8` / `I32` / `I64` / `U64` / `F64` / `Bool` | `int8_t` / `uint8_t` / `int32_t` / `int64_t` / `uint64_t` / `double` / `bool` | `i8` / `i8` / `i32` / `i64` / `i64` / `double` / `i1` | 形参、返回、数据 |
| `*T`（T 为标量或指针） | `T*` | `ptr` | 同上 |
| `String` | `const char*` | `i8*` | 仅形参：借出，只在本次调用期间有效 |
| `StringHandle` | `bk_str_handle*` | `stringHandle` → `ptr` | 形参与返回：运行时段持有的一份拷贝，见「句柄」 |
| `(A, B) -> C` | `C (*)(A, B)` | `cFunction` → `ptr` | 仅形参：回调地址，见「回调」 |

三类拒绝各有码：表外类型（对象、元组、集合、未知名）报 `E4-028`；语言层有而 IR 表达不了的宽度（`I16` / `U16` / `U32` / `F32`）报 `E4-029`；`String` 落在返回位报 `E4-030`。回调另有两条：实参不是顶层自由函数、或签名不逐位相同，报 `E4-031`；回调签名里出现 `Bool`，报 `E4-032`。变参另有两条：`|varargs` 写在数据条目上报 `E4-033`；变参尾的实参不是 C 标量或指针报 `E4-034`。

句柄另有两条：`StringHandle` 写在 C 面之外（普通变量、字段、方法、非 `|c` 函数的签名）报 `E4-035`——它不是 Pini 的通用类型，放行等于开出第四条字符串路径。

判据只有一份：`FFIType` 负责「标注 → 边界类型」，语义校验、降载、解释器三处读它，不各自再判一遍。拼写仍归后端——LLVM 的声明与头文件的 C 原型各取所需。

### 借出

`String` 形参在 C 侧是 `const char*`：UTF-8、NUL 结尾，**只在本次调用期间有效**。C 要保存必须自己 `strdup`；能长期持有的形态是句柄，不是借出。

| 通道 | 做法 |
|---|---|
| 解释器 | thunk 把串编码成临时缓冲，调用返回即 `free`；分配早于调用，抛错路径同样归还 |
| LLVM | 直接传串值 `i8*`；拼接临时串在调用点之后释放，常量串在只读段 |

注意 —— 字面量与常量串落在只读段，C 侧往这个指针里写就是段错误。要可写缓冲，声明成 `*U8` 自己 `malloc`，别指望借出的串能改。

注意 —— 解释器的 shim 表按「名字 + 形状」命中：`strlen: (String,)` 与 shim 的 `*T` 不相容，落到通用 thunk；`cstr` 的声明形状就是借出，行为不变。

注意 —— 解释器的 thunk 整条走 GPR 或整条走浮点：`atof: (String,) -> (F64,)` 这类混合签名在 `run` 报错、`run-llvm` 正常。这条限制与形参写 `String` 还是 `*U8` 无关，是既有形状。

### 取回

内建 `c字符串(p: *U8,) -> (String,)`：从指针读到 NUL，复制成 Pini 串。两通道同一语义——解释器按 UTF-8 解码，LLVM 接运行时段 `bk_str_from_cstr`（实现落在 `bk_str_dup`，结果进计数串账）。

- 空指针读成空串，与 `bk_str_dup(nil)` 同一约定：C 侧返回 `NULL` 时不必先判空。
- 复制品归 Pini 持有，作用域退出时归还；C 的缓冲此后可自由释放。
- 没有额外的 `unsafe` 门禁：读内存的形参与 `load` 同规——指针怎么来的由那条路负责（foreign 调用本身已在 unsafe 位）。

注意 —— 非法 UTF-8 在解释器侧变成 U+FFFD（Swift 串只能持合法 Unicode），LLVM 侧原样搬字节；两通道对坏字节的展示可能不同，正常 UTF-8 输入无分歧。

`-> String` 在 FFI 返回位仍拒绝（`E4-030`），理由不是保守：C 返回的指针可能是静态缓冲、可能是库内部缓冲、也可能是 `malloc` 的，Pini 侧无从判断归属；复制是唯一不需要猜的形态，而它已经由 `c字符串` 显式写出。

### 回调

块内形参位上的函数类型就是 C 函数指针，语法不新增：

```
[libc|foreign]
qsort: (*U8, U64, U64, (*U8, *U8,) -> (I32,),) -> ()
```

**传出去**（Pini 调 C）：实参位上写一个顶层自由函数的名字，交出的是 `@mangle(名)` 本身。四条判据都在语义期：名字解析到顶层自由函数（方法、闭包、变量、形参、`main`、`|test`、泛型都不行）；签名与形参声明逐位相同；无 `using` 形参；不含 `Bool`。包一层适配器就多了一个 C 侧看不见的名字，所以不包。

`Bool` 单列一条拒绝理由：Pini 的 `i1` 与 C 的 `_Bool`（零扩展的 `i8`）在寄存器层不是一个约定，回调方向没有转发层能替它转。

**传进来**（C 调 Pini）：导出函数的函数类型形参在头文件里写成 `ret (*)(params)`，转发层把裸地址包成一个 Pini 函数值 —— `code` 是固定签名的适配 thunk，`env` 就是那个裸地址。Pini 函数体里 `f(x)` 照常写，仍是间接调用，不需要第二种调用节点。转发层只搬指针，不清算它的生命周期。

| 通道 | 做法 |
|---|---|
| LLVM（导入） | `call void @qsort(..., ptr @_u6BD4_u8F83)` —— 地址即符号 |
| LLVM（导出） | `@__pini_cb_N` 适配 thunk：`call ret %env(args)` |
| 解释器（导入） | 一组固定签名桩（`pini_cb_0..3`），槽位绑定 Pini 可调用体，调用结束即解绑 |

解释器的桩按整数约定接收八个机器字，因此**含 `F64` 的回调在 `run` 上不可用**（浮点走向量寄存器），`run-llvm` 正常。这与「GPR 与浮点混合签名」是同一条既有边界。同一次调用里同类回调最多四路：C 侧没有上下文区分两个同类指针。

回调里抛出的 Pini 错误不会穿过 C 栈：解释器的桥先把它记在线程局部，等 C 调用返回后由 thunk 抛出（LLVM 侧的错误本来就以陷阱收场，没有可穿的通道）。C 线程上找不到槽位（指针被存下来、换线程再调）属于程序错误，桥直接终止并说明原因。

注意 —— 地址的「进程期有效」与「调用期有效」是两件事：函数指针本身不变，但它捕获不到任何东西（判据一），所以跨调用重入同一函数是安全的；不安全的是 C 把地址存下来在**另一个线程**调，那时解释器的槽位表找不到登记。

### 变参

C 变参函数在块内用 `|varargs` 标出，声明里的形参表就是固定前缀：

```
[libc|foreign]
printf|varargs: (String,) -> (I32,)

main|func() -> (I32,):
    unsafe printf("n=%d\n", 42)
```

为什么用标志不用 `...`：`...` 要进类型文法，词法、函数类型、`TypeAnnotation` 与所有匹配点都得跟着改；而「这个符号是变参」本来就是符号的性质，不是类型表达式的一部分。代价是读者要记住「这个标志只对函数条目成立」，所以写错位置有专门的码（`E4-033`，`E4-034`）。

调用点放宽的只是上限：实参不少于固定前缀，多出来的进变参尾。变参尾只收 C 标量与指针（`String` 按借出、回调不收），其余一律 `E4-034`。**默认实参提升由发射层做**：

| Pini 实参 | 传法 |
|---|---|
| `Bool` | `i32`（`zext`） |
| `I8` / `U8` | `i32`（`sext` / `zext`） |
| `I32` / `I64` / `U64` / `F64` | 原宽度 |
| `*T` / `String` | `ptr` / `i8*` |

LLVM 不做默认实参提升 —— 它看到的是 IR，不是源码，指望后端替我们补是错的。调用点还必须把函数类型写全：`call i64 (i64, ...) @va_sum(...)`；只按实参表推会得到 `i64 (i64, i32)`，后端据此按非变参摆放实参，C 侧 `va_arg` 读到的是栈上的旧值。

| 通道 | 行为 |
|---|---|
| LLVM | `declare i32 @printf(ptr, ...)`，调用点按上表提升 |
| 解释器 | 调用点拒绝，报 `E5-019`，文案给两条出路：换 `run-llvm`，或在 C 侧写固定参数的 shim |

拒绝而非降级，理由是实测：解释器转发靠「bitcast 成八个 GPR」，而 Apple arm64 把变参放在栈上，位转调用拿到的是垃圾。引 libffi 会成为第一个第三方依赖；编译期生成 C shim 需要预先固定签名，而每个调用点的实参类型都不同；白名单只覆盖 printf 家族，且与「只声明、不插桩」的边界纪律冲突。三条都不如明说这条只在 LLVM 上成立。

声明处另有一条警告（`E7-006`）：作者写声明时就知道这条边界，好过跑起来才发现。

### 句柄

三层字符串的最后一层：C 要把串存下来，就收一个不透明指针。

```
[libc|foreign]
bk_str_handle_new: (String,) -> (StringHandle,)
bk_str_handle_len: (StringHandle,) -> (I64,)
bk_str_handle_release: (StringHandle,) -> ()

main|func() -> (I32,):
    var h = unsafe bk_str_handle_new("你好")
    print(unsafe bk_str_handle_len(h))
    unsafe bk_str_handle_release(h)
    return 0
```

形参位写 `StringHandle` 时，Pini 串在边界上被复制一份并记 +1（`bk_str_handle_new`），那一份随调用交给 C，由 C 释放；已经是句柄的实参原样传。返回位写 `StringHandle` 时，运行时段交出的指针直接成为 Pini 的一个句柄值——它在 Pini 侧只是一个 token：不参与计数、不能 `load`、不能当 `String`，唯一的去处是交给下一个收句柄的 C 函数。

C 面是五个入口：`new` / `bytes` / `len` / `retain` / `release`。字节视图不以 NUL 为界读，长度以 `len` 为准；计数归 C，`release` 归零时运行时段释放那份拷贝。`build --shared` 的头文件在这份签名用到句柄时自动带上这五个声明与不透明类型。

| 通道 | 行为 |
|---|---|
| LLVM | 形参位包 `bk_str_handle_new`，返回位原样交出；`retain` / `release` 由 C 调 |
| 解释器 | 调用点拒绝，报 `E5-020`：`bk_str_handle_*` 只活在运行时段，`pini` 进程没有这些符号 |

声明处另有一条警告（`E7-007`），理由与变参同一条：写声明时就知道这条边界。

`StringHandle` 不进普通代码：它出现在 `[..|foreign]` 之外、且函数不在 `|c` 条目里时报 `E4-035`。这条限制换来的是一句话说得清的判据——**C 只读一次用借出；C 返回指针用取回；C 要存下来用句柄。**

### 链接口径

解释器与 LLVM 通道各有一套解析方式，读的是同一份清单：解释器按块名 `dlopen` `lib<块名>.{dylib,so}`，LLVM 通道把 `[ffi]` 的 `libs` 拼成 `-l`、`search_paths` 拼成 `-L`（非系统目录另加 rpath）。`compile`、`run-llvm`、`test-llvm`、`build --shared` 四条都走这套。

块名与库名允许脱钩：块名只服务解释器的默认加载，链接什么完全由 `libs` 决定 —— 一个块可以调两家库的符号，也可以只挂一个与块名无关的名字。`libs` 里的名字不带 `-l` 前缀。

注意 清单只影响编译器发的链接参数，不改 dylib 自身的 install name：库若是裸文件名（`clang -shared -o libx.dylib` 的默认产物），运行期 dyld 仍可能找不到它；这种库应带 `@rpath/libx.dylib` 或绝对路径。这不是编译器能替它改的。

`run-llvm` 走 `lli`，没有链接期，改为对每个能找到的 `lib<名>.{dylib,so}` 传 `--dlopen`；找不到的不报错——macOS 的系统库位于共享缓存、磁盘上没有文件，抢先报错会误伤它们，真缺符号时 `lli` 的报错更准确。

### 数据符号

数据符号的地址就是 `dlsym` 的返回值；它绑定的是外部存储，不是 Pini 的副本。

```
var n = unsafe optind          ; 读：按外部存储的左值取
var p = unsafe &optind         ; 取址：符号地址本身，不复制
unsafe store(p, 3)             ; 写：走既有指针原语
```

写不另造语句形态。`unsafe` 是表达式前缀（`unsafe 表达式`），不是语句前缀；为写操作新增 `unsafe x = 1` 这类语句形态，会破掉「不安全消耗点 = 表达式」这条既有规则。地址加 `store` 已经够用。

注意 —— `&局部变量` 是快照（解释器实现如此，写回不更新原变量），`&外部数据符号` 是符号地址本身。同一个前缀内建按操作数改变语义，这是 `&` 唯一一处这样。理由：外部存储没有 Pini 副本可快照。

注意 —— `readonly` 只挡得住「取址结果直接作 `store` 目标」这一形。先 `var p = unsafe &符号` 再 `unsafe store(p, ...)` 追不到来源：类型里不携带「这个指针指向只读符号」。声明方的承诺在 C 侧，Pini 侧只挡最直白的那一笔。

### 常量

C 的「常量」是两类东西，混在一起会做错。

| 类别 | 是不是符号 | 进法 | 求值时机 |
|---|---|---|---|
| `extern const` 数据对象 | 是 | `名\|readonly: 类型` | 运行期读存储 |
| 宏（`EOF`、`M_PI`、`S_IRUSR`） | 不是，`dlsym` 永远找不到 | `名\|macro: 类型` | 构建期跑 C 预处理器 |

`readonly` 只是声明方的承诺：ELF 与 Mach-O 的符号表不携带 const 限定，链接期无法验证。它的价值在类型检查——写了 `readonly` 的符号，赋值与 `store` 都在语义期拒绝。不叫 `|let`：`let` 描述 Pini 的绑定，换 `var` 就能写；`readonly` 描述 C 对象自身的声明，换不掉。

`|macro` 是另一回事：它没有存储，只是一个构建期算出来的值。所以它能读不能取址，`readonly` 由它蕴含，不用另写。

#### Swift 在这件事上做了什么

Swift 会把「简单常量宏」导入成全局常量：字面量，或字面量与已定义宏之间的 `+` `-` `>` `==` 之类运算。做这件事的是 Clang importer 的 `ImportMacro.cpp`，它按 token 形态逐种匹配，源码里留着一句 FIXME——「让 Clang 把展开当常量表达式解析，而不是做这些特例模式匹配」。这句话本身就是结论：手写模式匹配不是这条路该有的样子。

它的失败方式更值得记：`#define X SDL_UINT64_C(...)` 或 `#define X (某个常量表达式)` 会被静默跳过，Swift 侧看不到任何提示；社区的标准绕过是「写一个返回该宏的 C 函数」。语言层面少一个常量不报错，这种设计不能学。

| | Swift | Pini |
|---|---|---|
| 求值者 | 自己按 token 模式匹配 | C 预处理器（`cc -E`） |
| 覆盖范围 | 字面量与少数运算 | 展开后能落到字面量或整数四则的 |
| 失败方式 | 静默跳过 | 报错并打印展开原文 |

#### 求值路径

1. `pini.toml` 的 `[ffi]` 增加 `headers` 与 `include_paths`，声明宏的来源头与 `-I` 路径。
2. 构建期为块内每个 `|macro` 条目生成一行探针，`cc -E -P` 展开，按标记行读回。
3. 读回的内容按常量表达式解析：整数允许四则与位运算（结果精确）；浮点只接受字面量（自己算会与 C 编译器的舍入不一致）。
4. 值按声明类型查范围，然后作为常量烘进 IR——三个通道读到同一个字面量，不经过 `dlsym`。

编译器取 `/usr/bin/cc`，换工具链用 `PINI_CC` 指绝对路径：`Process` 只认可执行文件的绝对路径，不查 `PATH`。

```
[libc|foreign]
EOF|macro: I32
M_PI|macro: F64
```

代价写在明处：声明了宏常量的模块，`check` 与 `run` 都需要 C 编译器。这是宏常量的入场费——值只能由 C 的头文件体系给出。没声明的模块照旧零依赖，「单文件不用工具链」的故事不变。

`errno` 是这条路的边界样本：两边都是函数式宏（Darwin `(*__error())`，glibc `(*__errno_location ())`），展开后不是常量，构建期直接报错并打印原文。实测输出是「宏常量 `errno` 展开后是 `(*__error())`，不是常量表达式：运算符 `*` 出现在不该出现的位置」——原文与理由一起给，读者看得出该写 shim 而不是改声明。要用它就写 `pini_errno: () -> (*I32)` 加一行 C shim。

不给「块内写值」的后门仍然成立：`EOF: I32 = -1` 看着像导入，实际是 Pini 侧自己造了个常量，与外部世界再无关系；哪天 C 侧改了值，没有任何门禁会响。`|macro` 保住了「值来自头文件」这条链路，只是把求值提前到了构建期。

### 冲突裁决

这张表是「不遮蔽」的执行面。前提是把作用域从文件级升到模块级——符号表本来就按模块合并（`IRExecutor.swift:264`），文件级可见性只制造「声明在 A、用不了在 B」，挡不住同名冲突。

| 情形 | 裁决 |
|---|---|
| 同模块两文件同名同型 | 合并为一条 |
| 同名异型 | 报错：同一外部符号的两种类型断言无法并存 |
| 同名异库 | 报错：解析目标不唯一 |
| 宏常量与符号同名 | 报错：一个是构建期值，一个是运行期存储，无法并存 |
| 与本地函数 / 类型同名 | 报错：本地定义会盖住外部符号 |
| 与导出名同名 | 报错：导出会定义导入所声明的符号 |
| 块内重复 | 报错 |
| 标识符非 C 标识符 | 报错 |

同时删掉两处现存的「后者胜」：`IRExecutor.foreignDecls` 的字典覆写，以及 `IRLowerer` 只取首个返回类型。

## 导出面

### 可导出的东西

先前的判断是「只有函数能导出」，理由是 Pini 没有模块级存储。这条判断错了一半：给定块（`[名|given]`）确实是一块进程级存储，但 `using` 形参并不是通向它的引用。

两层要分开。**默认实例的盒**由 `bk_given_get` 惰性物化、恰一次、地址稳定到进程结束（`PiniRuntime.swift:525`）；而 `using` 形参在取用点拿到的是这个盒的**副本**——发射层 `memcpy` 载荷到新分配的一份（`IREmitter.swift:3084`），解释器同样返回值（`IRExecutor.swift:1248`）。于是：

| 动作 | 结果 |
|---|---|
| C 写字段区 | Pini 下一次取用拷到新值，读得到 |
| Pini 在 `using` 体内写字段 | 只改副本，盒不变，C 读不到 |
| Pini 经引用字段（`*T` / 对象引用）往下写 | 双方共享那一块内存，可见 |

C 面发布的是**盒**，不是副本。C 面的量因此在数据流上是单向的：C 可写、Pini 可读；反向要么把字段声明成引用类型，要么另导出 setter 函数。这不是实现取舍，是 `using` 的副本语义决定的。

| 类别 | 块内写法 | C 侧形态 |
|---|---|---|
| 函数 | `对外名\|c = Pini 自由函数` | 一个 C 函数 |
| 模块级量 | `对外名\|c = 给定块` | 结构体视图 + 取址函数 |

方法、泛型、`|test`、`main` 仍不进 C 面；泛型给定块要按实参特化，v1 也拒。

给定块能导出，靠的是别的 Pini 值没有的一条性质：生命周期是进程级。`bk_given_get` 把盒缓存在进程里直到结束，地址不变，所以 C 拿到字段区指针后不会遇到「对象已释放」。普通对象与集合没有这个保证，因此不进 C 面。

注意 —— 这不是给语言新增全局可变状态。给定块本来就是进程级存储，导出只是给它加一个 C 可见的名字；Pini 侧改不动它，原因见上表。

### 语法

```
; calc.pini
[calc|export]
calc_add|c = 加法
calc_state|c = 计数器状态
```

文法增量：

```
export-item ::= IDENT [ '|' ('c' | 'pini') ] '=' IDENT;
```

目标写在条目上：`|c` 走 C ABI，`|pini` 或省略走模块可见性。一个块因此管两种发布面，语言与符号写在同一行，源文件读得出产物形态。

条目只有一形：左边是名字，右边是本模块的某个顶层符号；右端是自由函数就发 C 函数，是给定块就发结构体视图加取址函数。模块内同名重声明由语义层先拦（E3-004），故查表只有一个答案。

块头必须等于文件名，所以产物 `libcalc.{dylib,so}`、生命周期 `calc_init` / `calc_shutdown`、头文件保护名都取文件名。要换库名就重命名文件；这是「块头 = 文件名」换来的唯一约束。

每个文件至多一个 export 块；每个模块至多一个文件带 `|c` 条目。两个文件各带 `|c` 条目时报错并点名两个文件，不静默取其一。这套写法与 `[文件名|export]` 是同一个块，不再有「两块并存」。

### 标识符转 ASCII

Pini 标识符可以是 UTF-8，C 标识符只能是 ASCII。每个对外名字都过一遍 `CName.escape`：

| 源字符 | 输出 |
|---|---|
| `A`–`Z`、`a`–`z`、`0`–`9`、`_` | 原样 |
| 其他（含全部非 ASCII） | `_u` + 6 位大写十六进制 |

ASCII 名字零变化是硬要求：`calc_add|c = 加法` 的对外名就是 `calc_add`。下划线若也转义，`calc_add` 会变成 `calc_0add`，等于把最常用的命名风格毁掉。

单射靠两条导出期禁令守住，不靠转义表：

- 名字里含字面 `_u` 加 6 位十六进制 ⇒ 拒。它与转义输出同形，解码时无法区分是码位还是原文。
- 转写后落在 C 保留区（`__` 开头或 `_` 加大写字母开头）⇒ 拒。这类名字 C 编译器照样接受，但属未定义行为。

固定 6 位宽度是第三条：`点` → `_u0070B9`。变宽的话 `_u70B9` 后面接一个数字会被读成更长的码位。6 位也顺手把「4 位字面量」排除在撞名之外——`_u70B9` 不是合法的转义形状，原样保留即可。

左名直接写 `加法|c = 加法`，对外名是 `_u52A0_u6CD5`——合法但难读，所以推荐显式给 ASCII 名。字段名走同一条规则，中文字段在 C 侧就是 `_uXXXX` 形状；要可读就让字段名用 ASCII。

转义只发生在 C 面。导入侧不转：那里的标识符就是外部符号名，转一道等于把名字换掉，而「名即符号」禁的正是这个——所以导入项写不出 C 标识符就报错（见冲突裁决表末行），不会替你改名。

不复用 `IRName.mangle`：那套只转非 ASCII、不动下划线，宽度也随码位变（`%04X`），`点` 与字面 `_u70B9` 会撞。IR 侧的名字是编译器私事，改它要同时动解释器与两处发射的符号一致性；对外名是 ABI 契约，值得单独一条函数。两套名字不要求一致。

C 面还要查一次撞名：两个 `|c` 名字经 escape 后相同即报错，字段同理。查得到的只是 C 面内部的撞名；C 侧自己写的符号撞上来，编译器看不见。

### 模块级量

给定块的存储是一块地址稳定的缓冲，字段区在 4 槽箱头之后（`IRLayout.standard.headerSlotCount`）。C 侧看到的是字段区的视图：

```c
typedef struct calc_state_s {
    int32_t count;
    int32_t limit;
} calc_state_t;

calc_state_t* calc_state_get(void);   /* 盒的字段区；Pini 侧 using 拷的是副本，不指向这里 */
```

```
[计数器状态|given]
    count: I32 = 0
    limit: I32 = 100
```

导出规则四条：

- 字段须全部 C 兼容；有一个不合格就整块拒，不留「部分字段」的半布局。
- 结构体只镜像字段区，不镜像箱头：取址函数在 LLVM 侧跨过头，C 不需要知道头有多宽。
- 头文件为结构与每个字段生成 `_Static_assert`（`sizeof` 与 `offsetof`），布局漂移在 C 编译期就红，而不是运行期读到错位。
- 直连还是访问器：直连（上面这种）与「每字段一对 get/set」相比，API 面小、无调用开销、读写即时。访问器唯一的好处是字段名不进 C，省掉转义后的怪名字，代价是每字段多两个符号。选直连——这个位置的意义就在于 C 能直接读写它；Pini 侧读写同一块存储要靠引用字段或 setter，与选哪种形无关。

字段名走同一条转义规则，所以上面的例子写的是 ASCII。若字段写成 `计数`，C 侧就是 `_u008BA1_u006095`——合法但没人愿意在 C 里敲。想让 C 侧可读，字段名就用 ASCII；这是「名即符号」在字段上的同一笔代价。

想让读写读起来像全局量，调用方自己加一行 `#define calc_state (*calc_state_get())` 即可。生成器不替你做：宏会把它之后所有同名标识符一并替换，连 `calc_state_t` 的用法都可能被卷进去，这种便利得让使用方自己决定要不要。

注意 —— C 侧写入不做任何校验。Pini 侧的不变量（「count 不得超过 limit」这类）在边界上没有防线，所以给定块导出适合放配置——C 写、Pini 读。要让 Pini 侧也写，字段得声明成引用类型，或者另导出一个 setter 函数。

注意 —— 导出函数在边界内填的默认实例是**副本**：函数体读到的是调用时刻的一份拷贝，写回只落在拷贝上。要让函数改动对 C 可见，同样走引用字段或 setter。

### using 参数

导出函数的 C 原型不含 `using` 形参：它在边界内由默认实例填充，而 C 没有第二个实例可传。

```
; Pini
累加|func(using 状态: 计数器状态, n: I32,) -> (I32,):
    return 状态.count + n

; 生成的 C
int32_t calc_add(int32_t n);
```

反方向不成立：Pini 侧可以显式传自备实例（`累加(自备, 5)`），C 侧不能。这是 `using` 的语义在边界上的自然截断，不是遗漏。

如果 `using` 形参的类型没有可导出的给定块，函数本身照样能导出——实参在模块内部物化，C 看不见，也不需要看见。

### 类型映射

| Pini | C | 首版 |
|---|---|---|
| `I8` / `U8` | `int8_t` / `uint8_t` | 支持 |
| `I32` | `int32_t` | 支持 |
| `I64` | `int64_t` | 支持 |
| `U64` | `uint64_t` | 支持 |
| `F64` | `double` | 支持 |
| `Bool` | `bool` | 支持，见风险 |
| `*T` | `T*`；T 限 C 标量，非标量目标拒绝 | 支持 |
| 给定块类型 | `<C名>_t` 结构体加 `<C名>_get()` | 支持，字段须全 C 兼容 |
| `()` | `void` | 支持 |
| `^T` | 状态码 + 出参 | 支持，见下 |
| `I16` / `U16` / `U32` / `F32` | — | 拒绝：IR 无对应类型 |
| `String` | `const char*` | 仅形参：转发层入口复制一份，C 可保留原串 |
| `StringHandle` | `bk_str_handle*` | 形参与返回：C 侧拿不透明指针，自己 `retain` / `release` |
| `(A, B) -> C` | `C (*)(A, B)` | 仅形参：转发层把裸地址包成 Pini 函数值 |
| 集合 / 对象 / 元组 | — | 拒绝：非 C 布局 |

拒绝项不是保守，是三通道一致性：IR 表达不了的类型放进来，解释器能跑、LLVM 跑不了，同一个程序换通道就换行为。

形参 `String` 的复制落在转发层入口（`bk_str_dup`），调用返回时释放那一份：C 传栈上的临时缓冲也安全，Pini 若把串存进字段，存下的是自己持有的复制品。返回位仍拒——返回的是 Pini 的临时串，C 拿不到释放权，也说不清有效到什么时候。

### Result 降级

`^T` 不进 C 边界，降成「状态码返回 + 出参」：

```
; Pini
取长度|func(s: *U8,) -> (^I32,):

; 生成的 C
int32_t calc_len(const uint8_t* s, int32_t* out);   /* 0 成功，1 失败 */
```

错误消息不跨边界。err 槽在 IR 里是一个类型擦除的机器字，没有可安全解码的字符串形状，所以 C 侧只拿到状态码（取值见下节），名字另经 `calc_strerror` 还原。`last_error` 这个名字也不再预留 —— 符号从未实现，占着它只会挡住想自己导出错误访问器的库；要错误细节，就把消息写进导出的给定块字段，或另导出一个返回 `*U8` 的函数。

### 错误码

失败码有三个固定值：`0` 成功、`1` 未归类失败、`2` 取消。写成 `Result<T, E>` 时 E 进错误集，失败码改由 E 给出，`^T` 保持 `1`/`2`。

分配在语义层的 `ErrorCodePlan`，降载只搬运结果：头文件常量、导出桩返回值、`calc_strerror` 取同一张表。四种来源分三段落座：

| 来源 | 区间 | 触发 |
|---|---|---|
| 派生 | `0x0100`–`0x3FFF`：类型序左移 8 位，或上用例 tag | `enum` 写 `实现: 错误` |
| 手写 | 作者给的任意值，须 ≥ 3 | 扩展块的 `码() -> (I32,)` |
| 自动 | `0x4000` 起，顺序分配，跳开已占位 | 非 enum 写 `实现: 错误` 且没有 `码()` |
| 散列 | `0x1000_0000`–`0x3FFF_FFFF` | `enum` 再写 `实现: 稳定码` |

手写优先是分配顺序，不是优先级声明：手写码先落位，散列与自动再避开。散列不会因为手写码临时加进来而改自己算出的值 —— 它只让开，不顺延别人的位置。

派生码的类型序按类型名排序，只数进错误集的类型：加一个内部错误类型不会挤动已发布库的码，改用例声明顺序会。这是默认档的已知代价，要跨版本稳定就选散列档。

散列键是 `块名 · 类型名 · 用例名` 三段以 U+0000 连接，FNV-1a 64 位后对区间长度取模。块名取导出块头（= 文件名 = 库名），改文件名会改码，这是有意的：C 面的身份就是库名。同一导出面内撞位时按名字字典序线性顺延，条目上记步数，头文件注释写「顺延 N 步」；未撞位则码只由三段名字决定，加删其它类型都不动它。

散列码不是 `基址 | tag`，运行时需要按 tag 查表：`bk_error_from_enum` 多收一个 `const int32_t*`，发射层为每个稳定错误类型发一份模块级常量数组，构造点传指针；派生与自动码传 `null`，运行时保持「基址或 tag」的老路径。

**申报校验**。`码()` 的意义是「把码钉死」，所以它一旦写错就不能按未申报处理 —— 那会让作者以为钉住了，实际拿到的是自动码。四种情形报 `E4-027`：写在 `enum` 上（用例码由 tag 派生）、函数体不是单条 `return <整数字面量>`、值落在 `0`–`2`（固定码）、值超出 `i32`。

**撞码**。自动码与散列码都会避让，剩下的相撞只可能是两个手写码取同值，或手写码压到某个派生码上。发 `E7-005` 而不报错：把两个错误合成一个 C 状态码可能是有意的，编译器没有立场替作者否决它，但必须让作者知道 C 侧从此分不清这两者。

**区间容量**。派生区一个字节的类型序、一个字节的用例 tag：第 64 个错误类型会从 `0x4000` 起与自动区重叠，单个类型的第 257 个用例会溢到下一个类型的基址。两处都报 `E4-027`，并指向越界的那一个类型 —— 静默溢出的后果是两个不相干的错误共用一个码。

**码 → 名字**。每个导出面附带 `const char* <块>_strerror(int32_t code)`：`0`/`1`/`2` 答 `success`、`unclassified error`、`cancelled`，其余按码表查，答条目上的 `类型名.用例名`（UTF-8），未登记的码答 `NULL`。表是两张模块级常量（码数组与名字指针数组），转发体只是一次 `bk_error_lookup`；不取二分是因为错误集通常几十条，维护「表必须有序」这条隐式不变量比线性扫贵。名字取 Pini 原名而不是宏名的 `_uXXXX` 形式：可读性在调试场景压倒 ASCII 洁癖。

### 生命周期

```c
void calc_init(void);
void calc_shutdown(void);
```

`calc_init` 不是空实现：它把每个导出的给定块物化一遍（走 `bk_given_get`），否则 C 可能在 Pini 代码首次取用之前就读到还没物化的槽。`calc_shutdown` 仍是空实现——盒持有到进程结束，没有可归还的东西。两个符号都要留：后补一个必需调用是破坏性 ABI 变更，今天不留，明天加就得让所有已有调用方改代码。

所有权只看分配者：`*U8` 由哪个分配器给出，就由 C 用同一个分配器归还 —— 首版没有 `pini_free`，编译器不替 C 分配跨边界的字符串。Pini 不得把 ARC 对象的地址交出去。给定块的字段区是唯一允许长期外借的地址——因为它的生命周期本来就是进程级。字符串进出边界的把手（不透明句柄 + 字节视图）由第二版接上，见导入面的「句柄」与导出面的类型映射。

导出函数默认不承诺线程安全；异步与调度器不跨边界。给定块字段区的跨线程同步同样归调用方，C 面不提供锁。

### 发射物

| 产物 | 来源 | 现状 |
|---|---|---|
| `calc.h` | `pini emit <模块内文件> calc.h --backend c` | 已落地：走既有后端接缝，含函数原型、量与结构体、`_Static_assert` |
| `libcalc.dylib` | `pini build --shared <模块内文件或模块目录>` | 已落地：发 IR 与链接并成一条命令，产物名取自文件名，默认落在当前目录，`-o` 可改 |
| 不生成 C 实现 | — | 见下 |

共享库这条路有三处与 `emit` 不同，都不出新的语义：

- 产物名是 `lib<文件名>.<后缀>`，文件名先过 `CName.escape`，与头文件里的生命周期符号同源，调用方按同一个名字写 `-l`。
- 运行时按 `-lPiniRuntime` 动态链接，其目录写进 rpath；找不到运行时直接失败，不发一个注定加载不了的库。
- 链接在缺符号时失败：Darwin 的 `-shared` 默认如此，Linux 补 `-Wl,--no-undefined`。

入口要求由命令定，不按模块内容散判。`build --shared` 无条件不要求 `main`；`emit` 要求它，除非模块带 `|c` 条目 —— 那是「这个模块对外发布 C 面」的声明，库没有进程入口是常态；`compile` 与 `run-llvm` 一律要求，它们要落地成能跑起来的进程。两头不靠的模块（既无 `main` 又无 `|c` 条目）在三条命令上都照旧报 E6-004。



#### 头文件路线与 C 后端路线

| | 头文件路线 | C 后端路线 |
|---|---|---|
| 解决的需求 | C 能按契约调到 Pini | Pini 能编译到任何有 C 编译器的平台 |
| 交付物 | `.h` + `.dylib` + 运行时 | `.h` + `.c` |
| 覆盖面 | 只有导出面 | 能力矩阵十四族，逐族表态 |
| 语义实现份数 | 一份 | 两份，漂移没有门禁会响 |
| 工期形态 | 一个分片 | 一个后端 |
| 与现有架构 | 复用 `PiniBackend` 接缝 | 新增第四条通道 |

两个先例值得摆出来。Zig 没有 C 后端，它给 C 调用方的做法是 `export fn` 加 `-femit-h` 生成头文件，交付的是编译产物——它的头文件至今有覆盖不全的老问题（结构体定义漏发，见其 issue 13049），正好提醒我们：结构体 typedef 必须一起发，不能只发函数原型。Nim 反过来，C 后端是它的默认后端，所以宏能直接走预处理器、`importc` 直接写 C 原型——但那是一开始就把「C 是目标」写进架构的代价，不是后来加的互操作特性。

结论：走头文件路线。判据不是工期，是需求层级——「C 能调到 Pini」是互操作需求，「不依赖 LLVM」是部署需求。把两者捆进一个决策，会让互操作被部署的工期拖住。

C 后端路线的真实成本也不是「再加一个 emitter」：C 里没有 ARC、闭包、给定块、调度器的直接对应物，要么在 C 上重建运行时，要么用能力矩阵拒掉那些族。这已经等同于第二个 LLVM 后端的规模，而它换来的东西与 C 互操作无关。

不堵后路：头文件生成读的是 `IRExportBlock`，C 后端路线将来要读的也是同一份数据。后端若落地，头文件契约不变，变的只是它背后的实现——转发层换成真正的 C 实现。

改判条件，出现任一条再启动 C 后端路线：

- 目标平台没有可用的 LLVM。
- C 调用方不能接受「拿 `.dylib` 加运行时」的分发形态。
- 需要把生成的代码交给审计方逐行读。

头文件路线自己的主要代价就是把运行时塞给调用方，缓解办法是静态链进产物，而不是换成 C 后端路线。

导出在 LLVM 侧不需要新调用约定。Pini 函数已经发成朴素函数（`IREmitter.swift:731`，签名里没有隐藏环境指针，也没有显式 sret），标量签名与 C 同形；导出只需补两类转发：函数名转发 `define @calc_add(...) { call @mangle(加法) }`，以及给定块的取址转发 `define ptr @calc_state_get() { %o = call ptr @bk_given_get(@__given_slot_<T>, @__given_init_<T>, <字节数>) ; %f = GEP 跨过 4 槽头 ; ret ptr %f }`。头文件由同一张符号表生成，结构与字段的 `_Static_assert` 常数取自 `IRLayout`。

## 风险

| 风险 | 说明 | 处置 |
|---|---|---|
| `Bool` 的 ABI | Pini `Bool` 在 IR 是 `i1`，C `_Bool` 的寄存器约定需实测确认 | arm64 macOS 实测可用（`bool calc_not(bool)` 往返正确）；换平台要重验，不合就改发 `i8` 并补 `zeroext` |
| 平台名差 | Darwin 的 `stdout` 是宏（`__stdoutp`），Linux 上是真符号；不遮蔽规则下两边写不进同一条 | 平台各自成文件，或 C 侧 shim 统一成稳定名 |
| 工具链入场费 | 声明了宏常量的模块，`check` 与 `run` 需要 C 编译器，解释器通道不再是纯零依赖 | 只在声明宏时触发；找不到编译器就指名报错，不静默降级成「常量不存在」 |
| 导出名冲突 | 无隐式前缀，`add` 这种 `\|c` 名字会与别的库撞 | 建议写成 `<库>_<动作>`；程序内同名可由编译器查，链接期撞名查不了 |
| 布局即 ABI | 给定块的字段顺序、类型一改，C 侧结构体立刻错位 | 头文件带 `sizeof` 与 `offsetof` 断言，错位在 C 编译期就红；改布局按破坏性变更对待 |
| 不变量失守 | C 直写字段可以造出 Pini 侧认为不可能的状态 | C 面只放配置（C 写、Pini 读）；文档写明边界上不做校验，也不加校验 |
| 迁移面 | 4 个 `.pini` 引用 foreign，其中 3 个有合法块 | 工作量小，但 golden 输出要同步 |
| 死配置 | `[ffi].libs` 已接线：LLVM 侧化成 `-l`，解释器侧本来就按块名加载 | 两处语义不同但同源，文档写清「块名与库名可脱钩」即可 |
| 变参的提升做漏 | `i8` 直接传，C 侧读到的宽度与 `va_arg` 要的不一致 | 提升表与 `E4-034` 同批落地；用例覆盖 `I8` / `U8` / `Bool`，C 侧按 `int` 读回比对 |
| 变参只在一条通道 | 解释器转发是固定槽位位转，而 arm64 把变参放栈上 | 声明期 `E7-006` + 调用点 `E5-019`，文案给 `run-llvm` 与 shim 两条出路 |

## 尚未定

**构建期依赖**：宏常量让 `check` 与 `run` 在声明了宏的模块上需要 C 编译器。这是「依赖预处理器」的直接后果，也是唯一需要点头的代价。备选是只在 `build` 时求值、把结果写进产物，`run` 读缓存——多一层缓存文件，换掉工具链依赖。

**求值范围**：建议整数四则加浮点字面量，够覆盖 `(MAX / 2)`、`EOF`、`M_PI`。更宽的做法是生成探针程序并运行，能覆盖任意 C 常量表达式，代价是交叉编译失效；留作后手。

**首版不做**：函数式宏、含 `sizeof` 或类型转换的宏、非 C ABI。回调与变参已由第二版接上，边界见导入面各自小节。
