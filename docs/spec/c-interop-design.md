# C 互操作：导入面与导出面

本文把 C 互操作拆成两个面。导入面把既有 `[库|foreign]` 块从「只能声明函数签名」改成「一张外部符号表」；导出面把 Pini 自由函数与给定块存储发布成 C 符号。两块均已落地，状态见文末分片表。不含 C++ / Rust 互操作、回调、变参、结构体按值、异步跨边界。

**「不覆盖」的读法**：名同（标识符即外部符号名）、只声明（导入不产生定义）、不遮蔽（同名冲突一律报错）。三条各自可独立成立——若你只指其中一条，对应小节可单独裁掉。

## 改前现状

| 事实 | 位置 |
|---|---|
| 块内只有函数签名，形态是裸签名 `malloc(大小: I64,) -> (*I8,)`；`\|unsafe` 写法已被判非法 | `testParserRejectsDraftForeignSignatureForm.pini` |
| 块名即库键：`libc` 走进程映像，其余按 `search_paths` 找 `lib<名>.{dylib,so}` | `FFILoader.swift:22` |
| 符号名等于 Pini 名，无别名机制：解释器 `dlsym`、LLVM 发 `@mangle(名)` | `IRExecutor.swift:395`、`IREmitter.swift:367` |
| 作用域文件级（跨文件 E5-017），但 IR 与解释器按模块合并，同名后者覆盖前者 | `IRExecutor.swift:264` |
| 多返回：IR 只取第一个返回类型，解释器注册期整条拒绝 | `IRLowerer.swift:807`、`ForeignThunk.swift:27` |
| 类型面：解释器认 I16/U16/U32/F32，IR 只认 I8/U8/I32/I64/U64/F64/Bool | `IRLowerer.swift:5608` |
| `[ffi].libs` 解析进配置，无消费方 | `FileLoader.swift:269` |
| 解析靠前瞻区分「签名」与「带体函数」 | `Parser.swift:589` |
| 无导出面：`[文件名\|export]` 是模块可见性重命名，与 C 无关 | `ImportExportDecl.swift` |

这张表里有两件事直接决定新形状的可行性。前瞻启发式会消失：`标识符: 类型` 不可能是顶层声明开头（`top-level-decl` 里没有以标识符加冒号起头的形态），块尾判据退化成两 token 前瞻；导出面则要从零建，IR 里连导出块的位置都没有。

## 三条不变量

| 不变量 | 内容 | 执行面 |
|---|---|---|
| 名即符号 | 块内标识符就是外部符号名，不提供别名映射 | 标识符须为 C 标识符（ASCII 字母、数字、下划线，不以数字起头） |
| 只声明 | 导入不产生定义、不插桩、不拦截 | LLVM 侧只发 `declare`；不为导入符号合成任何包装 |
| 不遮蔽 | 同名冲突一律报错，不合并、不后者胜 | 模块级一张符号表，冲突在语义期裁决 |

名即符号是这三条里最贵的。它换掉的是「Pini 侧随便起中文名、另行指向 C 符号」的自由——边界上的标识符只能是外部世界已有的那几个 ASCII 名。补偿手段是本仓既有的写法：边界保持原名，中文命名留给安全封装层（`examples/ffi_module/cstring.pini` 的 `c串长度` 就是这层）。

## 两条路线

| | 声明视图 | 桥接层 |
|---|---|---|
| 标识符 | 外部符号名 | Pini 别名，外部名另置于块内 |
| 生成代码 | 无 | 每个符号一个 shim（函数转发、变量取址转发） |
| 平台差异 | 写 C shim 库（一行一个符号） | 块内按平台切分支 |
| 与「不覆盖」 | 天然满足 | 别名即盖面，须靠约定自律 |
| 代价 | 名字受外部世界约束；平台差异要在 C 侧解决 | 两套名字长期并存，改名要同步两处 |

按「不覆盖」这条约束，只有声明视图成立——桥接层的别名本身就是外部符号的盖面。桥接层唯一的正当理由是平台差异无法用 shim 吸收；本仓 `examples/ffi_module/lib/ffilib.c` 已经证明 shim 吸收得动，所以不另立路线。

## 导入面

### 语法

```
[libc|foreign]
malloc: (U64,) -> (*U8,)
free: (*U8,) -> ()
stdout: *U8
optind: I32

[ffilib|foreign]
ffi_version|readonly: I32
```

两块并存不是笔误：一个文件可以绑多个库，每块一个，块名仍是库键（`FFILoader.swift:22` 的既有语义不变）。

文法增量：

```
foreign-decl     ::= '[' IDENT '|' 'foreign' ']' foreign-body;
foreign-body     ::= { foreign-symbol };
foreign-symbol   ::= IDENT { '|' foreign-flag } ':' type-annotation;
foreign-flag     ::= 'readonly';
```

与现状的唯一差异是条目形状。函数签名从 `malloc(大小: U64,) -> (*U8,)` 变成 `malloc: (U64,) -> (*U8,)`——函数类型语法语言里早就有（`examples/lambda-typed.pini` 的 `(I32,) -> (I32,)`），这里只是把它放到冒号右边。

代价是参数名消失：函数类型不带标签，`大小` 这类名字写不进去，只能用行尾注释补。不建议为 foreign 单独给函数类型加标签——同一套类型语法在别处不带标签，只在块内带，读者要多记一条规则。

标志位放在标识符与冒号之间，与语言其余修饰符同位（`名|unsafe`、`名|test`、`[名|foreign]`）。冒号由此只做一次切分：左边是符号与它的标志，右边是类型——扫一眼左列就知道有哪些符号，不用读到行尾。`readonly` 不入关键字表，走 `|given` / `|import` / `|export` 那条标识符白名单路径（`Parser.swift:490`），词法不动。

标志是封闭白名单，v1 只有 `readonly`；未知标志报错。这条必须显式做：修饰符位现在收任意标识符（`Parser.swift:1424` 的 `parseIdentifier`），不做白名单校验，`|readonyl` 会静默通过，而这个错只在读回数据时才显形。多条标志可并列、顺序无关；同一条写两次即报错。

注意 —— 这不是把已废弃的 `malloc|unsafe(大小: I64,) -> (*I8,)` 写法请回来。标志位后面必须跟冒号与类型；旧写法没有冒号，照旧报错。

| 标志 | 适用 | 语义 | 状态 |
|---|---|---|---|
| `readonly` | 数据符号 | 禁写：`store(&符号, ...)` 在语义期拒绝 | v1 |
| `macro` | 任意类型条目 | 不解析符号，构建期由 C 预处理器求值并烘成常量；蕴含 `readonly`，不可取址 | v1 |
| `threadlocal` | 数据符号 | 每次访问重新取地址（TLS 描述符不是普通符号地址） | 缓；v1 报错并提示写 shim 函数 |
| `weak` | 函数 | `dlsym` 未命中不 fail-fast，返回空句柄 | 缓；先确认空句柄在 Pini 侧怎么表达 |

### 判型

条目是函数还是数据，由类型决定，不另设关键字。

| 类型 | 含义 | 调用面 | 可带标志 |
|---|---|---|---|
| 函数类型 | 外部函数 | 只能调用，不能取作函数值 | 无（v1） |
| 其余类型 | 外部数据符号（变量 / 外部常量） | 读、取址 | `readonly` |
| 其余类型 + `\|macro` | 编译期常量 | 只读，不取址 | `macro` |

函数类型进块前须满足三条：捕获集为空、取用位为空、返回至多一项。多返回在语义期报错，不再留给 IR 静默截断。

导入的函数不能作值，原因是 Pini 的函数值统一是 `{ code, env }` 胖指针（`IRNode.swift:65`），而 C 函数没有环境槽。要传回调，走 C 侧 shim。

导入符号属模块内部，不进包级可见性（`Visibility.swift:187` 的既有裁决不变）。解析仍是注册期 fail-fast：声明了却解析不到的符号在加载时报错，哪怕从未调用——「只声明」不等于「可以悬空」。

### 数据符号

数据符号的地址就是 `dlsym` 的返回值；它绑定的是外部存储，不是 Pini 的副本。

```
var n = unsafe optind          ; 读：按外部存储的左值取
var p = unsafe &optind         ; 取址：符号地址本身，不复制
unsafe store(p, 3)             ; 写：走既有指针原语
```

写不另造语句形态。`unsafe` 是表达式前缀（`unsafe 表达式`），不是语句前缀；为写操作新增 `unsafe x = 1` 这类语句形态，会破掉「不安全消耗点 = 表达式」这条既有规则。地址加 `store` 已经够用。

注意 —— `&局部变量` 是快照（解释器实现如此，写回不更新原变量），`&外部数据符号` 是符号地址本身。同一个前缀内建按操作数改变语义，这是 `&` 唯一一处这样。理由：外部存储没有 Pini 副本可快照。

注意 —— `readonly` 只挡得住「取址结果直接作 `store` 目标」这一形。先 `var p = unsafe &符号` 再 `unsafe store(p, ...)` 追不到来源：类型里不携带「这个指针指向只读符号」。声明方的承诺在 C 侧，Pini 侧只挡最直白的那一笔。

### 常量

C 的「常量」是两类东西，混在一起会做错。

| 类别 | 是不是符号 | 进法 | 求值时机 |
|---|---|---|---|
| `extern const` 数据对象 | 是 | `名\|readonly: 类型` | 运行期读存储 |
| 宏（`EOF`、`M_PI`、`S_IRUSR`） | 不是，`dlsym` 永远找不到 | `名\|macro: 类型` | 构建期跑 C 预处理器 |

`readonly` 只是声明方的承诺：ELF 与 Mach-O 的符号表不携带 const 限定，链接期无法验证。它的价值在类型检查——写了 `readonly` 的符号，赋值与 `store` 都在语义期拒绝。不叫 `|let`：`let` 描述 Pini 的绑定，换 `var` 就能写；`readonly` 描述 C 对象自身的声明，换不掉。

`|macro` 是另一回事：它没有存储，只是一个构建期算出来的值。所以它能读不能取址，`readonly` 由它蕴含，不用另写。

#### Swift 在这件事上做了什么

Swift 会把「简单常量宏」导入成全局常量：字面量，或字面量与已定义宏之间的 `+` `-` `>` `==` 之类运算。做这件事的是 Clang importer 的 `ImportMacro.cpp`，它按 token 形态逐种匹配，源码里留着一句 FIXME——「让 Clang 把展开当常量表达式解析，而不是做这些特例模式匹配」。这句话本身就是结论：手写模式匹配不是这条路该有的样子。

它的失败方式更值得记：`#define X SDL_UINT64_C(...)` 或 `#define X (某个常量表达式)` 会被静默跳过，Swift 侧看不到任何提示；社区的标准绕过是「写一个返回该宏的 C 函数」。语言层面少一个常量不报错，这种设计不能学。

| | Swift | Pini |
|---|---|---|
| 求值者 | 自己按 token 模式匹配 | C 预处理器（`cc -E`） |
| 覆盖范围 | 字面量与少数运算 | 展开后能落到字面量或整数四则的 |
| 失败方式 | 静默跳过 | 报错并打印展开原文 |

#### 求值路径

1. `pini.toml` 的 `[ffi]` 增加 `headers` 与 `include_paths`，声明宏的来源头与 `-I` 路径。
2. 构建期为块内每个 `|macro` 条目生成一行探针，`cc -E -P` 展开，按标记行读回。
3. 读回的内容按常量表达式解析：整数允许四则与位运算（结果精确）；浮点只接受字面量（自己算会与 C 编译器的舍入不一致）。
4. 值按声明类型查范围，然后作为常量烘进 IR——三个通道读到同一个字面量，不经过 `dlsym`。

编译器取 `/usr/bin/cc`，换工具链用 `PINI_CC` 指绝对路径：`Process` 只认可执行文件的绝对路径，不查 `PATH`。

```
[libc|foreign]
EOF|macro: I32
M_PI|macro: F64
```

代价写在明处：声明了宏常量的模块，`check` 与 `run` 都需要 C 编译器。这是宏常量的入场费——值只能由 C 的头文件体系给出。没声明的模块照旧零依赖，「单文件不用工具链」的故事不变。

`errno` 是这条路的边界样本：两边都是函数式宏（Darwin `(*__error())`，glibc `(*__errno_location ())`），展开后不是常量，构建期直接报错并打印原文。实测输出是「宏常量 `errno` 展开后是 `(*__error())`，不是常量表达式：运算符 `*` 出现在不该出现的位置」——原文与理由一起给，读者看得出该写 shim 而不是改声明。要用它就写 `pini_errno: () -> (*I32)` 加一行 C shim。

不给「块内写值」的后门仍然成立：`EOF: I32 = -1` 看着像导入，实际是 Pini 侧自己造了个常量，与外部世界再无关系；哪天 C 侧改了值，没有任何门禁会响。`|macro` 保住了「值来自头文件」这条链路，只是把求值提前到了构建期。

### 冲突裁决

这张表是「不遮蔽」的执行面。前提是把作用域从文件级升到模块级——符号表本来就按模块合并（`IRExecutor.swift:264`），文件级可见性只制造「声明在 A、用不了在 B」，挡不住同名冲突。

| 情形 | 裁决 |
|---|---|
| 同模块两文件同名同型 | 合并为一条 |
| 同名异型 | 报错：同一外部符号的两种类型断言无法并存 |
| 同名异库 | 报错：解析目标不唯一 |
| 宏常量与符号同名 | 报错：一个是构建期值，一个是运行期存储，无法并存 |
| 与本地函数 / 类型同名 | 报错：本地定义会盖住外部符号 |
| 与导出名同名 | 报错：导出会定义导入所声明的符号 |
| 块内重复 | 报错 |
| 标识符非 C 标识符 | 报错 |

同时删掉两处现存的「后者胜」：`IRExecutor.foreignDecls` 的字典覆写，以及 `IRLowerer` 只取首个返回类型。

## 导出面

### 可导出的东西

先前的判断是「只有函数能导出」，理由是 Pini 没有模块级存储。这条判断错了一半：给定块（`[名|given]`）确实是一块进程级存储，但 `using` 形参并不是通向它的引用。

两层要分开。**默认实例的盒**由 `bk_given_get` 惰性物化、恰一次、地址稳定到进程结束（`PiniRuntime.swift:525`）；而 `using` 形参在取用点拿到的是这个盒的**副本**——发射层 `memcpy` 载荷到新分配的一份（`IREmitter.swift:3084`），解释器同样返回值（`IRExecutor.swift:1248`）。于是：

| 动作 | 结果 |
|---|---|
| C 写字段区 | Pini 下一次取用拷到新值，读得到 |
| Pini 在 `using` 体内写字段 | 只改副本，盒不变，C 读不到 |
| Pini 经引用字段（`*T` / 对象引用）往下写 | 双方共享那一块内存，可见 |

导出面发布的是**盒**，不是副本。导出的量因此在数据流上是单向的：C 可写、Pini 可读；反向要么把字段声明成引用类型，要么另导出 setter 函数。这不是实现取舍，是 `using` 的副本语义决定的。

| 类别 | 块内写法 | C 侧形态 |
|---|---|---|
| 函数 | `C名 = Pini名` | 一个 C 函数 |
| 模块级量 | `C名: 给定块类型` | 结构体视图 + 取址函数 |

方法、泛型、`|test`、`main` 仍不进导出面；泛型给定块要按实参特化，v1 也拒。

给定块能导出，靠的是别的 Pini 值没有的一条性质：生命周期是进程级。`bk_given_get` 把盒缓存在进程里直到结束，地址不变，所以 C 拿到字段区指针后不会遇到「对象已释放」。普通对象与集合没有这个保证，因此不进导出面。

注意 —— 这不是给语言新增全局可变状态。给定块本来就是进程级存储，导出只是给它加一个 C 可见的名字；Pini 侧改不动它，原因见上表。

### 语法

```
[calc|c]
calc_add = 加法
calc_state: 计数器状态
```

文法增量：

```
export-c-decl    ::= '[' IDENT '|' 'c' ']' NEWLINE { export-c-item };
export-c-item    ::= IDENT '=' IDENT     ; 函数：C 名 = Pini 自由函数
                   | IDENT ':' IDENT     ; 量：C 名 : 给定块类型
```

`=` 与 `:` 的分工与导入面同一套读法：冒号右边是类型，等号右边是定义。函数有定义可绑，量只有类型可指，于是形状不同——不是两套语法，是同一句话说两种东西。

键是 C 符号名，值是 Pini 侧的名字。类型由定义或给定块派生，不在块里重写——重写就有两份签名，漂了没有任何门禁会响。块名命名产物（`libcalc.dylib` / `libcalc.so`）与两个生成的生命周期符号（`calc_init` / `calc_shutdown`），不参与条目符号名，也不自动加前缀：要前缀就把前缀写进键（如上例的 `calc_`）。

这与 `[文件名|export]` 的条目形态相同而语义不同：那一个管模块间可见性，这一个管 C ABI。两块并存，不合并。

模块内最多一个 C 导出块。要产出两个库就分两个模块，避免合并规则。

### 标识符转 ASCII

Pini 标识符可以是 UTF-8，C 标识符只能是 ASCII。每个对外名字都过一遍 `CName.escape`：

| 源字符 | 输出 |
|---|---|
| `A`–`Z`、`a`–`z`、`0`–`9`、`_` | 原样 |
| 其他（含全部非 ASCII） | `_u` + 6 位大写十六进制 |

ASCII 名字零变化是硬要求：`calc_add = 加法` 的对外名就是 `calc_add`。下划线若也转义，`calc_add` 会变成 `calc_0add`，等于把最常用的命名风格毁掉。

单射靠两条导出期禁令守住，不靠转义表：

- 名字里含字面 `_u` 加 6 位十六进制 ⇒ 拒。它与转义输出同形，解码时无法区分是码位还是原文。
- 转写后落在 C 保留区（`__` 开头或 `_` 加大写字母开头）⇒ 拒。这类名字 C 编译器照样接受，但属未定义行为。

固定 6 位宽度是第三条：`点` → `_u0070B9`。变宽的话 `_u70B9` 后面接一个数字会被读成更长的码位。6 位也顺手把「4 位字面量」排除在撞名之外——`_u70B9` 不是合法的转义形状，原样保留即可。

裸写 `加法` 也能导，对外名是 `_u52A0_u6CD5`——合法但难读，所以推荐显式给 ASCII 名。字段名走同一条规则，中文字段在 C 侧就是 `_uXXXX` 形状；要可读就让字段名用 ASCII。

转义只发生在导出侧。导入侧不转：那里的标识符就是外部符号名，转一道等于把名字换掉，而「名即符号」禁的正是这个——所以导入项写不出 C 标识符就报错（见冲突裁决表末行），不会替你改名。

不复用 `IRName.mangle`：那套只转非 ASCII、不动下划线，宽度也随码位变（`%04X`），`点` 与字面 `_u70B9` 会撞。IR 侧的名字是编译器私事，改它要同时动解释器与两处发射的符号一致性；对外名是 ABI 契约，值得单独一条函数。两套名字不要求一致。

导出期还要查一次撞名：两个键经 escape 后相同即报错，字段同理。查得到的只是导出面内部的撞名；C 侧自己写的符号撞上来，编译器看不见。

### 模块级量

给定块的存储是一块地址稳定的缓冲，字段区在 4 槽箱头之后（`IRLayout.standard.headerSlotCount`）。C 侧看到的是字段区的视图：

```c
typedef struct calc_state_s {
    int32_t count;
    int32_t limit;
} calc_state_t;

calc_state_t* calc_state_get(void);   /* 盒的字段区；Pini 侧 using 拷的是副本，不指向这里 */
```

```
[计数器状态|given]
    count: I32 = 0
    limit: I32 = 100
```

导出规则四条：

- 字段须全部 C 兼容；有一个不合格就整块拒，不留「部分字段」的半布局。
- 结构体只镜像字段区，不镜像箱头：取址函数在 LLVM 侧跨过头，C 不需要知道头有多宽。
- 头文件为结构与每个字段生成 `_Static_assert`（`sizeof` 与 `offsetof`），布局漂移在 C 编译期就红，而不是运行期读到错位。
- 直连还是访问器：直连（上面这种）与「每字段一对 get/set」相比，API 面小、无调用开销、读写即时。访问器唯一的好处是字段名不进 C，省掉转义后的怪名字，代价是每字段多两个符号。选直连——这个位置的意义就在于 C 能直接读写它；Pini 侧读写同一块存储要靠引用字段或 setter，与选哪种形无关。

字段名走同一条转义规则，所以上面的例子写的是 ASCII。若字段写成 `计数`，C 侧就是 `_u008BA1_u006095`——合法但没人愿意在 C 里敲。想让 C 侧可读，字段名就用 ASCII；这是「名即符号」在字段上的同一笔代价。

想让读写读起来像全局量，调用方自己加一行 `#define calc_state (*calc_state_get())` 即可。生成器不替你做：宏会把它之后所有同名标识符一并替换，连 `calc_state_t` 的用法都可能被卷进去，这种便利得让使用方自己决定要不要。

注意 —— C 侧写入不做任何校验。Pini 侧的不变量（「count 不得超过 limit」这类）在边界上没有防线，所以给定块导出适合放配置——C 写、Pini 读。要让 Pini 侧也写，字段得声明成引用类型，或者另导出一个 setter 函数。

注意 —— 导出函数在边界内填的默认实例是**副本**：函数体读到的是调用时刻的一份拷贝，写回只落在拷贝上。要让函数改动对 C 可见，同样走引用字段或 setter。

### using 参数

导出函数的 C 原型不含 `using` 形参：它在边界内由默认实例填充，而 C 没有第二个实例可传。

```
; Pini
累加|func(using 状态: 计数器状态, n: I32,) -> (I32,):
    return 状态.count + n

; 生成的 C
int32_t calc_add(int32_t n);
```

反方向不成立：Pini 侧可以显式传自备实例（`累加(自备, 5)`），C 侧不能。这是 `using` 的语义在边界上的自然截断，不是遗漏。

如果 `using` 形参的类型没有可导出的给定块，函数本身照样能导出——实参在模块内部物化，C 看不见，也不需要看见。

### 类型映射

| Pini | C | 首版 |
|---|---|---|
| `I8` / `U8` | `int8_t` / `uint8_t` | 支持 |
| `I32` | `int32_t` | 支持 |
| `I64` | `int64_t` | 支持 |
| `U64` | `uint64_t` | 支持 |
| `F64` | `double` | 支持 |
| `Bool` | `bool` | 支持，见风险 |
| `*T` | `T*`；目标不透明时 `void*` | 支持 |
| 给定块类型 | `<C名>_t` 结构体加 `<C名>_get()` | 支持，字段须全 C 兼容 |
| `()` | `void` | 支持 |
| `^T` | 状态码 + 出参 | 支持，见下 |
| `I16` / `U16` / `U32` / `F32` | — | 拒绝：IR 无对应类型 |
| `String` / 集合 / 对象 / 元组 / 函数 | — | 拒绝：非 C 布局 |

拒绝项不是保守，是三通道一致性：IR 表达不了的类型放进来，解释器能跑、LLVM 跑不了，同一个程序换通道就换行为。

### Result 降级

`^T` 不进 C 边界，降成「状态码返回 + 出参」：

```
; Pini
取长度|func(s: *U8,) -> (^I32,):

; 生成的 C
int32_t calc_len(const uint8_t* s, int32_t* out);   /* 0 成功，1 失败 */
```

错误消息不跨边界。err 槽在 IR 里是一个类型擦除的机器字，没有可安全解码的字符串形状，所以 C 侧只拿到状态码 `1`。`calc_last_error()` 因此 v1 不发：发一个永远返回空串的符号，比不发更容易误导。需要错误细节的调用方，把消息写进导出的给定块字段，或另导出一个返回 `*U8` 的函数。

### 生命周期

```c
void calc_init(void);
void calc_shutdown(void);
```

`calc_init` 不是空实现：它把每个导出的给定块物化一遍（走 `bk_given_get`），否则 C 可能在 Pini 代码首次取用之前就读到还没物化的槽。`calc_shutdown` 仍是空实现——盒持有到进程结束，没有可归还的东西。两个符号都要留：后补一个必需调用是破坏性 ABI 变更，今天不留，明天加就得让所有已有调用方改代码。

所有权只有一条：返回给 C 的 `*U8` 由调用方用 `pini_free` 归还，Pini 不得把 ARC 对象的地址交出去。给定块的字段区是唯一允许长期外借的地址——因为它的生命周期本来就是进程级。字符串进出边界的把手（不透明句柄 + 字节视图）留到第二版，首版让 Pini 侧自己写 `*U8` 封装。

导出函数默认不承诺线程安全；异步与调度器不跨边界。给定块字段区的跨线程同步同样归调用方，导出面不提供锁。

| `libcalc.dylib` | `pini emit <模块内文件> calc.ll` 后 `clang -shared calc.ll -lPiniRuntime` | 暂无内置产物模式；`build` 仍是 `check` 的别名 |

#### 头文件路线与 C 后端路线

| | 头文件路线 | C 后端路线 |
|---|---|---|
| 解决的需求 | C 能按契约调到 Pini | Pini 能编译到任何有 C 编译器的平台 |
| 交付物 | `.h` + `.dylib` + 运行时 | `.h` + `.c` |
| 覆盖面 | 只有导出面 | 能力矩阵十四族，逐族表态 |
| 语义实现份数 | 一份 | 两份，漂移没有门禁会响 |
| 工期形态 | 一个分片 | 一个后端 |
| 与现有架构 | 复用 `PiniBackend` 接缝 | 新增第四条通道 |

两个先例值得摆出来。Zig 没有 C 后端，它给 C 调用方的做法是 `export fn` 加 `-femit-h` 生成头文件，交付的是编译产物——它的头文件至今有覆盖不全的老问题（结构体定义漏发，见其 issue 13049），正好提醒我们：结构体 typedef 必须一起发，不能只发函数原型。Nim 反过来，C 后端是它的默认后端，所以宏能直接走预处理器、`importc` 直接写 C 原型——但那是一开始就把「C 是目标」写进架构的代价，不是后来加的互操作特性。

结论：走头文件路线。判据不是工期，是需求层级——「C 能调到 Pini」是互操作需求，「不依赖 LLVM」是部署需求。把两者捆进一个决策，会让互操作被部署的工期拖住。

C 后端路线的真实成本也不是「再加一个 emitter」：C 里没有 ARC、闭包、给定块、调度器的直接对应物，要么在 C 上重建运行时，要么用能力矩阵拒掉那些族。这已经等同于第二个 LLVM 后端的规模，而它换来的东西与 C 互操作无关。

不堵后路：头文件生成读的是 `IRExportBlock`，C 后端路线将来要读的也是同一份数据。后端若落地，头文件契约不变，变的只是它背后的实现——转发层换成真正的 C 实现。

改判条件，出现任一条再启动 C 后端路线：

- 目标平台没有可用的 LLVM。
- C 调用方不能接受「拿 `.dylib` 加运行时」的分发形态。
- 需要把生成的代码交给审计方逐行读。

头文件路线自己的主要代价就是把运行时塞给调用方，缓解办法是静态链进产物，而不是换成 C 后端路线。

导出在 LLVM 侧不需要新调用约定。Pini 函数已经发成朴素函数（`IREmitter.swift:731`，签名里没有隐藏环境指针，也没有显式 sret），标量签名与 C 同形；导出只需补两类转发：函数名转发 `define @calc_add(...) { call @mangle(加法) }`，以及给定块的取址转发 `define ptr @calc_state_get() { %o = call ptr @bk_given_get(@__given_slot_<T>, @__given_init_<T>, <字节数>) ; %f = GEP 跨过 4 槽头 ; ret ptr %f }`。头文件由同一张符号表生成，结构与字段的 `_Static_assert` 常数取自 `IRLayout`。

## 风险

| 风险 | 说明 | 处置 |
|---|---|---|
| `Bool` 的 ABI | Pini `Bool` 在 IR 是 `i1`，C `_Bool` 的寄存器约定需实测确认 | arm64 macOS 实测可用（`bool calc_not(bool)` 往返正确）；换平台要重验，不合就改发 `i8` 并补 `zeroext` |
| 平台名差 | Darwin 的 `stdout` 是宏（`__stdoutp`），Linux 上是真符号；不遮蔽规则下两边写不进同一条 | 平台各自成文件，或 C 侧 shim 统一成稳定名 |
| 工具链入场费 | 声明了宏常量的模块，`check` 与 `run` 需要 C 编译器，解释器通道不再是纯零依赖 | 只在声明宏时触发；找不到编译器就指名报错，不静默降级成「常量不存在」 |
| 导出名冲突 | 无隐式前缀，`add` 这种键会与别的库撞 | 建议键写成 `<库>_<动作>`；程序内同名可由编译器查，链接期撞名查不了 |
| 布局即 ABI | 给定块的字段顺序、类型一改，C 侧结构体立刻错位 | 头文件带 `sizeof` 与 `offsetof` 断言，错位在 C 编译期就红；改布局按破坏性变更对待 |
| 不变量失守 | C 直写字段可以造出 Pini 侧认为不可能的状态 | 导出块只放配置（C 写、Pini 读）；文档写明边界上不做校验，也不加校验 |
| 迁移面 | 4 个 `.pini` 引用 foreign，其中 3 个有合法块 | 工作量小，但 golden 输出要同步 |
| 死配置 | `[ffi].libs` 无人消费 | 与符号表一起接线，或删掉；留着比删掉更容易误导 |

## 尚未定

**构建期依赖**：宏常量让 `check` 与 `run` 在声明了宏的模块上需要 C 编译器。这是「依赖预处理器」的直接后果，也是唯一需要点头的代价。备选是只在 `build` 时求值、把结果写进产物，`run` 读缓存——多一层缓存文件，换掉工具链依赖。

**求值范围**：建议整数四则加浮点字面量，够覆盖 `(MAX / 2)`、`EOF`、`M_PI`。更宽的做法是生成探针程序并运行，能覆盖任意 C 常量表达式，代价是交叉编译失效；留作后手。

**首版不做**：函数式宏、含 `sizeof` 或类型转换的宏、变参、回调、非 C ABI。
