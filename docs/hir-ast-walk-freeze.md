# AST 走查冻结口径 + 调试面可验清单

> 落件 = **P3-G4（2026-09-16）**。状态：**在册，现行**。
> 对象：P4 删除 AST 走查**之前**的这段过渡期，以及调试面「哪半边现在就能验」。
> 本件是**纪律**，不是设计：它不描述代码该怎么改，只规定改的时候要留下什么。

## 0. 为什么要这一件

P4 会删掉 AST 走查，只留 HIR 引擎。但从现在到 P4 之间，AST 走查**仍在服役**：
它还是默认执行引擎（`PINI_INTERP_ENGINE` 默认 `ast`），解释器测试、调试器、
CPS 都建在它上面。

这段过渡期有个具体的失败方式：走查路径被随手改动，而改动的人没意识到自己在
给一个**预定要删**的东西加负担。等 P4 真来删的时候，这些改动要么一起被删掉
（白做），要么变成必须迁移的活（额外成本），而**没有任何一处记录**说明它们
为什么存在。

`D-B3=A` 已经裁过：末态是退役，不是冻结成第二前端（新语法只在 HIR 侧实现，
冻结的实现会腐烂）。所以这里要管的不是「不许动」，而是**动的时候留下痕迹**。

## 1. 冻结口径

**冻结 = 改动须声明，不是禁止改动。**

- 允许改：修 bug、加断言、改共享单源、任何有理由的改动。
- 要求：命中 §2 清单的改动，**提交信息里必须带 `[ast-walk]`**，并说明改了什么、
  为什么必须现在改、以及它在 P4 时的归宿（随走查一起删 / 需迁到 HIR / 无所谓）。
- 门禁：`hooks/commit-msg` 调 `tools/ast-walk-freeze-check.py`，命中清单而无标记
  即**拒绝提交**。想跑一遍而不提交：`python3 tools/ast-walk-freeze-check.py`。

定位是**门槛，不是禁令**：它拦的是「无意识改动」，不拦任何有理由的改动——
带上标记、写清理由即可通过。

## 3. 例外与升级

- 一次提交里既有冻结面又有别的改动：**照常带标记**，无需拆提交。
- 门禁本身要改（清单增删）：改 `tools/ast-walk-freeze-check.py` 里的 `FROZEN`，
  并在提交信息里说明增删理由。
- P4 完成、走查删除后：**本件整体作废**，连同 `hooks/commit-msg` 里的对应段落一起删。
  作废判据 = `Interpreter.swift` 的走查求值入口不再存在。

## 4. 调试面：现在可验的那半边

调试面在 P1-5 被拆成两半。`DebugContext` 有四个字段，它们的**可验性不同**：

| 字段 | 来源 | 现在可验？ | 说明 |
|---|:---:|:---:|---|
| `depth` | 引擎自身状态 | ✅ | 供 step-over 判定（`.over(d)` 用 `ctx.depth <= d`），与位置无关 |
| `callStack` | 引擎自身状态 | ✅ | 停事件展示用，与位置无关 |
| `variables` | 引擎自身状态 | ✅ | 停事件展示用，与位置无关 |
| `location` | AST 位置 | ❌ | 断点匹配（`breakpointMatches`）与停事件定位都依赖它 |

**可验那半边 = `depth` / `callStack` / `variables`**：这三个字段来自引擎自身状态，
不依赖位置基准，所以**现在**就可以对两台引擎做同形验证，不必等位置落地。

**不可验那半边 = `location`**：HIR 节点没有位置（`HIRExecutor` 只有 `noLocation`
占位）。P1-5 已把 HIR 侧对暂停点的接线判为休眠态（接了必然报 `noLocation`，
断点按行号相等匹配 ⇒ 永不命中，比「调试器还不在」更坏），由一条会变红的断言钉住。
它的前置是 `docs/issue-hir-node-source-position-2026-09-12.md`，归 **P4**。

**REPL 是另一条接缝，不在本清单内**：实测 `ReplSession` 不消费 `debugHook`，
与调试面无关；它迁移的真实前置是「每次求值新建 `Interpreter()`」这一形态对齐
（P4 会翻转默认引擎）。本件只登记，不作承诺。

  纪律格只会让它变重。
