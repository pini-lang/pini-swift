# `P0d`（`Char` 类型落地）排期方案 —— 三个选项与建议

> **性质**：**方案件，不含裁决**（用户 2026-09-17 指令 = 「考虑 `P0d` 如何排期」）。
> **背景**：常设阻塞队列把 `P0d` 记为「已裁 + 有前置工单 + **未排期**」的**悬挂格**
> （`docs/issue-hir-blocker-queue-2026-09-17.md` §4 末条）。本件把「怎么排」摊成选项。
> ⚠️ **本件不排期、不动源码、不改 `ADR-033`**；排期决定须另行点名。

---

## 1. 事实基础（全部实测，2026-09-17）

| # | 事实 | 测法 / 出处 |
|---|---|---|
| 1 | `HIRType` **0 个 `char` case**，`P0d` 从未开工 | `grep -c 'case char' Sources/PiniCore/HIR/HIRNode.swift` → **0** |
| 2 | 契约把它列为**未落地的预留位** | `docs/spec/hir-contract.md` §4.1「`char` 节点（**待 `P0d` 落地**）」；同处 §4.2 的 `.join` **已于 2026-09-17 兑现** ⇒ 翻转完成后 **`char` 是唯一还空着的预留位** |
| 3 | **迁移面三类**（`ADR-033 D4` 实测清单） | ① 三处类型表示各加 `char` case（`Value` / `HIRType` / `TypeAnnotation`）② **六处**谓词签名 `String` → `Char`（`is_letter` · `is_ascii_digit` · `is_number` · `chars` · `ord` · `chr`）③ **两处**返回类型（`s[i]`、`chars` 元素） |

| 6 | **不在顺序硬约束链内** | 主计划的链是 `P0 → P0c → P0b → P1 → P2 → P3 → P4`，**不含 `P0d`**；全 `docs/` 范围**无任何延后/取消裁决** ⇒ 它是**未排期**，不是被否 |
| 7 | LLVM 端工程量已压过 | `ADR-033 D5`：LLVM 端**只调 runtime shim**（加若干 `bk_string_grapheme_*`），**不在 IR 内实现 UAX#29** |

## 2. 排期前要过的四道约束（这些决定了「能不能顺手做」）

1. **它是语言面变更，且要动契约**：`HIRType` 加一个 case ⇒ 契约 §1 同步、计数 **61 → 62**、
   三锚点（`interp-hir` / `printer` / `llvm`）同步 ⇒ 按治理纪律**走 `spec §1.3`**（`ADR-040` 是同形的先例）。
   ⚠️ **契约行 / enum case / 三锚点必须同批** —— `ADR-040` 已实测过中途态是红的。
2. **它改用户可见行为**：`s[i]` 从 `String` 变 `Char`、`chars` 元素类型变 ⇒ **既有程序与夹具会动**。
   ⚠️ 本件**未测**影响面（要测就得先实现或先做静态普查）；这是下面三个选项共同的未知量。
3. **主线正在不可逆面之前**：`LR-4` 的 `G-6`（删 4100 行 AST 走查）**不可逆**。
   走查还在的窗口里做语言面变更，好处是**能并排对照两个引擎**；翻转之后就只能靠 golden 与 LLVM 臂。
4. **「一名两义」现在就存在**：FFI 的单字节 `Char` 与 spec §2.7「`Char` 不进 FFI 标量集」已经不一致
   （`ADR-033 D2` 的裁决要**改的就是这个现状**）—— 也就是说**前置项的价值不依赖于 `P0d` 本体何时做**。

## 3. 三个选项

| 选项 | 做什么 | 代价 | 收益 |
|---|---|---|---|
| **A · 并入 `LR-4`**（排在 `G-6` 之前，作 `P4-γ` 的一个单元） | 前置腾名 + 三处类型表示 + 六处谓词签名 + 两处返回类型 + 契约 §1/§4.1 + LLVM shim | 中断主线，且**插在不可逆面前**：影响面（约束 2）未测，一次语言面变更会让 `G-6` 的残余清单**在临门前变动**；契约计数变更要再走一次 §1.3 | 走查仍在 ⇒ **两引擎可并排对照**，落地质量最高 |
| **B · 排在 `LR-4` 之后**（独立里程碑） | 同上，但排在 `P5` 之后 | 契约核验会**长期带一个未落地预留位**（约束见事实 2）⇒ 必须在 `P5` 收口时**显式登记处置**，否则「契约 clean」的读数长期失真 | 主线不被打断；`G-6` 的残余清单不再临门变动 |
| **C · 只做前置腾名**（`CChar` rename），类型落地另排 | 实施 `issue-ffi-char-rename-cchar-2026-09-12.md`（腾名：3 处代码 + spec §2.7 增补） | 一次**半途**工作（但很小：3 处代码 + 一处规范增补）；腾名后 `Char` 名**空置**（在 `P0d` 落地前，grapheme `Char` 并不存在，属**预留名**） | **解的是现在就存在的冲突**（约束 4）；且它**与主线正交**，不碰契约节点、不碰 HIR |

## 4. 我的建议：**C 先行，`P0d` 本体取 B**

三条理由：

1. **C 的收益与 `P0d` 的排期无关** —— 它解的是「FFI 单字节 `Char` 与规范不一致」这个**现行**冲突，
   而该冲突**现在就成立**（约束 4）。⇒ 让 `C` 等 `P0d` 的排期，等于让一个已知不一致**无故多存在一段时间**。
2. **A 的「走查窗口」收益被高估** —— `P0d` 改的是**类型表示与内建签名**，
   而两引擎的对照（`ast ⇄ hir`）在**类型层**本来就是分开的（同一份 `TypeChecker` 服务两侧）。
   ⇒ 真正需要并排对照的是**新类型的运行语义**，那部分由既有夹具面与探针覆盖，不依赖走查是否还在。
3. **B 的唯一代价可以被一次文档动作消掉** —— 把「`char` 预留位的处置」写进 `P5` 收口清单
   （落地 / 显式延后，二选一），「契约 clean 长期带空位」这件事就变成**已登记的读数**，而不是隐形的失真。

⚠️ **两条前置纪律**（无论取哪个选项）：
- `P0d` 落地时**必须走一次 `spec §1.3`**（契约计数变更），并把「契约行 / enum case / 三锚点」同批交付。
- 落地**之前先做一次影响面普查**（哪些夹具/示例动 `s[i]` 与 `chars`）——
  否则「无新增红」这条判据在开工当天才知道分母。

## 5. 不做范围

- 本件**只提案**：不含裁决、不排期、不建分支、不改源码。
- 不改 `ADR-033`（它已 Accepted，三决策与迁移面清单**本件照抄不改**）。
- 不把「字符字面量 `'c'`」与 `P0d` 合并（`ADR-033 D3` 已裁**拆格**）。
