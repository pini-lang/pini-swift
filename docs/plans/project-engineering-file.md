# 项目工程档案：Pini（pini-swift 实现仓）

> 本件是跨轮次工程记忆的载体。回访时先读本件恢复上下文，再读 `backend-layering-plan.md` 看当前进度。
> 登记纪律：ADR 只增不删，废弃的标状态；接口约定是契约，实现不得擅自偏离。

## 1. 项目概况

一句话目标：实现 Pini 语言 —— 静态类型、行敏感、缩进敏感、组合式的系统编程语言，单层 IR 服务多后端。

当前阶段：**工程周期 ④ 评审与重构**。结构评审已完成，修订计划已采纳，Linux CI 已建成并实测通过。
最后更新：2026-10-30。

| 本机开发工具链 | Apple Swift 6.4（与声明一致） | `swift --version` |

CI 的三条口径：

- **工具链与包声明同版**：镜像取 6.4，与 `swift-tools-version:6.4` 对齐；低版本工具链解析不了该包，
  故不设版本矩阵 —— 矩阵只会把「声明与镜像不一致」变成一条红两条绿。
- **LLVM 成对安装**：`clang-18` 与 `llvm-18` 同源，`lli` 因此可用。测试套件里 `run-llvm` 需要 `lli`，
  缺它时那批判据只能失败，不能静默跳过。
- **不以 root 运行**：只读文件的权限判据在 root 下恒真，那一条会从判据退化成空判。入口脚本对此有断言。

## 3. 架构决策记录（ADR）

### ADR-001 单层 IR 服务全部后端

状态：**生效**（先于本轮，记在 `../spec/ir-contract.md` 与参考件）

- 场景：需要同时服务解释器、LLVM、字节码、WASM、JIT 五个后端名册成员。
- 决策：编译器中端只有一套带类型的结构化语句树 IR；所有分析以它为输入面，各后端自行降级。
- 理由：多套 IR 会让「同一语义」在层与层之间产生翻译损耗，且每套都要自己的契约与检查器。
- 代价：IR 必须自己承载足够事实，否则后端只能各自补推导 —— 本代价正是 ADR-004 的起因。

### ADR-002 摘除 C 通道

状态：**已完成**（2026-10-30，提交 `1c89a6f`）

- 场景：为验证多后端可行性接入了第三个后端（C）。
- 决策：整条移除 —— 实现 3,440 行、测试 1,121 行、计划件与语料一并删。
- 理由：通道停在 42/51，剩余缺口是并发族，而该族没有判据；继续重建等于把编译器最贵的一段
  复制第三遍。
- 代价：少了一个零依赖宿主通道；换来的是把问题定性为结构问题而非工程量问题。

### ADR-003 解释器保持独立实现

状态：**生效**

- 场景：运行时语义存在两份实现（`RuntimeOps` 与 `PiniRuntime`）。
- 决策：只统一内建**清单与契约**，不统一实现；解释器保持独立，不接 C-ABI 运行时。
- 理由：仓内既定判据是「两条通道同时错会互相认证」；解释器的价值在于它是独立的一份。
- 代价：同一语义长期维护两份，任何内建变更都要改两处 —— 用三方对照脚本兜住。

### ADR-004 采纳「中端上提」，先薄化后端后硬化边界

状态：**已采纳，未执行**（计划见 `backend-layering-plan.md`）

- 场景：新增后端的边际成本约等于复制一遍编译器（ADR-002 实测）。
- 决策：先做布局归位与所有权归位（中端补齐），再补后端接缝与内建清单，最后拆 target 硬化边界。
- 理由：拆 target 的收益取决于层内职责已单一；在发射器还兼着 ARC 与布局时拆，只是换个目录。
- 代价：布局与所有权的手术都在 5,581 行文件内进行，冲突面大；期间边界仍靠约定。

### ADR-005 不引入 HIR / MIR 双层

状态：**已裁，不采纳**（2026-10-30）

- 场景：评估「中端指令化（MIR）」路线作为结构问题的解法。
- 决策：不采纳，改用同一套 IR 上的 pass 链。
- 理由：与 ADR-001 冲突；且当前问题不是 IR 不够低，是职责没分层。
- 代价：pass 链的表达力弱于专用 MIR；若将来出现需要打破结构化控制流的优化，须重开此案。

### ADR-006 Linux CI 用钉死工具链的容器镜像

状态：**已落地并实测**（2026-10-30）

- 场景：原 CI 跑 `swift:6.2` / `6.3` 矩阵，而包声明 6.4；镜像里也没有 `lli`，`run-llvm` 那批判据
  在 Linux 上不可能通过。实测证明问题比这更早：**Linux 侧从来就编不过** —— 三处平台差异会直接
  掐死构建（见下面的代价一栏）。
- 决策：单镜像、单工具链、无矩阵；工具链与系统依赖全部烘进 `ci/Dockerfile`，运行时不装任何东西；
  GitHub 只负责构建镜像并挂载源码跑同一条入口脚本（`ci/entrypoint.sh`），本地用 `ci/run-local.sh`
  跑同一条。
- 理由：矩阵把「版本不匹配」摊成多行红绿，读的人要自己推断哪行才是真信号；单一版本 + 启动自检
  把这类问题压成一条明确的失败信息。运行时装包还会引入源站抖动，属于不可控变量。
- 代价：建 CI 的同时补了四处平台差异 —— 两处 `pthread` 销毁器形参在 Glibc 下可空、一处
  `pthread_getattr_np` 未被 Swift 的 Glibc 模块导出（改用符号直连）、一处测试目标的并发检查口径
  随平台而异（统一为 Swift 5 模式）。升级工具链还要改镜像并重建。

### ADR-007 测试目标的语言模式与源码目标对齐

状态：**已撤销**（同日被 ADR-008 取代；保留以记沿革）

- 场景：同一份测试代码在 macOS 编得过、在 Linux 编不过 —— 两端对 `@Sendable` 捕获的判决不同。
- 决策：测试目标显式设为 Swift 5 模式，与三个源码目标一致。
- 理由：当时以「判据跨平台同解」为先，降低一档语言模式是最小改动。
- 代价：测试代码失去严格并发检查，且这是**退行** —— 用降低判据换取两端一致，等于把问题藏起来。
  撤销的理由见下一条。

### ADR-008 测试目标回到 Swift 6，用显式声明迁移

状态：**生效并实测**（2026-10-30）

- 场景：ADR-007 把测试目标降到 Swift 5 后，Linux 确实绿了，但那是把严格并发检查关掉换来的。
- 决策：撤销 ADR-007。测试目标回到包级 `v6`；用 `tools/add-sendable.py` 给测试里的 struct
  批量补 `Sendable`，其余错误逐个按类型语义修：`FutureValue` 与两个替身调度器声明
  `@unchecked Sendable`（状态本就由锁保护），`Scheduler.spawn` 的 `work` 声明为 `@Sendable`
  （它确实跨线程），跨线程共享的可变状态装进 `SendableBox`。
- 理由：这些声明是**事实**的登记，不是让编译器闭嘴的开关 —— 握手处本来就有锁与信号量。
  批量脚本只负责机械部分，判断仍逐点做。
- 代价：源码 target 当时仍是 `v5`，包级迁移只完成了一半；`spawn` 的 `@Sendable` 会在源码翻 v6 时
  把一批旧闭包的捕获逐个暴露出来，届时须按同一口径修，不能改回 `@escaping` 了事。后一半见下一条。

### ADR-009 源码三个 target 翻 Swift 6

状态：**生效并实测**（2026-10-30）

- 场景：ADR-008 把测试目标挽回 `v6` 后源码仍停在 `v5` —— 同一段语义在两处受不同强度的检查，
  而 `Scheduler.spawn` 的 `@Sendable` 在源码侧没有对应约束。
- 决策：去掉三个 target 的语言模式覆写，全包走 `v6`。机械部分交给 `tools/add-sendable.py`
  （本轮扩到 `enum`，含 `indirect`）：AST 的 40 个值类型全部显式遵循 `Sendable`；其余逐个定性 ——
  已有锁的类写 `@unchecked Sendable`（`GCDScheduler` · `IRExecutor` · `DiagnosticResources` ·
  `ModuleDependencyLoader` · `DAPServer` · `ThreadLocal`），已有锁的全局表写 `nonisolated(unsafe)`
  并在注释里点名守护者；派发口引入 `WorkHandoff`，把「这一趟归工作者」写在跨线程那一行。
- 理由：AST 全是值类型、无 `class`，跨线程传递本就安全，缺的只是声明；需要判断的是那几个持有
  可变状态的类，它们每一处都已经有锁，由锁承担而不是由编译器猜。
- 代价：`Value` 仍未声明 `Sendable`，`ControlSignal` / `IRControlSignal` 因 `Error` 隐含 `Sendable`
  留下两条警告 —— 要不要给 `Value` 定性是语义裁决（`ObjectReference` 可变），不是迁移动作。
  另有三处平台差异被这次迁移逼出来：Glibc 的 `stdout` / `stderr` 是可变全局量（改走 `fflush(nil)`
  与 `write(2, …)`），裸指针进 `Thread` 闭包以位模式过界。

## 5. 接口约定

### 5.1 已确认（方向级，来自 ADR-004）

| 契约 | 内容 |
|---|---|
| **类型定型** | 降载之后类型定型，下游不得再推类型 |
| **布局归位** | 布局是 IR 的事实，后端只读 |
| **所有权归位** | 所有权由中端插入，后端只翻译指令 |
| **单层 IR** | 中端只做 IR→IR，不引入第二套 IR |
| **清单唯一** | 内建清单唯一，实现可多份 |

五条的判据形态（违反时长什么样）已落成 `../spec/ir-contract.md` 第 5 节，以该处为准。

### 5.2 拟议未钉（落码前须复核）

- `PiniBackend` 协议的成员与返回形态（`emit(_:) -> BackendOutput` 只是候选形状）。
- `BackendCapabilities` 的组织粒度：拟按节点族，不按节点逐个（逐个会变成第二份节点表）。
- `BuiltinSpec` 的字段集与三方对照脚本的输入格式。

注意 解释器不实现后端协议 —— 它是执行器不是发射器。这条在落码时不得被「统一接口」的
动机抹掉。

### 5.3 验收标准

**结构计划收尾**：三条同时成立才算完成，缺一条都算未完成。前两条可以靠少写功能凑数，
第三条不能 —— 编译期边界不可伪造。

| 判据 | 通过线 |
|---|---|
| 后端接得上 | 新增一个只输出 JSON 的后端，改动面为「1 个新文件 + 1 行注册」，且跑通全部语料 |
| 边际成本降下来 | 字节码 `embedded_min` 通道的生产代码不超过 1,000 行 |
| 边界硬得住 | `Syntax` 里写一行 `import PiniBackendLLVM`，编译必须失败 |

**逐行动作**的通过线见 `backend-layering-plan.md` 的执行表：每行都带通过线、判定方式与回退，
不写「基本可用」这类无法证伪的措辞。

**CI**（已达成的读数，后续改动不得低于此线）：

| 判据 | 通过线 | 实测 |
|---|---|---|
| 一次提交跑完全部判据 | 四道门禁 + 构建 + 全量测试，退出码可判 | 退出码 0 |
| 测试条数不得缩水 | 268 条 / 44 套件，49 条已知问题 | 268 / 44，49 |
| 跨平台同解 | macOS 与 Linux 的通过条数与已知问题数一致 | 两端同为 268 / 44 / 49 |
| 工具链错配早失败 | 声明值与实际值不符时第一步就红，且报出两个数 | 入口脚本自检覆盖 |
