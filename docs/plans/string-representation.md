# LLVM 侧字符串：复杂度优先的重构方案

- 状态：**三批已落地**（`8340519` 批一、`e98108b` 批二、批三与稀疏表并入其后），落点见 §13.5
- 相关：`string-design-survey.md`（各语言取舍调研，本件每个决定都指向它）
- 范围：LLVM 通道（`pini compile` / `run-llvm`）与 `PiniRuntime` 的字符串族
- 不在范围内：解释器通道 `Value.string`、`StringHandle`、FFI 借出约定

## 1. 结论

编译产物在字符串上**比解释器慢 34 倍**，不是常数因子的问题。同一段逐字符扫描统计词数的程序，扫 21600 字符：

| 执行方式 | 耗时 | 每字符 |
|---|---|---|
| 理想（机器码字节循环） | 约 0.05 ms | 2–5 ns |
| 解释器 `run` | 53 ms | 1.7 µs |
| 编译产物 `compile` | **1656 ms** | 77 µs |

规模翻倍（5400 / 10800 / 21600）：编译产物 113 / 422 / 1656 ms，比值 3.7 与 3.9 —— 标准二次方；解释器 21.0 / 31.5 / 52.8 ms，没有二次方项。

原因一句话：**机器码没有在做字符串这件事**。每个 `s[i]` 变成一次 `bk_string_char_at` 调用，函数内部先把整串 `String(cString:)` 物化再取第 i 个字素。

核心算法已经预演过（独立 Swift 程序，见 §12），同一台机器、同一个 21600 字符的串：

| 操作 | 现状 | 带头表示 | 倍率 |
|---|---|---|---|
| `s[i]` | 3.91 µs/次 | **0.46 ns/次** | 8500 倍 |
| `len(s)` | 32.8 µs/次 | **0.5 ns/次** | 65000 倍 |

重构后同一段程序落到进程启动的量级：21600 字符的扫描已测不出计算时间（整程序 5.0 毫秒，空程序 4.9 毫秒）。

## 2. 三次「整串重做」

现状的每一处二次方都是同一个形态：为回答一个局部问题，把整串重新做一遍。

| 形态 | 触发 | 现状 |
|---|---|---|
| 重算 | `len(s)` | `String(cString:)` 复制 + `count` 数字素，每次 O(n) |
| 复制 | `s[i]` | 复制整串，走到第 i 个字素，再 dup 一个单字符 |
| 物化 | `contains` / `indexOf` / `split` | 先摊成 `[Character]`（每字符一次堆分配）再处理 |

## 3. 复杂度对照

| 操作 | 改造前 | 现在 | 下界 |
|---|---|---|---|
| `len(s)` | O(n) | **O(1)** 读头字段 | O(1) |
| `s[i]`（任意串） | O(n) | **O(1)**：ASCII 直取；非 ASCII 走稀疏表（常数 ≤64）或顺序游标 | O(1) |
| `s[a:b]` | O(n + k) | **O(k)** 一次 memcpy | O(k) |
| `a + b` | O(a+b)，精确分配 | **O(a+b)**，唯一持有就地长 | O(a+b) |
| `s = s + x` 累加 | O(n²) | **O(n)** 摊还 | O(n) |
| `contains` / `indexOf` | O(n·m) + 两次物化 | **O(n)** 字节级 + 字素折算 | O(n) |
| `split` | O(n)，每字符一次堆分配 | **O(n)**，零逐字分配 | O(n) |
| `upper` / `lower` / `trim` | O(n)，三次整串拷贝 | **O(n)** 单趟 | O(n) |
| `==` / `<` | O(n) `strcmp`（要扫到 NUL） | **O(n)** `memcmp`，长度不等即 O(1) 返回 | O(n) |
| `retain` / `release` | O(1) + 全局锁 | **O(1)** 原子，无锁 | O(1) |

只有切片停在 O(k)：载荷必须保持 NUL 结尾才能零拷贝借给 C。见 §7 对 Swift `Substring` 的取舍。

## 4. 五条设计原则

1. **元数据进头。** `len` 是一次 load；ASCII 串的 `s[i]` 是一次 load 加一次边界比较。发射器直接发 IR，不调函数。
2. **一遍扫描，不许先物化再处理。** 所有「转 `[Character]` 再遍历」的写法删掉，改在 UTF-8 字节上走。
3. **唯一持有就地长。** 计数为 1 且容量够就原地追加，不够按倍增扩容；计数大于 1 才分裂。
4. **只有跨字符边界的事才落运行时。** ASCII 快路径全在机器码里；非 ASCII 才进 Swift 分段。
5. **字素索引是付过费的。** 语言承诺了字素簇语义，就得为它付一张稀疏表，而不是让每次下标都重走一遍。

## 5. 表示

`String` 的值仍是 `i8*`，指向载荷首字节；载荷前 16 字节头：

| 偏移 | 字段 | 含义 |
|---|---|---|
| 0 | `rc` | 引用计数。`0` = 不归值域所有（字面量、进程期常量）；`>0` = 堆上、可增容 |
| 4 | `len` | 字节数，不含 NUL |
| 8 | `cap` | 载荷容量（不含 NUL）；`cap >= 128` 时载荷之后有一个 8 字节的表槽 |
| 12 | `graphemes` | 字素数；`-1` = 未算。**`graphemes == len` 当且仅当纯 ASCII**，不需另设标志 |

`len` / `cap` / `graphemes` 都是 i32，串长上限 2³¹−1 字节，超限即 panic —— 与语言层 `len()` 返回 `I32` 一致，与 Java 数组、.NET 默认上限同档。

不变量：

1. 载荷恒 NUL 结尾且 `cap >= len + 1` ⇒ `const char*`、`strcmp`、`printf("%s")`、FFI 借出全部继续成立。
2. `rc == 0` 的串不归值域所有：`retain` / `release` 空转，追加必须改新分配。这条替代 `_bkStrLive` 登记表，**全局锁随之删除**。
3. 就值域而言，串的存储一律可写：字面量发射成可写全局而非只读常量段 —— 字素数缓存与表槽都要写一次。只读常量段一写就是 SIGBUS。
4. 就地追加只在 `rc == 1` 且容量够时发生 —— 别名安全由计数保证，不靠发射器判断；就地追加同时丢弃表槽，旧偏移全部作废。

### 5.1 稀疏字素表

只在「含非 ASCII」且「容量 ≥ 128 字节」的串上建，惰性，一次 O(n)：

- 每 64 个字素记一个 u32 字节偏移，表长 `4 × ⌈字素数 / 64⌉`；
- 表槽在载荷 NUL 之后、同一块分配内，按 `载荷 + cap + 8` 向下对齐定位；`cap < 128` 的串没有槽，也不建表；
- `s[i]`：取 `表[i / 64]` 与下一项作字节区间，只物化这一块，不再复制整串；
- 线程本地再缓存**上一次物化的那一块**及其块内 65 条字节偏移，于是块内任意下标都是两次数组读；
- 缓存的命中判据包含块内字节比对：串释放后同地址被新串复用时会失配，拿旧偏移去切新内容不会发生。

内存上限是文本的 6.25%（1 字节/字素时），CJK 约 2%，纯 ASCII 为 0。表在串释放时一并归还。

## 6. 逐操作的算法

- **`len`**：读 `graphemes`；为 `-1` 时算一次并回填。
- **`s[i]`**：ASCII 直取；非 ASCII 命中游标则一步，否则按 `i/64` 跳表再走剩余步数。
- **`s[a:b]`**：两端定位后一次 memcpy；负界尾计数与夹取规则照旧。
- **`a + b`**：目标按 `max(需求, 2×cap)` 扩容；`a` 唯一持有时直接追加。
- **`s = s + x`**：赋值点识别「目标变量与左操作数同源」⇒ 走就地追加入口。
- **`contains` / `indexOf`**：字节级 `memmem`（UTF-8 自同步，合法串里任何字节匹配都落在码点边界上）；`indexOf` 再把字节偏移折成字素序号。
- **`split`**：单趟扫分隔符，命中即复制该段。
- **`upper` / `lower`**：单趟映射；结果长度可能变化的字符走慢路径。
- **`trim`**：两端各一次字节扫描，一次 memcpy。
- **`==` / `<`**：先比 `len`，再 `memcmp`。UTF-8 字节序与码点序一致，`<` 用 `memcmp` 直接就是码点序。

## 7. Swift 经验的取舍

调研见 `string-design-survey.md` §3 与 §4。Swift 是唯一把「人看到的字符」当索引单位的语言，它踩过的坑与付出的代价最值得抄，也最值得反着来。

| Swift 的做法 | 取 / 弃 | 理由 |
|---|---|---|
| UTF-8 原生存储（Swift 5 重写 String 的核心决定） | 取 | 我们本就必须（FFI 零拷贝）；Swift 证明在 UTF-8 上扫描与比较不吃亏 |
| 字素簇作为字符单位 | 取 | 规范已定，不回头 |
| breadcrumbs：每 64 单位一张稀疏偏移表 | 取 | 见下一行 |
| 表放载荷之后、标志借容量字段 | 取 | 这是 Swift 为了 ABI 稳定被迫想出来的招；我们的头也是冻结布局，同一招直接可用 |
| 表惰性构建、按需付内存 | 取 | 纯 ASCII 一分不花 |
| `String.Index` 里缓存「距下个字素多远」 | 取 | 我们的线程游标是它的粗粒度版 |
| `count` 是 O(n)，接受这个价 | **弃** | 头里 4 字节就能换 O(1)。Swift 不肯付，是因为它把 String 压到 16 字节且要 ABI 稳定 |
| 禁止整数下标 | **弃** | Swift 禁，是因为它做不到 O(1)，怕人误以为是免费的；我们做得到，就不必禁 |
| `Substring` 共享存储换 O(1) 切片 | **弃** | 需要 16 字节 `guts+offset` 或引入第二个类型；我们守 8 字节裸指针与零拷贝 FFI，切片 O(k) |
| `==` 按规范等价（NFC/NFD 视为相等） | **弃** | 逐字节比较才能让 `contains` / `indexOf` 上 O(n)；Go、Rust、Java、C#、Python 全按码元或码点比较，Swift 是唯一做规范等价的 |
| 短串内联（≤15 字节塞进值里） | **暂弃** | 要把值加宽到 16 字节，波及每个槽位、字段、数组元素箱；触发条件见 §11 |

一句话概括这次的吸取：**Swift 的教训不是「字素太贵所以别做」，而是「字素确实贵，问题是谁来付」。Swift 让调用方每次付 O(n)；我们让字符串自己付 4 字节加一张稀疏表，调用方付 O(1)。**

其中两条被弃的做法留了回头路：切片若成为热点，加一个 `Substring` 视图类型即可（届时要放弃切片的零拷贝借出）；短串若在剖析里显形，把值加宽到 16 字节做内联。

### 7.1 由此定下的三条

**比较判据 = 码点序列。** 现状双后端已经不一致（实测 NFC `é` 与 NFD `é`：解释器 `==` 给 true，LLVM 给 false；`contains` 两边都给 true）。统一到字节，同时修掉这条分歧，并让 `contains` / `indexOf` 拿到 O(n)。代价：`"é"` 的两种写法不再相等。解释器必须同批改，否则分歧从「后端之间」变成「版本之间」。

**切片 = 复制，O(k)。** 理由见上表 `Substring` 行。

**非 ASCII 随机访问 = 稀疏表 + 游标。** 只有游标时随机访问仍 O(n)；只有表时顺序访问每步要走 64 次解码。两者叠加才同时拿到「顺序 O(1)」与「随机 O(1) 常数 64」。

## 8. 分批

按复杂度收益排，每批独立可跑、可回退。三批均已落地，判据见 §13.5；批三的「临时值链复用」尚未做 ——
它省的是中间串的一次分配，不影响阶。

### 批一 元数据

16 字节头落地；字面量改为带头常量（`rc = 0`）；删 `_bkStrLive` 与锁；`len` / `s[i]` 改读头；三处固定 4096 字节栈缓冲（`IREmitter.swift:5910` / `5971` / `6015`）改为增长缓冲。

收益：`len` 与 ASCII `s[i]` 到 O(1)（§1 的预演读数）；插值与 `join` 的长度上限消失（顺带修掉 4200 字节 SIGBUS / 8192 字节 SIGSEGV / `join` 5399 字节 SIGSEGV）；每次操作的锁消失。

### 批二 扫描

`char_at` / `slice` / `contains` / `index_of` / `split` / `trim` / `upper` / `lower` 改字节级单趟；稀疏表与游标落地；`==` / `<` 改 `memcmp`。

收益：顺序扫描 O(n²)→O(n)。这一批单独就能把 1656 ms 压到毫秒级。

### 批三 拼接

`bk_str_concat(lhs, rhs, ownsLhs)` 容量倍增 + 临时值链就地复用；`s = s + x` 自赋值就地追加单列 —— 它改变「拼接操作数用完即还」的既有约定，按本仓规矩先补 `docs/spec/ir-contract.md` §7.2 条目（中端决定动作、后端只翻译），再动代码。

收益：累加 O(n²)→O(n)。

### 规范跟随项

比较判据统一到字节序列后，`docs/spec/pini-reference-v0.md` 字符串一节写明「比较按 UTF-8 字节序列，不做规范等价」。
`Char` 的语义另立一节（字素簇单位 · 值即自持 · 长度不设限），类型表里「Unicode 标量、0 到 0x10FFFF」的旧说法同期删掉。

## 9. 复杂度门禁

只测绝对时间挡不住回归，机器一换数就变。门禁改成两条：

1. **倍增比**：每个探针跑 n 与 2n，断言 `t(2n) / t(n) <= 2.6`（线性上限 2 加余量）。二次方给 3.5–4，一测就红。对机器噪声不敏感，适合本地与夜间跑。
2. **分配计数**：调试模式（`PINI_STR_DEBUG=1`）统计分配次数，断言与 n 的关系是 O(1) 或 O(n)。确定性，可进 CI。

探针集：词数扫描、`len` 循环、拼接 25k–200k、`join` 大数组、20 万字串随机取字符、`split` + `contains` 大文本。落 `bench/complexity/`。

## 10. 嵌入式 profile

问题：16 字节头加稀疏表，在 MCU 上会不会太大。

### 10.1 先看 Embedded Swift 怎么算这笔账

官方文档（`docs.swift.org` 的 Embedded Swift/Using strings）把 String 的操作按「要不要 Unicode 数据表」分成两半，表是 `libswiftUnicodeDataTables.a`，**不链就报 `_swift_stdlib_*` 未定义**：

| 需要 Unicode 表 | 不需要 Unicode 表 |
|---|---|
| String 之间 `==`、排序、哈希（字典键） | `StaticString` 的任何操作 |
| `.count` | 创建、拼接、插值、`print` |
| `.split()`、逐字符迭代、**下标** | `.utf8` / `.utf16` / `.unicodeScalars` 视图及其 `.count` |
| `.uppercased()` / `.lowercased()` | 把上述视图当字典键 |

官方对表的描述只有一句「non-negligible size」，并把这笔代价设计成**必须手动链接**——让用的人知道自己在付。具体字节数需在目标工具链上用 `size -m` 实测，本机两套工具链都没带嵌入式标准库，无法给出可信数字。

### 10.2 Pini 的嵌入式通道现状：已经站在「不要表」那一侧

`EmbeddedMinBackend` 的 26 条指令里，字符串只做三件事：常量、`CONCAT`、`TOSTR`（配合 `PRINT`）。而 `lenCall`、`subscriptGet`、`stringCase`、`stringContains`、`stringSplit`、`stringIndexOf`、`stringSubstring`、`stringTrim*`、`arrayJoin` 一律抛 `unsupported`。

也就是说，**现有能力边界正好落在「不需要 Unicode 表」的半边**，只是当时没有明说。

### 10.3 结论：表示是 profile 的属性，不是语言的属性

| | host（LLVM） | embedded_min（VM） |
|---|---|---|
| 值 | `i8*` | 裸 C 串指针 |
| 头 | 16 字节 `{rc, len, cap, graphemes}` | **0 字节**，NUL 结尾 |
| 容量 / 就地追加 | 有 | 无（拼接一律新分配） |
| 稀疏字素表 | 有（非 ASCII） | 无 |
| Unicode 表 | 有（标准库自带） | 无 |
| `len` / `s[i]` | O(1) | 编译期拒绝（现状如此） |

嵌入式的子集只有「常量、拼接、插值、打印」，这四件事用裸 C 串加 `strlen` 就够：不需要长度字段，不需要容量，不需要计数，不需要字素。**头大不大，与嵌入式无关，因为它不装这个头。**

共享的是 IR 语义与契约（`docs/spec/ir-contract.md` §0.2 已规定实现细节不进语义列），不是内存布局。这与契约自己的纪律一致：布局是注记，不是语义。

### 10.4 两条边界与触发条件

- **若嵌入式将来要 `len` / `s[i]`**：那是字素语义，必须要 grapheme break 表。届时只带 grapheme break，不带规范化表 —— 因为我们的相等判据是字节（§7.1），`nfd_decompositions` / `getNormData` 这两张最大的表用不上。这是 §7.1 那个决定的额外红利：同样的功能，我们要付的表比 Swift 少。
- **若 LLVM 通道要直接出裸机目标**（现在不出）：16 字节头与稀疏表得按 profile 常量裁掉，头宽改成编译期常量，而不是另写一份运行时。

不建议的做法：让嵌入式 `len` 返回字节数。那会让同一份源码在两个 profile 上语义分裂，比多花几百 KB 闪存糟得多。

## 11. 代价与触发条件

| 项 | 说明 | 触发重审的信号 |
|---|---|---|
| 短串内存约 ×2 | 16 字节头：6 字节串的分配块从 16 涨到 32 | 剖析里小串分配占主导 ⇒ 值加宽到 16 字节做内联 |
| 稀疏表内存 | ≤ 文本 6.25%，仅非 ASCII 且字素数 > 128 的串 | 长文本常驻内存成为瓶颈 ⇒ 表降到每 128 字素一条 |
| 串长上限 2 GiB | `len` / `cap` 是 i32 | 真要读更大文件 ⇒ 头换 i64（所有字段同步） |
| 切片 O(k) | 复制换零拷贝借出 | 切片成为热点 ⇒ 引入 `Substring` 视图类型 |
| 头偏移两处各写一份 | 发射器（IR 常数）与运行时段（`_bkStrHeaderBytes`） | 永远：用 `bk_str_header_bytes()` 加测试断言相等 |
| 写只读段 | 对 `rc == 0` 的串就地追加会 SIGBUS | 永远：追加入口以 `rc == 1 && cap > 0` 挡住 |
| 惰性表的并发构建 | 两个线程可能同时建表 | 永远：`cap` 标志位做原子 CAS，赢家建、输家退化为线性扫描 |
| 失去「双重释放无操作」 | 登记表删除后读已释放内存 | 永远：`PINI_STR_DEBUG=1` 保留登记表做检测 |
| 别名被就地改写 | 唯一判据是 `rc == 1` | 永远：补「先别名、再拼接、回看别名」用例 |

## 13. 待裁项

批二开工前还有三处岔路。每处给现状读数、为何现在定、各自代价。

### 13.1 字素粒度

`s[i]` 的静态类型是 `char`，规范把 `Char` 定义为「Unicode 标量（0 到 0x10FFFF）」，实现返回的却是完整字素簇：
NFD 形式的 `é`（`65 CC 81`）取第 0 位，得到的串长度为 1、与 `"e"` 不等 ⇒ 它是三字节的 `é`，不是 `e`。
LLVM 层 `Char` 与 `String` 同为 `i8*`，所以每次下标读都要分配 32 字节。

实测五十一点八万次「取字符 + 与字面量比较」十四点八毫秒，同规模纯整数循环四点九毫秒 ⇒ 十九纳秒一次，分配占大头。
批二把 `contains` / `split` 改快之后，顺序扫描仍停在这个数上。

| | 做什么 | 代价 |
|---|---|---|
| 维持指针 | 不动 | 扫描停在十九纳秒/字符，「比解释器快」在扫描类负载上做不到 |
| 八字节内联 | 七字节 UTF-8 加一字节长度或标签，超长溢出到堆；槽宽不变 | `char` 的 LLVM 拼写从 `i8*` 改 `i64`，发射层八到十二处、运行时六到八处构造与消费点 |
| 码点立即数 | `Char` 变 `i32` | `len` 数字素而下标数字素 ⇒ `s[len-1]` 越界；要么改 `len` 的单位，要么改下标的单位 |

建议八字节内联：语义不动、槽宽不动，代价集中在 Char 的构造与消费。
码点立即数省事，但制造单位分裂，比性能问题更贵。

### 13.2 索引表

非 ASCII 的 `s[i]` 现在把整串物化成 Swift `String` 再走到目标位（`bk_string_char_at` 后半段），
O(n) 时间加 O(n) 分配。`String` 的分段算法复现不了，这条路绕不开 Unicode 表。

若 13.1 选八字节内联，非 ASCII 定位只有两条路：维持整串物化，或建 §5.1 的稀疏表
（每 64 字素一条 `u32`，内存不超过文本的 6.25%，载荷尾部一个 8 字节槽，建表走一把只在首次争用的锁，追加后失效）。

定案是**建表**。判据不是剖析占比，而是一组可复现的读数：中文文本逐字符扫描 2000 / 4000 / 8000 字，
原实现 37 / 132 / 509 毫秒，倍增比 3.5 与 3.9 —— 标准二次方，且 `Char` 内联之后一分钱没变
（代价在整串物化，不在分配）。这类负载不需要剖析就能判定：任何按字素下标遍历非 ASCII 文本的程序都走这条路。

建表后同一组读数：8000 字 5.4 毫秒（其中进程启动约 5 毫秒），80000 字 12.4 毫秒；块缓存命中时单次下标约 37 纳秒。
首次建表是一次 O(n)，与解释器首次 `len()` 同阶。

### 13.3 判据收口

`==` 与 `match` 现在是 `strcmp`（字节），解释器是 Swift `String` 的 `==`（规范等价），
同一个 NFC/NFD 用例在两通道给相反答案，这个分歧现在就存在。批二把 `contains` 改成字节级之后，
分歧会从一处扩到三处。

两个选择：同批把解释器的 `==` / `contains` / `indexOf` / `split` 一起收窄到字节
（`Value.swift` 三处比较、`IRExecutor.swift` 三处分支、`StdlibPini` 的 Pini 源、规范补一条），
或先只改 LLVM、解释器保持。

建议同批。分歧是会扩散的债，后置还会让双后端对照在非 ASCII 用例上出现假红。

### 13.4 已清除的同类风险

`Error` 的消息串曾以裸 `strdup` 进值域，归还时减掉 malloc 块头。
审计其余入口：`argv` / `listDir` / `readFile` / `moduleRoot` / `double_to_string` / `error_message` 全部带头。
只剩 `_bkProgramBase` 的进程期缓存是裸 `strdup`，它只被 `String(cString:)` 读，不进值域。

### 13.5 三条定案的落点

| 待裁项 | 定案 | 落在哪里 |
|---|---|---|
| 字素粒度 | 八字节内联（7 字节 UTF-8 加一字节长度，更长的复制成自持块） | `Char` 的 LLVM 拼写改 `i64`；持有语义改惰性；比较走 `bk_char_equal` / `bk_char_equal_string` |
| 索引表 | 建（见 13.2） | 载荷尾部槽加线程本地块缓存；`bk_str_table_min_cap()` 与发射器的常数同源 |
| 判据收口 | 同批，两条通道一起改 | `RuntimeOps` / `IRExecutor` / `Value` 与发射层同一条字节判据 |

一条实现上的取舍值得记下：块缓存**不保留**源串。保留会让 `rc` 从 1 变成 2，
而就地追加要求 `rc == 1` —— 于是「先读一个字符，再追加」的循环会退化成每次重分配，把摊还 O(1) 打回二次方。
代价是缓存可能指向一条已释放、地址又被复用的串，所以命中判据里加了块内字节比对。

### 13.6 字符的自持与长度上限

`Char` 的指针形态原先指向源串载荷，语义上等于借用：源串一归还就成了悬垂值，
八字节以上的字素（区域旗帜对、零宽连接序列）当场可复现。长度到 127 字节还会 panic，
而语言层面没有「字素太长」这种错误。

现在指针形态一律指向一条**带头串**，计数为 1：打包时就从源串复制出来，值离开表达式后不欠源串任何东西。
长度格写 `127` 作哨兵，真长读头里的 `len`，于是任意长的字素簇都装得下；判等与转串的栈缓冲也改成按真长开。
这条路径就是「值即自持」的实现 —— 不分析逃逸点，所有 `Char` 都按已逃逸处理。

份额怎么走：`Char` 归在计数族（`IRShareKind.char`），保留与释放走 `bk_char_retain` / `bk_char_release`，
内联形态在这两个函数里直接返回。变量、字段、数组元素、聚合成员按同一套规则持有与归还，
一个长字素的生命周期结束在最后一个持有者手里，不再累积成进程期常量。

早先有一版驻留表（按内容去重、块 `rc == 0`），在计数落地后退役：块一旦不计数，retain / release 全是空转。
七字节以内仍内联，常见文本（ASCII、CJK、带变音符的拉丁字母、四字节 emoji）一分钱不花。

### 13.7 聚合的成员份额

`Result` / `Optional` / 元组原先按「整块搬移、内部不记账」处理，契约把它记作缺口。
后果不是泄漏而是双释放：`var r = .some(s)` 里临时值那份留在账上，槽退出又还一次。
现在 `IRType.ownedAggregateMembers` 给出名单（槽位、类型、保护 tag），构造点逐成员保留、
解构点逐成员归还，覆盖与退出各还一次；`Optional` / `Result` 的未选中槽先用 `select` 换成零值再动作。

`try` 的载荷走同一套：操作数求值后先定下「这份聚合归本层」，成功与错误两条路径各还一次。
判据不能只看节点形状 —— `wait` 作用在已结算的 `Result` 上是原样透传，那是借用；当成新份额就会
让两个槽指向同一条串、各释放一次。

数组元素的聚合同理，只是元素槽里放的是结构体字节：`tag 8` 标记它，深拷与销毁时的成员动作
由发射层合成的 `__bk_agg_<n>_retain` / `_release` 承担，数组创建时经 `bk_array_set_element_hooks` 登记。
宽度写成 LLVM 常量表达式，由后端按自己的 DataLayout 求值。字典与集合还没有这对钩子，仍拒绝聚合键值。
