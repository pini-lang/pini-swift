# 后端分层修订计划（中端上提）

- 性质：**工程结构计划**。不改变语言语义，不改变用户可见行为，不新增 IR 层。
- 适用范围：编译器自身的分层与后端接缝。
- 权威次序：语言面语义以 `../spec/pini-reference-v0.md` 为准；IR 节点语义以 `../spec/ir-contract.md`
  为准；运行时段符号面以 `../spec/runtime-abi.md` 为准。本件只排工程动作，不定义语义。
- 状态：**执行中**，方案取「先薄化后端，后硬化边界」。立契约 · 布局先决 · 布局归位已完成；
  所有权归位六片 · 后端接缝 · 内建清单已落地（见 6.3.7 / 6.4 / 6.5）；拆边界进行中，语法层已独立（6.6）。
- 判据来源：2026-10-30 对工作树的实测，读数见「基础读数」。

注意 本计划**不引入第二套 IR**。参考件把 IR 定为单层、唯一的分析 IR；下文所有 pass 都作用在
同一套 `IRModule` 上，pass 前后是同一个 IR 的不同阶段，不是两种表示。

注意 全文的动作名与契约名都是**主题词**，不编序号。表的行序即执行顺序；后文回指只用主题词，
不用「第一步 / 第 1 阶段」这类称呼。

## 1. 问题

一句话：**少一层**。前端、降载、后端三层齐全，中端（IR 到 IR 的 pass 层）不存在 —— 于是
「所有后端必须一致同意的事实」（布局、所有权、能力门）寄居在 LLVM 发射器里。

后果不是风格问题，是边际成本问题。新增一个后端的代价接近「复制一遍编译器最贵的一段」，
而不是「写一张类型映射表」。这一点有一次整通道实验作证：C 通道为接进来付了生产代码 3,440 行
（发射器 3,055 · 类型映射 277 · 头文件 108）与测试 1,121 行，最终停在 42/51；摘除时的理由是
「把它重建成 C 等于把编译器最贵的一段复制第三遍」。

另一条同源证据：摘除前实测，两个发射器之间有 47 个同名函数。

## 3. 缺陷

七条，标题即主题词。每条给出今天的位置与破坏后果。

### 3.1 布局寄居

对象头四格、字段偏移、枚举标签与载荷槽、`Result` 三槽、`Optional` 标签，全部由
`IREmitter` 在发射时现推（`headerSlotCount` · `fieldLayout` · `slotSizeExpression`）。
IR 里没有「布局」这一概念，后端问不出「这个结构的第三个字段在第几槽」。

后果：第二个后端要么复制这套推导，要么与第一个后端对布局给出不同答案 —— 后者是静默的
跨通道不兼容，只在特定程序上表现为读错字段。

### 3.2 所有权寄居

`pendingReleases` · `releaseFunctionDefs` · `emitReleases` · `ensureReleaseFunction` 等
15 个名字含 `Release` / `Retain` 的函数里，决定「何时插入所有权动作」的那一半在发射器内完成。

后果：每加一个后端就重做一遍所有权插入。C 通道的提交标题把这件事写在明面上
（`feat(cbackend): mirror the ownership insertion points`）。参考件已把这条登记为偏离，
代码尚未跟上。

### 3.3 IR 认识 LLVM

`IRType.llvmSpelling` 定义在 `IRNode.swift`，返回 `i8*` · `%struct.<mangled>*` 这类拼写。
更重的一处是它进了**用户可见报错**：降载器与执行器各有一处把 `llvmSpelling` 直接插进
诊断文案（`IRLowerer.swift:1562` · `IRExecutor.swift:1303`）。

后果：一条语言级诊断里出现 `double`，是把后端表示升格成了语言事实；将来换后端，同一错误的
文案会跟着变。

### 3.4 运行时两份

解释器的内建是 `RuntimeOps`（Swift，`Value` 域）；LLVM 通道的内建是 `PiniRuntime`
（96 个 C-ABI 导出）。字符串、集合、格式化各写一遍。

注意 **这里不能简单「统一成一个实现」**。仓内既定判据是「两条通道同时错会互相认证」，
解释器的价值正在于它是一份独立实现。故本计划只统一**清单与契约**（谁存在、签名是什么、
各后端在哪降级），不统一实现。把解释器改成调 C-ABI 运行时，等于把唯一的独立判据变成镜像。

### 3.5 边界靠目录

单 target，层与层之间没有编译器可执行的边界；`Parser` 引 `CodeGen` 不会被拦，只会被 review 拦。

### 3.6 契约靠崩溃

`IREmitter` 52 处 `fatalError`，注释一律写「IRLowerer guarantees」。违反契约的表现是
编译器崩，而不是诊断。参考件记录过一次同型事故：发射侧对某个位置的拒绝是内部断言，
编译器直接崩，而外侧判据只看「非零退出 + 报文措辞」，看不出那是崩溃。

### 3.7 接受面分裂

没有能力声明，也没有 IR 验证器。「哪些程序可编译」等于「发射器碰巧实现了哪些节点」。
参考件为字节码设计了验证器分层（离线 / 加载时 / 运行时加签名），却没为所有后端共用的 IR
设计对应物 —— 这是内部不对称。

## 4. 目标结构与契约

```
  前端      词法 · 语法 · AST · 语义与类型检查
   │        产出：带类型的 AST
   ▼
  降载      AST → IR（70 节点，类型在此定型）
   │        产出：IRModule
   ▼
  中端      IR → IR 的 pass 链：布局 → 所有权 → COW → 能力门
   │        产出：IRModule（布局与所有权已定型）
   ▼
  后端      每个后端只做「节点 → 目标表示」
   │        产出：LLVM IR 文本 · 字节码 · 其他
   ▼
  运行时    内建语义清单 + C-ABI 面
```

五条契约，标题即回指用的称呼：

| 契约 | 内容 | 判据形态 |
|---|---|---|
| **类型定型** | 降载之后类型定型，下游不得再推类型 | 后端源码中不出现类型推导分支 |
| **布局归位** | 布局是 IR 的事实，后端只读 | 后端不出现偏移、槽数、对齐的字面量与推导 |
| **所有权归位** | 所有权由中端插入，后端只翻译指令 | 后端源码中不出现 retain / release 合成 |
| **单层 IR** | 中端只做 IR→IR，不引入第二套 IR | pass 的输入输出同为 `IRModule` |
| **清单唯一** | 内建清单唯一，实现可多份 | 清单 ↔ 运行时导出 ↔ 各后端降级点三方对照 |

五条已落成 `../spec/ir-contract.md` 第 5 节。**该处为准**，本表只是摘要：判据的措辞以契约为准，
本表与契约不一致时改本表。

关于接缝的形状（**拟议，落码前须复核**）：

```
protocol PiniBackend {
    var identifier: String { get }
    var capabilities: BackendCapabilities { get }   // 按节点族声明
    func emit(_ module: IRModule) throws -> BackendOutput
}
```

注意 **解释器不实现该协议**。它是执行器不是发射器，强迫它伪装成发射器会把「执行」与
「翻译」两种职责压进同一个接口。接缝只覆盖「产出目标表示」的后端。

### 6.3 所有权归位

新增 `OwnershipPass`：消费降载产物，产出同一套 IR，在存储点上标出所有权动作，并让发射器按
单一清理栈归还局部。发射器只翻译，不再自己决定「这里该 retain」。

注意 第一阶段只加字段、不增节点（语句仍 17），计数基线不动；第二阶段才追加 `bindStmt` /
`retainStmt` 与 `temp`。`../spec/ir-contract.md` 的计数基线按「节点数 = 条目数」钉死，
两者同批改；编号 append-only，不复用已分配的段。

### 6.3.2 模型

三个状态：**持有**（当前求值握一份 +1）· **借用**（不握份额，不得释放）· **别名**（别处已握一份，
落进新存储点前要 copy 或 retain）。

四个动作：`take`（移交，零额外动作）· `copy`（结构体深拷贝）· `retain`（对象 / 枚举 / 容器 /
字符串留一份）· `release`（还一份）。

五个存储点：`allocVar` · `storeVar` · `fieldStore` · `subscriptStore` · `returnStmt`。
四个别名点沿用现有 `yieldsAlias`：`load` · `subscriptGet` · `fieldGet` · `optionalGet`。

**清理栈**：同一作用域内，`defer` 体与局部值的释放共用一条栈，按登记顺序入栈、退出逆序执行。
`defer` 只能引用它之前声明的局部值，故那些值在它之后释放；`defer` 之后声明的局部值在它之前
释放。这条次序是语言事实（参考 6.5），不是 pass 的实现选择。

注意 解释器也消费 `IRModule`。所有权动作对它是无操作（Swift 值由运行时管理），但它必须接受携带
这些动作的节点，不得据此改变求值结果。

### 6.3.3 两条路线

| 路线 | 存储点注解 | 具名临时 |
|---|---|---|
| 做法 | 五个存储点加 `adopt` 注解；`allocVar` 登记为持有，退出由清理栈归还；表达式形状不动 | 再把子表达式提成 `bindStmt` 临时，临时值也进动作 |
| 改动面 | 7 个字段，不增语句（17 → 17）；发射器删账本、两栈合一；降载不动 | 存储点注解的全部 + `bindStmt` / `retainStmt`（17 → 19）+ `temp`（53 → 54） |
| 命中下降 | 43 / 77 | 74 / 77 |
| 风险 | 低：不增语句，清理次序可逐条对照旧账本 | 高：提命名改所有表达式的发射顺序，字节比对全失效 |
| 适用 | 作用域 · 覆盖 · 返回 | 调用实参 · 拼接操作数 · 打印 · 容器元素 |

建议 **存储点注解先行、具名临时随后**。前者搬完 43 处后，发射器只剩「按清理栈翻译」与「临时
账本」；后者只处理 31 处，且此时前者已有独立测试，能做结构断言。

### 6.3.4 节点草案（拟议，落码前须复核）

```
case allocVar(name: String, type: IRType, mutable: Bool, initializer: IRExpr?, adopt: IRAdopt)
case storeVar(name: String, type: IRType, value: IRExpr, adopt: IRAdopt, releaseOld: Bool)
case fieldStore(base: IRExpr, field: String, value: IRExpr, fieldType: IRType, adopt: IRAdopt, releaseOld: Bool)
case subscriptStore(container: IRExpr, index: IRExpr, value: IRExpr, elementType: IRType, adopt: IRAdopt)
case returnStmt(value: IRExpr?, adopt: IRAdopt)
```

`IRAdopt` = `.take` · `.copyStruct` · `.retain` · `.none`。

注意 `releaseOld` 是布尔而不是另插一条释放语句：`a = a` 要求新值先站住、再释放旧值。顺序由 pass
决定、由后端按固定三步翻译；拆成两条语句会把顺序交给语句排列。

具名临时阶段再增 `bindStmt(temp:value:type:)` · `temp(name:type:)` · `retainStmt(name:type:)`。计数
基线：语句 17 → 19；表达式 53 → 54。契约第 2/3 节条目、`IRStmt` / `IRExpr`、`tools/ir-contract-check.py`
三处同批改。

### 6.3.5 pass 算法与四条裁定

算法：

1. 作用域帧与 `IRBlock` 同构；`allocVar` 入帧并登记为持有，帧随块弹出。
2. 退出不插语句：发射器把「局部释放」与 `defer` 体放进同一条清理栈，按登记顺序逆序执行。
3. 存储点按别名点判 `adopt`；标量与外部指针 `.none`。
4. 返回：先 adopt，再由清理栈归还全部开放帧。
5. `panicStmt` 之后不清理：进程不返回，释放无对象。
6. pass 必须幂等：对输出再跑一次，`IRModule` 必须相等。
7. 判不准时按借用处理（不释放）：宁可漏一份，不可悬垂。pass 不产出诊断、不拒绝程序 —— 语言面
   是「部分信任开发者」，插入动作不改变可编译集合。

注意 注解在 IR 构造处填，不另设遍历 pass：规则是纯句法的（`IRType.adoption(of:)`），再遍历一遍只是
抄一次；闭包体里的语句也只有在构造时才拿得到，否则要写一份覆盖 53 个表达式节点的重写。等具名临时
阶段需要数据流时再引入 pass —— 那时它本来就要重写表达式，遍历是绕不开的成本。

四条边界已裁：

| 边界 | 裁定 | 依据 |
|---|---|---|
| 退出次序 | 单一清理栈：`defer` 体与局部释放按登记顺序逆序；不引入单独的作用域退出动作 | Swift 6.4 实测（`-Onone` / `-O` 同解）与 TSPL |
| 容器分裂 | 唯一化消费原句柄、产出新句柄；写回是移交，不插释放 | `isKnownUniquelyReferenced` 文档；运行时注释写明份额已转移 |
| 捕获持有 | 逃逸闭包持有捕获、销毁时释放；非逃逸借用。释放侧缺失，单列缺口 | TSPL 与 Swift 6.4 实测 |
| 任务实参 | 共享模型：借用实参保留份额，临时实参移交；协议留在后端 | SE-0430 的 `sending` 与 Pini 的调用后可用语义 |

### 6.3.6 三个前置缺口

**内建效果表**。pass 要知道每个产值节点给的是持有还是借用。今天发射器的账本只认 `stringConcat` ·
`interpString` · `join` · `construct` · `enumConstruct` · 三个集合字面量；`stringCase`（5399）·
`stringSubstring`（2473）· `stringTrimLeft/Right` · `stringSplit`（5410）都返回运行时新分配的计数串
或句柄，却没有入账 ⇒ 临时值（直接打印、作实参、作拼接操作数）每次泄漏一份。按源码推断，未跑泄漏读数。

注意 pass 不得照抄这本账 —— 账本身是缺口。清单落地前，具名临时阶段无法开工。

**闭包销毁**。逃逸闭包持有捕获（契约 7.6），但闭包值 `{ptr, ptr}` 没有销毁钩子：环境块是裸
`malloc`，捕获槽由 `bk_slot_alloc` 分配且无 `free` ⇒ 捕获槽与捕获值都不释放，捕获对象的 `deinit`
永不触发。这是一条独立缺口，不塞进存储点 pass；等函数值有释放路径后再归位。

**哑后端**。本行验收要求「哑后端跑通全语料」，而哑后端属「后端接缝」。两条器械都不在本行内 ⇒
本行收尾线改写为「两通道输出不变 + 决策族归零」，接缝仍按计划次序走。

三条同时成立才算这份计划完成，缺一条都算未完成：

| 判据 | 通过线 |
|---|---|
| 后端接得上 | 新增一个只输出 JSON 的后端，改动面为「1 个新文件 + 1 行注册」，且能跑通全部语料 |
| 边际成本降下来 | 字节码 `embedded_min` 通道的生产代码 ≤ 1,000 行 |
| 边界硬得住 | `Syntax` 里写一行 `import PiniBackendLLVM`，编译失败 |

注意 第三条是三条里唯一**不可伪造**的：前两条可以靠少写功能凑数，编译期边界不能。

## 8. 风险

| 风险 | 触发条件 | 处置 |
|---|---|---|
| 契约计数基线漂移 | 所有权归位追加节点 | 先改 `../spec/ir-contract.md`，再改代码；同步检查器 |
| IR 变胖导致降载变慢 | 布局与所有权都进 IR 之后 | 所有权归位后实测一次降载耗时，留读数；不用感觉代替测量 |
| 52 处断言与 pass 冲突 | 所有权 pass 移动了释放点 | 断言保留到 pass 有独立测试；一次删一条，删一条跑一次全量 |
| 两通道在搬移期间短暂不一致 | 布局归位与所有权归位的中间态 | 新旧两路并存 + 断言相等，跑全量后再删旧路 |
| 拆 target 期间无法并行开发 | 拆边界 | 该行单独开分支，冻结其它结构改动 |
| 清理量挤占结构改动 | 拆边界暴露的 `public` 面 | 单列一笔，不与结构改动同批评 |

## 9. 治理

- 语义先于实现：任何改动先在 `../spec/ir-contract.md` 落条目，再改代码。该件自身的变更规则
  已经这么写，本计划只是遵守它。
- 门禁随行接入，不攒到最后：立契约时警告级，后端接缝时转硬门禁。新门禁挂进 `ci/entrypoint.sh`，
  不在 workflow 里另写一遍 —— 两处各写一份，两份必然漂。
- 每一行单独分支、单独合并；合并后显式切回工作分支。分支与提交约定见 `../../GIT_WORKFLOW.md`。
- 本件只增不删。某行完成后在该行标注状态，不删行 —— 删行会让后续回访失去追溯链。
