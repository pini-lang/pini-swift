# 后端分层修订计划（中端上提）

- 性质：**工程结构计划**。不改变语言语义，不改变用户可见行为，不新增 IR 层。
- 适用范围：编译器自身的分层与后端接缝。
- 权威次序：语言面语义以 `../spec/pini-reference-v0.md` 为准；IR 节点语义以 `../spec/ir-contract.md`
  为准；运行时段符号面以 `../spec/runtime-abi.md` 为准。本件只排工程动作，不定义语义。
- 状态：**已采纳**，方案取「先薄化后端，后硬化边界」。执行未开始。
- 判据来源：2026-10-30 对工作树的实测，读数见「基础读数」。

注意 本计划**不引入第二套 IR**。参考件把 IR 定为单层、唯一的分析 IR；下文所有 pass 都作用在
同一套 `IRModule` 上，pass 前后是同一个 IR 的不同阶段，不是两种表示。

注意 全文的动作名与契约名都是**主题词**，不编序号。表的行序即执行顺序；后文回指只用主题词，
不用「第一步 / 第 1 阶段」这类称呼。

## 1. 问题

一句话：**少一层**。前端、降载、后端三层齐全，中端（IR 到 IR 的 pass 层）不存在 —— 于是
「所有后端必须一致同意的事实」（布局、所有权、能力门）寄居在 LLVM 发射器里。

后果不是风格问题，是边际成本问题。新增一个后端的代价接近「复制一遍编译器最贵的一段」，
而不是「写一张类型映射表」。这一点有一次整通道实验作证：C 通道为接进来付了生产代码 3,440 行
（发射器 3,055 · 类型映射 277 · 头文件 108）与测试 1,121 行，最终停在 42/51；摘除时的理由是
「把它重建成 C 等于把编译器最贵的一段复制第三遍」。

另一条同源证据：摘除前实测，两个发射器之间有 47 个同名函数。

## 3. 缺陷

七条，标题即主题词。每条给出今天的位置与破坏后果。

### 3.1 布局寄居

对象头四格、字段偏移、枚举标签与载荷槽、`Result` 三槽、`Optional` 标签，全部由
`IREmitter` 在发射时现推（`headerSlotCount` · `fieldLayout` · `slotSizeExpression`）。
IR 里没有「布局」这一概念，后端问不出「这个结构的第三个字段在第几槽」。

后果：第二个后端要么复制这套推导，要么与第一个后端对布局给出不同答案 —— 后者是静默的
跨通道不兼容，只在特定程序上表现为读错字段。

### 3.2 所有权寄居

`pendingReleases` · `releaseFunctionDefs` · `emitReleases` · `ensureReleaseFunction` 等
15 个名字含 `Release` / `Retain` 的函数里，决定「何时插入所有权动作」的那一半在发射器内完成。

后果：每加一个后端就重做一遍所有权插入。C 通道的提交标题把这件事写在明面上
（`feat(cbackend): mirror the ownership insertion points`）。参考件已把这条登记为偏离，
代码尚未跟上。

### 3.3 IR 认识 LLVM

`IRType.llvmSpelling` 定义在 `IRNode.swift`，返回 `i8*` · `%struct.<mangled>*` 这类拼写。
更重的一处是它进了**用户可见报错**：降载器与执行器各有一处把 `llvmSpelling` 直接插进
诊断文案（`IRLowerer.swift:1562` · `IRExecutor.swift:1303`）。

后果：一条语言级诊断里出现 `double`，是把后端表示升格成了语言事实；将来换后端，同一错误的
文案会跟着变。

### 3.4 运行时两份

解释器的内建是 `RuntimeOps`（Swift，`Value` 域）；LLVM 通道的内建是 `PiniRuntime`
（96 个 C-ABI 导出）。字符串、集合、格式化各写一遍。

注意 **这里不能简单「统一成一个实现」**。仓内既定判据是「两条通道同时错会互相认证」，
解释器的价值正在于它是一份独立实现。故本计划只统一**清单与契约**（谁存在、签名是什么、
各后端在哪降级），不统一实现。把解释器改成调 C-ABI 运行时，等于把唯一的独立判据变成镜像。

### 3.5 边界靠目录

单 target，层与层之间没有编译器可执行的边界；`Parser` 引 `CodeGen` 不会被拦，只会被 review 拦。

### 3.6 契约靠崩溃

`IREmitter` 52 处 `fatalError`，注释一律写「IRLowerer guarantees」。违反契约的表现是
编译器崩，而不是诊断。参考件记录过一次同型事故：发射侧对某个位置的拒绝是内部断言，
编译器直接崩，而外侧判据只看「非零退出 + 报文措辞」，看不出那是崩溃。

### 3.7 接受面分裂

没有能力声明，也没有 IR 验证器。「哪些程序可编译」等于「发射器碰巧实现了哪些节点」。
参考件为字节码设计了验证器分层（离线 / 加载时 / 运行时加签名），却没为所有后端共用的 IR
设计对应物 —— 这是内部不对称。

## 4. 目标结构与契约

```
  前端      词法 · 语法 · AST · 语义与类型检查
   │        产出：带类型的 AST
   ▼
  降载      AST → IR（70 节点，类型在此定型）
   │        产出：IRModule
   ▼
  中端      IR → IR 的 pass 链：布局 → 所有权 → COW → 能力门
   │        产出：IRModule（布局与所有权已定型）
   ▼
  后端      每个后端只做「节点 → 目标表示」
   │        产出：LLVM IR 文本 · 字节码 · 其他
   ▼
  运行时    内建语义清单 + C-ABI 面
```

五条契约，标题即回指用的称呼：

| 契约 | 内容 | 判据形态 |
|---|---|---|
| **类型定型** | 降载之后类型定型，下游不得再推类型 | 后端源码中不出现类型推导分支 |
| **布局归位** | 布局是 IR 的事实，后端只读 | 后端不出现偏移、槽数、对齐的字面量与推导 |
| **所有权归位** | 所有权由中端插入，后端只翻译指令 | 后端源码中不出现 retain / release 合成 |
| **单层 IR** | 中端只做 IR→IR，不引入第二套 IR | pass 的输入输出同为 `IRModule` |
| **清单唯一** | 内建清单唯一，实现可多份 | 清单 ↔ 运行时导出 ↔ 各后端降级点三方对照 |

五条已落成 `../spec/ir-contract.md` 第 5 节。**该处为准**，本表只是摘要：判据的措辞以契约为准，
本表与契约不一致时改本表。

关于接缝的形状（**拟议，落码前须复核**）：

```
protocol PiniBackend {
    var identifier: String { get }
    var capabilities: BackendCapabilities { get }   // 按节点族声明
    func emit(_ module: IRModule) throws -> BackendOutput
}
```

注意 **解释器不实现该协议**。它是执行器不是发射器，强迫它伪装成发射器会把「执行」与
「翻译」两种职责压进同一个接口。接缝只覆盖「产出目标表示」的后端。

## 5. 不做的事

| 不做 | 理由 |
|---|---|
| 上 HIR / MIR 双层 | 违反单层 IR 的既定裁决；今天的问题不是 IR 不够低，是职责没分层 |
| 把解释器接到 C-ABI 运行时 | 会把唯一的独立判据变成镜像，见「运行时两份」 |
| 先拆 target | 拆完 `IREmitter` 仍是 5,581 行，只是换了个目录，边际成本一分不降 |
| 为统一而统一两份运行时实现 | 同上；统一清单即可，实现保持两份 |
| 顺手重写 `IRLowerer` | 它不在本计划的因果链上；先让后端变薄，再谈降载器拆分 |

## 6. 执行顺序与验收标准

表的行为执行顺序。每一行的「验收标准」都必须**可测量**：给出通过线、判定方式（跑什么、
看哪个读数），不写「基本可用」「大致通过」这类无法证伪的措辞。任一行的验收标准不达标，
不进下一行。

| 动作 | 产出 | 验收标准（通过线） | 判定方式 | 回退 |
|---|---|---|---|---|
| **立契约** | `../spec/ir-contract.md` 增「后端义务」一节（已成文：该件第 5 节；警告级门禁未接） | 五条契约各有一条可判定的表述；条目里不出现 `bk_*` · `alloca` · 引用计数布局 | 人工逐条核 + 一条警告级门禁：发射器出现 retain 合成时报出 | 无代码改动，删节即回退 |
| **布局归位** | 新增 `IRLayout`；降载产出；发射器改读 | 发射器里布局推导归零；51 个示例与 58 个夹具的两通道输出逐字节不变 | `rg 'headerSlotCount\|slotSizeExpression\|fieldLayout' IREmitter` = 0；`tools/ir-parity-probe.py` 全量 MATCH | 新旧两路并存，发射器断言两者相等，跑一轮全量再删旧路 |
| **所有权归位** | `OwnershipPass`（IR→IR） | 决策族函数从发射器移除（现存 15 个里的决策部分，翻译族保留并注明只翻译不决策）；所有权寿命套件全绿；哑后端跑通全语料且源码无 retain 字样 | `rg 'pendingReleases\|emitReleases\|emitReassignRelease\|emitRetainIfAliased\|releaseOwnedTemporary' IREmitter` = 0；`OwnershipLifetimeTests` 全绿；哑后端 100 行以内接得上 | 断言保留到 pass 有独立测试后，再逐条删 |
| **后端接缝** | `PiniBackend` 协议 + 能力声明 + CLI 注册表 | 新增一个哑后端只加 1 个文件 + 1 行注册，不改既有文件 | 按此新增一次，`git diff --stat` 出现文件数 = 2 | 注册表可先并存：旧字符串分派保留一个版本 |
| **内建清单** | `BuiltinSpec` 表；三方对照脚本 | 脚本能双向报缺口：清单有而运行时无导出 / 有导出而无降级点 | 脚本自造两条缺口各报一次；正常树零报 | 脚本先只报不拦，稳定后转门禁 |
| **拆边界** | 六个 target：`Syntax` / `Semantics` / `IR` / `BackendLLVM` / `RuntimeABI` / `CLI` | 依赖方向由编译期强制：`Syntax` 引不到 `BackendLLVM` | `swift build` 通过；故意加一行越界 import，编译必须失败；构建时长前后各留一次读数 | 拆分之一旦卡住，保留已拆的叶子，未拆的暂留 `Core` |
| **试点后端** | 字节码 `embedded_min` 26 条指令的最小通道 | 接入生产代码不超过 1,000 行；能力矩阵改为活表进 CI | `git diff --stat` 数新增行；能力矩阵在 CI 里产出三列并随提交更新 | 试点失败即回查「所有权归位」的 pass 边界 |

### 6.1 立契约

先把「后端不许推导什么」写成条目，再动代码。该节只写义务，不写实现：不出现 `bk_*`、
不出现 `alloca`。条目一旦落地，后续各行的验收标准全部引用它，不再各自表述。

状态：**已成文**，落在该件第 5 节，五条各带一条源码形状判据。**未完成的是警告级门禁** ——
它归「门禁随行」，不与文档同批；门禁接上之前，本行验收只满足前一半。

### 6.2 布局归位

`IRLayout` 承载：名义类型头四格、字段偏移与对齐、枚举标签位与载荷槽、`Result` 三槽、
`Optional` 标签。降载产出、放进 `IRModule`，发射器只读。

注意 布局属契约里的「布局约定」而非「语义」。它必须新开一节承载，**不得写进节点语义列** ——
否则重犯一次「把实现选择写成语义」的错误（`fileRead` 的 64 KiB 缓冲是前例）。

验收的可证伪形态分两层：发射器里再也搜不到布局推导（结构），且两通道输出逐字节不变（回归）。
只满足后者说明布局只是搬了个位置。

### 6.3 所有权归位

新增 `OwnershipPass`：消费降载产物，产出同一套 IR，节点上多出显式的所有权指令与释放点。
发射器把这些指令逐条翻译，不再自己决定「这里该 retain」。

注意 该 pass 会改变 IR 的节点集（语句节点 17 之后追加）。`../spec/ir-contract.md` 的计数基线
是按「节点数 = 条目数」钉死的等式，必须同步重编；编号 append-only，不复用已分配的段。

### 6.4 后端接缝

协议 + 能力声明 + 注册表。能力声明按节点族给，不按节点逐个给 —— 逐个给会变成第二份节点表，
与 IR 节点集必然漂移。

注意 能力声明的来源必须是**一张表**，不是散在后端各处的 `if`。表的读法要与
`../spec/ir-contract.md` 的节点编号对齐，这样「某后端不支持 X」能直接落到条目号上。

### 6.5 内建清单

`BuiltinSpec`：名字、签名、语义标签、各后端的降级键。三方对照沿用
`../spec/runtime-abi.md` 已有的「清单数 = 导出数」自检，扩成三方：清单 ↔ 导出 ↔ 降级点。

### 6.6 拆边界

六个 target，依赖方向由 `Package.swift` 强制。顺序按「先拆叶子」：`Syntax` 与 `RuntimeABI`
先独立，`IR` 次之，`BackendLLVM` 最后 —— 它与 `IR` 双向纠缠（布局与所有权还在它里面时
拆不动，故本行必须排在「布局归位」与「所有权归位」之后）。

注意 拆 target 会暴露一批「只是为了跨文件可见而写 `public`」的 API。清理量要单列一笔，
不混进结构改动里评。

### 6.7 试点后端

不是目标，是**验证前六行真的降低了成本的实验**。它失败，说明「布局归位」与「所有权归位」
没做干净 —— 那时回到那两行复查 pass 边界，不要就地给试点后端打补丁。

## 8. 风险

| 风险 | 触发条件 | 处置 |
|---|---|---|
| 契约计数基线漂移 | 所有权归位追加节点 | 先改 `../spec/ir-contract.md`，再改代码；同步检查器 |
| IR 变胖导致降载变慢 | 布局与所有权都进 IR 之后 | 所有权归位后实测一次降载耗时，留读数；不用感觉代替测量 |
| 52 处断言与 pass 冲突 | 所有权 pass 移动了释放点 | 断言保留到 pass 有独立测试；一次删一条，删一条跑一次全量 |
| 两通道在搬移期间短暂不一致 | 布局归位与所有权归位的中间态 | 新旧两路并存 + 断言相等，跑全量后再删旧路 |
| 拆 target 期间无法并行开发 | 拆边界 | 该行单独开分支，冻结其它结构改动 |
| 清理量挤占结构改动 | 拆边界暴露的 `public` 面 | 单列一笔，不与结构改动同批评 |

## 9. 治理

- 语义先于实现：任何改动先在 `../spec/ir-contract.md` 落条目，再改代码。该件自身的变更规则
  已经这么写，本计划只是遵守它。
- 门禁随行接入，不攒到最后：立契约时警告级，后端接缝时转硬门禁。新门禁挂进 `ci/entrypoint.sh`，
  不在 workflow 里另写一遍 —— 两处各写一份，两份必然漂。
- 每一行单独分支、单独合并；合并后显式切回工作分支。分支与提交约定见 `../../GIT_WORKFLOW.md`。
- 本件只增不删。某行完成后在该行标注状态，不删行 —— 删行会让后续回访失去追溯链。
