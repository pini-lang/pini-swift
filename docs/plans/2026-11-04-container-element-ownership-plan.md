# 容器元素所有权：把「写入即持有」收进运行时

- 状态：已落地。契约保持移动语义，不采用「接管」；五处行为缺陷按「补漏」逐个修掉（末条是验证时新发现的切片），写入口统一为「调用方自带一份、本入口必消费」；高风险入口补注释，四个写入口的 Swift 标识符带 `_unsafe`（C 符号不变）。
- 基线：`586a57d`；全量测试记录 502 条
- 上承：`docs/spec/ir-contract.md` 第 7 节、`docs/spec/runtime-abi.md` 第 3.1 节
- 触发：CI 上 `writingAHandleSlotBalancesTheInnerShareCount` 的 UAF，`1fee22b` 已按测试写法补了一次 retain

## 结论

- 现状不是「销毁时不 release」。数组销毁会把元素那一份还掉（「销毁归还」的读数 2→1）；CI 崩在反方向 —— 写入方少带了那一份，容器替它还了。
- 真正的毛病是契约把一次所有权拆给了两方：运行时按「移动」只搬字节，写入方必须在写前自己持一份。Pini 没有所有权类型，这条义务只能靠纪律守，漏一次就是悬垂。CI 只是第一个踩到的。
- 建议改成「接管」：写入时由运行时取一份，销毁时还一份，写入方保留自己那份。三个现存缺陷（键悬垂、去重漏份、键替换漏份）由同一条规则一并消失，且故障方向从悬垂变成泄漏。

## 现状取证

### 各层各说什么

| 层 | 位置 | 说的是什么 |
|---|---|---|
| 运行时文档 | `runtime-abi.md:65` | 「取用时谁分配谁交出，交给容器后由容器负责」——读起来像容器接管 |
| 运行时注释 | `PiniRuntime.swift:18` | 「`bk_*_set` 只做字节复制（移动语义）、不 retain，别名点的 retain 由 codegen 负责」——与文档差一次 retain |
| 运行时实现 | `PiniRuntime.swift:343`、`:372`、`:681`、`:810` | 写入口只 memcpy；`deinit` 逐个元素 release（`:166`、`:654`、`:786`） |
| IR 契约 | `ir-contract.md:396`、`:407` | 存储位含「容器元素」；接收动作是「移交 / 拷贝 / 保留」三选一 |
| 降载 | `IRShare.swift:57` | `adoption(of:sharingStructs:)`：临时值 `.take`，别名 `.retain` |
| 发射 | `IREmitter.swift:4276` | `adoptElement` 把上面那条翻成 `bk_handle_retain` / `bk_str_retain` |

文档说「容器负责」，代码说「写入方先持一份，容器只负责还」。两者差的正是 CI 崩掉的那一次 retain。

### 探针读数

五条探针都在现有的 `libPiniRuntime.dylib` 上直调 C ABI，不经过编译器。「销毁归还」「重复插入计数」「键重写计数」「裸指针计数」是 C 程序（`/tmp` 下临时文件，不入库），「新造键发射」是 `pini emit` 的产物结构。

| 探针 | 做法 | 读数 | 结论 |
|---|---|---|---|
| 销毁归还 | 句柄先多持一份，再写进数组、销毁数组 | 2 → 2 → 1 | 销毁确实归还元素那一份 |
| 重复插入计数 | 同一个句柄写两次（两次都按 adopt 先 retain），销毁集合 | 份额 2，应为 1 | 重复插入吞掉了写入方那一份 |
| 键重写计数 | 同一个串键写两次，销毁字典 | 计数 2，应为 1 | 键已存在时，新键那份被丢弃 |
| 裸指针计数 | 把一个仍在册的 Pini 串指针按 `*U8` 写进数组，销毁数组 | 计数 1 → 0 | 数组替一个它没 retain 的串还了一份 |
| 新造键发射 | `d[键(1)] = 2`，键是插值出来的新串 | 产物在 `bk_dict_set` 之后紧跟 `bk_str_release(键)` | 字典留下的是悬垂指针 |

「新造键发射」的产物形状（`pini emit` 摘录）：

```
%t10 = call i8* @_u952E(i32 1)      ; 新串，计数 1
store i8* %t10, ptr %t11            ; 键 box 只放指针字节
%t14 = call ptr @bk_dict_set(ptr %t13, ptr %t11, i32 8, i32 3, ...)
call void @bk_str_release(ptr %t10) ; 字典手里的键从此悬垂
```

读键按 C 串内容比较（`_bkBoxesEqual` 的 `.str` 支），所以悬垂不必然当场崩：缓冲区没被复用就照样命中。这类缺陷只能靠产物结构或分配器压力显形。

修后复跑同一组探针：

| 探针 | 读数 | 判据 |
|---|---|---|
| 销毁归还 | 2 → 2 → 1 | 不变：销毁照旧归还元素那一份 |
| 重复插入计数 | 1 | 重复插入把写入方那一份还掉了 |
| 键重写计数 | 1 | 既有键的新键份被还掉了 |
| 裸指针计数 | 1（元素 tag 写 6） | 数组销毁不再动它指向的串 |
| 新造键发射 | `bk_dict_set` 之后没有 `bk_str_release(键)` | 键仍归字典持有 |

注意 —— 「销毁后计数没降」还有一条正常路径：`append` 产出的兄弟数组共享同一块元素存储，`_BkArrayBox.deinit` 只在最后一个持有者离开时才 `releaseAllElements`（`PiniRuntime.swift:203`）。观测点若落在先销毁的那个数组上，会看到计数不动。这与「不 release」是两回事。

## 缺陷清单

五处都已在同一分支内修掉（末条是验证时新发现的）；下面是修前读数与各自的修法，判据见「用例」。

### 键悬垂

`d[新造键] = v` 这条路只给值做了接收动作，键没有。发射层把新键当成「读完即扔的操作数」释放掉（`IREmitter.swift:1836`），而 `bk_dict_set` 只搬了指针字节。字典字面量那条路是给键做了 adopt 的（`IREmitter.swift:4522`），所以这是下标写独有的漏。

后果：键指针在写入后立刻失效。分配器一旦复用那块缓冲，后续 `d[同一个键]` 读不到，或读到别人的内容。

已修：键与值同规，写前走 `adoptElement`（别名 retain、临时值销账），`bk_dict_set` 之后不再释放键。

### 去重漏份

`bk_set_add` 命中重复元素时直接返回，不落槽（`PiniRuntime.swift:818`）。写入方按 adopt 补的那一份没有归宿 —— 容器不释放它，写入方也不会再释放第二次。集合元素是句柄或串时，每重复插入一次漏一份，集合永不回收。

已修：命中重复时 `_bkReleaseIfHandle(elem, elemTag)` 把写入方那一份就地归还；写入口一律「带一份、必消费」。

### 键替换漏份

`bk_dict_set` 命中既有键时保留旧键 box，丢弃新键 box（`PiniRuntime.swift:692`）。键的 adopt 已经付过，于是同样漏一份。字符串键漏的是串计数，容器键漏的是句柄份额。

已修：命中既有键时先 `_bkReleaseIfHandle(key, keyTag)`，再替换值；零宽值提前返回的路径也归还键。

### 裸指针串号

`arrayElementABI` 让 `*T` 与 `Future` 共用 `str` 那一格（tag 3，`IREmitter.swift:4260`）。销毁时 `_bkReleaseIfHandle` 见到 tag 3 就调 `bk_str_release`（`PiniRuntime.swift:83`）。旁注写的是「运行时那两条钩子只在 handle tag 上动手」（`IREmitter.swift:4257`）——与实现不符：串那一格也动手，只是被登记表挡住了非本运行时的指针。

后果：C 回传的借出串指针若正好是某个在册 Pini 串的用户指针，数组销毁会替它减一份。`*T` 的元素相等性也走 `strcmp`，指针身份被换成了内容比较。

已修：`_BkTag` 新增 `rawPtr = 6`，`arrayElementABI` 的 `.pointer` 与 `.future` 改用它；`_bkBoxesEqual` 补 `.rawPtr` 支，按指针值比较。`Char` 与 `String` 仍旧同为 tag 3。

### 切片漏份

数组切片新建一个数组，元素从 `bk_array_get` 的箱里逐格字节复制。发射层只给 `%bk_array*` 元素补 retain，`String`、`Dict`、`Set` 元素的拷贝不带份额 —— 源数组仍握一份，新数组却以为自己也有，销毁时各还一次。

后果：`var b = a[0:2]` 之后两个数组共用同一批计数元素，任一方销毁都会替另一方减一份；两边都销毁即双释放。

已修：按 `boxFamily(of:)` 统一补一份（串走 `bk_str_retain`、容器走 `bk_handle_retain`、名义箱走 `bk_nominal_retain`），标量与裸指针零动作。

## 取舍

三栏是三种契约，不是三种实现。

| | 补漏（保持移动语义） | 接管（推荐） | 显式标志 |
|---|---|---|---|
| 写入时 | 运行时不取份；写入方必须先持一份 | 运行时取一份 | 调用方传 `take` / `copy`，运行时照办 |
| 销毁时 | 运行时还一份 | 运行时还一份 | 同左 |
| 写入方义务 | 每次写前自带一份 | 无（临时值由发射层写后归还） | 选对标志 |
| 漏一次 retain | 悬垂 | 不成立 | 悬垂 |
| 漏一次 release | 不成立 | 泄漏 | 泄漏 |
| 键悬垂 · 去重漏份 · 键替换漏份 | 要打三个补丁 | 一条规则一并消掉 | 要打三个补丁 |
| 额外开销 | 零 | 每个临时元素一对 retain / release | 零 |
| ABI 面 | 不动 | 四个符号行为变，签名不变 | 四个符号加一个参数 |

建议「接管」，理由三条。

- 它与文档已经写下的话一致（「交给容器后由容器负责」），不需要向读者解释第二种所有权。
- 它把故障方向统一到「泄漏」这一侧。`IRShare.swift:115` 已经立过这条判据：拿不准时选保守方向，漏一份好过悬垂。当前契约在运行时这一层恰好反着来。
- 它消掉的是规则，不是三处补丁。「补漏」要求「写入口只在落槽时消费那一份，不落槽就还回去」，比现在更绕；而且写入方漏带时，这个「还回去」会把原来的静默泄漏变成悬垂 —— 正是 CI 那一类。

「显式标志」保留零开销，但把选择摆到调用方面前：选错仍然是悬垂，只是错得更容易看见。它比「补漏」好，比「接管」差。

`StringHandle` 不在这条契约里：它在 `shareClass` 里是 inert，容器元素 ABI 也不收它（`arrayElementABI` 没有这一格）。C 侧那份计数始终由 C 侧说定，与本文的三种取舍都无关。

注意 —— 以下「改动面」「落地顺序」「用例」三节按「接管」写，本次未采用，保留作下次决策的底稿。

| 文件 | 改什么 |

发射层的六个落点：数组下标写、字典下标写（值）、数组字面量、字典字面量（键与值）、集合字面量、`append`。字典下标写的键不动 —— 它现在就是「写后归还自己那份」，正好是新规则要的形状。

### 运行时的动作顺序

写入替换旧元素时，先 retain 新值、再 release 旧值。反过来会在 `a[0] = a[0]` 这类自赋值上先释放后取份：若那是最后一份，先 free 再 retain 就是悬垂。字典值替换同理。

### 裸指针 tag

新增一格 `rawPtr = 6`，`*T` 与 `Future` 改用它：retain / release 两条钩子都不认这一格，元素相等性按指针值比较。这一条独立于「接管」——接管只能把「悬垂」降成「替外部指针记账」，语义仍然是错的。

## 落地顺序

接管（运行时）→ 发射层 → 裸指针 tag → 用例 → 收口（文档）→ 全量。

注意 —— 运行时必须先于发射层。中间态是「运行时取份 + 发射层仍预 retain」，每个临时元素多一份，表现为泄漏；反过来先改发射层则是少一份，表现为悬垂。方向不能反。

文档放最后：改动期间契约以本文为准，代码落定后一次改齐三处（运行时文档、IR 契约、件头注释）。

## 用例

新增五条运行时用例，与本文探针一一对应。

- 别名写入不预 retain，销毁后计数回到基线。这条直接覆盖 CI 那次。
- 集合重复插入：插入前后份额不变。
- 字典既有键重写：键计数不变。
- 字典下标写用新造键：写入后键仍可读回，且计数回到基线。
- `*T` 元素：销毁数组不动它指向的串计数。

再加一条产物结构判据（不必新增测试）：`pini emit` 的产物里，`bk_handle_retain` 只应出现在变量别名点，不应出现在容器写之前。

验收：五条探针复跑读数符合预期；全量测试与各道门禁全绿；`tools/runtime-abi-check.py` 的清单数仍是 107（签名与符号都不变）。

## 风险

| 风险 | 说明 | 处置 |
|---|---|---|
| 仓外调用方 | 若有手写调用方仍按旧规则「写前 retain」，接管后每写一次漏一份 | `bk_*` 不是公开 C 面（公开面是 `build --shared` 的头文件），本仓内只有发射层与两个测试文件；文档写明新规则 |
| 性能 | 每个临时元素多一对 retain / release；容器是 O(1)，字符串是一次锁 | `bench/` 没有数组构造项，建议补一条一万元素数组构造读数，留作基线 |
| 中间态 | 运行时与发射层分开落地时计数不平衡 | 同一分支内连续两笔，先运行时后发射层；中间态只允许泄漏 |
| 解释器 | 第 7.8 节说资源动作对它是无操作 | 不改；`IRExecutor` 的 `subscriptStore` 本就不看 adopt |
| 值语义结构体 | `arrayElementABI` 拒绝名义类型，容器装不进结构体 | 保持拒绝；`.copyIn` 对 valueBox 不做承诺 |

## 已落地的处置

- 契约不变，仍是移动语义；写入口的性质写成一句可查的规则：调用方自带一份，本入口必消费 —— 落槽则接管，不落槽则归还。
- `PiniRuntime.swift`：`bk_set_add` 命中重复、`bk_dict_set` 命中既有键，两处各自 `_bkReleaseIfHandle` 归还写入方那一份；零宽提前返回的两条路径同样归还；`bk_array_set` 收到空句柄时归还，不留悬空的份额。
- `IREmitter.swift`：字典下标写的键改走 `adoptElement`（别名 retain、临时值销账），并去掉写后的 `releaseOperand` —— 那一句正是键悬垂的来源。
- `PiniRuntime.swift` + `IREmitter.swift`：新增 `rawPtr = 6`，`*T` 与 `Future` 的元素 ABI 换到这一格，`_bkBoxesEqual` 按指针值比较；`str` 那一格不再收裸指针。
- `IREmitter.swift`：数组切片按 `boxFamily` 给计数元素补一份 —— 串、容器、名义箱各走自己的 retain，标量与裸指针零动作。
- 四个写入口的 Swift 标识符带 `_unsafe`；`@_cdecl` 的 C 符号、生成 IR、107 符号清单不变。
- 新增 `Tests/PiniTests/ContainerElementOwnershipTests.swift`：六条回归，前三条问运行时计数（去重、键重写、裸指针），后三条问产物结构（键不在写后释放、指针 tag 为 6、切片元素带一份）。
- 四个写入口、句柄加减、三个销毁入口与 `_bkReleaseShare` 补了份额契约注释，一行一条，便于按名检索。

## 尚未定

- 是否加一条 debug 期双释放陷阱：`_bkReleaseShare` 先在活动登记表里查，查不到就 `bk_panic`。它能把「第二次释放已回收的 box」从随机崩溃变成确定性失败，代价是 debug 下每次归零多一次线性查表。
- 是否把 `Char` 与 `String` 的元素 tag 分开。两者现在同为 tag 3，语义上也确实同构（都是计数串），暂时没有分开的理由。
