# C 错误通道调研

**问题**：`^T` 导出到 C 只交状态码 `0/1`。调用方知道失败了，不知道失败原因。本次调研回答：错误能不能作为数据过边界；若能，以什么形态、要动哪一层。

## 判据

「错误即数据」在本项目不是口号：参考手册 §8.4 把错误定义为 `Error` / `CancelError` 名义类型的值，经 `Result` 显式传播，不在调用栈上抛异常。落到 C 边界，同一条原则拆成三条可判定的要求：

| 判据 | 含义 | 反例 |
|---|---|---|
| 回传 | 错误随本次调用的返回值或出参回到调用点 | 事后调 `last_error()` 查询 |
| 所有权 | 谁持有、活多久、谁释放，调用方不必猜 | 交出一个指向被调函数栈帧的地址 |
| 并发 | 两个会话同时失败互不覆盖 | 进程级单槽 |

另有工程判据：**ABI 面积** —— 每个导出函数多几个参数、返回形态是否整体变形。

## 现状

### 错误值是进程期自持的堆盒

`Error("msg")` 在 IR 里唤的是 `bk_error_create`，得到一个 `i64` 句柄（`Sources/PiniIR/IR/IRLowerer.swift:3535`）。运行时把消息 `strdup` 进一个盒子，用 `passRetained` 交出去，之后不再释放（`Sources/PiniRuntime/PiniRuntime.swift:1790`、`:1801`）。

读侧是两个纯函数，都只吃那个字：

| 读法 | 落点 | 行为 |
|---|---|---|
| `e.message` | `bk_error_message` | 返回盒内 C 串；文档写明「指针在对象存活期（= 进程期）内稳定」 |
| `isCancel(e)` | `bk_error_is_cancel` | 读盒上的标志位 |

所以错误在运行时**已经**是数据：两种类型、独立所有权、可并发读取、消息可任意拼接（运行时已经复制了一份）。C 边界缺的不是表示，是导出面没把那个字交出去。

注意 —— 上一版把「同一函数再调一次，旧 Result 读到新消息」当作悬垂证据。那个复现写错了：handler 里先 `return`，程序根本没走到第二次读。重做后旧 Result 仍读到「第一次」，解释器与 LLVM 一致。盒子是自持的，不悬垂。

### 错误槽的合法值域没有约束

`Result<T, E>` 的 E 在类型层不参与定形（`Sources/PiniIR/IR/IRNode.swift:29` 明说这一点；`TypeChecker` 让 `err` 成员的类型直接等于 E）。于是 `err(42)` 能过检查，运行到 `e.message` 时 42 被当作地址解引用 —— 实测 LLVM 直接崩溃。

这是错误槽唯一的真实缺陷：不是悬垂，是**谁都能往那个字里塞东西，读侧却假定它一定是盒**。任何 C 通道都建在这个假定上，所以值域得先收。

## 先例

| 先例 | 形态 | 错误在哪 |
|---|---|---|
| Zig | `!T` 错误联合 + `@errorName(e)` | 错误是返回值的一部分；名字是静态表的纯投影，详见下节 |
| Win32 | `HRESULT` + `FormatMessage` | 码即数据；文案是码的纯函数 |
| Rust FFI | `#[repr(C)]` 结果结构体或出参 | 错误值走数据，调用方拥有 |
| Swift | `throws` → `NSError**` 出参 | 错误对象所有权转给调用方，要 release |
| POSIX | `errno` | 环境状态，非数据；本调研判为反例 |

可借两条：Zig 的「码是数据、文案是投影」，Rust 的「结构体返回、零隐藏状态」。Swift 的出参形态多一层所有权转移，只在必须转移对象所有权时才值得 —— 这里不需要，盒子本来就归库所有。

### Zig：错误集、整数码、静态名字表

四件机制：

| 机制 | 做法 | 对我们的意义 |
|---|---|---|
| 错误集 | `error{ A, B }` 是编译期封闭集合，同一错误名全程序同一个整数值 | 「码有语义」的前提 |
| 错误联合 | `E!T` 是标签值，错误随返回值走 | 与 `^T` 同向 |
| 整数编码 | `anyerror` 默认 u16，`@intFromError` / `@errorFromInt` 互通 | 码可存、可传、可比较 |
| 名字投影 | `@errorName` 返回静态串，无人调用就不生成名字表 | 码到文案是纯函数，零分配 |

C 边界的两条硬规矩：

- **错误联合不许直接过 C**。`export fn f() !u32` 在编译期就被拒，报 `return type ... not allowed in function with calling convention 'C'`。Zig 不给错误联合定义 ABI，跨 DLL 同样如此；官方立场是错误没有 ABI，跨边界必须自己映射成码。
- **映射由边界包装器手写**。通行写法是 `catch |e| return code`；要带名字就填调用方缓冲——成功写值，失败把 `@errorName(e)` 拷进调用方给的字节缓冲，长度走出参。Zig 没有「错误到码」的内建。

一条警示：`@errorFromInt` 的文档明说整数表示**不保证跨源码改动稳定**，所以它只适合进程内传递，不宜当对外 ABI。我们的 `0/1/2` 是自己定的契约，不受这条限制。

能借的与不能借的：

- 借：错误是值、码是数据、名字是投影；映射发生在边界包装器里，不在语言运行时。
- 借：码只在错误集封闭时才有语义。Pini 的 E 不受约束（`err(42)` 都能过检查），所以内建最多给 `0/1/2`，给不出更细的码。
- 不能借：错误集本身。那是语言特性（声明式、编译期可查），内建函数补不了；要更细的码，得先有错误分类。
- 注意：`@errorName` 的名字表「用了才生成」；将来若加 `错误名(e)`，同样可以做成静态表，但它属于诊断，不进 C ABI。

### Rust：类型优先，码不承诺

| 层 | 做法 | 说明 |
|---|---|---|
| 库 | `thiserror` 派生，每个变体一个类型化错误 | 生态共识：库用 thiserror，应用用 anyhow |
| 应用 | `anyhow`，只传播与附加上下文 | 不区分具体类型，也不产生码 |
| 标准库 | `std::error::Error` 没有 code | 只有分类与来源链 |
| 分类枚举 | `io::ErrorKind` 标 `#[non_exhaustive]` | 文档明说会增长、不建议穷尽匹配；数值不承诺 |
| 原生码 | `io::Error::raw_os_error() -> Option<i32>` | 是 OS 的 errno，不是库自己编的号 |
| FFI | 手写 `match`，或 `#[repr(i32)]` 无载荷枚举 | 判别值由作者显式写 |

三条结论：

- Rust 不给错误自动编号。能跨 FFI 的都是「有判别值的类型」；带数据的 struct 错误在边界上只能手写映射。这与「enum 派生、非 enum 申报」的分法同向。
- `ErrorKind` 的数值不承诺稳定，只承诺分类与名字。这与「C 侧按符号名比对、不写字面量」是同一条纪律。
- 未分类错误有专门的隐藏变体 `Uncategorized`，用户不能命名。对应我们的 `1` 未归类：能收到，不能主动构造。

## 错误集：码从哪里来
码表、状态结构这类通道形态都以「码已知」为前提；码本身从哪来，是另一个决定。三种来源：

| 来源 | 码的含义 | 漂移 | 需要什么 |
|---|---|---|---|
| 固定语义 | 0 成功 / 1 失败 / 2 取消 | 无 | 无 |
| 错误集 | 每个错误类型或错误值一个码 | 有新错误时位移 | 特征 + 载体 + 清点 |
| 手写 | 作者给的数字 | 无 | 查重诊断 |

### 特征要先于载体

`Error` 与 `CancelError` 现在是内建 struct（`TypeChecker.swift` 的 `registerConcurrencyBuiltins` 段），有 `message` 字段，与特征无关。`实现:` 的校验只跑在 struct / object / given 三个声明上（`verifyTraitConformance` 的三个调用点），`EnumDecl` 没有 `traits` 字段，parser 给的是 `methods: []`。trait 本身只能约束方法（`TraitDecl.signatures` 是 `[FuncDecl]`），不能要求字段。

于是「确立 Error 为内置特征」的实际形态是：

- 新增 trait（暂名 `错误`），方法集为空，只表示「这个类型进错误集」；
- 消息由内建 `消息(e)` 提供，默认取用例名，作者可在扩展块写 `消息()` 覆盖；
- `Error` / `CancelError` 声明遵循，不需要额外补方法；
- `Error("msg")` 的构造保留：`Error` 仍是类型，特征只是它额外满足的约束。

注意 —— 不能把 `Error` 本身改成 trait：那样 `Error("msg")` 这个构造调用就不存在了，而它是现有代码与示例的入口。

### 两种载体

| 维度 | enum 载体 | 宽容载体 |
|---|---|---|
| 如何入集 | 声明 `实现: 错误` | 有签名匹配的 `消息()` 方法 |
| 码的来源 | 用例 tag，降载层已有 | 扫描 + 排序 + 编号 |
| 封闭性 | 声明即全集 | 任何类型都可能悄悄进入 |
| 泛型 | 类型参数禁入即可封闭 | 静态枚举不出全集 |
| 新增错误 | 追加在末尾时旧 tag 不动 | 排序一变，后续全移 |
| 语言改动 | enum 补 traits、parser、校验三处 | 不改声明，新增一个 pass 与诊断 |

enum 载体的关键优势不在「更类型安全」，而在**码是既有布局的投影**：`EnumCase` 的 tag 按声明序分配，IR 的枚举布局本来就把它放在第 4 格（`IRNode.swift` 的 `case enumeration` 注释）。清点时不需要给用例重新编号，只需要给错误类型一个类型序。

宽容载体的清点代价可算：遍历声明 × 方法表 O(D × M)，排序 O(K log K)，K 为命中类型数。D 几千、M 十几个时是十万级比较，毫秒内，可缓存。**时间可行，封闭性不可行**：`Result<T, E>` 的 E 不受约束，泛型函数返回 `^T` 时 T 的错误类型要到实例化才定，静态拿不到全集。跨模块同理——`FileLoader.loadDirectory` 一次收全包，单库内可封闭；多库各自编译，码不跨库一致。

### 码的形状

保留三个固定码：`0` 成功、`1` 未归类失败、`2` 取消。业务码从 3 起，两种排法：

- 扁平顺序：错误值按全库声明序编号。可读、连续，插入即位移。
- 分层码：`类型序 << 8 | 用例 tag`。类型序变动才位移，用例追加不动；上限 256 类型 × 256 用例。

注意 —— 无论哪种，C 侧都不应写字面量：头文件出常量，C 代码按符号名比对，重编译即同步。码只在「旧库 + 新头文件」时才错配。

### 默认派生与自动兜底

两类载体处理不同，但共用一张码表：

| 载体 | 码从哪来 | 作者要写 | 警告 |
|---|---|---|---|
| enum 且 `实现: 错误` | 派生：类型序左移 8 位加用例 tag | 一行 `实现: 错误` | 无 |
| 非 enum 且 `实现: 错误` | 有 `码()` 常量就用手动值，否则自动分配 | 可选 `码() -> (I32,)` | 自动分配时一条 |
| 内建 `Error` / `CancelError` | 固定 `1` / `2` | 无 | 无 |

默认派生三样，都基于既有信息：

- 码：`类型序 << 8 | 用例 tag`。类型序取错误 enum 全限定名的字典序，改声明顺序不动码。
- 名字：`类型名.用例名` 进静态表，顺序与码一致，供 `calc_strerror`。
- 消息：`消息(e)` 内建默认返回名字；作者在扩展块写了 `消息()` 则优先，派生不覆盖。

注意 —— 默认处理是零样板，不是零成本：派生要落成类型层的方法或内建分派、降载层的表读取、运行时的字符串表，三处都得有，只是作者不写。

非 enum 的规则是「不承诺、不申报、不静默」：

- 不申报：不要求作者写任何东西，`实现: 错误` 即可编译。
- 自动：编译器分配一个码，排在派生区之后。
- 不静默：在类型声明处发一条警告，写明生成的码、该码不保证跨版本稳定、以及如何固定它。
- 不承诺：自动码只保证同一次编译内一致；跨版本漂移由警告与文档明示。

手动覆盖走约定方法 `码()`：函数体只有 `return <整数字面量>` 时才算数，其余形态报错——写了却没写对，静默退回自动比报错更糟。手动码与派生码、自动码在同一个命名空间查重。

警告的形态（编号 `E7-004`，接在既有三条语义警告之后）：

```
警告 E7-004：类型 `文件错误` 未指定错误码，已自动分配 16385。
             该码不保证跨版本稳定；要固定它，在扩展块写 `码() -> (I32,)` 返回一个常量。
```

内建 `Error` / `CancelError` 是特例：语言代它们固定成 `1` / `2`，不发警告，也不需要作者写任何东西。这条也让「取消可辨」不依赖字符串约定。

这个分法把自动编号的范围收到「显式声明为错误的 enum」；非 enum 的码由编译器兜底、作者可选固定。两条路都进同一张表，所以 `calc_strerror` 与头文件常量只需一套。

## 候选

### 码表

```c
int32_t calc_div(int32_t a, int32_t b, int32_t* out);
const char* calc_strerror(int32_t code);   /* 纯函数，静态串 */
```

错误值就是码；文案由库的表投影。零分配、并发安全、ABI 只多一个纯函数。
代价：码要有语义来源。语言层没有错误分类，只能取 `0/1/2`（成功/失败/取消）或由编译器按消息字面量编号。

### 状态结构

```c
typedef struct { int32_t code; const char* message; } calc_status_t;  /* 0 成功 1 失败 2 取消 */
calc_status_t calc_div(int32_t a, int32_t b, int32_t* out);
```

每次调用都带回码与消息，无隐藏状态、零分配 —— 盒子已经在了，导出桩只是把 `bk_error_message` 的返回值填进去。
代价：`^T` 导出的返回形态整体变形，现有 C 调用方要改。

### 缓冲出参

```c
int32_t calc_div(int32_t a, int32_t b, int32_t* out, char* err, size_t cap);
```

任意消息（含拼接），调用方给缓冲，生命周期归调用方。
代价：每个 `^T` 函数加两个参数；调用方每次都要备缓冲，即便成功。消息本来就有稳定指针，这条多做了一次复制。

### 错误句柄

```c
calc_error_t* calc_div(int32_t a, int32_t b, int32_t* out);  /* NULL = 成功 */
const char* calc_error_message(const calc_error_t*);
bool calc_error_is_cancel(const calc_error_t*);
void calc_error_release(calc_error_t*);
```

错误是拥有型数据，可保存、可比较、可跨调用；`isCancel` 一起过边界。
代价：四五个新符号，外加一条 release 契约（盒子现在不释放，交出去就得定谁来释放）。

### 旁路槽

```c
int32_t calc_div(int32_t a, int32_t b, int32_t* out);
const char* calc_last_error(void);   /* 线程局部，下一次失败覆盖 */
```

ABI 面积最小。
代价：违反回传与并发两条判据，错误会被下一次调用覆盖。**不采用。**

## 对照

语义维度：

| 候选 | 回传 | 所有权 | 并发 | 取消可辨 | 消息来源 |
|---|---|---|---|---|---|
| 码表 | 是 | 无对象 | 安全 | 码等于 2 | 静态表 |
| 状态结构 | 是 | 库持有，进程期 | 安全 | 码等于 2 | 任意 |
| 缓冲出参 | 是 | 调用方 | 安全 | 另加一个出参 | 任意 |
| 错误句柄 | 是 | 调用方 release | 安全 | 访问器 | 任意 |
| 旁路槽 | 否 | 不确定 | 不安全 | 另查一次 | 任意 |

工程维度：

| 候选 | 新增分配 | 调用方负担 | ABI 破坏 | 新增符号 | 需改语言层 |
|---|---|---|---|---|---|
| 码表 | 无 | 无 | 否 | 1 | 码的来源要定 |
| 状态结构 | 无 | 无 | 是（改返回形态） | 0 | 值域约束 |
| 缓冲出参 | 无 | 每次备缓冲 | 是（每函数 +2 参） | 0 | 值域约束 |
| 错误句柄 | 无（盒子已在） | 必须 release | 是（改返回形态） | 4–5 | 值域约束 |
| 旁路槽 | 无 | 无 | 否 | 1 | 无 |

## 推荐

**方向已定：状态码。** 错误过边界只留码，不带消息；消息留在 Pini 侧，要诊断就写日志或另开函数。

1. **值域**：把 `err(...)` 的载荷限定为 `Error` / `CancelError`。不收，任何通道都可能在第一个非盒载荷上崩；收的代价是要改 `IRNode` 里「E 不受约束」那条注释与参考手册 §11.1 的表述。
2. **边界**：`^T` 导出继续返回 `int32_t`，`0` 成功 / `1` 失败 / `2` 取消。取消位由 `bk_error_is_cancel` 读，导出桩把标签 1 细分成 1 与 2。
3. **内建**：`错误码(e) -> I32`，给手写 C 面函数用 —— 捕获到错误后一行折成码，不必每个函数重写 `isCancel` 分支。
4. **不采用**状态结构与错误句柄：消息不进 ABI；Zig 的先例也把名字表归为诊断，不当协议。

错误集（见上节）是码来源的上位方案，与这条路线不冲突：通道仍是 `int32_t`，导出签名一个字不改，只是失败时的取值从 `1` 换成错误集里的码。它要先立特征，故单列一档，待裁定。

注意 —— 这条路线不再改 `^T` 的签名，现有 C 调用方只需要知道 `2` 的含义。自定义码不在内建里做：语言没有错误分类，`错误码` 只能答 `0/1/2`；要更细的码，先有错误集那样的语言特性。

## 分步

| 步骤 | 内容 | 验收 |
|---|---|---|
| 值域 | 类型层限定 `err(...)` 载荷为 `Error` / `CancelError` | `err(42)` 报类型错；全量绿 |
| 取消位 | 导出桩在失败分支读 `bk_error_is_cancel`，把码分成 `1` / `2`；头文件注明三态 | C 调用方能区分业务失败与取消 |
| 内建 | `错误码(e) -> I32`：注册表、类型签名、IR 节点、解释器分支、运行时段、测试 | 手写 C 面函数一行取码；解释器与 LLVM 同值 |
| 特征与派生 | trait `错误`（标记式）；enum 补 `实现:`；派生码与名字表；E 收紧 | `err(42)` 报类型错；错误 enum 可枚举；码表稳定可缓存 |
| 非 enum 兜底 | 自动分配码；实现处发 E7-004 警告；`码()` 常量覆盖；与派生码同表查重 | 不写 `码()` 也能导出；警告含码与固定办法 |
| 码入盒 | `_BkErrorBox` 增 `code`；`err` 降载时写入静态码；导出桩读码 | C 调用方拿到错误集码；解释器与 LLVM 同值 |
| 头文件 | 导出枚举常量与 `calc_strerror` 静态表 | C 侧按符号名比对，不写字面量 |

## 待决

**E 要不要收紧？** 收紧：错误槽的读侧假定成立，`e.message` 不再可能崩；代价是改语言层「E 不受约束」的既有选择，参考手册要同步。这是本路线唯一还没点头的前置。

**要不要自定义码？** 已由错误集回答：手写 `码()` 常量就是自定义码，与派生码同表查重。没有错误集时，内建只能答 `0/1/2`。

**错误集的载体已定：enum 派生、非 enum 自动兜底。** 用户裁定：enum 由编译器默认处理（码、名字、消息）；非 enum 不申报、自动分配码、实现处发警告、可选择手动固定。宽容实现（有 `消息()` 即算错误）不进这条路线。

**码按类型还是按用例？** 建议按用例。按类型的话，`enum 文件错误 { 不存在, 权限不足 }` 两个用例同码，仍要读消息才能定位，等于没解决原问题。

**泛型参数能不能当错误类型？** 建议一律拒：`^T` 的 E 若是类型参数，错误集就不再封闭，码无法在编译期定。这条与「E 收紧」是同一件事的两个说法。

**非 enum 未申报码已定：自动分配并警告。** 不报错、不折成 `1`：在实现处发一条警告，写明自动码与固定办法。跨版本漂移由「不承诺」明示，作者写 `码()` 常量即可固定。

**错误特征已定：标记式。** `实现: 错误` 只表示入集，方法集为空；消息由内建 `消息(e)` 提供，作者可覆盖。派生因此不需要给每个 enum 合成方法。

**码表范围：导出面可达，还是全模块？** 建议导出面可达：码只对 C ABI 有意义，库内部错误不该占码，也不该让 `pini check` 每次都刷警告。可达性从导出函数的 `^T` 出发做传递闭包。

**自动码与手动码撞了怎么办？** 建议手动优先、自动避让：先排派生码与手动码，自动码填入剩余区间；作者手写的两个码相同则报错。自动区建议从 `0x4000` 起，派生区上限 `0x3FFF`（63 个类型 × 256 用例），两段隔开。
