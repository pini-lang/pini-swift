# 工单：IO 上限源于发射器实现细节，被 `ADR-034` 判准固化

- 状态：**Open（只登记，不实施）** —— 2026-09-12 立案
- 级别：宿主级
- 发现于：LR-4 / P0b（`ADR-034` D3 裁决的对齐后果）
- 关联：`docs/spec/adr/adr-034-hir-contract.md`（D3 A1/A2、D4 缺陷立案）、
  `docs/issue-interpreter-hir-gap-audit-2026-09-12.md`（E3 实测来源）、
  `docs/spec/hir-contract.md`（受影响节点条目）

## 现象

`ADR-034` D2 的判准（**优先兼容 LLVM 端**）要求把两侧分歧统一到 LLVM 侧。落地后，
以下两项**实现细节**将写进 HIR 契约，成为全体后端的义务：

| # | 项 | 固化后的语义 | 来源（实现细节） | 位置 |
|---|---|---|---|---|
| 1 | `readLine` | 超长行按 **256 字节**截断 | `fgets(base, 256, stdin)` 的栈缓冲尺寸 | `Sources/PiniCore/CodeGen/IREmitter.swift` |
| 2 | `fileRead` | 超过 **64 KiB** 截断 | `alloca [65536 x i8]` + 单次 `fread` 的缓冲区尺寸 | 同上 |

**为什么这是缺陷**：两个数字都不是语言设计选择，而是**发射器为自身方便**取的尺寸
（与 `ADR-031` §2.1 记的「100 处 `unsupported` 抛点 = 发射器方便」同族）。

其中 #2 更严重：**静默截断**（无错误、无警告、无返回标记）——读到大文件时返回**不完整
内容而调用者无从察觉**，属数据丢失类缺陷。

## 影响面（实测）

| 调用点 | 现状 | 受影响 |
|---|---|---|
| `examples/io.pini` | `readLine()` 为**注释态** | 否 |
| `examples/selfhost/src/main.pini` | `readFile("/tmp/pini_cmd.txt")` 等 | 否（命令文件远小于 64 KiB） |
| `Tests/PiniTests/IOTests/testReadLine.pini` | 注入 `"world\n"` | 见下 |
| 既有语料 | 无大文件读取用例 | 否 |

⇒ **当前零用户受害**（无真实用例触及上限）。这是「现在立案而不紧急修」的依据。

| 层 | 内容 |

## 待定项（未裁，需另行裁决）

1. `readLine` 是否应有长度上限？若有，取值应据**语言设计**而非缓冲尺寸；
   若无，应改为无上限（或返回 `Result` 让调用者处理超长）。
2. `fileRead` 的截断是否应改为**显式错误**（`Result` 或 panic）而非静默？
   这是本工单最优先的一项——静默数据丢失无法被调用者防御。
3. 两项改造是否应与 B 组字符语义对齐（`docs/issue-hir-string-slice-byte-based-2026-09-11.md`）
   合批？二者都触及同一批 IO 节点。

## 处置

**不实施**。理由：① 当前零用户受害；② 收紧上限或改签名均属**改用户可见行为**，
须走 spec §1.3 并评估迁移面；③ 按「完成计划 → 记下缺陷 → 提出工单」，
P0b 的职责是记录而非扩面。

**建议排期**：P0b 之后由用户点名。可与「IO 语义格」（`ADR-034` D4 拆项）合批评估——
该项本就要改 A1–A3 的实现面，同批处理可省一次迁移窗口。

## 补记：`readLine` 上限的**第二重后果**——超长行的流位置语义（2026-09-14 实测）

**背景**：IO 语义格（`ADR-034` D4 拆项）已按判准把 A 组三项统一到 LLVM 侧，本工单的
两项上限由此**落地为双侧一致**（解释器侧改为 `IOLimits`，与发射器共享同一常量）。
落地实测见 `docs/issue-interpreter-hir-p2-plan-2026-09-13.md` §11。

但落地只覆盖了**返回值**，未覆盖**流位置**。二者在超长行上分开：

| 输入 | 冻结参照臂（`interp-ast`） | LLVM 臂 |
|---|---|---|
| 300 个 `x` + `\n`，随后 `second\n`；两次 `readLine()` | `len(a) = 255`，`len(b) = 7` | `len(a) = 255`，`len(b) = 46` |

首读两臂一致（上限确实对齐），**第二读分歧**：解释器侧的 `readLine` 是**行 API**——
它把整行读到内存再截断，行**已被整条消费**；LLVM 侧的 `fgets` 是**定长缓冲 API**——
只取走 255 字节，**剩余部分留在流里**给下一次读。⇒ 上限之后的字节，
一侧被丢弃、一侧被顺延成下一行。

**为什么本工单要收它**：这不是与上限并列的第二个缺陷，而是**上限自身的第二重后果**——
只要「行 API 实现定长缓冲语义」这个组合还在，两者就必然同时出现。修其一不修其二，
只会把分歧从返回值搬到流位置（本格即为此）。

**处置**：**不实施**（与主体同）。理由同一——改它要把解释器侧从行 API 换成定长缓冲
消费，属**改用户可见行为**，须走 spec §1.3。**建议并入本工单待定项 #1 一并裁决**：
「`readLine` 是否应有长度上限」的答案同时决定本项——**若取消上限**，流位置分歧自然消失；
**若保留上限**，则须同时钉死超限部分的去向（丢弃 vs 顺延）。

**未受害证据**：当前语料无超长行用例（实测 `--filter` 全部 IO 夹具输入均 ≤ 8 字节）。
