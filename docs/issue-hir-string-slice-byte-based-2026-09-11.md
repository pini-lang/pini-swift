# Issue：HIR 字符串切片按字节切，产出非法 UTF-8

- 状态：**Open（2026-09-11 立案；2026-09-12 由 P0 审计扩写范围并补入三通道实测证据；
  2026-09-12 由 P0c 复审订正根因结论——去掉「待语言层裁决」这一前置，实施路径已解锁；未实施）**
- 发现来源：M6c 的 C3 格（`len(String)` 字符计数）勘测期间的伴生发现
- 关联：`docs/issue-llvm-rewrite-plan-2026-09-07.md`（M6c 的 C3 格）；
  `docs/spec/issue/archive/issue-interpreter-hir-gap-audit-2026-09-12.md`（P0 审计，本次证据来源）；
  `docs/spec/adr/adr-019-unicode-char-model.md`（D1 grapheme 裁决，**权威依据**）；
  `docs/spec/adr/adr-033-char-type.md`（`Char` 类型引入，本工单为其 D5 的落地面）

> **范围已扩写（2026-09-12）**：立案时只覆盖**切片**一处。P0 的三通道实测证明
> 这是**一个语言层缺口**，实际表现在 **`len` / 切片 / `substring` / `contains` / `split` / `case`
> 六处**。文件名保持不变（改名会破坏入向引用），范围以本节为准。
>
> **归类订正（2026-09-12，随 P1-4 收口）**：上列**六处中的 `split` 不属本单的字符模型族**。
> `"a,,b".split(",")` 两侧的差异（解释器 3 段 / LLVM 2 段）根因是**空 token 策略**，
> 与「字符」如何定义（字素簇 / 码点 / 字节）**无关**。该处**已由 A4 裁决**：
> 统一到 LLVM 侧、**跳过空 token**，**须改的是解释器**（见 `docs/spec/hir-contract.md`
> 条目 39，及其 §6 汇总表的 A 组行）。
> ⇒ **本单实际承载五处字符语义对齐**（`len` / 切片 / `substring` / `contains` / `case`）；
> `split` 与它们**无共同代码路径**，须按 A 组另案处置，**不可混进同一次字符对齐改动**。
> 错位成因（留档）：P0 审计按「**六处都表现为两侧不一致**」分组，**未按根因分组**。

## 现象（三通道实测）

```
main|func() -> ():
    let s = "你好世界"
    print(s[1:3])
    return
```

| 通道 | 结果 |
|---|---|
| 解释器 | `好世`（按**字符**偏移） |
| 旧后端 | `Error: IRGen Error [E6-002]`——**根本不支持切片** |
| **HIR** | `��`（按**字节**偏移切出半个字符，输出非 UTF-8 字节序列） |

## 性质

- **不是翻转阻塞**：旧后端没有参考实现，也没有夹具依赖该形态，因此不进阻塞清单。
- **但翻转后是新的用户可见缺陷**：解释器能跑的程序，翻转后在 LLVM 侧产出乱码。
  属于「翻转把可跑程序变坏」这一类，需与 C 类格区分对待。

## 与 C3 的关系（同一根因族，已部分处理）

C3 修的是 `len(String)`：旧实现按字节计数，HIR 已改为按字符计数并与解释器对齐。
切片的病同源——**字节偏移当字符偏移用**——但 C3 的修复**没有覆盖切片路径**。

本次为不静默改变既有行为，把切片路径**显式改名**为 `emitStringByteLength`
（名字即语义，字节行为保持原样），字符计数走新增的 `emitStringCharCount`。
两个语义从此在代码里可见，而切片仍未修。

## 建议处置

> **⚠️ 订正（2026-09-12，P0c 复审）**：本节初稿以「**先裁决、再对齐**」开篇，把「语言层裁决
> 『字符』模型」列为**处置的第一步**。**该前置已不存在** —— 裁决早已做出（见下「根因」节的订正块）。
> ⇒ 处置路径**缩短为一跳**：直接按已裁决模型对齐实现。

1. ~~**语言层裁决「字符」模型**（走 spec §1.3 治理）~~ —— **已完成，无需再做**：
   `ADR-019 D1`（Accepted 2026-08-29）钉定 **grapheme cluster**；`ADR-033`（Accepted 2026-09-12）
   裁决 `Char` 表示 = 与 `String` 同构，并定 LLVM 端 grapheme 分段走 `bk_string_grapheme_*` shim
   （不在 IR 内实现 UAX#29）。
   **本项原担心的代价**（切片字节边界定位需字素簇遍历、LLVM 侧成本高于 `memcpy`）
   **已由 `ADR-033` D5 处置**：成本落在 runtime shim（UCD 表只住 runtime，`ADR-019 D4`），
   LLVM 侧只发调用。
2. **按已裁决模型统一五处**：`len` / 切片 / `substring` / `contains` / `case`
   —— 目标是**grapheme**（`len` 现取码点、切片与 `substring` 现取字节，三者均须改）。
   （`case` 的 ASCII-only 大小写是同一模型问题在 Unicode 上的表现。）
   （**`split` 已移出本项**：其差异是空 token 策略、属 A4 裁决，见上方「归类订正」。
   本条初稿写「六处」且含 `split`，系按「两侧不一致」而非按**根因**分组。）
3. **`substring` 的 `(start, length)` 单独修**：这一处**不需要语言层裁决**
   （注册表已定 `(start, end)`），属 HIR 偏离规范，可独立对齐。
4. **补差分夹具**：至少覆盖 ① `start ≠ 0` 的 `substring`、② CJK 切片、
   ③ 组合字符的 `len` 与 `contains`、④ 含空段的 `split`、⑤ 非 ASCII 大小写。
   —— 这五类正是**现有语料恰好全部回避**的形态（即本工单长期不可见的成因）。
5. **遗留项（本工单不解决，仅登记）**：`substring` 越界时 `memcpy` 长度未夹紧，
   需另设计可观测探针判定是否真越界读。

估工关键未知项：切片当前是否只走 HIR 侧自实现的字节路径，还是与 `substring`
共用同一段发射代码——共用的情形下改动面会同时覆盖两个 API。

**该未知项已由 P0 审计回答（2026-09-12）**：**不共用同一函数，但共用同一根因**。
切片走 `sliceCall` → 切片 helper；`substring` 走 `stringSubstring` → **内联 `memcpy`**
（`IREmitter` 的 `emit` 内联分派）。两者都缺**字符/字节语义的语言层裁决**。
⇒ 按本工单建议 2 统一到「字符」层时，**改动面必须同时覆盖 `len` + 切片 + `substring`
三条路径**（`len` 已按字符计数，但它取的是**码点**而非字素簇，见下）。

## 三通道实测（2026-09-12，P0 审计补入）

夹具形态与结论（`pini run` = 解释器；`pini run-llvm` = HIR → LLVM；**只比 stdout**）：

| 表达式 | 解释器 | HIR/LLVM | 判定 |
|---|---|---|---|
| `"hello".substring(0, 5)` | `hello` | `hello` | 一致（**对照项**：两义在 start=0 时重合） |
| `"hello".substring(1, 4)` | `ell` | **`ello`** | **不一致** |
| `"hello".substring(2, 100)` | `llo` | `llo` | 输出一致（但见下「不能读成安全」） |
| `"café".upper()` | `CAFÉ` | **`CAFé`** | **不一致**（`toupper` 逐字节，ASCII-only） |
| `"你好世界".substring(0, 2)` | `你好` | **乱码** | **不一致** |
| `"你好世界"[1:3]` | `好世` | **乱码** | **不一致**（原立案现象，复现） |
| `"你好世界".len()` 形态（`len(s)`） | `4` | `4` | 一致（**但定义不同**，见下） |
| `"a,,b".split(",")` | `[a, , b]` / 长度 `3` | **`[a, b]` / 长度 `2`** | **不一致**（`strtok` 跳过空 token） |
| `"你好世界".contains("世界")` | `true` | `true` | 一致（合法 UTF-8 且对齐字素边界时同解） |
| `("e" + U+0301).contains("e")` | **`false`** | **`true`** | **不一致**（分解式 Unicode） |
| `("e" + U+0301)` 的 `len` | **`1`** | **`2`** | **不一致** |

### 根因：三义并存 —— **规范已裁、实现偏离**（2026-09-12 订正，推翻本节初稿结论）

> **⚠️ 订正块（2026-09-12，P0c 复审）**：本节初稿标题为「语言层的『字符』定义**未裁决**，
> 三义并存」，并据此把「语言层裁决」当作处置前置。**该结论错误，现予推翻。**
> **裁决早已存在**：`ADR-019 D1`（Accepted **2026-08-29**）已钉定字符模型 = **grapheme cluster**，
> 且**明文「不采用 Unicode scalar 或 UTF-8 byte 模型」**；`ADR-033`（Accepted 2026-09-12）
> 进一步裁决 `Char` 表示 = 与 `String` 同构。
> ⇒ 三义并存**不是规范空白，而是实现偏离规范**：HIR 侧 `len`=码点、切片/`substring`=字节，
> **二者均与 D1 冲突**（解释器侧的 grapheme 才是合规一侧）。
> **成因（留档）**：立案与 P0 审计都是**先看代码、后看规范**，顺序反了 —— 代码里三义并存，
> 就默认规范没说话，而实际是规范说了、实现没听。
> **本工单据此降级**：不再需要「语言层裁决」这一步，直接按已裁决模型对齐实现。

| 位置 | 偏移 / 长度的单位 | 与 `ADR-019 D1`（grapheme）的关系 |
|---|---|---|
| 解释器（`len` / 切片 / 下沉下标） | **字素簇**（Swift `Character`） | **✅ 合规** |
| HIR 的 `len`（`emitStringCharCount`） | **码点**（UTF-8 解码后的 code point 数） | ❌ 偏离 |
| HIR 的切片 / `substring` | **字节** | ❌ 偏离 |

对 ASCII 与 CJK 三者**恰好重合**，故此前不可见；一旦出现**组合字符**（`e` + U+0301）
或**跨字节边界**取值，三者立刻分道扬镳。
⇒ C3 格把 `len` 「改成按字符计数」时，两侧对「字符」的理解**本就不同**，
所以那次修复**没有真正对齐**，只是让多数语料看起来一致。

### `substring` 另有一处独立缺陷（参数语义分歧）

| 出处 | 第二参数语义 |
|---|---|
| `BuiltinRegistry`（权威注册表，`paramNames: ["start", "end"]`） | **end**（绝对索引） |
| `StdlibPini.swift`（解释器下沉实现 `substring\|self(start, end,)`） | **end** |
| `StdlibTests` 断言 `"hello".substring(1, 4) == "ell"`（半开区间） | **end** |
| HIR 侧：节点自述 / lowerer 变量名 / `memcpy(..., length)` | **length** |

⇒ **HIR 侧是偏离方**（注册表与测试早已裁决）。该分歧长期全绿的原因有二：
① `StdlibTests` 的 `runProgram` 直接 `Interpreter()`，**只驱动解释器**，对 HIR 无约束力；
② 全部差分夹具**恰好都写 `substring(0, N)`**，此时 `length == end - start`，分歧被恒等掩盖。

### 关于 `substring(2, 100)` 的审慎说明

实测两侧输出**一致**（均 `llo`）—— 这**推翻了**「会打印垃圾」的初判。
原因是 `print` 按 C 串打印，遇首个 NUL 即停，掩盖了多余的拷贝。
但代码面 `memcpy` 的长度**未夹紧到 `len - start`**，故「输出一致」**不能**读成
「该路径安全」。**是否真存在越界读，须另设计可观测探针**（本工单遗留项）。
