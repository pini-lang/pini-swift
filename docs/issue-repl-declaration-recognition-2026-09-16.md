# 工单：REPL 的声明识别与多行输入不匹配 Pini 语法（类型声明事实上无法输入）

- 状态：**Open（2026-09-16 立案；LR-4 P4-4 勘测时实测发现，只登记不修）**
- 发现渠道：P4-4（REPL 引擎接缝）—— 为写双引擎用例而驱动求值核时，实测输入形态全部落空
- 严重度：**中**（不影响表达式求值，那是 REPL 的主路径；影响「声明累积」这一条对外宣传的能力）
- 归属：**CLI 侧的输入分类与续行检测**（`ReplSession.swift`），不是求值核、也不是任一引擎
- 定位：**不在 P4-4 内修** —— P4-4 的对象是引擎接缝（让求值能换引擎、且可测），这两条是既有的
  REPL 功能缺陷，与本批的引擎迁移无关，且修它们会把一批「形态对齐」扩成一批「REPL 重做」

## 现象（2026-09-16 实测，`pini repl` 与求值核两条路径都验过）

### 一、声明起始词表不匹配 Pini 的真实声明语法

`ReplSession.declarationStarters`（P4-4 后移入求值核的判定，语义未变）判「输入是不是声明」
用的是**前缀匹配**，其词表是：

```
{  object  enum  trait  func  let  var  import  export
```

而 Pini 的声明形态是**行首定界符或 `名字|` 前缀**：

| Pini 声明 | 实际写法 | 是否被认到 | 实测后果 |
|---|---|---|---|
| 引用类型 | `{名字}` | ✅（`{` 命中） | — |
| 值类型 | `(名字)` | ❌（`(` 不在表内） | 判为表达式 ⇒ 包进 `print(...)` ⇒ 解析错 |
| 枚举 | `[名字]` | ❌（`[` 不在表内） | 同上 |
| 特征 | `<名字>` | ❌（`<` 不在表内） | 同上 |
| 自由函数 | `名字\|func(...)` | ❌（**不以 `func` 开头**） | 同上 |
| 导入块 | `[main\|import]` | ❌（不以 `import` 开头） | 同上 |

⇒ **六种声明形态只有一种能被输入。**

**实测**（端到端，`pini repl`）：

```
>> add|func(a: I32, b: I32,) -> (I32,):
    return a + b
```
被当作表达式 ⇒ 包装成 `print(add|func(...))` ⇒ `E2-001` 解析错。

### 二、`let` / `var` 被当成声明，但它们是**语句**

`let` / `var` 在词表里，所以 `var x = 1` 会被**累积进顶层声明表**。而 Pini 的顶层不接受变量声明
⇒ 累积出的模块本身不合法 ⇒ **后续每一次求值都会失败**。

**实测**：输入 `var x = 1` 后不报错（`mainNotFound` 被吞），再输入 `x + 1` ⇒
`RuntimeError`（模块里那个非法顶层 `varDecl` 使整次求值失败）。**一次误输入会毒化整个会话。**

### 三、`{名字}` 单行括号平衡 ⇒ 无法输入多行体

续行检测（`needsContinuation`）用**括号平衡**判「输入是否完整」。`{盒子}` 一行里 `{` 与 `}`
成对 ⇒ 判为完整 ⇒ **立即提交** ⇒ 此时模块只有类型声明、没有 `main` ⇒ 报「无 main」
（AST 侧被吞、HIR 侧是降载错）。成员行随即被当作**独立输入**处理 ⇒ `v: I32 = 7` 被判为表达式
⇒ `E2-006` 解析错。

**实测**（HIR 侧，`PINI_INTERP_ENGINE=hir pini repl`）：

```
>> {盒子}
错误: HIR lowering error at 0:0: no 'main' function found
>> v: I32 = 7
错误: 解析错误: Error: Parse Error [E2-006] ... print(v: I32 = 7)
```

⇒ **Pini 的类型声明事实上无法在 REPL 里输入**（除了用反斜杠续行这种绕过）。

## 后果（本单的实际代价）

1. **对外宣传的能力不可用**：`:help` 写「声明类型（func/struct/object/enum/trait）会累积到会话中」，
   而实测只有 `{名字}` 勉强能进累积、且无法输入其成员。
2. **误输入会毒化会话**：第二条使 `let`/`var` 一旦被输入，之后**每次求值都失败**，而报错信息
   指向当前输入、不指向真正的原因（那条非法的顶层声明）。
3. **与 P4 的关系**：P4 本体要把默认引擎切到 HIR。REPL 的**表达式路径在 HIR 下已实测可用**
   （P4-4 交付，两引擎逐项一致），故本单**不阻塞翻转**；但「REPL 能声明」这条能力在翻转后
   仍然不可用，且会被记成 HIR 侧的问题——**这不是 HIR 的问题**。

## 处置选项（未裁决）

- **A：把词表换成「按行首定界符 + `名字|` 前缀」识别**，并把 `let`/`var` 从词表移除
  （它们不是顶层声明）。最小面：只改判定函数；但「`(名字)` / `[名字]` / `<名字>`」需要
  判断**单写 vs 双写**（`((名字))` 是扩展块），判定比前缀匹配复杂。
- **B：不做输入分类，改为「先当声明解析，失败再当表达式解析」**。更贴语言实际，但两种解析
  都要试 ⇒ 错误信息可能来自「另一条路」，需要明确报告策略。
- **C：只修第二条（`let`/`var` 移出词表）+ 第一条立案留后**。代价最小、直接消掉「毒化会话」
  这一最难受的后果。

**倾向**（供立项参考，非裁决）：**C 优先**——它把「一次误输入毁掉会话」这个真实伤害先消掉，
且改动是一行；A/B 属 REPL 输入层的重做，值得单独一批。

## 不做范围

**本单不修。** REPL 的表达式路径在 P4-4 已确认两引擎可用，本单的对象是**输入分类与续行检测**，
与引擎无关。开工需点名。
