# Pini 解释器 vs LLVM 编译器后端 — 执行速度基准报告

> 测量日期：2026-08-14 ｜ 机器：Apple Silicon (arm64) macOS ｜ LLVM 22（Homebrew）
> 复现：`cd Pini && python3 bench/run_benchmarks.py`

## 一、结论速览

同一段 Pini 程序，**解释器前端（`run`）比编译器后端（LLVM 生成机器码）慢约 3~4 个数量级**：

| 维度 | 差距 |
|------|------|
| **纯执行速度**（剥离编译/JIT/进程启动开销） | 解释器慢 **≈2,000x ~ 6,100x** |
| 端到端 `run` vs `run-llvm`（JIT） | 解释器慢 **≈100x ~ 170x** |
| 端到端 `run` vs `compile`（AOT） | 解释器慢 **≈23x ~ 37x** |
| `-O2` 优化额外红利（纯函数被常量折叠） | 可达 **≈10⁵x ~ 10⁶x** |

端到端差距远小于纯执行差距，是因为 LLVM 后端的一次性固定开销（JIT 编译 ~0.15s、clang 编译 ~0.6s、进程启动 ~0.4s）会淹没「毫秒级」的真实执行时间——对短程序尤其明显。

## 二、Benchmark 程序

三个计算密集型程序，统一结构 `compute|func() -> (I32,)`，覆盖不同计算特征：

| 程序 | 特征 | 单次输出 |
|------|------|----------|
| `bench_fib.pini` | 递归斐波那契 `fib(30)`（函数调用密集，~166 万次递归） | `832040` |
| `bench_loop.pini` | `while` 累加 500 万次（循环 + 算术，无函数调用） | `5000000` |
| `bench_primes.pini` | 试除法统计 10 万以内质数（嵌套循环 + 取模 + 分支） | `9592` |

## 三、实测数据

### A. 端到端墙钟（真实命令耗时，秒，3 次取中位数）

| Benchmark | `run` 解释器 | `run-llvm` JIT | `compile` AOT | 端到端加速比 |
|-----------|-------------|----------------|---------------|--------------|
| fib(30) 递归 | **25.485** | 0.150 | 0.685 | 170x / 37x |
| loop 500 万累加 | **19.925** | 0.146 | 0.625 | 136x / 32x |
| primes 10 万质数 | **14.570** | 0.148 | 0.625 | 98x / 23x |

### B. 纯执行 CPU 时间（单次计算，剥离启动/编译开销）

> 机器码端用「内部循环重复 R 次」摊薄 ~0.4s 进程启动，取 user+sys CPU 时间除以 R。

| Benchmark | 解释器 | lli JIT | AOT `-O0` | AOT `-O2` | 加速比（解释器/`-O0`） |
|-----------|--------|---------|-----------|-----------|------------------------|
| fib(30) 递归 | 25.485 s | 3.28 ms | 4.87 ms | 0.03 ms | **≈5,236x** |
| loop 500 万累加 | 19.925 s | 10.92 ms | 3.26 ms | 0.03 ms | **≈6,109x** |
| primes 10 万质数 | 14.570 s | 2.83 ms | 7.06 ms | 3.29 ms | **≈2,065x** |

几何平均纯执行加速比 ≈ **4,000x**（三个 benchmark 分别 5,236 / 6,109 / 2,065）。

## 四、解读

1. **基础差距（`-O0`）约 2,000~6,000 倍**：解释器每条语句都要经过 AST 树遍历、`Value` 枚举分派、动态类型判断、ARC 计数等运行时开销；而 LLVM 后端把同样的逻辑编译成原生 arm64 机器码，`while`/算术/分支都退化为几条寄存器指令。这是解释型执行与编译型执行之间天然且稳定的数量级鸿沟。

2. **JIT（`lli`）执行速度与 AOT `-O0` 相当甚至略优**（fib 3.28ms vs 4.87ms、primes 2.83ms vs 7.06ms），说明 `lli` 的 JIT 代码生成质量良好；但 loop 场景 `-O0` 反超（3.26ms vs 10.92ms），反映不同后端对纯循环的寄存器分配差异。总体上二者都在「毫秒级」。

3. **`-O2` 的额外红利**：fib 与 loop 的纯函数结果被编译器**常量折叠 / 死代码消除**直接预计算（单次 0.03ms ≈ 空转），加速比飙到 10⁵~10⁶ 倍；primes 因 `isPrime` 的循环边界 `d * d <= n` 无法静态确定，`-O2` 只能到 3.29ms（≈4,400x）。这体现编译器后端在优化上还有解释器完全无法企及的纵深。

4. **端到端差距被固定开销稀释**：`run-llvm` 的 0.15s 几乎全是 IR 生成 + JIT 编译；`compile` 的 0.6s 几乎全是 clang 编译 + 进程启动。只有当程序执行时间远超这些固定开销时，LLVM 后端的真实优势才会在端到端显现——而本项目的三个 benchmark 在解释器端都只需 15~25s，机器码端 <10ms，恰好落在「固定开销主导」的区间。这也说明：**对需要反复运行或计算密集的 Pini 程序，编译后端收益巨大；对一次性短脚本，JIT/编译的启动成本可能抹平甚至反超解释器。**

## 五、方法学与口径

- **为何要「进程内重复」**：机器码单次执行仅几毫秒，被进程启动（实测空程序 `print(0)` 也要 ~0.4s）完全淹没。脚本自动生成「内部循环 R 次调 `compute()`」的变体（R 取 50~200），用 `resource` 采集子进程 user+sys CPU 时间除以 R，得到可信的单次执行时间。
- **解释器端 wall≈CPU**：计算密集、几乎无 IO，`run` 的墙钟中位数即视作 CPU 时间。
- **基准口径**：加速比 = 解释器单次 CPU / AOT `-O0` 单次 CPU；`-O2` 列仅作优化潜力参考，因「结果被预计算」不代表真实计算开销。
- **正确性护栏**：脚本对每个 benchmark 校验「解释器 / JIT / AOT 输出一致且等于期望」，本次全绿（各后端均输出 `832040` / `5000000` / `9592`）。
